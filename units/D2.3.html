    1안전한 프로비저닝이란

    왜 필요한가

    프로비저닝(Provisioning)은 자산을 쓸 수 있게 제공하는 과정입니다. 서버를 설치해 서비스에 투입하는 것, 클라우드에 인스턴스를 띄우는 것, 직원에게 노트북을 지급하는 것이 모두 프로비저닝입니다. “안전하게 프로비저닝한다”는 것은 처음부터 안전한 상태로 제공한다는 뜻입니다.

    원본의 핵심 원칙은 보안을 나중에 덧붙이지 않는다입니다. 기본 설치 상태로 배포한 뒤 보안 설정을 하려 하면 두 가지 문제가 생깁니다. 설정하기 전까지 노출되는 구간이 생기고, 일부 시스템은 영영 설정되지 않습니다.

    보충이 흐름의 순서가 곧 판단 기준입니다. 실무에서는 급하게 배포하고 나중에 정리하는 일이 흔하지만, 원본은 시험이 등록 → 기준선 적용 → 배포 순서를 요구한다고 정리합니다. “일단 배포하고 다음 주에 강화하자”는 선택지는 순서를 뒤집은 것입니다.

    2정보와 자산의 소유권

    쉬운 설명

    공식 개요 2.3의 첫 세부 항목이 Information and asset ownership입니다. 모든 자산에는 명시적 소유자가 있어야 합니다. 원본은 세 역할을 구분합니다.

    역할책임
    Information Owner 정보 소유자데이터 분류, 접근 승인, 보존 결정
    System Owner 시스템 소유자시스템의 보안 상태, 통제 구현, 인가
    Custodian 데이터 관리자소유자 결정에 따른 일상 운영과 보호

    System Owner와 Information Owner는 다를 수 있습니다. 인사 시스템을 IT가 운영하면 IT 책임자가 System Owner이지만, 인사 데이터의 분류와 접근 승인은 인사팀장(Information Owner)이 합니다.

    소유자가 실제로 하는 일

    • 분류 결정과 재검토
    • 접근 권한 승인과 주기적 검토
    • 보존 기간 결정
    • 위험 수용 여부 판단

    소유자는 퇴사나 조직 개편으로 공석이 되기 쉽습니다. 그래서 소유자 변경을 인사·조직 변경 프로세스와 연결해야 합니다.

    원문 사례 — 소유자 없는 서버. 침해 조사에서 진입점이 된 서버의 소유자를 찾을 수 없었습니다. 등록된 소유자는 3년 전 퇴사한 직원이었고, 그 뒤 패치나 검토가 한 번도 없었습니다. 조직은 소유자 변경을 퇴사·조직 개편 절차에 연결하고, 분기마다 소유자가 유효한지 점검하게 바꿨습니다. 원본의 결론은 소유자 공석은 보안 공백과 같다입니다.

    보충System Owner와 Information Owner가 갈리는 이유는 질문이 다르기 때문입니다. “이 데이터를 누가 봐도 되는가, 얼마나 보관하는가”는 데이터의 사업적 가치를 아는 사람이 답하고, “이 서버의 패치와 설정이 기준을 만족하는가, 운영을 승인할 것인가”는 시스템을 책임지는 사람이 답합니다. 하나의 서버에 여러 부서의 데이터가 있으면 System Owner는 한 명이고 Information Owner는 여럿일 수 있습니다.

    가상 예시병원에 설치된 장비 여러 대를 원격으로 관리하는 서버가 있습니다. 서버의 패치와 접근 통제는 회사 서비스 운영팀장이 책임지고(System Owner), 서버에 모이는 장비 사용 기록의 열람 범위와 보존 기간은 그 기록의 업무 책임자가 정합니다(Information Owner). 운영팀장이 다른 부서로 옮기면서 후임을 지정하지 않으면, 서버는 계속 돌아가지만 패치 승인과 예외 검토를 할 사람이 없습니다. 원문 사례(실제 원본에 실린 사례)에서는 이런 공백이 3년간 이어졌습니다.

    연결D1.3 보안 거버넌스에서 소유자는 결정하고 관리자는 수행한다고 배웠습니다. 이 단원은 거기에 System Owner를 더해, 데이터에 대한 결정과 시스템에 대한 결정을 나눕니다. 개인정보 맥락의 Controller·Processor까지 포함한 데이터 역할 전체는 D2.4 데이터 생애주기에서 다룹니다. 퇴사 절차와 연결하는 방법은 D1.8 인적 보안의 퇴사 체크리스트, 소유자가 권한을 주기적으로 검토하는 일은 D5.5 프로비저닝 생애주기의 접근 검토입니다. 위험 수용 여부 판단은 D1.9 위험 관리의 위험 대응 중 수용이고, 그 결정은 권한 있는 사람이 기록으로 남겨야 합니다.

    원본 연습문제 · D2.3-Q01

    침해 조사에서 해당 서버의 등록 소유자가 3년 전 퇴사한 직원으로 확인되었고 그 이후 패치나 검토가 전혀 이루어지지 않았다. 재발을 가장 직접적으로 막을 통제는?

    1. 외부 침투 테스트 빈도를 높인다.
    2. 모든 서버에 추가 엔드포인트 탐지 에이전트를 배포한다.
    3. 자산 소유자 갱신을 인사 퇴사·조직 개편 프로세스와 연결한다.
    4. 모든 시스템의 로그 보존 기간을 연장한다.
    정답과 해설 보기

    정답 C. 소유자 공석은 보안 공백과 같다. 아무도 책임지지 않으므로 패치도 검토도 폐기도 이루어지지 않는다. 소유자 변경을 인사·조직 변경 프로세스와 연결하고 주기적으로 소유자 유효성을 점검해야 구조적으로 해결된다.

    • A · 침투 테스트는 발견 수단이며 관리 주체 부재를 해결하지 못한다.
    • B · 탐지 에이전트는 침해 후 탐지를 돕지만 미관리 상태를 바꾸지 못한다.
    • D · 로그 연장은 사후 조사용이다.

    3자산 인벤토리

    왜 필요한가

    D2.1 자산 식별과 분류의 첫 문장이 “가진 것을 모르면 보호할 수 없다”였습니다. 자산 인벤토리(Asset Inventory)는 그 “가진 것”의 목록입니다. 공식 개요 2.3은 인벤토리의 예로 유형(tangible)과 무형(intangible)을 명시합니다.

    구분원본이 드는 예
    유형 자산서버, 네트워크 장비, 단말, 모바일 기기, 저장 매체, 시설, 출력 장비
    무형 자산데이터, 소프트웨어와 라이선스, 지식재산, 클라우드 리소스, 도메인과 인증서, 계약 권리

    인벤토리 항목이 담아야 할 것

    항목왜 필요한가 (보충)
    고유 식별자(자산 태그)같은 자산을 여러 목록에서 하나로 맞추기 위해
    자산 유형과 사양어떤 기준선과 패치가 적용되는지 정하기 위해
    소유자와 관리자누구에게 묻고 누가 승인하는지
    분류 등급어느 수준의 통제를 적용하는지
    물리적·논리적 위치사고 때 어디로 가야 하는지, 어느 법이 적용되는지
    구성 정보와 설치 소프트웨어새 취약점이 발표되면 영향 받는 자산을 찾기 위해
    수명주기 상태조달·운영·폐기 예정 중 어디에 있는지
    의존 관계이 자산이 멈추면 어떤 업무가 멈추는지

    원본은 의존 관계가 특히 중요하다고 합니다. 어떤 자산이 어떤 업무를 지탱하는지 알아야 업무 영향 분석(BIA)과 변경 영향 분석을 할 수 있습니다. 이런 구성 항목과 그 관계를 기록하는 데이터베이스를 CMDB(Configuration Management Database)라고 합니다.

    보충무형 자산 목록에 도메인과 인증서가 들어가는 이유는 이것들이 만료되는 자산이기 때문입니다. 도메인 갱신을 놓치면 남이 그 도메인을 사서 고객 메일을 받을 수 있고, 인증서가 만료되면 서비스가 멈춥니다. 소유자와 만료일이 목록에 없으면 담당자가 바뀌는 순간 잊힙니다.

    연결의존 관계가 필요한 BIA는 D1.7 업무연속성 요구사항, 변경 영향 분석은 D7.9 변경 관리에서 다룹니다. 인벤토리에 설치 소프트웨어까지 기록하면, D1.11 공급망 위험 관리의 SBOM은 그것을 소프트웨어 구성요소 수준까지 내린 목록이 됩니다. 새 취약점이 발표되었을 때 “우리 자산 중 어디에 영향이 있는가”를 몇 분 안에 답할 수 있는지가 인벤토리 품질의 실전 시험이며, 이것은 D7.8 패치·취약점 관리의 취약점 관리와 이어집니다.

    원본 연습문제 · D2.3-Q07

    물리 하드웨어와 함께 완전한 자산 인벤토리에 포함되어야 할 항목은?

    1. IP 주소가 할당된 장치만.
    2. 소프트웨어 라이선스, 데이터셋, 클라우드 리소스, 도메인, 인증서.
    3. 당해 회계연도에 구매한 자산만.
    4. 조직의 주 데이터센터 내부에 위치한 자산만.
    정답과 해설 보기

    정답 B. 공식 시험 개요는 유형(tangible)과 무형(intangible) 자산을 모두 명시한다. 데이터, 소프트웨어와 라이선스, 지식재산, 클라우드 리소스, 도메인과 인증서, 계약 권리가 무형 자산에 해당한다.

    • A · IP 가 없는 매체, 문서, 라이선스도 자산이다.
    • C · 구매 시기로 자산 여부를 가르지 않는다.
    • D · 클라우드와 원격지 자산이 누락된다.

    4인벤토리를 살아 있게 유지하기

    작동 방식: 자동 발견 + 수동 등록

    인벤토리는 한 번 만들고 끝나는 문서가 아닙니다. 원본은 다섯 가지 수단을 결합하라고 합니다.

    수단무엇을 찾는가
    능동 스캔네트워크 스캔으로 응답하는 기기
    수동 모니터링트래픽을 관찰해 미등록 기기 식별(스캔에 응답하지 않는 기기도 통신하면 보인다)
    에이전트단말에 설치해 상세 정보 수집
    클라우드 API클라우드 리소스 목록 조회
    조달·인사 연동구매와 입퇴사 정보를 인벤토리에 연결

    가장 큰 공백: 섀도 IT와 클라우드

    인벤토리의 가장 큰 공백은 섀도 IT입니다. 부서가 자체 구매한 SaaS, 테스트용으로 띄워 둔 클라우드 인스턴스, 개인이 연결한 기기가 여기에 해당합니다. 발견되지 않은 자산은 패치도 모니터링도 받지 못합니다.

    클라우드에서는 공백이 더 빨리 생깁니다. 몇 번의 클릭으로 리소스가 생기기 때문입니다. 원본이 드는 실질적 수단은 태깅 정책 강제와 미태깅 리소스 자동 차단·알림입니다.

    원문 사례 — 태깅되지 않은 클라우드 리소스. 클라우드 비용 분석 중 소유자를 알 수 없는 인스턴스 40여 개가 발견되었습니다. 일부는 테스트용으로 띄운 뒤 방치된 것이었고, 보안 그룹이 전체 공개로 설정되어 있었습니다. 조직은 소유자·환경·분류 태그를 필수로 강제하고, 미태깅 리소스는 생성을 차단하거나 자동 종료하도록 정책을 코드로 만들었습니다.

    보충이 사례에서 문제를 찾은 것이 보안팀이 아니라 비용 분석이었다는 점이 눈여겨볼 만합니다. 청구서는 모든 리소스를 빠짐없이 셉니다. 그래서 클라우드 청구 내역과 인벤토리를 대조하는 것도 섀도 자산을 찾는 방법입니다. 또 자동 확장 환경에서는 서버 목록이 조회할 때마다 달라집니다. 이때는 개별 인스턴스보다 그것을 만들어 내는 코드·이미지 버전·배포 계정·운영 책임자를 자산 목록에 연결해야, 서버 하나를 지워도 같은 문제가 다시 생성되는지 판단할 수 있습니다.

    연결섀도 IT는 D2.1 자산 식별과 분류에서 “가장 큰 공백 요인”으로 처음 나왔고, D1.12 인식·교육·훈련의 외부 AI 서비스 사용 문제, D8.4 도입 소프트웨어 평가의 도입 소프트웨어 평가에서 다시 나옵니다. 네트워크에 붙는 미등록 기기를 막는 기술(네트워크 접근 통제, NAC)은 D4.2 네트워크 구성요소, 클라우드 사용을 가시화하는 CASB는 D2.6 데이터 보안 통제에서 다룹니다.

    원문 위치: D2.3.md §3 인벤토리 유지 방법, §4 Shadow IT, §7 사례 3 · 기존 문제 주제(섀도 IT, 클라우드 태깅)

    5자산 수명주기

    공식 개요 2.3의 세 번째 항목 Asset management는 자산을 수명 전체에 걸쳐 관리하는 일입니다. 원본은 일곱 단계와 단계별 보안 활동을 제시합니다.

    단계보안 활동
    1. 계획·요구 정의보안 요구사항 포함
    2. 조달공급망 검증, 계약 보안 조항
    3. 등록인벤토리 등재, 소유자 지정, 태깅
    4. 보안 구성기준선 적용, 강화(hardening)
    5. 배포운영 환경 투입
    6. 운영·유지보수패치, 구성 드리프트 점검, 권한 검토
    7. 폐기정화, 처분, 인벤토리 제거

    각 단계가 끊기면 공백이 됩니다. 조달했는데 등록하지 않으면 유령 자산(목록에 없는 실물)이 되고, 폐기했는데 인벤토리에 남으면 실체 없는 항목(실물 없는 목록)이 쌓입니다.

    보충두 공백은 위험의 종류가 다릅니다. 유령 자산은 보호받지 못하는 실물이므로 공격 경로가 됩니다. 실체 없는 항목은 그 자체로 위험하진 않지만 목록에 대한 신뢰를 떨어뜨립니다. 목록이 현실과 다르다는 것을 아는 순간 사람들은 목록을 보지 않게 되고, 그러면 유령 자산을 찾는 수단도 함께 잃습니다. 폐기 단계의 “정화”는 저장 매체의 데이터를 복구할 수 없게 지우는 일이며, 매체를 조직 밖으로 내보낼 때는 더 강한 방법이 필요합니다.

    연결계획 단계에 보안 요구를 넣는 것은 D3.10 정보시스템 생애주기의 정보시스템 생애주기와 D8.1 SDLC 보안의 SDLC가 시스템·소프트웨어 관점에서 같은 이야기를 합니다. 조달 단계의 공급망 검증은 D1.11 공급망 위험 관리, 폐기 단계의 정화 방법(Clear / Purge / Destroy)과 선택 기준은 D2.4 데이터 생애주기에서 다룹니다.

    원본 연습문제 · D2.3-Q13

    자산 관리 생애주기의 올바른 순서는?

    1. 배포, 취득, 폐기, 인벤토리 등록, 운영.
    2. 운영, 취득, 배포, 인벤토리 등록, 폐기.
    3. 소유자가 지정된 상태로 취득과 인벤토리 등록, 안전한 설정과 배포, 유지보수와 모니터링을 포함한 운영, 정화와 인벤토리 말소를 포함한 폐기.
    4. 인벤토리 등록, 폐기, 취득, 배포, 운영.
    정답과 해설 보기

    정답 C. 자산은 취득 시점에 소유자가 지정되고 인벤토리에 등록되어야 이후 모든 통제의 대상이 된다. 안전한 기준 설정으로 배포하고 운영 중 유지보수와 모니터링을 적용하며 폐기 시에는 매체 정화와 인벤토리 말소를 함께 수행한다. 등록이 배포 이후로 밀리면 그 사이 자산은 통제 밖에 있다.

    • A · 배포가 취득보다 앞설 수 없다.
    • B · 운영이 취득보다 앞설 수 없다.
    • D · 폐기가 취득보다 앞설 수 없다.

    조직의 통제를 떠날 예정이며 매우 민감한 데이터를 담았던 매체에 적용해야 하는 정화 방법은?

    1. 파괴 증명서를 받는 파쇄나 분쇄 같은 파괴. 소거나 정화는 매체를 온전히 남기고 올바른 수행에 의존하기 때문이다.
    2. 식별할 수 없도록 파일 이름을 변경한다.
    3. 파일을 삭제하고 휴지통을 비운다.
    4. 드라이브를 한 번 포맷한다.
    정답과 해설 보기

    정답 A. 정화 방법은 데이터 민감도와 매체의 이후 용도로 결정된다. 조직 안에서 재사용한다면 소거나 정화로 충분할 수 있지만 통제를 떠나고 민감도가 높으면 복구 시도 자체를 불가능하게 하는 파괴가 맞다. 삭제와 포맷, 이름 변경은 데이터를 남기므로 어느 경우에도 정화가 아니다. 파괴 증명서는 수행 증빙으로 보관한다.

    • B · 이름 변경은 내용을 지우지 않는다.
    • C · 삭제는 데이터를 남긴다.
    • D · 포맷은 데이터를 남긴다.

    6보안 기준선, 골든 이미지, 강화

    쉬운 설명

    개념무엇인가
    보안 기준선 Security Baseline시스템 유형별로 충족해야 할 최소 보안 설정의 목록
    골든 이미지 Golden Image / Gold Master기준선이 이미 적용된 표준 설치 이미지
    강화 Hardening불필요한 것을 제거해 공격면을 줄이는 작업

    기준선은 “무엇을 만족해야 하는가”이고, 골든 이미지는 “만족한 상태로 시작하는 수단”이며, 강화는 기준선에 들어가는 내용의 큰 부분입니다.

    골든 이미지가 주는 것

    • 배포 시점부터 안전 — 나중에 설정하는 공백이 없다
    • 일관성 — 시스템마다 설정이 다르면 통제도 감사도 불가능하다
    • 신규 배포가 빨라진다

    강화의 기본 항목

    • 불필요한 서비스·포트 비활성화
    • 기본 계정 제거 또는 비활성화
    • 기본 자격증명 변경 — 원본은 바꾸지 않은 기본 비밀번호를 가장 흔한 침해 경로로 꼽는다
    • 불필요한 소프트웨어 제거
    • 로깅 활성화
    • 최소권한 적용

    참조 기준으로 CIS Benchmarks, DISA STIG(미 국방부 보안 기술 구현 지침), 벤더 보안 가이드가 쓰입니다.

    원문 사례 — 기본 자격증명으로 뚫린 장비. 신규 네트워크 장비를 설치하고 “나중에 설정하자”며 기본 계정을 그대로 두었습니다. 2주 뒤 외부에서 기본 자격증명으로 접속해 내부망 거점으로 삼았습니다. 골든 이미지와 배포 전 강화가 있었다면 구조적으로 막혔을 사안이고, 원본은 보안 설정을 배포 후 작업으로 두면 반드시 누락이 생긴다고 정리합니다.

    보충골든 이미지로 설치했다고 기준선 검증이 끝난 것은 아닙니다. 이미지는 만든 시점의 기준선을 담고 있으므로, 이미지가 오래되었거나 기준선에 새 요구가 추가되면 이미지로 설치한 시스템도 검증에서 실패할 수 있습니다. 이미지에도 버전과 갱신 주기가 있어야 하고, 배포 후에는 기준선 대비 점검(8절)이 따라와야 합니다.

    가상 예시Windows 기반 장비를 병원에 출하하는 회사가 있다고 합시다. 공장에서 설치하는 운영체제 이미지에 불필요한 서비스 중지, 기본 관리자 계정 비활성화, 장비별로 다른 초기 비밀번호, 로깅 설정이 이미 들어 있으면 그것이 골든 이미지입니다. 반대로 현장 엔지니어가 설치 후 체크리스트를 보며 하나씩 설정하는 방식이면, 장비마다 설정이 조금씩 달라지고 바쁜 날에는 몇 항목이 빠집니다. 출하된 수백 대 중 어느 장비가 어떤 상태인지 아무도 모르게 됩니다.

    연결기준선이라는 문서가 정책·표준·지침과 어떻게 다른지는 D1.6 정책·표준·절차·지침에서 봤습니다(시스템 유형별 최소 설정이면 기준선). 기준선을 운영 중에 측정하고 자동으로 되돌리는 일은 D7.3 구성 관리, 기본 자격증명 같은 공장 출하 설정의 위험은 D3.5 아키텍처별 취약점의 취약점 평가에서 다시 나옵니다. 공격면 축소는 D3.1 안전한 설계 원칙의 보안 설계 원칙 중 하나입니다.

    CISSP 관점배포 순서를 묻는 상황에서는 ① 소유자와 인벤토리 등록이 되었는가 ② 기준선이 배포 전에 적용되었는가를 봅니다. “먼저 운영에 투입하고 나중에 강화한다”는 선택지는 순서가 뒤집힌 것입니다. 침해 경로를 묻는 상황에서 신규 장비의 기본 계정이 그대로였다면 강화 누락, 즉 기본 자격증명 미변경이 핵심입니다.

    원문 위치: D2.3.md §3 보안 기준선과 골든 이미지, §4 Security Baseline·Golden Image·Hardening, §6 CIS Benchmarks·DISA STIG, §7 사례 2 · 기존 문제 주제(골든 이미지, 기본 자격증명)

    7클라우드와 코드형 인프라

    왜 통제의 성격이 바뀌는가

    원본은 클라우드의 위험은 속도라고 말합니다. 잘못된 구성이 몇 초 만에 전 세계에 노출될 수 있습니다. 그래서 배포 전 검증(예방)이 배포 후 탐지보다 중요해집니다.

    수단뜻
    IaC Infrastructure as Code 코드형 인프라인프라를 코드로 정의한다. 코드 검토, 버전 관리, 자동 검증이 가능해진다
    정책 코드화 Policy as Code“공개 스토리지 버킷 금지” 같은 규칙을 배포 파이프라인에서 강제한다
    자동 태깅과 미준수 차단태그 없는 리소스, 규칙 위반 리소스의 생성을 막는다
    임시 자격증명장기 키 대신 단기 토큰을 쓴다

    보충IaC가 보안에 주는 가장 큰 변화는 인프라 설정이 코드 리뷰와 변경 이력의 대상이 된다는 점입니다. 손으로 콘솔에서 설정을 바꾸면 누가 왜 바꿨는지 남지 않지만, 코드로 바꾸면 변경 요청과 승인과 차이(diff)가 남습니다. 대신 코드 저장소와 배포 파이프라인 자체가 중요한 자산이 됩니다. 파이프라인에 침입하면 모든 인프라를 바꿀 수 있기 때문입니다. 임시 자격증명이 권장되는 이유도 비슷합니다. 장기 키는 코드나 설정 파일에 남아 유출되기 쉽고, 유출되면 회수할 때까지 계속 쓸 수 있습니다.

    연결예방·탐지 통제의 구분은 D1.9 위험 관리에서 봤습니다. 배포 파이프라인의 보안 통제와 파이프라인 안의 비밀값·단기 자격증명은 D8.2 개발 생태계 보안 통제, 클라우드 서비스 모델(IaaS·PaaS·SaaS)의 취약점은 D3.5 아키텍처별 취약점, 공동 책임 모델은 D3.1 안전한 설계 원칙·D8.4 도입 소프트웨어 평가, 사람 아닌 서비스 계정의 수명주기는 D5.5 프로비저닝 생애주기에서 다룹니다. 운영 단계의 자동화된 구성 관리는 D7.3 구성 관리입니다.

    원문 위치: D2.3.md §3 클라우드와 코드형 인프라, §4 IaC, §5 셋째 표 · 기존 문제 주제(배포 전 검증)

    8구성 관리와 구성 드리프트

    쉬운 설명

    구성 관리(Configuration Management, CM)는 자산의 구성을 알려진 상태로 유지하는 활동입니다. 구성 드리프트(Configuration Drift)는 시간이 지나며 실제 구성이 기준선에서 벗어나는 현상입니다. 원인은 긴급 조치, 임시 변경, 수동 작업입니다.

    대응 두 가지

    방식드리프트 대응
    전통적 운영주기적 준수 점검 — 기준선 대비 차이를 찾아 시정
    불변 인프라 Immutable Infrastructure변경하지 않고 새 이미지로 교체 — 드리프트가 구조적으로 생기지 않는다

    원본은 변경 관리(Change Management)와의 연결을 강조합니다. 승인되지 않은 변경이 드리프트의 주원인이므로, 변경 절차와 구성 점검이 함께 작동해야 합니다.

    원문 사례 — 구성 드리프트. 장애 대응 중 임시로 방화벽 규칙을 열어 두고 원복하지 않았습니다. 6개월 뒤 정기 점검에서 발견되었습니다. 불변 인프라로 전환한 영역에서는 같은 문제가 생기지 않았습니다. 변경이 필요하면 새 이미지를 배포하므로 임시 변경이 쌓일 수 없기 때문입니다.

    보충구성 관리와 변경 관리는 같은 문제를 반대쪽에서 봅니다. 변경 관리는 “바꾸기 전에 승인받는다”(예방), 구성 점검은 “승인된 상태와 지금이 같은가”(탐지)입니다. 변경 관리만 있으면 승인 없이 바뀐 것을 모르고, 구성 점검만 있으면 차이를 발견해도 그것이 승인된 변경인지 판단할 근거가 없습니다. 위 사례에서 긴급 변경 자체는 정당했을 수 있습니다. 빠진 것은 긴급 변경 뒤의 사후 검토와 원복 확인입니다.

    판단 순서구성이 기준선과 다르다는 것을 발견하면 ① 그 변경에 승인 기록이 있는가 ② 있으면 기준선을 갱신할 일인가, 기한이 지난 임시 변경인가 ③ 없으면 무단 변경이므로 원복하고 원인(누가, 어떤 경로로)을 찾는다 순서로 봅니다. 같은 일이 반복되면 점검을 늘리기보다 불변 인프라처럼 드리프트가 생길 수 없는 구조를 검토합니다.

    연결운영 단계의 구성 관리(베이스라이닝, 자동 교정)는 D7.3 구성 관리, 변경 관리 절차와 긴급 변경은 D7.9 변경 관리에서 다룹니다. 원본이 관련 표준으로 드는 NIST SP 800-53의 CM 통제군과 SP 800-128(보안 구성 관리 지침)이 이 절의 근거 문서입니다.

    이해 확인 · 자작 상황 문제 (실제 시험 문제 아님)

    한 회사의 웹 서버 50대 중 12대에서 기준선에 없는 관리 포트가 열려 있는 것이 정기 점검으로 발견되었다. 변경 관리 시스템에는 해당 포트를 연 기록이 없다. 같은 일이 지난 1년간 세 번 있었다. 장기적으로 가장 효과적인 대책은?

    1. 점검 주기를 분기에서 매주로 늘린다.
    2. 12대의 포트를 닫고 담당자에게 경고한다.
    3. 서버를 수정하지 않고 새 이미지로 교체하는 방식으로 운영을 바꾸고, 수동 접근 경로를 제한한다.
    4. 기준선에 해당 포트를 추가해 위반이 아니게 만든다.
    정답과 해설 보기

    정답 C. 반복되는 무단 변경은 구조의 문제입니다. 변경할 수 없는 운영 방식이면 드리프트가 구조적으로 생기지 않습니다.

    • A: 발견은 빨라지지만 생기는 것을 막지 못합니다.
    • B: 지금의 12대는 고쳐지지만 네 번째가 생깁니다. 당장의 시정으로는 필요하지만 장기 대책은 아닙니다.
    • D: 승인되지 않은 변경을 기준선이 따라가면 기준선이 의미를 잃습니다. 포트가 업무상 필요하다면 변경 절차를 거쳐 기준선을 바꿔야 합니다.

    조건을 바꿔 보기: 이미지 교체가 불가능한 오래된 시스템이라면, 무단 변경을 자동으로 탐지해 되돌리는 구성 관리 도구와 변경 관리 연동이 현실적인 대안입니다.

    9소프트웨어 자산 관리

    소프트웨어도 자산이고, 라이선스 준수는 법적 의무입니다. 원본이 드는 활동은 네 가지입니다.

    • 설치 소프트웨어 인벤토리
    • 라이선스 보유 수량과 사용량 대조
    • 승인되지 않은 소프트웨어 탐지
    • EOL / EOS 추적 — 수명 종료(End of Life)와 지원 종료(End of Support). 지원이 끝난 소프트웨어는 패치를 받지 못해 위험 자산이 된다

    가상 예시구매한 라이선스는 40개인데 인벤토리에서 설치 45개가 발견되었고, 그중 5개는 소유자와 버전이 기록되어 있지 않습니다. 라이선스 5개를 더 사면 법적 문제는 해결되지만 보안 문제는 남습니다. 그 5개가 어디서 무슨 업무에 쓰이는지, 승인된 버전과 설정인지, 지원 기간 안의 버전인지를 따로 확인해야 합니다. 그리고 앞으로는 프로비저닝할 때 설치·버전·라이선스·책임자가 함께 등록되는지를 검증합니다.

    보충EOL/EOS는 의료기기나 산업 장비처럼 오래 쓰는 장비에서 특히 문제가 됩니다. 장비는 10년 이상 쓰는데 그 안의 운영체제는 그보다 먼저 지원이 끝날 수 있습니다. 인벤토리에 운영체제 버전과 지원 종료일이 있으면 언제 대안(업그레이드, 격리, 보완 통제)을 준비해야 하는지 미리 알 수 있습니다. 지원 종료 후에도 써야 한다면 그것은 위험 수용 결정이므로 소유자의 승인이 필요합니다.

    연결라이선스의 법적 성격(저작권, 오픈소스 라이선스의 의무)은 D1.4 법률·규제·컴플라이언스, 도입할 소프트웨어의 보안 평가와 오픈소스 관리는 D8.4 도입 소프트웨어 평가, EOL·EOS 자산을 언제 교체하고, 교체할 수 없는 레거시 시스템을 보완 통제(격리, 가상 패치)로 어떻게 버티는지는 바로 다음 단원 D2.5 자산 보존 (EOL·EOS), 운영 중 패치 공백 관리는 D7.8 패치·취약점 관리에서 다룹니다. 원본이 드는 ISO/IEC 19770은 IT 자산 관리 표준입니다.

    원문 위치: D2.3.md §3 소프트웨어 자산 관리, §4 EOL / EOS, §6 ISO/IEC 19770 · 기존 문제 주제(EOL 자산, 라이선스)

    10종합 이해 확인

    여러 절을 함께 써야 풀리는 문제입니다.

    종합 · 자작 상황 문제

    침해 조사 결과 다음이 확인되었다. ㉠ 진입점은 인벤토리에 없는 테스트용 클라우드 인스턴스였다. ㉡ 그 인스턴스는 기본 설치 이미지로 띄워졌고 관리자 계정이 기본 비밀번호였다. ㉢ 인스턴스를 만든 직원은 반년 전 퇴사했다. 세 항목에 대응하는 개선을 바르게 짝지은 것은?

    1. ㉠ 미태깅 리소스 생성 차단과 클라우드 API 기반 자동 발견 / ㉡ 기준선이 적용된 골든 이미지만 배포 허용 / ㉢ 소유자 변경을 퇴사 절차에 연결
    2. ㉠ 클라우드 사용 금지 / ㉡ 비밀번호 정책 공지 / ㉢ 퇴사자 징계
    3. ㉠ 침해 후 탐지 강화만으로 충분 / ㉡ 사고 후 비밀번호 변경 / ㉢ 문제없음
    4. ㉠ 연 1회 수동 인벤토리 / ㉡ 배포 후 한 달 안에 강화 / ㉢ 인사팀에 통보
    정답과 해설 보기

    정답 A.

    • ㉠ 클라우드는 공백이 빨리 생기므로 태깅 강제와 자동 발견이 필요합니다(4절). 금지(B)는 우회를 부르고, 연 1회(D)는 속도를 따라가지 못합니다.
    • ㉡ 배포 시점부터 안전해야 합니다(6절). “배포 후 한 달 안에”는 노출 구간을 인정하는 것입니다.
    • ㉢ 소유자 공석은 보안 공백입니다(2절). 퇴사 절차와 연결해야 자동으로 드러납니다.

    11핵심 개념을 내 말로 설명하기

    복습

    자산을 인벤토리에 올렸는데 배포 승인 전에 무엇이 더 필요하나요?

    설명 확인하기

    책임자와 보호할 데이터를 확인한 뒤 승인된 기준선을 적용하고 실제 설정이 맞는지 검증합니다. 인계 후 생길 변경과 예외도 등록해야 운영에서 일탈을 구별할 수 있습니다.

    12핵심 요약

    1. 안전한 프로비저닝 = 처음부터 안전한 상태로 제공. 보안을 나중에 덧붙이지 않는다.
    2. 소유자 없는 자산이 가장 위험하다. 소유자 변경을 퇴사·조직 개편 절차에 연결한다.
    3. Information Owner(분류·접근 승인·보존) ≠ System Owner(시스템 보안 상태·통제 구현·인가). Custodian은 일상 수행.
    4. 인벤토리는 유형 + 무형(데이터, 소프트웨어·라이선스, 지식재산, 클라우드 리소스, 도메인·인증서, 계약 권리).
    5. 인벤토리 필수 항목: 식별자, 유형·사양, 소유자·관리자, 분류, 위치, 구성·설치 소프트웨어, 수명주기 상태, 의존 관계(BIA·변경 영향 분석의 근거).
    6. 유지: 능동 스캔, 수동 모니터링, 에이전트, 클라우드 API, 조달·인사 연동. 섀도 IT가 가장 큰 공백, 클라우드는 태깅 강제·미태깅 차단.
    7. 수명주기: 계획 → 조달 → 등록 → 보안 구성 → 배포 → 운영 → 폐기. 끊기면 유령 자산·실체 없는 항목.
    8. 기준선 = 최소 보안 설정 목록, 골든 이미지 = 기준선이 적용된 표준 이미지. 등록 → 기준선 적용 → 배포 순서.
    9. 강화: 불필요 서비스·포트 제거, 기본 계정 비활성화, 기본 자격증명 변경, 불필요 소프트웨어 제거, 로깅, 최소권한. 참조: CIS Benchmarks, DISA STIG.
    10. 클라우드의 위험은 속도. IaC + 정책 코드화 + 태깅 강제 + 임시 자격증명, 배포 전 검증이 핵심.
    11. 구성 드리프트는 승인되지 않은 변경에서 온다. 변경 관리와 구성 점검을 함께. 불변 인프라는 교체 방식으로 드리프트를 구조적으로 제거.
    12. 소프트웨어 자산 관리: 설치 인벤토리, 라이선스 대조, 미승인 소프트웨어 탐지, EOL/EOS 추적.
    원문 위치: D2.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약(13항목). 원본의 “오답 방향”, “시험은 ~을 요구한다” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다. 원본 §6의 ISO/IEC 27002:2022(자산 인벤토리, 자산 소유권, 허용 사용)와 CIS Controls는 여기에 적어 둡니다.

    자산을 사용 가능한 상태로 제공하는 과정. 안전한 프로비저닝은 처음부터 안전한 상태로 제공하는 것이다.

    Information Owner / System Owner · 정보 소유자 / 시스템 소유자

    정보 소유자는 분류와 접근 승인을, 시스템 소유자는 시스템의 보안 상태와 통제 구현을 책임진다. 서로 다를 수 있다.

    Asset Inventory · 자산 인벤토리

    조직이 보유한 유형·무형 자산의 목록. 소유자, 분류, 위치, 의존 관계를 포함한다.

    Asset Tag · 자산 태그

    자산을 고유하게 식별하는 표식. 물리 라벨이나 클라우드 태그 형태다.

    CMDB — Configuration Management Database · 구성 관리 데이터베이스

    구성 항목과 그 관계를 기록하는 데이터베이스.

    Security Baseline · 보안 기준선

    시스템 유형별로 충족해야 할 최소 보안 설정의 집합.

    Golden Image / Gold Master · 골든 이미지

    보안 기준선이 적용된 표준 설치 이미지. 배포 시점부터 안전한 상태를 보장한다.

    Hardening · 강화

    불필요한 서비스·계정·소프트웨어를 제거해 공격면을 줄이는 작업.

    Configuration Drift · 구성 드리프트

    시간이 지나며 실제 구성이 기준선에서 벗어나는 현상.

    Immutable Infrastructure · 불변 인프라

    변경 대신 새 이미지로 교체하는 운영 방식. 구성 드리프트를 구조적으로 제거한다.

    IaC — Infrastructure as Code · 코드형 인프라

    인프라를 코드로 정의해 버전 관리, 검토, 자동 검증이 가능하게 하는 방식.

    Shadow IT · 섀도 IT

    조직의 승인과 인벤토리를 거치지 않고 사용되는 시스템·서비스.

    EOL / EOS — End of Life / End of Support · 수명 종료 / 지원 종료

    제품 수명 종료와 지원 종료. 지원 종료 자산은 패치를 받지 못해 위험 자산이 된다.

    2. 물리 하드웨어와 함께 완전한 자산 인벤토리에 포함되어야 할 항목은?
    3. 자산 관리 생애주기의 올바른 순서는?
    4. 조직의 통제를 떠날 예정이며 매우 민감한 데이터를 담았던 매체에 적용해야 하는 정화 방법은?
    5. 한 회사의 웹 서버 50대 중 12대에서 기준선에 없는 관리 포트가 열려 있는 것이 정기 점검으로 발견되었다. 변경 관리 시스템에는 해당 포트를 연 기록이 없다. 같은 일이 지난 1년간 세 번 있었다. 장기적으로 가장 효과적인 대책은?
    6. 침해 조사 결과 다음이 확인되었다. ㉠ 진입점은 인벤토리에 없는 테스트용 클라우드 인스턴스였다. ㉡ 그 인스턴스는 기본 설치 이미지로 띄워졌고 관리자 계정이 기본 비밀번호였다. ㉢ 인스턴스를 만든 직원은 반년 전 퇴사했다. 세 항목에 대응하는 개선을 바르게 짝지은 것은?
