    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    취약점 관리와 패치 관리는 자주 같은 말처럼 쓰이지만 범위가 다릅니다. 원본의 첫 문장이 이 단원의 핵심입니다. 패치 관리는 취약점 관리의 한 수단이다. 모든 취약점이 패치로 해결되지 않고(설정 오류, 설계 결함, 지원 종료 제품), 모든 패치가 보안 목적도 아닙니다. 둘을 같은 것으로 다루면 패치할 수 없는 취약점이 관리에서 사라집니다. 의료기기처럼 패치가 쉽지 않은 자산을 다루는 분에게 특히 중요한 단원입니다.

    원본 연습문제 · D7.8-Q01

    패치 관리를 취약점 관리와 동일한 것으로 다루는 것이 잘못인 이유는?

    1. 취약점 관리는 애플리케이션에만, 패치는 운영체제에만 적용된다.
    2. 패치 관리는 탐지 통제이고 취약점 관리는 예방 통제다.
    3. 모든 취약점이 패치로 해결되지 않으므로 설정 결함과 설계 약점, 지원 종료 제품이 관리에서 완전히 빠지게 된다.
    4. 패치 관리가 취약점 관리보다 더 잦은 스캔을 요구한다.
    정답과 해설 보기

    정답 C. 패치 관리는 취약점 관리의 한 수단일 뿐이다. 설정 오류와 설계 결함, 지원 종료 제품의 취약점은 패치로 해결되지 않으므로 둘을 같게 다루면 패치할 수 없는 취약점이 관리 범위에서 사라진다. 또한 모든 패치가 보안 목적인 것도 아니다.

    • A · 둘 다 자산 유형을 가리지 않는다.
    • B · 둘 다 예방 성격이며 통제 유형 구분이 핵심이 아니다.
    • D · 스캔 빈도는 두 개념의 차이가 아니다.

    원본은 취약점 관리 실패의 가장 흔한 뿌리가 도구가 아니라 인벤토리 공백이라고 말합니다. 관리 대상에 없는 자산은 스캔되지 않고 패치되지 않습니다. 전형적 공백은 섀도 IT와 부서 자체 도입 시스템, 스캔 주기 사이에 생겼다 사라지는 클라우드 인스턴스·컨테이너, 사내망 스캔에 잡히지 않는 원격 단말, 지원 종료 제품과 내장 장비입니다.

    원문 사례 — 인벤토리 공백이 만든 침해. 취약점 지표가 양호했지만, 침입 경로는 마케팅팀이 자체 도입해 IT가 모르던 외부 노출 서버였습니다. 스캔 대상에 없었으므로 지표에도 나타나지 않았습니다. 외부 공격 표면 자동 발견, 인벤토리와 스캔 대상의 상시 대조, 미등록 자산 수를 위험 지표로 관리했습니다.

    연결자산 인벤토리는 D2.3 안전한 프로비저닝, 커버리지 검증은 D6.1 평가·테스트·감사 전략의 5절에서 다룹니다.

    원본 연습문제 · D7.8-Q11

    취약점 관리의 기본 순환은?

    1. 공급업체 권고가 나오기를 기다린 뒤 영향받는 시스템만 스캔한다.
    2. 전부 패치한 뒤 무엇이 누락되었는지 스캔한다.
    3. 자산을 식별하고 스캔으로 취약점을 식별한 뒤 위험에 따라 우선순위를 정하고 교정 또는 완화하고 검증한 다음 반복한다.
    4. 배포 시 한 번 스캔하고 이후에는 기준선에 의존한다.
    정답과 해설 보기

    정답 C. 자산 식별이 먼저다. 모르는 자산은 스캔 범위에 들어오지 않는다. 식별된 취약점을 전부 동시에 고칠 수 없으므로 위험으로 우선순위를 정한다. 교정 후 검증하지 않으면 실제로 해결되었는지 알 수 없고, 새 취약점이 계속 공개되므로 일회성이 아니라 순환이다.

    • A · 권고를 기다리면 탐지가 늦는다.
    • B · 우선순위 없는 전면 패치는 비현실적이다.
    • D · 새로 공개되는 취약점을 놓친다.

    원본 연습문제 · D7.8-Q04

    취약점 지표는 양호해 보였으나 마케팅팀이 구축하고 IT 가 알지 못했던 외부 노출 서버를 통해 침해가 발생했다. 근본 문제는?

    1. 마케팅팀이 직접 패치할 수 있도록 관리 권한을 부여해야 했다.
    2. 스캐너의 시그니처 데이터베이스가 최신이 아니었다.
    3. 인벤토리 밖의 자산은 스캔되지도 패치되지도 않으므로 지표에도 나타나지 않는다.
    4. 인터넷 노출 시스템에 대한 취약점 스캔 빈도가 너무 낮았다.
    정답과 해설 보기

    정답 C. 취약점 관리 실패의 가장 흔한 뿌리는 도구가 아니라 인벤토리 공백이다. 관리 대상에 없는 자산은 스캔 대상이 아니므로 지표가 양호하게 보인다. 외부 공격 표면 자동 발견과 인벤토리 대조를 상시화하고 미등록 자산 수를 위험 지표로 관리해야 한다.

    • A · 권한 부여는 미등록 자산 문제를 해결하지 않는다.
    • B · 시그니처 문제라면 등록된 자산에서도 누락이 나타난다.
    • D · 애초에 스캔 대상이 아니었으므로 빈도 문제가 아니다.

    3식별과 검증

    • 인증 스캔·에이전트 기반: 운영 자산의 정확한 패치 수준, 오프라인·원격 단말 포괄.
    • SCA: 애플리케이션 의존성의 알려진 취약점.
    • 컨테이너 이미지 스캔: 빌드 시점과 레지스트리에서.
    • 클라우드 설정 평가: 취약점보다 오설정이 주된 위험.
    • 공급자 공지와 위협 인텔리전스: 스캐너가 아직 모르는 신규 취약점.
    • 침투 테스트와 코드 검토: 자동 스캔이 못 찾는 논리·인가 결함.

    스캔 주기는 위험 기반으로 차등하고, 중요 변경 후와 신규 공개 시 즉시 추가 스캔합니다. 결과는 거짓 양성을 걸러 낸 뒤 전달합니다.

    연결인증·비인증 스캔과 기법별 한계는 D6.2 보안 통제 테스트의 2절, 거짓 양성 검증은 D6.4 결과 분석과 보고의 1절에서 다룹니다.

    원문 위치: D7.8.md §3 전 과정 — 식별, 검증

    4평가와 우선순위

    원본의 원칙: CVSS 점수만으로 정하면 안 된다.

    요소의미
    악용 상태공개 악용 코드, 실제 악용 확인 여부
    노출 경로인터넷 노출 / 내부 / 격리
    인증 요구인증 없이 악용 가능한가
    자산 중요도업무 영향, 데이터 분류
    보완 통제WAF, 분할, 탐지가 이미 있는가
    연쇄 가능성다른 결함과 조합되는가

    원본의 예: 점수 7.5지만 인터넷 노출 결제 시스템에서 실제 악용 중인 취약점이, 점수 9.8지만 격리망 내부의 인증 필요 취약점보다 먼저입니다. 실무에서는 조치 기한을 위험 등급별 SLA로 정하며(“실제 악용 + 인터넷 노출”은 긴급 경로), 구체적 숫자는 조직의 위험 수용 수준과 규제가 정합니다.

    원문 사례 — 점수 기준이 놓친 악용 중 취약점. 조치 기준이 CVSS 9.0 이상이어서, 7.5지만 공개 악용 코드가 있고 인터넷에 노출된 결제 시스템 취약점이 3개월간 방치되었습니다.

    가상 예시같은 취약점이 인터넷에 노출된 환자 포털과, 운영 중 멈추기 어려운 병동 장비에 함께 있고 점수는 같습니다. 포털은 노출 경로와 악용 상태를 보고 빠르게 패치하거나 취약 기능을 끕니다. 장비는 제조사 검증과 정비 창구가 필요하므로, 그때까지 네트워크 분할과 접근 제한으로 도달 가능성을 먼저 줄이고 예외로 등록합니다. 점수가 같아도 조치 경로와 기한은 다릅니다.

    원문 위치: D7.8.md §3 전 과정 — 평가와 우선순위, §7 사례 3 · 원본의 “보상 통제”는 제작기준에 따라 “보완 통제”로 적음

    5조치 선택

    조치내용
    패치 적용기본 수단
    설정 변경취약 기능 비활성화, 접근 제한
    보완 통제분할, WAF 가상 패치, 탐지 강화
    제거쓰지 않는 소프트웨어·서비스 삭제. 가장 확실한 조치
    수락권한 있는 승인, 기한, 재검토

    원본은 “쓰지 않는 것을 지우는 것”이 가장 효율적인 취약점 관리라고 말합니다. 설치되어 있지 않으면 패치할 필요도 없습니다. 조치 완료 주장만으로 종결하지 않고 재스캔으로 확인합니다.

    보충패치 배포 도구가 “성공”을 반환한 것은 설치 작업의 기록일 뿐입니다. 대상 장비의 실제 버전과 설정을 확인하고 취약 상태가 해소되었는지 검증한 뒤에 조치를 종결합니다.

    연결예외와 위험 수락은 D6.4 결과 분석과 보고의 4절에서 다룹니다.

    원문 위치: D7.8.md §3 전 과정 — 조치 선택, 검증과 보고

    6패치 관리

    1. 인지: 공급자 공지, 취약점 피드, 자동 수집
    2. 적용 대상 판단: 영향받는 자산 식별
    3. 사전 검증: 테스트 환경에서 기능·성능 영향
    4. 변경 승인: 변경 관리 절차
    5. 단계적 배포: 카나리 → 일부 → 전체
    6. 확인: 적용 성공, 재부팅 완료
    7. 롤백 준비: 실패 시 복구 경로

    원본은 사전 검증의 현실을 이렇게 요약합니다. 검증 없이 배포하면 장애 위험, 검증만 하다 늦으면 침해 위험. 그래서 위험 기반으로 차등하고(외부 노출 고위험은 간소 검증 후 신속, 내부 안정성 요구는 충분히), 대표성 있는 테스트 환경을 확보합니다.

    긴급 패치(out-of-band): 실제 악용 중인 취약점은 정규 주기를 기다리지 않습니다. 긴급 변경 경로가 미리 정의되어 있어야 하고(사후 승인과 기록이 전제), 판단 기준(악용 확인, 노출, 자산 중요도)이 없으면 매번 논쟁합니다.

    흔한 실패결과
    적용 후 재부팅 안 함패치가 활성화되지 않음 → 적용률 ≠ 유효 적용률
    일부 자산 누락오프라인, 전원 꺼진 단말, 에이전트 미설치
    기준 이미지 미반영신규 시스템이 다시 취약
    의존성·호환성선행 패치, 레거시 앱이 깨짐
    배포 실패를 모름실패 보고가 없으면 영구 공백

    원문 사례 — 적용률 97%, 유효 적용률 68%. 재부팅 완료 여부를 함께 집계하자 유효 적용률은 68%였고, 재부팅하지 않은 시스템에서 커널 패치가 활성화되지 않았습니다.

    원문 사례 — 검증 없이 배포한 패치. 긴급하다는 판단으로 검증 없이 전사 배포했다가 핵심 업무 앱이 호환성 문제로 멈춰 반일 장애가 났습니다. 위험 기반 차등, 카나리 단계 적용, 롤백 경로 사전 확보로 대응했습니다.

    원문 사례 — 기준 이미지 미반영. 매월 같은 취약점이 신규 서버에서 반복 탐지되었고, 조치 종결 조건에 기준 이미지 반영 여부를 넣었습니다.

    연결변경 관리와 긴급 변경은 D7.9 변경 관리, 기준 이미지는 D7.3 구성 관리의 3절에서 다룹니다.

    원문 위치: D7.8.md §3 패치 관리, §7 사례 2, 사례 4, 사례 5

    7패치할 수 없는 자산

    현실에 반드시 존재합니다. 원본의 원칙은 방치가 아니라 관리입니다.

    유형접근
    지원 종료(EOL) 제품네트워크 분할과 접근 제한(도달 가능성 축소가 가장 효과적), 가상 패치(WAF·IPS), 탐지 강화, 기능 축소, 보완 통제 문서화와 예외 등록(만료일·재검토), 교체 계획
    의료·산업 장비(인증 문제로 변경 제약, 가용성이 안전과 직결)
    공급자 의존(조직에 패치 권한 없음)
    운영 중단 불가 시스템
    호환성 제약

    원본의 경고: 보완 통제는 임시 수단이다. 교체 로드맵과 예산이 없으면 영구 예외가 된다.

    원문 사례 — 지원 종료 시스템의 영구 예외. EOL 제품에 보완 통제를 적용하고 예외로 등록했는데, 4년 뒤에도 예외는 그대로였고 교체 예산은 한 번도 배정되지 않았으며, 그 사이 보완 통제 일부는 환경 변경으로 무효가 되어 있었습니다. 예외에 교체 계획과 예산 상태를 필수 항목으로 넣고, 재평가 때 보완 통제 유효성도 함께 검증했습니다.

    보충패치율만 보고하면 임시 예외로 빠진 장비가 얼마나 오래 남아 있는지 보이지 않습니다. 예외의 기간, 대상의 중요도, 보완 통제의 검증 여부를 별도로 보고해야, “누락”과 “합의된 예외”를 같은 숫자로 섞지 않을 수 있습니다. 의료기관이라면 제조사의 패치 승인 상태도 함께 추적합니다.

    연결내장·OT 시스템의 취약점은 D3.5 아키텍처별 취약점, 예외 관리는 D6.4 결과 분석과 보고의 4절, 자산 보존과 EOL은 D2.5 자산 보존 (EOL·EOS)에서 다룹니다.

    원문 위치: D7.8.md §3 패치할 수 없는 자산, §7 사례 6

    8환경별 차이

    환경요점
    클라우드공급자 책임 영역은 조직이 패치하지 않음. 고객 영역(IaaS 게스트 OS, 컨테이너 이미지, 앱 의존성). 주된 위험은 오설정. 단기 자원은 패치가 아니라 새 이미지로 교체
    컨테이너실행 중 컨테이너를 패치하지 않음 → 이미지 재빌드·재배포. 기본 이미지가 핵심. 빌드 파이프라인·레지스트리 스캔, 실행 중 이미지 버전 추적
    OT / ICS가용성과 안전 최우선. 스캔 자체가 장애를 유발할 수 있음 → 패시브 식별, 수동 인벤토리. 유지보수 창구가 드묾. 분할과 단방향 게이트웨이. 승인되지 않은 패치는 보증·인증을 무효화할 수 있음
    모바일·원격 단말사용자 행동 의존, 사내망 미연결. 조건부 접근(패치 수준 미달 시 접근 제한)이 가장 효과적인 강제 수단

    원문 사례 — OT 환경 스캔이 유발한 공정 중단. IT 취약점 스캐너를 생산 네트워크에 적용하자 일부 제어 장비가 비정상 패킷에 반응해 재시작되어 공정이 멈췄습니다. 패시브 식별과 수동 인벤토리로 전환하고, 분할과 단방향 게이트웨이를 주된 통제로 삼고, 패치는 공급자 승인과 유지보수 창구에 맞추는 별도 절차를 세웠습니다.

    원문 사례 — 원격 단말 패치 공백. 원격 근무 전환 뒤 사내망에 연결되지 않는 단말의 패치율이 급락했습니다. 클라우드 기반 배포로 전환하고 조건부 접근으로 패치 수준 미달 단말의 접근을 제한했습니다.

    연결불변 인프라는 D7.3 구성 관리의 6절, 책임 공유 모델은 D6.1 평가·테스트·감사 전략의 4절, 기기 상태 기반 접근은 D4.2 네트워크 구성요소의 5절(NAC)에서 다룹니다.

    원본 연습문제 · D7.8-Q08

    IT 취약점 스캐너를 생산 제어 네트워크에 적용했고 일부 제어기가 비정상 패킷에 반응해 재시작되어 공정이 중단되었다. 대신 무엇을 해야 하는가?

    1. 생산 시간 중에 더 낮은 강도로 스캔을 반복한다.
    2. 공급자 개입 없이 사용 가능한 모든 패치를 즉시 적용한다.
    3. 패시브 식별과 수동 인벤토리를 사용하고 분할과 단방향 게이트웨이를 주된 통제로 삼으며 공급자가 승인한 유지보수 창구에 맞춰 패치한다.
    4. 제어 네트워크를 취약점 관리 범위에서 영구적으로 제외한다.
    정답과 해설 보기

    정답 C. OT 환경은 가용성과 안전이 최우선이고 스캔 자체가 장애를 유발할 수 있다. 패시브 식별과 수동 인벤토리로 자산을 파악하고 분할과 단방향 게이트웨이로 도달 가능성을 줄이며 패치는 공급자 승인과 드문 유지보수 창구에 맞춰 별도 절차로 수행한다.

    • A · 강도를 낮춰도 능동 스캔은 위험이 남는다.
    • B · 공급자 승인 없는 패치는 보증과 인증을 무효화할 수 있다.
    • D · 범위 제외는 통제 공백을 영구화한다.

    10다른 프로세스와 SBOM

    프로세스관계
    자산 관리범위를 정함
    구성 관리기준 이미지와 설정 기준선에 반영
    변경 관리패치 배포 승인 경로
    위협 인텔리전스악용 여부 판단 근거
    사고 대응미조치 취약점이 침입 경로
    공급망공급자 구성요소의 취약점. SBOM이 영향 범위 산정을 가능하게 함

    SBOM(Software Bill of Materials)이 중요한 이유: 널리 쓰이는 라이브러리의 치명적 취약점이 공개될 때 “우리가 그것을 쓰는지”를 몇 시간 안에 답할 수 있는가가 대응 속도를 결정합니다.

    원문 사례 — SBOM 없이 맞은 라이브러리 취약점. 조직이 “우리가 그것을 쓰는지” 확인하는 데 3주가 걸렸고 그 사이 일부 시스템이 악용되었습니다. 모든 앱의 빌드 파이프라인에 SBOM 생성을 넣고 중앙 저장소에서 구성요소 단위로 조회할 수 있게 했습니다.

    보충의료기기 분야에서는 제조사가 제품의 SBOM을 제공하는 것이 규제 기관 제출 요구와 연결되어 논의되고 있습니다. 병원 쪽에서는 제조사 SBOM을 받아 자체 자산 인벤토리와 연결해 두면 신규 취약점 공개 때 영향 장비를 빠르게 찾을 수 있습니다. 구체적 제출 요건은 관할 규제를 직접 확인해야 하며 이 교재는 확인하지 않았습니다.

    연결공급망 위험은 D1.11 공급망 위험 관리, 외부 소프트웨어 구성요소의 보안 영향은 D8.4 도입 소프트웨어 평가에서 다룹니다.

    원문 위치: D7.8.md §3 다른 프로세스와의 관계, §7 사례 7

    1. ㉠ 97%면 양호 / ㉡ 기준을 8.0으로 낮춤 / ㉢ 예외 연장 / ㉣ 야간에만 스캔
    2. ㉠ 유효 적용률을 주 지표로, 재부팅 경과 추적 / ㉡ 악용 상태·노출·인증 요구·자산 중요도·보완 통제를 함께 / ㉢ 교체 계획·예산을 예외 필수 항목으로, 보완 통제 유효성 재검증 / ㉣ 패시브 식별·수동 인벤토리, 분할·단방향 게이트웨이, 공급자 승인에 맞춘 패치
    3. ㉠ 재부팅 강제 후 지표 폐기 / ㉡ 모든 취약점 즉시 패치 / ㉢ EOL 시스템 즉시 폐기 / ㉣ OT는 관리 대상에서 제외
    4. ㉠ 적용 성공 로그로 종결 / ㉡ 점수만 사용 / ㉢ 예외 영구화 / ㉣ IPS로 대체

    복습

    패치가 설치됐다는 알림으로 모든 조치를 끝낼 수 있나요?

    설명 확인하기

    설치 성공은 작업 결과입니다. 실제 자산에서 필요한 버전과 동작이 확인돼 취약 상태가 없어졌는지 판단해야 합니다. 미적용 자산에는 보완과 재검토 일정을 둡니다.

    13핵심 요약

    1. 패치 관리 ⊂ 취약점 관리. 같게 다루면 패치할 수 없는 취약점이 사라진다.
    2. CVE(무엇), CWE(어떤 유형), CVSS(심각도), KEV 류(실제 악용 — 가장 강한 신호).
    3. 전 과정: 인벤토리 → 식별 → 검증 → 우선순위 → 조치 → 재스캔 → 보고. 실패의 뿌리는 인벤토리 공백.
    4. 우선순위: 악용 상태, 노출, 인증 요구, 자산 중요도, 보완 통제, 연쇄. 점수 단독 금지. 위험 등급별 조치 SLA.
    5. 조치: 패치, 설정, 보완 통제, 제거(가장 확실), 수락. 성공 로그가 아니라 재스캔으로 종결.
    6. 패치 절차: 인지 → 대상 → 사전 검증 → 변경 승인 → 단계적 배포 → 확인 → 롤백 준비. 검증 없으면 장애, 늦으면 침해. 긴급 경로 사전 정의.
    7. 실패: 재부팅 안 함(유효 적용률), 누락, 기준 이미지 미반영, 호환성, 실패 미인지.
    8. 패치 불가 자산(EOL, 의료·산업 장비, 공급자 의존): 분할·접근 제한, 가상 패치, 탐지 강화, 예외 등록, 교체 계획.
    9. 환경: 클라우드(책임 공유, 이미지 교체), 컨테이너(재빌드), OT(스캔이 장애, 패시브), 원격(조건부 접근).
    10. 지표: 커버리지, 유효 적용률, 최장 경과, 악용 확인 조치율. 평균은 꼬리를 숨김. SBOM이 대응 속도를 결정.
    원문 위치: D7.8.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    14주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Vulnerability Management · 취약점 관리

    약점 식별부터 조치 검증까지의 전 과정.

    Patch Management · 패치 관리

    공급자 수정 사항의 획득·검증·배포·확인. 취약점 관리의 한 수단이다.

    CVE / CWE / CVSS — Common Vulnerabilities and Exposures / Common Weakness Enumeration / Common Vulnerability Scoring System · 공개 취약점 식별 / 약점 유형 분류 / 취약점 심각도 점수 체계

    개별 취약점 식별자 / 결함 유형 분류 / 심각도 점수 체계.

    KEV (Known Exploited Vulnerabilities) · 실제 악용이 알려진 취약점

    실제 악용이 확인된 취약점 목록. 우선순위의 강력한 신호다.

    SCA (Software Composition Analysis) · 소프트웨어 구성 분석

    애플리케이션 의존성의 알려진 취약점을 식별하는 분석.

    SBOM (Software Bill of Materials) · 소프트웨어 구성 명세서

    소프트웨어 구성요소 목록. 영향 범위 산정 속도를 결정한다.

    Virtual Patching · 가상 패치

    WAF 나 IPS 로 악용 트래픽을 차단해 패치 전까지 보호하는 방식.

    Out-of-band Patch · 긴급 패치

    정규 주기 외에 긴급 배포하는 패치.

    Effective Patch Rate · 유효 적용률

    재부팅까지 완료되어 실제로 활성화된 적용 비율.

    EOL (End of Life) · 수명 종료

    지원 종료. 패치가 더 이상 제공되지 않는 상태.

    Staged Rollout · 단계적 배포

    카나리 적용 후 범위를 점진적으로 확대하는 배포 방식.

    Compensating Control · 보완 통제

    패치가 불가능할 때 위험을 줄이는 대체 수단.

    Conditional Access · 조건부 접근

    패치 수준 같은 기기 상태를 접근 조건으로 삼는 통제.
