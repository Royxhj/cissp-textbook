    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    인증이 “당신은 누구인가”를 확인했다면, 인가는 “그렇다면 이 객체에 이 작업을 해도 되는가”에 답합니다. 공식 개요 5.4는 여섯 가지 모델(DAC, MAC, RBAC, 규칙 기반, ABAC, 위험 기반)과 정책 집행 구조(PDP·PEP)를 듭니다. 이름을 외우기보다 누가 답을 정하고, 무엇을 근거로 정하는가를 보면 여섯 모델이 한 표로 정리됩니다.

    원본 연습문제 · D5.4-Q20

    어떤 사용자가 로그인에는 성공했으나 보고서를 열 때 접근 거부 메시지를 받았다. 어느 단계가 거부한 것인가?

    1. 사용자명이 인식되지 않았으므로 식별.
    2. 행위가 기록되지 않았으므로 책임추적성.
    3. 비밀번호가 틀렸으므로 인증.
    4. 사용자의 신원은 확립되었으나 그 권한에 해당 자원이 포함되지 않으므로 인가.
    정답과 해설 보기

    정답 D. 로그인 성공은 식별과 인증을 통과했다는 뜻이다. 그 뒤 특정 자원에 대한 접근이 막혔다면 인가 단계의 결정이다. 두 단계를 구분하지 못하면 문제 해결 방향이 어긋난다. 인증 실패는 비밀번호나 다중 인증 문제이고 인가 실패는 역할과 권한 배정 문제다.

    • A · 로그인에 성공했으므로 식별은 통과했다.
    • B · 기록은 사후 단계다.
    • C · 로그인에 성공했으므로 인증은 통과했다.

    2DAC — 임의적 접근 통제

    객체 소유자가 자기 재량으로 다른 주체에게 권한을 줍니다. 파일 시스템 ACL, 공유 드라이브 권한, 문서 공유 링크가 전형입니다. 객체마다 ACL을 두어 주체별 권한을 기록합니다.

    장점단점·위험
    유연하고 직관적, 협업에 적합권한 확산을 통제할 수 없음. 소유자가 임의로 공유하면 조직 정책을 우회. 전체 접근 그림을 알기 어려움
    권한 전파: 받은 사람이 또 공유
    악성코드가 사용자 권한으로 실행되면 그 사용자의 모든 권한을 그대로 행사
    권한 상속이 깊어지면 상위 폴더 변경이 예측 못 한 노출을 만듦

    원문 사례 — 소유자 재량이 만든 노출. 한 직원이 재무 자료 폴더를 “링크를 가진 모든 사람”으로 공유했고 그 링크가 외부로 전달되었습니다. DAC에서는 소유자가 조직 정책보다 앞서 공유할 수 있습니다. 대응은 분류 라벨이 붙은 자료의 외부 공유를 시스템이 차단하게 한 것, 즉 DAC 위에 강제적 제약을 얹은 것입니다.

    연결분류 라벨과 취급 규칙은 D2.1 자산 식별과 분류, 외부 유출 탐지(DLP)는 D2.6 데이터 보안 통제에서 다룹니다.

    원문 위치: D5.4.md §3 DAC, §7 사례 2 · 공식 개요 5.4 “Discretionary access control (DAC)”

    3MAC — 강제적 접근 통제

    시스템이 라벨과 정책으로 강제합니다. 소유자도 권한을 넘길 수 없습니다. 군사·정보기관 환경, SELinux, 다중등급 보안(MLS) 시스템이 전형입니다.

    구성요소의미
    주체의 인가 등급 clearance사람이 다룰 수 있는 최고 등급
    객체의 분류 classification자료의 민감도 등급
    구획 compartment알 필요성(need-to-know)의 범위

    접근 조건: 등급 ≥ 분류 그리고 동시에 해당 구획에 알 필요성이 인정되어야 합니다. 등급이 높아도 구획이 다르면 거부됩니다.

    장점은 정책이 일관되게 강제되고 소유자 재량으로 우회되지 않는다는 것, 단점은 경직되고 라벨 관리·재분류 비용이 크다는 것입니다. 원본은 MAC 환경에서 사용자가 자기 문서를 임의로 공유할 수 없다는 점이 DAC와의 결정적 차이라고 정리합니다.

    확인 필요원본은 MAC이 “D3.1의 Bell-LaPadula와 Biba 모델로 형식화된다”고 적었지만, 원본 묶음에서 두 모델이 실제로 다뤄지는 곳은 D3.2 보안 모델입니다. 이 교재는 D3.2로 연결했습니다. 요지: Bell-LaPadula는 기밀성(no read up / no write down), Biba는 무결성(no read down / no write up)입니다.

    원본 연습문제 · D5.4-Q01

    어떤 정부 시스템에서 문서에는 분류 라벨이, 사용자에게는 인가 등급이 부여된다. 문서를 작성한 사용자도 다른 사용자에게 그 문서의 접근 권한을 줄 수 없고 시스템이 라벨만으로 결정한다. 사용 중인 접근 통제 모델은?

    1. 시스템이 라벨을 강제하고 소유자에게 재량이 없으므로 강제적 접근 통제.
    2. 작성자가 문서를 소유하므로 임의적 접근 통제.
    3. 인가 등급이 역할처럼 작동하므로 역할 기반 접근 통제.
    4. 동일한 규칙이 모든 사용자에게 적용되므로 규칙 기반 접근 통제.
    정답과 해설 보기

    정답 A. 소유자가 권한을 넘길 수 없고 시스템이 라벨과 정책으로 강제하는 것이 MAC 의 결정적 특징이다. DAC 는 소유자 재량이 핵심이므로 이 설명과 반대다. MAC 에서는 등급이 분류보다 높거나 같고 동시에 해당 구획에 알 필요성이 있어야 접근된다.

    • B · 소유자 재량이 없다는 점이 DAC 를 배제한다.
    • C · 인가 등급은 역할이 아니라 라벨이며 RBAC 은 직무 기반이다.
    • D · 규칙 기반은 신원과 무관한 조건을 적용하며 라벨 기반 강제와 다르다.

    4RBAC — 역할 기반 접근 통제

    사용자
    →
    역할
    →
    권한
    →
    객체

    직무(역할)에 권한을 묶고 사람을 역할에 배정합니다. 기업 환경에서 가장 널리 쓰입니다.

    장점단점
    입퇴사·전보 처리가 간단, 권한 검토 가능, 직무 분리를 역할 설계로 구현역할 폭증: 예외를 역할로 계속 만들면 사용자 수에 가까운 역할이 생김

    직무 분리의 구현

    방식의미
    상호 배타적 역할(정적 분리)두 역할을 동시에 보유할 수 없음(구매 요청자 ↔ 승인자)
    동적 분리두 역할을 보유할 수는 있지만 같은 거래에서 동시에 행사할 수 없음
    역할 계층상위 역할이 하위 역할 권한을 상속

    원문 사례 — 역할 폭증으로 무너진 RBAC. 부서별·공장별·예외별 요청을 모두 새 역할로 처리하다 3년 뒤 직원 4,000명에 역할 3,200개가 되어 접근 검토가 사실상 불가능해졌습니다. 공통 직무 역할을 수십 개로 줄이고, 변동이 큰 조건(공장 코드, 프로젝트, 기기 상태)은 ABAC 속성으로 옮겼습니다. 역할은 안정적인 직무만, 속성은 변하는 조건을 맡게 했습니다.

    원문 사례 — 상호 배타적 역할로 구현한 직무 분리. 구매 시스템에서 한 사용자가 요청과 승인을 모두 할 수 있었습니다. 두 역할을 상호 배타로 선언하고 배정 단계에서 검증하게 했으며, 규모가 작아 분리할 수 없는 팀에는 동적 분리를 적용했습니다.

    보충‘의사’라는 역할만으로 모든 환자 기록을 볼 수 있게 하면 권한이 과도합니다. 담당 환자인지, 진료 목적인지 같은 조건은 역할로 표현하기 어렵고, 억지로 역할로 만들면 역할 폭증이 됩니다. 이런 조건을 속성으로 넣을 때는 그 속성의 출처(진료 배정 시스템)와 갱신 시점을 함께 정해야 합니다. 이것이 6절의 ABAC로 넘어가는 이유입니다.

    연결직무 분리 원칙은 D3.1 안전한 설계 원칙·D1.2 보안 개념 (CIA 등), 그룹과 역할의 관리는 D5.2 식별·인증 전략의 5절, 접근 검토는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D5.4.md §3 RBAC, §7 사례 1, 사례 6 · 공식 개요 5.4 “Role-based access control (RBAC)”

    5규칙 기반 접근 통제

    관리자가 정한 조건(if-then)을 모든 주체에 똑같이 적용합니다. 방화벽 ACL, 업무 시간 외 접근 차단, 특정 국가 IP 차단이 전형입니다.

    • 주체의 신원이 아니라 조건이 결정합니다. “모두에게 같은 규칙”이 특징입니다.
    • 규칙 순서가 결과를 바꾸므로 평가 순서와 기본 거부 규칙이 중요합니다.
    • 방화벽이 가장 흔한 예이며 마지막에 암묵적 거부(implicit deny)가 놓입니다.

    주의RBAC와 규칙 기반은 약어가 같아(RBAC) 혼동되기 쉽습니다. 보통 RBAC는 역할 기반을 뜻하고, 규칙 기반은 “Rule-based”로 풀어 씁니다.

    보충시간대나 출발 위치가 모든 사용자에게 공통 조건으로 작용하면 규칙 기반으로 읽습니다. 사용자의 직무, 대상 문서의 민감도, 로그인 상태를 함께 계산한다면 속성 기반 설명이 더 직접적입니다. 실제 정책은 둘이 섞여 있으므로 “무엇이 결과를 바꾸는가”부터 찾습니다.

    연결방화벽 규칙 운영은 D7.7 탐지·예방 수단, 방화벽 유형은 D4.2 네트워크 구성요소의 1절에서 다룹니다.

    원문 위치: D5.4.md §3 Rule-Based Access Control · 공식 개요 5.4 “Rule based access control”

    6ABAC와 위험 기반 접근 통제

    ABAC — 속성 기반

    주체 속성 + 객체 속성 + 작업 + 환경 속성의 조합을 정책으로 평가합니다. 표현력이 가장 높습니다.

    원문 예시허용 조건: 주체.부서 = 재무 AND 주체.직급 ≥ 과장 AND 객체.분류 ≤ 내부 AND 객체.소속부서 = 주체.부서 AND 환경.시간 ∈ 업무시간 AND 환경.기기상태 = 관리됨

    장점단점·전제
    역할 폭증 없이 세밀한 정책. 조건이 바뀌면 속성만 갱신정책 복잡도와 디버깅 난이도. 속성 품질에 전적으로 의존 — 속성 원천이 틀리면 정책이 조용히 잘못 동작. 신뢰할 수 있는 속성 원천과 속성 거버넌스가 전제

    원본은 ABAC를 제로 트러스트와 클라우드 환경의 기본 모델로 봅니다. 사용자와 자원이 폭발적으로 늘어나는 환경에서는 역할로 표현할 수 없기 때문입니다.

    위험 기반

    요청 시점의 위험 점수로 결정을 조정합니다. 적응형 인증(adaptive authentication)과 결합됩니다.

    신호결정
    위치와 이동 속도, 기기 상태·등록 여부, 시간대, 비정상 행위 패턴, 자격증명 유출 정보, 요청 자원의 민감도허용 / 추가 인증 요구(step-up) / 제한된 접근 / 거부

    정상 사용자의 마찰을 줄이면서 이상 상황에만 통제를 강화하는 것이 장점이고, 점수 산정이 불투명하고 오탐이 사용자 차단으로 이어진다는 것이 단점입니다. 원본은 위험 기반을 ABAC의 환경 속성을 동적으로 확장한 형태, 제로 트러스트의 지속 평가를 구현하는 수단으로 봅니다.

    원문 사례 — 위험 기반 통제의 오탐. “익숙하지 않은 국가에서의 로그인”을 고위험으로 처리해 추가 인증을 요구했더니, 출장이 잦은 영업팀이 공항 와이파이에서 추가 인증 수단에 접근하지 못해 업무가 멈췄습니다. 승인된 출장 정보를 신호로 반영하고, 네트워크 의존성이 없는 하드웨어 키로 보강했습니다. 원본의 결론은 신호 품질이 통제 품질을 결정한다입니다.

    연결제로 트러스트와 지속 평가는 D3.1 안전한 설계 원칙, 기기 상태 기반 접근은 D4.2 네트워크 구성요소(NAC)·D5.1 물리적·논리적 접근 통제의 3절에서 다룹니다.

    원본 연습문제 · D5.4-Q07

    어떤 시스템이 평소에는 비밀번호와 등록된 보안 키로 로그인을 허용하지만 인식되지 않은 기기와 비정상적인 위치에서 요청이 오면 비민감 데이터에 대한 읽기 접근만 허용하고 그 외에는 추가 인증을 요구한다. 적용 중인 모델은?

    1. 사용자가 추가 인증을 선택할 수 있으므로 임의적 접근 통제.
    2. 비정상 위치가 고정 규칙으로 거부되므로 규칙 기반 접근 통제.
    3. 요청의 평가된 위험에 따라 결정이 달라지므로 위험 기반 접근 통제.
    4. 시스템이 사용자의 선택을 무시하므로 강제적 접근 통제.
    정답과 해설 보기

    정답 C. 같은 사용자라도 요청 시점의 신호에 따라 결정이 달라지는 것이 위험 기반 접근 통제다. 결정은 허용, 추가 인증 요구, 제한된 접근, 거부로 조정된다. 제로 트러스트의 지속 평가를 구현하는 수단이며 신호 품질이 통제 품질을 결정한다.

    • A · DAC 는 객체 소유자의 권한 부여 재량을 뜻한다.
    • B · 고정 거부가 아니라 조건에 따라 접근 수준이 달라지고 있다.
    • D · MAC 은 분류 라벨 기반 강제이며 위험 점수와 무관하다.

    7접근 정책 집행 구조 (PDP / PEP)

    공식 개요가 명시한 항목입니다. 인가는 결정과 집행을 분리합니다.

    구성요소역할
    PEP Policy Enforcement Point요청을 가로채 허용·거부를 집행
    PDP Policy Decision Point정책을 평가해 결정 산출
    PIP Policy Information Point결정에 필요한 속성 공급
    PAP Policy Administration Point정책 작성·관리
    요청
    →
    PEP
    가로채기·집행
    ⇄
    PDP

    PIP 속성

    분리하는 이유: 정책을 한 곳에서 관리해 여러 집행 지점에 일관되게 적용하기 위해서입니다. 애플리케이션마다 자체 인가 로직을 가지면 정책 변경이 전부에 반영되지 않습니다.

    집행의 전제는 우회 불가능성입니다. PEP를 거치지 않는 경로가 하나라도 있으면 정책 전체가 무의미해집니다. 흔한 우회 경로는 직접 DB 접속, 관리 API, 레거시 인터페이스, “내부 전용”이라 가정한 서비스 간 호출입니다.

    원문 사례 — PEP 우회 경로. API 게이트웨이를 PEP로 두고 중앙 PDP에서 결정했지만, 배치 작업과 레거시 리포팅 도구가 DB에 직접 접속하고 있었습니다. 직접 접속을 차단하고, 배치도 게이트웨이를 경유하게 하고, DB에서 애플리케이션 계정 외 접속을 거부했습니다.

    제로 트러스트(NIST SP 800-207)는 같은 구조를 PE(Policy Engine) + PA(Policy Administrator) + PEP로 부릅니다. PE가 결정하고, PA가 세션을 구성·종료하며, PEP가 경로를 통제합니다.

    보충PEP의 “우회 불가”는 D3.4 시스템 보안 기능에서 다룬 참조 모니터의 요건(항상 호출됨, 변조 불가, 검증 가능)과 같은 생각입니다. 웹 화면은 자기 기록만 보여 주는데 같은 데이터를 주는 API가 아무 식별자나 받는다면, 인가가 하나의 결정 지점이 아니라 화면(표현 계층)에서만 이루어지고 있다는 뜻입니다. 데이터에 이르는 모든 경로가 같은 PEP를 지나야 합니다.

    연결참조 모니터와 완전한 중재는 D3.4 시스템 보안 기능, 제로 트러스트 구조는 D3.1 안전한 설계 원칙, API 수준의 인가 결함은 D8.5 안전한 코딩·D3.5 아키텍처별 취약점에서 다룹니다.

    원본 연습문제 · D5.4-Q14

    웹 인터페이스는 사용자가 자기 기록만 조회하도록 강제하는데 같은 데이터를 제공하는 REST API 는 임의의 기록 식별자를 수락한다. 이것이 가리키는 것은?

    1. 중복 검사를 생략하므로 API 가 더 효율적이다.
    2. 웹 인터페이스에 불필요한 제약이 있으므로 제거해야 한다.
    3. API 에 속도 제한이 없다는 것만 문제다.
    4. 인가가 단일 권위 지점이 아니라 표현 계층에서 강제되고 있다. 데이터에 이르는 모든 접근 경로가 같은 결정을 적용해야 하며 공유된 강제 구성요소를 쓰는 것이 바람직하다.
    정답과 해설 보기

    정답 D. 인가를 화면 쪽에 구현하면 같은 데이터로 가는 다른 경로가 검사를 건너뛴다. API, 배치 작업, 보고 도구, 데이터베이스 직접 접근이 모두 경로다. 완전 매개 원칙에 따라 모든 접근이 같은 결정 지점을 거쳐야 하며 공유 인가 구성요소나 데이터 계층 통제로 보장한다.

    • A · 효율이 아니라 통제 누락이다.
    • B · 웹 쪽 제약이 올바른 쪽이다.
    • C · 속도 제한은 무단 접근 자체를 막지 않는다.

    8모델 선택과 조합

    상황모델
    협업이 중심이고 소유자 판단이 적절하다DAC
    분류된 정보를 다루고 사용자 재량을 허용할 수 없다MAC
    직무가 명확하고 조직 규모가 크다RBAC
    신원과 무관한 조건으로 일괄 통제한다규칙 기반
    자원과 조건이 다양해 역할로 표현할 수 없다ABAC
    같은 사용자라도 상황에 따라 다르게 다뤄야 한다위험 기반

    원본은 실제 조직이 여러 모델을 계층적으로 조합한다고 말합니다. 예: 네트워크 계층은 규칙 기반, 애플리케이션 접근은 RBAC, 데이터 수준은 ABAC, 로그인 시점은 위험 기반.

    가상 예시의료기기 지원 포털에서 모든 현장 기사는 점검 문서를 읽을 수 있지만, 원격 설정 변경은 담당 장비에 대해 정해진 작업 기간에만 가능해야 합니다. 모든 조합을 역할 이름으로 만들자는 제안이 나왔습니다. 기사 역할(RBAC)로 기본 기능을 주고, 설정 변경은 장비의 고객 소속, 작업 승인 기간, 작업 위험 같은 속성(ABAC)을 더해 판단하는 편이 역할 폭증을 피합니다. 정책의 근거가 되는 속성의 출처와 변경 책임자도 함께 정합니다.

    원문 위치: D5.4.md §3 모델 선택 기준

    9인가 결정의 기본값과 실패 처리

    항목원칙
    기본 거부 default deny명시적으로 허용되지 않은 것은 거부. 모든 모델의 공통 원칙
    PDP 무응답거부(fail-secure)가 기본. fail-open을 택하면 공격자가 PDP를 방해해 통제를 무력화할 수 있음
    결정 캐싱성능을 위해 캐시하면 권한 회수가 캐시 만료까지 지연. 민감 작업은 캐시를 쓰지 않거나 TTL을 짧게

    원문 사례 — 결정 캐싱이 지연시킨 권한 회수. 인가 결정을 15분간 캐시했는데, 사고 대응 중 특정 사용자의 권한을 즉시 회수해도 그 세션은 최대 15분간 계속 접근할 수 있었습니다. 민감 작업은 캐시를 쓰지 않고, 권한 회수 때 캐시 무효화 이벤트를 전파했습니다.

    연결fail-secure와 fail-safe의 구분은 D3.1 안전한 설계 원칙, 같은 원리가 연합 IdP 장애에 적용된 사례는 D5.3 연합 식별의 9절에서 다룹니다.

    11핵심 개념을 내 말로 설명하기

    복습

    역할과 속성 중 하나만 사용할 수 있나요?

    설명 확인하기

    역할로 일상 기능의 권한 집합을 정하고, 데이터 소속이나 시간 같은 속성으로 조건을 좁힐 수 있습니다. 정책이 맞아도 요청이 통과하는 모든 경로에서 실제로 집행돼야 합니다.

    12핵심 요약

    1. 첫 질문: 누가, 무엇을 근거로 결정하는가. 소유자=DAC, 라벨=MAC, 직무=RBAC, 공통 조건=규칙 기반, 속성 조합=ABAC, 실시간 위험=위험 기반.
    2. DAC: 유연하지만 권한 확산·전파, 악성코드가 사용자 권한 그대로 행사. 민감 자료는 DAC 위에 강제 제약.
    3. MAC: 등급 ≥ 분류 그리고 구획(알 필요성). 소유자도 권한을 넘길 수 없음. BLP(기밀성), Biba(무결성).
    4. RBAC: 사용자→역할→권한. 직무 분리 = 상호 배타적 역할(정적), 같은 거래 동시 행사 금지(동적). 위험은 역할 폭증 → 변하는 조건은 속성으로.
    5. 규칙 기반: 모두에게 같은 if-then. 순서 중요, 끝에 암묵적 거부(방화벽).
    6. ABAC: 주체·객체·작업·환경 속성. 표현력 최고, 속성 품질에 의존. 제로 트러스트·클라우드의 기본.
    7. 위험 기반: 허용 / step-up / 제한 / 거부. ABAC 환경 속성의 동적 확장, 지속 평가. 신호 품질 = 통제 품질.
    8. PEP(집행) / PDP(결정) / PIP(속성) / PAP(정책). 결정과 집행 분리. PEP 우회 경로가 하나라도 있으면 무의미. 800-207은 PE·PA·PEP.
    9. 실무는 여러 모델의 계층적 조합.
    10. 기본 거부, PDP 무응답 시 fail-secure, 결정 캐싱은 회수 지연 → 민감 작업 캐시 금지·무효화 전파.
    원문 위치: D5.4.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 “시험 접근법” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    DAC (Discretionary Access Control) · 임의적 접근 통제

    객체 소유자가 재량으로 권한을 부여하는 모델. ACL 로 구현된다.

    MAC (Mandatory Access Control) · 강제적 접근 통제

    시스템이 라벨과 정책으로 강제하는 모델. 소유자가 권한을 넘길 수 없다.

    Clearance / Classification · 인가 등급 / 분류

    주체에게 부여된 등급과 객체에 부여된 등급. MAC 접근 판단의 두 축이다.

    RBAC (Role-Based Access Control) · 역할 기반 접근 통제

    역할에 권한을 묶고 사용자를 역할에 배정하는 모델.

    Role Explosion · 역할 폭증

    예외를 역할로 계속 만들어 역할 수가 관리 불가능해지는 현상.

    Mutually Exclusive Roles · 상호 배타적 역할

    동시에 보유할 수 없도록 지정된 역할. 직무 분리를 RBAC 으로 구현한다.

    Rule-Based Access Control · 규칙 기반 접근 통제

    관리자가 정한 조건을 모든 주체에 동일하게 적용하는 모델. 방화벽 ACL 이 전형이다.

    ABAC (Attribute-Based Access Control) · 속성 기반 접근 통제

    주체·객체·작업·환경 속성의 조합을 평가하는 모델. 표현력이 가장 높다.

    Risk-Based Access Control · 위험 기반 접근 통제

    요청 시점의 위험 점수로 결정을 조정하는 모델. 적응형 인증과 결합된다.

    PEP — Policy Enforcement Point · 정책 집행 지점

    요청을 가로채 결정을 집행하는 구성요소.

    PDP — Policy Decision Point · 정책 결정 지점

    정책을 평가해 허용·거부를 산출하는 구성요소.

    PIP — Policy Information Point · 정책 정보 지점

    결정에 필요한 속성을 공급하는 구성요소.

    PAP — Policy Administration Point · 정책 관리 지점

    정책을 작성하고 관리하는 구성요소.

    Default Deny · 기본 거부

    명시적으로 허용되지 않은 모든 접근을 거부하는 원칙.

    연습문제 5개

    문항을 선택하면 본문의 지문과 해설로 이동합니다.

    1. 어떤 사용자가 로그인에는 성공했으나 보고서를 열 때 접근 거부 메시지를 받았다. 어느 단계가 거부한 것인가?
    2. 어떤 정부 시스템에서 문서에는 분류 라벨이, 사용자에게는 인가 등급이 부여된다. 문서를 작성한 사용자도 다른 사용자에게 그 문서의 접근 권한을 줄 수 없고 시스템이 라벨만으로 결정한다. 사용 중인 접근 통제 모델은?
    3. 어떤 시스템이 평소에는 비밀번호와 등록된 보안 키로 로그인을 허용하지만 인식되지 않은 기기와 비정상적인 위치에서 요청이 오면 비민감 데이터에 대한 읽기 접근만 허용하고 그 외에는 추가 인증을 요구한다. 적용 중인 모델은?
    4. 웹 인터페이스는 사용자가 자기 기록만 조회하도록 강제하는데 같은 데이터를 제공하는 REST API 는 임의의 기록 식별자를 수락한다. 이것이 가리키는 것은?
    5. 다음 네 상황에 맞는 모델을 순서대로 고르면? ㉠ 문서 작성자가 원하는 동료에게 편집 권한을 준다. ㉡ 업무 시간 외에는 모든 사용자의 원격 접속을 막는다. ㉢ 재무 부서 과장 이상이, 관리되는 기기로, 자기 부서 내부 자료에만 접근한다. ㉣ 평소에는 바로 허용하지만 처음 보는 기기·위치에서는 추가 인증을 요구한다.
