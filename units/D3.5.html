    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    같은 “서버 보안”이라도 병원 영상 장비, 공장의 PLC, 클라우드의 서버리스 함수는 약점이 전혀 다릅니다. 이 단원은 시스템 유형마다 어디가 고유하게 약하고 무엇으로 완화하는지를 훑습니다. 공식 개요 3.5가 나열하는 유형이 많아 범위가 넓지만, 판단의 축은 두 가지입니다. 그 시스템이 무엇을 가장 중요하게 여기는가, 그리고 그 시스템만의 구조적 제약이 무엇인가.

    1시스템마다 위협 모델이 다르다

    원본의 출발점은 일반 IT 시스템의 통제를 그대로 가져다 쓰면 맞지 않는다입니다. 가장 큰 차이는 CIA의 우선순위입니다.

    환경우선순위
    일반 IT기밀성 → 무결성 → 가용성
    ICS / OT가용성·안전 → 무결성 → 기밀성

    산업 제어 환경에서는 인명 안전과 공정 가용성이 최우선입니다. 보안 패치를 위해 생산 라인을 멈추는 판단이 IT와 전혀 다른 이유입니다.

    보충표의 순서는 “늘 이렇다”는 규칙이 아니라 출발점입니다. 일반 IT 안에서도 결제 시스템은 무결성이, 응급실 전자의무기록은 가용성이 앞설 수 있습니다(D1.2 보안 개념 (CIA 등)에서 본 의료기관 사례). 이 단원의 각 절을 읽을 때마다 “이 시스템에서 무엇이 깨지면 가장 큰 피해가 나는가”를 먼저 묻는 습관을 들이면, 처음 보는 시스템 유형에도 같은 방식으로 접근할 수 있습니다.

    원본 연습문제 · D3.5-Q01

    산업제어시스템 환경의 보안 목표 우선순위는 전통적 IT 환경과 통상 어떻게 다른가?

    1. 두 환경의 우선순위는 동일하다.
    2. 제어 데이터는 민감하지 않으므로 무결성은 무관하다.
    3. 가용성과 안전이 기밀성보다 우선한다.
    4. 기밀성이 다른 모든 목표보다 우선한다.
    정답과 해설 보기

    정답 C. ICS/OT 환경에서는 중단이 생산 손실과 안전 사고로 직결되므로 가용성과 인명 안전이 최우선이고 그다음이 무결성, 기밀성 순이다. 일반 IT 의 기밀성 우선과 반대이며 이 때문에 IT 통제를 그대로 적용할 수 없다.

    • A · 우선순위가 다른 것이 핵심 차이다.
    • B · 제어 명령의 무결성은 안전과 직결되어 매우 중요하다.
    • D · 기밀성 우선은 일반 IT 환경의 특징이다.

    2클라이언트 기반 시스템

    핵심 위협은 클라이언트를 신뢰하는 설계입니다. 원본의 원칙은 클라이언트에서 오는 모든 입력은 신뢰할 수 없다입니다. 공격자는 클라이언트를 완전히 통제할 수 있기 때문입니다.

    • 클라이언트 측 검증만 믿는 것 — 검증은 반드시 서버에서도 한다
    • 로컬 캐시와 저장소에 남는 민감 데이터
    • 브라우저·플러그인 취약점, 악성 확장
    • 실행 코드 변조(리버싱, 메모리 패치)

    완화: 서버 측 검증, 저장 최소화, 코드 서명, 단말 보호, 최신 패치.

    원문 사례 — 클라이언트 검증만 믿은 결제. 모바일 앱이 할인율을 앱 안에서 계산해 서버로 보냈습니다. 공격자가 앱을 조작해 99% 할인을 적용한 요청을 보냈고 서버는 그대로 받아들였습니다. 할인율은 서버가 다시 계산했어야 했습니다.

    보충앱 화면의 입력 검사는 사용자 편의(빨리 오류를 알려 줌)를 위한 것이지 보안 통제가 아닙니다. 공격자는 앱을 거치지 않고 서버에 직접 요청을 보낼 수 있으므로, 서버 입장에서 클라이언트는 “누구든 될 수 있는 상대”입니다. 가격, 권한, 수량처럼 결과에 영향을 주는 값은 서버가 자기 데이터로 다시 계산하거나 확인해야 합니다.

    원문 위치: D3.5.md §3 클라이언트 기반 시스템, §7 사례 1 · 공식 개요 3.5 “Client-based systems”

    3서버 기반 시스템

    • 데이터 흐름 통제 — 서버 간 신뢰 경계 설정
    • 가용성 — 부하 분산, 이중화
    • 강화와 최소 기능
    • 서버 간 횡적 이동 차단 — 세그멘테이션

    보충서버를 볼 때는 고객이 쓰는 경로와 운영자가 쓰는 경로를 나눠 봐야 합니다. 고객용 웹 포트만 검토하고, 관리 콘솔·원격 접속·로그·백업에 누가 어느 경로로 들어오는지는 놓치기 쉽습니다. 관리 기능은 별도의 승인 경계(전용 관리망, 강한 인증) 뒤에 두고, 공개 기능은 최소 권한으로 운영합니다.

    연결강화와 최소 기능은 D2.3 안전한 프로비저닝, 세그멘테이션은 D4.1 네트워크 아키텍처, 이중화와 가용성은 D7.10 복구 전략에서 다룹니다.

    다중 인스턴스화

    다중 인스턴스화(Polyinstantiation)는 같은 키에 대해 등급별로 서로 다른 레코드가 존재하게 하는 기법입니다. 원본의 예로, “화물 302편 목적지”에 대해 Secret 사용자는 실제 목적지를, Unclassified 사용자는 다른 값을 봅니다. 저등급 사용자는 기밀 데이터가 있다는 사실 자체를 알 수 없습니다.

    원문 사례 — 추론을 막은 다중 인스턴스화. 저등급 사용자가 특정 화물 번호로 레코드를 입력하려 하자 “이미 존재함” 오류가 떴고, 그 오류만으로 고등급 레코드의 존재가 드러났습니다. 다중 인스턴스화를 적용해 등급별로 별도 레코드를 유지하자, 저등급 사용자는 자기 레코드만 보게 되었습니다.

    그 밖의 대응

    기법막는 것
    데이터베이스 뷰 View필요한 열·행만 노출
    셀 단위 접근 통제개별 값 단위 노출
    질의 제한결과 건수가 너무 적거나 많은 질의(집계·추론 공격)
    노이즈 추가통계 질의를 미세하게 왜곡해 개인 값 추론 방지
    매개변수화 질의 Prepared StatementSQL 삽입 방어의 표준
    다중 인스턴스화추론과 존재 노출

    보충질의 제한이 왜 “너무 적은 결과”를 막을까요. 통계만 볼 수 있는 사용자도 조건을 좁혀 결과가 한 명이 되게 만들면 그 사람의 값을 알아냅니다. “영업팀 평균 급여”와 “김 대리를 뺀 영업팀 평균 급여”를 차례로 물으면 김 대리의 급여가 계산됩니다. 결과 집합이 너무 작으면 거부하고, 통계에 작은 잡음을 섞는 것이 대응입니다. 반대로 결과가 너무 크면 집계로 대량 수집하는 것을 의심합니다.

    연결집계와 추론의 개념은 D2.1 자산 식별과 분류, 등급 체계와 BLP는 D3.2 보안 모델, SQL 삽입을 막는 코드 작성은 D8.5 안전한 코딩에서 다룹니다.

    원본 연습문제 · D3.5-Q11

    집계 통계에만 접근 권한이 있는 사용자가 작은 부분집합을 반복 질의해 특정 개인의 급여를 추론할 수 있게 되었다. 이것은 무엇이며 무엇으로 완화하는가?

    1. SQL 주입이며 매개변수화 쿼리로 완화한다.
    2. 집계를 통한 추론 공격이며 질의 집합 크기 제한, 셀 억제, 노이즈 또는 차분 프라이버시, 질의 양상 모니터링으로 완화한다.
    3. 권한 상승 결함이며 해당 사용자 계정 제거로 완화한다.
    4. 서비스 거부이며 질의 속도 제한만으로 완화한다.
    정답과 해설 보기

    정답 B. 각 질의는 인가된 범위 안에 있어 접근 통제가 위반되지 않는다. 문제는 여러 합법적 결과를 조합하면 보호되어야 할 개별 값이 드러난다는 것이다. 그래서 통제가 질의 단위가 아니라 질의 집합 수준에서 작동해야 한다. 최소 집합 크기를 요구하고, 민감한 셀을 억제하고, 결과에 노이즈를 더하고, 반복 질의 양상을 감시한다.

    • A · 주입이 아니라 인가된 질의의 조합이다.
    • C · 권한은 정상이며 결과 조합이 문제다.
    • D · 가용성 공격이 아니다.

    5암호 시스템

    원본의 핵심 문장은 대부분의 실패는 알고리즘이 아니라 구현과 운영에서 발생한다입니다.

    • 약한 알고리즘, 짧은 키, 구식 프로토콜
    • 키 관리 실패 — 하드코딩, 평문 저장, 교체 없음
    • 난수 품질 부족 — 예측 가능한 키
    • 인증서 검증 생략
    • 직접 구현한 암호(roll-your-own crypto)

    완화: 검증된 라이브러리, 하드웨어 난수, HSM/KMS 기반 키 관리, 알고리즘 민첩성(crypto-agility) 확보.

    가상 예시장비 소프트웨어가 로그 파일을 AES-256으로 암호화하는데, 키가 모든 장비의 프로그램 안에 같은 값으로 들어 있다고 합시다. 알고리즘은 강하지만, 누군가 장비 하나에서 프로그램을 분석해 키를 꺼내면 전 세계 모든 장비의 로그를 풀 수 있습니다. 장비마다 다른 키를 쓰고, 그 키를 장비의 보안 요소나 TPM에 보관하면 장비 하나가 털려도 그 장비로 피해가 한정됩니다.

    연결알고리즘 선택과 키 수명주기는 D3.6 암호 솔루션, 하드웨어 난수와 TPM·HSM은 D3.4 시스템 보안 기능, 암호 분석 공격은 D3.7 암호 분석 공격에서 다룹니다.

    원본 연습문제 · D3.5-Q22

    어떤 애플리케이션이 AES-256 을 올바르게 사용하지만 모든 고객 설치본에 같은 암호화 키가 컴파일되어 들어 있다. 약점은?

    1. AES-256 이 불충분하므로 더 긴 키가 필요하다.
    2. 암호 모드를 스트림 암호로 변경해야 한다.
    3. 암호 시스템이 알고리즘이 아니라 키 관리에서 실패한다. 키 하나가 추출되면 모든 고객이 침해되며 소프트웨어를 재배포하지 않고는 키를 교체할 수 없다.
    4. 키가 컴파일된 바이너리 안에 있으므로 약점이 없다.
    정답과 해설 보기

    정답 C. 암호 시스템의 실패는 알고리즘보다 키 관리에서 훨씬 자주 일어난다. 바이너리에 박힌 키는 역공학으로 추출할 수 있고 공유 키이므로 한 번 추출되면 전체 고객의 데이터가 열린다. 교체하려면 전원에게 새 버전을 배포해야 하므로 사실상 교체가 불가능하다. 고객별 키를 생성해 안전한 저장소에 두고 교체 가능한 구조로 설계해야 한다.

    • A · 키 길이 문제가 아니다.
    • B · 모드 변경이 키 공유 문제를 해결하지 않는다.
    • D · 컴파일은 은닉이며 보호가 아니다.

    문제 목록으로 돌아가기

    6산업제어시스템 (ICS / SCADA / OT)

    왜 IT와 다른가

    제약내용
    가용성 최우선중단이 생산 손실·안전 사고로 직결
    패치 어려움재부팅 불가, 벤더 인증 필요
    레거시 프로토콜Modbus, DNP3 등 인증·암호화 없음
    긴 수명10~20년 운영, 지원 종료 상태
    실시간 요구지연을 유발하는 통제를 적용하기 어렵다
    안전(Safety)보안보다 인명 안전이 상위

    완화 — 격리가 핵심

    • 네트워크 분할 — Purdue 모델 기반 계층 분리
    • 단방향 게이트웨이(data diode) — OT → IT 방향만 허용
    • 가상 패치
    • 전용 원격 접근 경로와 강한 인증
    • OT 전용 모니터링 — 산업 프로토콜을 이해하는 탐지
    • 안전 계장 시스템(SIS)은 별도로 분리

    원본의 경고는 이것입니다. IT 보안의 “일단 차단하고 본다”가 OT에서는 안전 사고를 일으킬 수 있다. 통제를 적용하기 전에 공정 영향 평가가 필수입니다.

    원문 사례 — ICS에 IT 통제를 적용한 결과. 보안팀이 생산 네트워크에 일반 취약점 스캐너를 돌렸고, 스캔 트래픽이 PLC를 재부팅시켜 생산 라인이 멈췄습니다. 원본은 OT에서는 능동 스캔이 위험할 수 있으므로 패시브 모니터링과 벤더가 승인한 도구를 쓰고 공정 영향 평가를 거쳐야 한다고 정리합니다.

    보충Purdue 모델은 공장 네트워크를 현장 장치(센서·액추에이터) → 제어기(PLC) → 감시·운전(HMI, SCADA) → 공장 운영 → 기업 IT 순의 층으로 나누고, 층 사이 경계에서 통신을 통제하는 참조 구조입니다(층 구성은 일반 지식에 근거한 보충). 단방향 게이트웨이는 물리적으로 한 방향만 신호가 가게 만든 장치라서, OT의 운전 데이터를 IT로 보낼 수는 있어도 IT에서 OT로 명령이 들어올 수는 없습니다. 안전 계장 시스템은 공정이 위험 상태가 되면 자동으로 멈추게 하는 마지막 안전장치이므로, 제어망이 침해되어도 영향을 받지 않도록 따로 둡니다.

    가상 예시병원의 영상 진단 장비도 OT와 비슷한 성격을 가집니다. 검사 중인 환자가 있으면 장비를 멈출 수 없고, 운영체제 업데이트는 제조사 검증 뒤에만 할 수 있으며, 10년 넘게 씁니다. 그래서 병원 IT팀의 일반 취약점 스캔이 장비를 멈추게 하지 않도록 스캔 대상에서 빼거나 제조사가 검증한 방식으로만 점검하고, 장비 구역을 분리하며, 원격 지원은 정해진 경로로만 열리게 합니다. D2.5 자산 보존 (EOL·EOS)의 영상 진단 장비 사례가 이 상황입니다.

    CISSP 관점OT 상황에서는 ① 우선순위가 가용성·안전이라는 점을 먼저 떠올리고 ② 즉시 패치·전면 차단·능동 스캔처럼 공정을 멈출 수 있는 선택지는 경계하며 ③ 격리(분할, 단방향 게이트웨이), 가상 패치, 패시브 모니터링, 공정 영향 평가 쪽을 봅니다. 사람의 안전이 걸려 있으면 그것이 다른 모든 고려보다 앞섭니다.

    연결교체할 수 없는 레거시의 보완 통제는 D2.5 자산 보존 (EOL·EOS), 네트워크 분할은 D4.1 네트워크 아키텍처, 탐지 수단의 운영은 D7.7 탐지·예방 수단에서 다룹니다. 원본은 NIST SP 800-82(OT 보안)와 IEC 62443(산업 자동화·제어 시스템 보안)을 관련 표준으로 듭니다.

    원문 위치: D3.5.md §3 산업제어시스템, §6 NIST SP 800-82·IEC 62443, §7 사례 2 · 공식 개요 3.5 “Industrial Control Systems (ICS)”

    7클라우드 기반 시스템

    서비스 모델별 고객 책임(IaaS: 운영체제 이상 전부, PaaS: 애플리케이션·데이터, SaaS: 데이터·IAM·설정)은 D3.1 안전한 설계 원칙에서 다뤘습니다. 원본이 드는 주요 취약점입니다.

    • 잘못된 구성(misconfiguration) — 원본은 클라우드 침해의 최대 원인으로 꼽는다. 공개 스토리지, 과다 권한
    • 과도한 IAM 권한 — 와일드카드 정책
    • 멀티테넌시 — 논리적 격리 실패, 부채널
    • 메타데이터 서비스 악용 — SSRF로 임시 자격증명 탈취
    • 데이터 소재지와 국경 간 이전
    • 섀도 IT와 미관리 리소스

    완화: IaC와 정책 코드화, CSPM(Cloud Security Posture Management, 클라우드 보안 상태 관리), 최소권한 IAM, 임시 자격증명, 암호화와 키 관리 분리, CASB.

    원문 사례 — 메타데이터 서비스를 통한 자격증명 탈취. 웹 애플리케이션의 SSRF 취약점으로 공격자가 클라우드 인스턴스 메타데이터 서비스에 접근해 임시 자격증명을 얻었습니다. 그 역할에 과도한 권한이 있어 스토리지 전체를 읽을 수 있었습니다. 최소권한 IAM 역할과 메타데이터 서비스 접근 제한이 필요했습니다.

    보충이 사례는 작은 취약점 두 개가 이어져 큰 사고가 된 경우입니다. SSRF(Server-Side Request Forgery)는 서버가 공격자 대신 내부 주소로 요청을 보내게 만드는 취약점이고, 클라우드 인스턴스 안에서만 접근할 수 있는 메타데이터 주소가 그 대상이 되었습니다. 둘째 고리는 인스턴스 역할의 과다 권한입니다. 어느 한쪽만 막혀 있었어도 피해는 작았을 것이므로, D3.1 안전한 설계 원칙의 심층 방어가 클라우드에서 어떻게 작동해야 하는지 보여 줍니다. 같은 데이터베이스라도 직접 운영할 때와 관리형 서비스를 쓸 때 패치·백업·접근 정책의 담당이 달라지므로, “클라우드”라는 이름 대신 구성 요소마다 누가 무엇을 하는지 적어 두는 것이 좋습니다.

    연결IaC와 태깅 강제는 D2.3 안전한 프로비저닝, CASB는 D2.6 데이터 보안 통제, 국경 간 이전은 D1.4 법률·규제·컴플라이언스, 도입 클라우드 서비스의 평가는 D8.4 도입 소프트웨어 평가에서 다룹니다. 원본은 NIST SP 800-144/800-145(클라우드 보안과 정의), CSA Cloud Controls Matrix를 관련 자료로 듭니다.

    원본 연습문제 · D3.5-Q32

    어떤 공급자가 가상 머신을 제공하고 고객이 그 위에 자기 운영체제와 애플리케이션을 설치한다. 어떤 서비스 모델인가?

    1. 서비스형 함수(FaaS).
    2. 서비스형 소프트웨어(SaaS).
    3. 서비스형 플랫폼(PaaS).
    4. 서비스형 인프라(IaaS).
    정답과 해설 보기

    정답 D. IaaS 는 연산과 저장, 네트워크를 제공하고 운영체제 위쪽은 고객이 맡는다. PaaS 는 런타임까지 공급자가 제공해 고객은 애플리케이션만 배포하고, SaaS 는 완성된 애플리케이션을 제공한다. FaaS 는 함수 단위로 실행되는 서버리스 모델이다. 모델이 올라갈수록 고객의 통제 범위와 책임이 줄어든다.

    • A · FaaS 는 함수 단위 실행 모델이다.
    • B · SaaS 는 완성된 애플리케이션을 제공한다.
    • C · PaaS 는 런타임까지 제공한다.

    8분산 시스템

    • 구성 요소 사이의 신뢰 경계가 많아 공격면이 넓다
    • 시간 동기화 — 로그 상관분석과 인증서 검증에 필수
    • 일관성과 가용성의 트레이드오프
    • 서비스 간 인증 부재 — 내부망 신뢰 가정

    완화: 상호 인증(mTLS), 메시지 무결성, 중앙 시간 동기화, 서비스 메시.

    보충시간 동기화가 보안 목록에 있는 이유는 두 가지입니다. 사고 조사에서 여러 서버의 로그를 시간순으로 맞춰야 공격 흐름이 보이는데, 시계가 몇 분씩 다르면 순서가 뒤집힙니다. 또 인증서와 토큰은 유효 시간을 가지므로 시계가 틀린 시스템은 만료된 인증서를 받아들이거나 유효한 것을 거부합니다.

    연결서비스 간에도 위치를 믿지 않는 것은 D3.1 안전한 설계 원칙의 제로 트러스트, TLS와 인증서 기반 통신은 D3.6 암호 솔루션·D4.3 안전한 통신 채널, 로그 상관분석은 D7.2 로깅·모니터링에서 다룹니다.

    원문 위치: D3.5.md §3 분산 시스템 · 공식 개요 3.5 “Distributed systems”

    9사물인터넷 (IoT)

    원본은 IoT를 구조적으로 취약하다고 표현합니다.

    • 기본 자격증명을 바꾸지 않은 채 배포
    • 업데이트 메커니즘 부재 또는 서명 검증 없음
    • 물리적 접근 용이 — 디버그 포트, 펌웨어 추출
    • 제한된 연산 자원 — 강한 암호 적용 곤란
    • 대규모 배포 — 침해되면 봇넷이 된다
    • 벤더 지원 조기 종료

    완화: 전용 네트워크 분할, 기본 자격증명 강제 변경, 서명된 펌웨어 업데이트, 인증서 기반 기기 식별, 아웃바운드 통제, 수명주기 관리.

    보충“아웃바운드 통제”는 IoT에서 특히 효과가 큽니다. 온도 센서가 접속해야 할 곳은 관리 서버 하나뿐이므로 그 외의 바깥 통신을 막으면, 기기가 털려도 봇넷 명령 서버에 접속하거나 다른 곳을 공격하는 데 쓰이기 어렵습니다. 기기마다 다른 초기 비밀번호를 쓰게 하는 것도 대규모 배포의 약점을 줄이는 방법입니다. 원본은 NIST IR 8259(IoT 기기 제조자의 보안 역량)를 관련 자료로 듭니다.

    연결기본 자격증명과 골든 이미지는 D2.3 안전한 프로비저닝, 서명된 업데이트와 보안 부팅은 D3.4 시스템 보안 기능, 기기 인증은 D5.2 식별·인증 전략에서 다룹니다.

    원문 위치: D3.5.md §3 사물인터넷, §6 NIST IR 8259 · 공식 개요 3.5 “Internet of Things (IoT)”

    10마이크로서비스와 API

    • 인증·인가 미흡 — 서비스 간 호출에 검증이 없다
    • 과다 데이터 노출 — API가 필요 이상을 반환하고 클라이언트가 걸러낸다
    • 객체 수준 인가 부재(IDOR) — 식별자만 바꾸면 남의 데이터가 조회된다
    • 속도 제한 부재
    • 버전 난립과 방치된 엔드포인트(shadow API)

    완화: API 게이트웨이, 서비스 간 mTLS, 토큰 기반 인가와 객체 단위 권한 검증, 스키마 검증, 속도 제한, API 인벤토리.

    보충IDOR(Insecure Direct Object Reference)은 단순하지만 흔합니다. 주소창의 /orders/1001을 /orders/1002로 바꿨더니 남의 주문이 보이는 경우입니다. 로그인했는지(인증)만 확인하고 “이 주문이 이 사용자의 것인가”(객체 수준 인가)를 확인하지 않아서 생깁니다. 과다 데이터 노출은 2절의 “클라이언트를 믿지 마라”의 다른 얼굴입니다. 화면에 안 보이게 걸러도 응답에 들어 있으면 공격자는 봅니다. 원본은 OWASP API Security Top 10을 관련 자료로 듭니다.

    연결인가 메커니즘은 D5.4 인가 메커니즘, 토큰 기반 인증(OAuth 등)은 D5.3 연합 식별, API 보안 코딩은 D8.5 안전한 코딩, 인벤토리의 공백(섀도 API도 섀도 IT의 한 형태)은 D2.3 안전한 프로비저닝에서 다룹니다.

    원문 위치: D3.5.md §3 마이크로서비스와 API, §6 OWASP API Security Top 10 · 공식 개요 3.5 “Microservices (e.g., API)”

    • 이미지 취약점 누적

    완화: 신뢰 레지스트리와 이미지 서명, 이미지 스캔, 비특권 실행, 읽기 전용 파일 시스템, 비밀 관리 도구, 네트워크 정책, 런타임 보호.

    가상 예시여러 팀의 업무를 한 호스트에 올리면서 팀마다 필요한 라이브러리가 달라 컨테이너로 나누자는 제안에 “가상 머신과 똑같이 격리된다”는 설명이 붙었습니다. 같은 회사 팀들이라면 컨테이너 + 비특권 실행 + 커널 패치로 충분할 수 있습니다. 하지만 서로 신뢰하지 않는 외부 고객의 코드를 함께 올린다면 커널을 공유하는 구조 자체가 위험이므로 VM이나 경량 VM을 써야 합니다. “얼마나 격리되는가”는 기술 이름이 아니라 함께 놓이는 대상이 서로 믿을 수 있는지로 판단합니다.

    연결컨테이너와 VM의 격리 강도는 D3.4 시스템 보안 기능, 이미지 서명과 공급망은 D8.2 개발 생태계 보안 통제, 비밀 관리는 D3.6 암호 솔루션에서 다룹니다. 원본은 NIST SP 800-190(컨테이너 보안)을 듭니다.

    원문 위치: D3.5.md §3 컨테이너화, §6 NIST SP 800-190 · 공식 개요 3.5 “Containerization”

    12서버리스

    • 이벤트 주입 — 다양한 이벤트 소스(파일 업로드, 메시지 큐, HTTP)가 모두 입력 경로다
    • 과도한 함수 권한 — 함수마다 최소권한을 적용하기 어렵다
    • 의존성 취약점
    • 가시성 부족 — 수명이 짧아 포렌식이 어렵다
    • 비동기 흐름의 복잡성

    완화: 함수별 최소권한 역할, 입력 검증, 의존성 관리와 SBOM, 구조화 로깅과 추적, 실행 시간·동시성 제한.

    보충서버리스에서는 서버가 사라지는 대신 함수와 권한이 자산이 됩니다. 함수 수십 개가 모두 같은 넓은 역할을 쓰면 하나만 털려도 전부를 쓸 수 있습니다. 또 실행이 끝나면 환경이 사라지므로 사고 뒤에 “그 순간의 상태”를 볼 수 없습니다. 그래서 사건 기록을 남기는 일을 실행 중에 미리 해 둬야 합니다(구조화 로그, 추적 ID).

    연결SBOM과 의존성 관리는 D1.11 공급망 위험 관리·D8.2 개발 생태계 보안 통제, 로깅과 추적은 D7.2 로깅·모니터링에서 다룹니다.

    원문 위치: D3.5.md §3 서버리스 · 공식 개요 3.5 “Serverless”

    13임베디드 시스템

    • 자원 제약으로 보안 기능을 탑재하기 어렵다
    • 업데이트 경로 부재 또는 현장 접근 필요
    • 펌웨어 추출과 리버싱
    • 하드코딩된 키와 자격증명
    • 긴 수명과 지원 종료

    완화: 보안 부팅과 신뢰 루트, 서명된 펌웨어, 디버그 인터페이스 비활성화, 하드웨어 보안 요소, 네트워크 격리.

    가상 예시의료 장비 안의 제어 보드를 생각해 봅시다. 개발 중에 쓰던 디버그 포트(JTAG, 시리얼 콘솔)가 양산품에 그대로 열려 있으면, 장비를 열 수 있는 사람은 펌웨어를 꺼내 분석하고 그 안의 키를 찾을 수 있습니다. 양산 시 디버그 인터페이스를 잠그고, 펌웨어는 서명 검증 후에만 실행되게 하며(보안 부팅), 키는 보안 요소에 넣는 것이 원본의 완화 목록을 이 장비에 적용한 모습입니다. 업데이트 경로를 설계 단계에서 만들어 두지 않으면, 취약점이 발견되었을 때 현장 방문 말고는 고칠 방법이 없습니다.

    연결보안 부팅과 신뢰 루트는 D3.4 시스템 보안 기능, 하드웨어 신뢰 루트와 PUF는 D1.11 공급망 위험 관리, 지원 종료 자산은 D2.5 자산 보존 (EOL·EOS)에서 다룹니다.

    원문 위치: D3.5.md §3 임베디드 시스템 · 공식 개요 3.5 “Embedded systems”

    14고성능 컴퓨팅과 엣지 컴퓨팅

    유형고유 위험완화
    HPC 고성능 컴퓨팅다수 사용자가 공유하는 대규모 자원, 작업 스케줄러 권한, 공유 파일 시스템의 데이터 분리, 연산 자원 자체가 탈취 대상(암호화폐 채굴), 성능 때문에 보안 기능을 끄는 관행다중 사용자 격리, 스케줄러 접근 통제, 작업 단위 감사, 자원 사용 이상 탐지
    엣지 컴퓨팅물리 보안 취약(통제되지 않은 장소), 분산 관리(패치·구성 일관성), 연결이 끊겼을 때의 자율 동작과 로컬 데이터, 대수가 많아 운영 부담저장 암호화, 기기 인증과 증명, 변조 감지, 중앙 집중 관리와 자동 배포, 최소 데이터 보관

    보충엣지 장비는 누군가 가져갈 수 있다는 전제로 설계합니다. 그래서 저장 데이터는 암호화하고, 장비가 변조되지 않았음을 중앙에 증명하게 하며(D3.4 시스템 보안 기능의 측정 부팅과 증명), 장비에 꼭 필요한 데이터만 둡니다. HPC에서 “연산 자원 자체가 탈취 대상”이라는 점은, 데이터 유출이 없어도 무단 채굴만으로 큰 비용 피해가 날 수 있다는 뜻입니다.

    원문 위치: D3.5.md §3 고성능 컴퓨팅, 엣지 컴퓨팅 · 공식 개요 3.5 “High-Performance Computing systems”, “Edge computing systems”

    15가상화 시스템

    위협설명
    VM 탈출게스트에서 하이퍼바이저로 침투
    VM 난립(sprawl)관리되지 않는 VM이 늘어나 패치·인벤토리 공백
    휴면 VM꺼져 있어 패치되지 않다가 오래된 상태로 기동
    스냅샷·이미지민감 데이터와 메모리 상태 포함
    자원 경쟁과 부채널공유 하드웨어
    하이퍼바이저 관리 평면침해 시 전체 장악

    완화: 하이퍼바이저 패치와 최소 기능, 관리 평면 분리, VM 수명주기 관리, 스냅샷 암호화와 보존 정책, 테넌트 분리, 휴면 VM 정기 점검.

    원문 사례 — 휴면 VM이 만든 구멍. 프로젝트가 끝난 뒤 꺼 둔 가상 머신을 1년 뒤 테스트용으로 켰는데, 1년치 패치가 빠진 채 네트워크에 연결되어 곧바로 침해되었습니다. 원본은 휴면 VM도 인벤토리 대상이며, 기동 전에 격리된 네트워크에서 패치하는 절차가 필요했다고 정리합니다.

    보충스냅샷은 “그 순간의 메모리”까지 담을 수 있어서, 실행 중이던 프로그램의 키나 비밀번호가 스냅샷 파일 안에 남을 수 있습니다. 그래서 스냅샷은 그 VM과 같은 등급의 데이터로 취급하고 암호화·보존 기간·폐기를 정해야 합니다. D2.2 자산 취급 요구사항의 “모든 사본은 원본과 같은 등급”이 가상화에서 나타나는 모습입니다.

    연결VM 탈출과 Ring -1은 D3.4 시스템 보안 기능, 인벤토리와 휴면 자산은 D2.3 안전한 프로비저닝, 관리 평면 보호는 D7.4 기본 보안 운영 개념의 특권 관리에서 다룹니다. 원본은 NIST SP 800-125(가상화 보안)를 듭니다.

    원문 위치: D3.5.md §3 가상화 시스템, §5 셋째 표, §6 NIST SP 800-125, §7 사례 5 · 공식 개요 3.5 “Virtualized systems”

    18핵심 요약

    1. 시스템마다 위협 모델이 다르다. ICS/OT = 가용성·안전 우선, 일반 IT = 기밀성 우선.
    2. 클라이언트에서 오는 모든 입력은 신뢰 불가. 서버 측 검증 필수.
    3. 서버: 신뢰 경계, 이중화, 강화, 세그멘테이션. 관리 경로와 업무 경로 분리.
    4. DB 위협: SQL 삽입 / 집계 / 추론 / 동시성. 다중 인스턴스화 = 등급별 별도 레코드 = 추론·존재 노출 방어. 뷰, 셀 단위 통제, 질의 제한, 노이즈, 매개변수화 질의.
    5. 암호 실패는 알고리즘이 아니라 키 관리·난수·구현에서. 알고리즘 민첩성.
    6. OT 제약: 패치 곤란, 레거시 프로토콜 무인증·무암호, 긴 수명, 실시간, 안전. 완화의 핵심은 격리(Purdue 분할, 단방향 게이트웨이, 가상 패치, SIS 분리). 통제 전 공정 영향 평가.
    7. 클라우드 최대 위험 = 잘못된 구성, 과도한 IAM. 메타데이터 서비스 + SSRF = 임시 자격증명 탈취. IaC, CSPM, 최소권한.
    8. 분산: 신뢰 경계 다수, 시간 동기화, mTLS.
    9. IoT·임베디드: 기본 자격증명, 업데이트 부재, 물리 접근(디버그 포트), 하드코딩 키, 긴 수명. 분할, 서명된 펌웨어, 보안 부팅, 아웃바운드 통제.
    10. API: 객체 수준 인가(IDOR), 과다 노출, 속도 제한, 섀도 API.
    11. 컨테이너: 이미지 신뢰, 커널 공유, 특권 실행, 비밀 관리. 서버리스: 이벤트 주입, 과도한 함수 권한, 가시성 부족.
    12. HPC: 공유 자원과 자원 탈취. 엣지: 물리 보안 취약 + 분산 관리 → 저장 암호화, 변조 감지, 증명.
    13. 가상화: VM 탈출 / VM 난립 / 휴면 VM / 스냅샷 / 관리 평면.
    원문 위치: D3.5.md §8 CISSP 시험 관점, §9 핵심 암기 요약(16항목). 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    19주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Client-Side Validation · 클라이언트 측 검증

    클라이언트에서 수행하는 입력 검증. 공격자가 우회할 수 있어 서버 측 검증을 대체할 수 없다.

    Polyinstantiation · 다중 인스턴스화

    같은 키에 대해 등급별로 다른 레코드를 존재하게 해 추론을 방지하는 데이터베이스 기법.

    ICS / SCADA / OT — Industrial Control Systems / Supervisory Control and Data Acquisition / Operational Technology · 산업제어시스템 / 감시 제어·데이터 수집 / 운영 기술

    산업제어시스템과 운영기술 환경. 가용성과 안전이 기밀성보다 우선한다.

    Purdue Model · 퍼듀 모델

    OT 환경을 계층으로 나누어 IT 와 OT 사이의 분리 구조를 정의하는 참조 모델.

    Data Diode · 단방향 게이트웨이

    물리적으로 한 방향 통신만 허용하는 장치. OT 에서 IT 로의 단방향 전송에 쓰인다.

    SIS — Safety Instrumented System · 안전 계장 시스템

    위험 상황에서 공정을 안전 상태로 전환하는 시스템. 제어 네트워크와 분리해야 한다.

    Misconfiguration · 잘못된 구성

    클라우드 침해의 최대 원인. 공개 스토리지, 과도한 권한이 대표적이다.

    Instance Metadata Service · 인스턴스 메타데이터 서비스

    클라우드 인스턴스에 임시 자격증명을 제공하는 내부 서비스. SSRF 로 악용될 수 있다.

    IDOR — Insecure Direct Object Reference · 안전하지 않은 직접 객체 참조

    식별자를 변경해 권한 없는 객체에 접근하는 취약점. 객체 수준 인가 검증으로 막는다.

    Shadow API · 관리 범위에 등록되지 않은 API

    문서화되지 않거나 방치된 API 엔드포인트. 인벤토리 공백이 된다.

    Privileged Container · 특권 컨테이너

    호스트 권한으로 실행되는 컨테이너. 탈출 위험이 크게 증가한다.

    Event Injection · 이벤트 주입

    서버리스 함수의 다양한 이벤트 소스를 통한 악성 입력 주입.

    VM Sprawl · VM 난립

    관리되지 않는 가상머신이 증가해 패치와 인벤토리에 공백이 생기는 현상.

    Dormant VM · 휴면 VM

    장기간 꺼져 있어 패치되지 않은 채 구형 상태로 기동되는 가상머신.
