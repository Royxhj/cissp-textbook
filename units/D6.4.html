    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    테스트는 데이터를 만들고, 분석은 판단을 만들고, 보고서는 그 판단을 행동으로 바꿉니다. 원본은 보고서의 성공 기준을 분명히 합니다. 분량이나 발견 건수가 아니라 조치가 일어났는가. 읽히지 않는 400페이지 보고서는 실패한 보고서입니다. 이 단원은 결과 분석, 보고서 작성, 그리고 공식 개요 6.4가 드는 교정·예외 처리·윤리적 공개를 다룹니다.

    ① 검증

    오류의미피해
    거짓 양성 false positive없는 결함을 보고신뢰 상실, 자원 낭비
    거짓 음성 false negative있는 결함을 놓침노출 지속 — 더 위험

    거짓 음성은 보고서에 나타나지 않기 때문에 발견하기 어렵습니다. 그래서 커버리지 분석과 다른 기법의 교차 검증이 필요합니다. 검증 방법은 수동 재현, 설정 직접 확인, 담당자 확인, 다른 도구로 교차 확인입니다.

    원문 사례 — 검증 없이 보고한 결과. 스캐너 출력 1,100건을 그대로 운영팀에 넘겼고, 상위 50건 중 31건이 거짓 양성이었습니다. 이후 운영팀은 보안팀 보고서를 우선 처리하지 않게 되었습니다. 보고 전 검증을 의무화하고, 발견마다 검증 상태를 표시하고, 거짓 양성률 자체를 보안팀 품질 지표로 삼았습니다.

    ② 중복 제거와 ③ 근본 원인

    같은 근본 원인이 여러 발견으로 중복 보고되는 경우가 많습니다. 서버 200대에 같은 패치가 빠졌다면 발견 200건이 아니라 “패치 배포 프로세스 결함” 1건입니다. 집계하지 않으면 건수에 압도되어 우선순위가 무너집니다.

    증상가능한 근본 원인
    서버 다수의 패치 누락패치 배포 프로세스 미작동, 자산 미등록
    과도한 권한 다수역할 설계 부재, 회수 절차 없음
    같은 취약점 반복 출현기준 이미지 미수정, 배포 자동화에 반영 안 됨
    설정 오류 반복수동 구성, 기준선 미적용

    원본은 근본 원인을 고치지 않으면 같은 결함이 다음 테스트에 다시 나온다고 말합니다. 같은 설정 오류가 분기마다 새 서버에서 반복되는데 매번 개별 건만 닫는다면, 빠진 것은 빌드 과정이나 이미지에 대한 근본 원인 분석입니다.

    원문 사례 — 212건이 사실은 1건. “패치 누락” 212건은 같은 패치가 212대에서 빠진 것이었고, 원인은 배포 도구가 특정 사업장 서버 그룹에 닿지 못한 설정 오류였습니다. 근본 원인 1건으로 집계해 배포 경로를 고치자 재발이 사라졌습니다.

    보충묶는 데도 주의가 필요합니다. 경고가 비슷해 보인다는 이유만으로 같은 원인으로 묶으면 다른 취약 상태를 놓칩니다. 보고서에는 ① 관측된 결과 ② 공통 원인이라고 판단한 근거 ③ 고친 뒤 다시 본 증거를 각각 적습니다. 심사에서 부적합을 “같은 근본 원인의 여러 사례”로 묶을 때와 같은 원칙입니다.

    ④ 위험 평가와 ⑤ 우선순위

    기술적 심각도를 조직 맥락으로 변환합니다. 고려 요소: 악용 가능성(공개 악용 코드, 인증 필요 여부), 노출 경로(인터넷 / 내부 / 격리), 자산 중요도, 기존 보완 통제(WAF, 분할, 탐지), 공격 연쇄 가능성.

    원본은 낮은 심각도 결함들의 연쇄가 치명적 경로를 만드는 경우가 많다고 강조합니다. 침투 테스트 보고서가 “공격 경로(attack path)”로 서술하는 이유입니다. 우선순위는 심각도 순서가 아니라 위험 감소 효율 순서입니다. 한 조치로 여러 결함이 해소되는 항목(기준 이미지 수정, 패치 프로세스 복구)이 먼저입니다.

    원문 사례 — 낮은 심각도의 연쇄. 중대 결함 없이 낮음·중간 등급뿐이었지만, 침투 테스트 팀이 정보 노출(낮음) → 유효 계정명 확보 → 약한 잠금 정책(중간) → 비밀번호 스프레이 성공 → 과도한 공유 권한(중간) → 도메인 관리자 자격증명 획득의 경로를 제시했습니다. 보고서에 공격 경로 서술을 의무화하고, 경로의 한 고리를 끊는 조치를 최우선으로 올렸습니다.

    연결CVSS와 우선순위의 맥락은 D6.2 보안 통제 테스트의 2절, 커버리지 분석은 D6.2 보안 통제 테스트의 7절, 비밀번호 스프레이는 D5.6 인증 시스템의 8절에서 다룹니다.

    원본 연습문제 · D6.4-Q01

    보안 테스트에서 거짓 음성이 일반적으로 거짓 양성보다 더 위험한 이유는?

    1. 거짓 음성은 검증 과정에서 분석가의 시간을 더 많이 소비한다.
    2. 거짓 음성은 항상 스캔 도구에 결함이 있음을 의미한다.
    3. 거짓 음성은 준수 점수에 반영되지만 거짓 양성은 반영되지 않는다.
    4. 거짓 음성은 실제 노출을 그대로 남기고 보고서에 나타나지 않아 발견하기 어렵다.
    정답과 해설 보기

    정답 D. 거짓 양성은 검증 과정에서 걸러지며 신뢰 상실과 자원 낭비라는 비용을 낳는다. 거짓 음성은 실제 결함이 보고되지 않아 노출이 지속되는데 보고서에 나타나지 않으므로 존재 자체를 알기 어렵다. 대응은 커버리지 분석과 다른 기법의 교차 검증이다.

    • A · 검증 시간을 소비하는 것은 거짓 양성이다.
    • B · 도구 결함이 아니라 기법의 한계인 경우가 대부분이다.
    • C · 준수 점수 반영 방식은 위험성 비교의 근거가 아니다.

    원본 연습문제 · D6.4-Q16

    테스트 결과에서 같은 설정 오류가 분기마다 새 서버에서 반복된다. 시정은 매번 각 건을 닫는다. 무엇이 빠져 있는가?

    1. 각 건을 더 빨리 찾도록 더 빠른 스캐너.
    2. 빠진 것이 없다. 각 건을 닫는 것이 올바른 시정이다.
    3. 근본 원인 분석이다. 반복은 개별 서버가 아니라 빌드 과정이나 이미지를 가리키므로 수정은 골든 이미지와 프로비저닝 자동화, 배포를 통제하는 기준선 점검에 들어가야 한다.
    4. 발견 사항이 더 주목받도록 더 높은 심각도 등급.
    정답과 해설 보기

    정답 C. 같은 결함이 새 자산에서 계속 나타나면 개별 시정은 증상만 없애고 원인은 그대로 둔다. 원인이 이미지나 자동화 스크립트에 있으면 거기서 고쳐야 이후 생성되는 자산에 재발하지 않는다. 반복 지표를 추적해 개별 시정으로 끝낼 사안과 공정 수정이 필요한 사안을 구분해야 한다.

    • A · 탐지 속도는 재발을 막지 않는다.
    • B · 증상만 반복 제거하는 방식이다.
    • D · 등급 상향은 원인을 바꾸지 않는다.

    보고서의 보호와 재검증

    취약점 보고서는 공격 지침서입니다. 접근 제한, 암호화 보관·전송, 배포 대상 최소화, 보존 기간과 파기 절차가 필요하고, 테스터 측 사본 처리도 계약에 명시합니다.

    조치 완료 주장만으로 종결하지 않고 재검증(retest)으로 확인한 뒤 종결합니다. 재검증에서 흔히 발견되는 것은 일부 자산에만 적용되었거나, 다른 경로가 남아 있거나, 조치가 다른 기능을 깨뜨린 경우입니다.

    원문 사례 — 조치 완료 주장과 재검증. 개발팀이 인가 결함 조치를 완료했다고 통보했지만, 재검증에서 웹 화면 경로만 고쳐졌고 모바일 앱이 쓰는 별도 엔드포인트는 그대로였습니다. 재검증을 종결 전 필수 단계로 두고, 발견 항목에 영향 범위를 명시해 모든 경로가 포함되게 했습니다.

    보충“완료”를 승인할 때 두 기록을 구분해 남깁니다. 담당자의 조치 기록에는 무엇을 바꿨는지가 있고, 재검증 기록에는 문제가 해결되었다는 근거가 있습니다. 앞의 것만 있으면 시정 조치의 유효성 확인이 빠진 것입니다. 심사에서 시정 조치 완료와 유효성 확인을 따로 보는 것과 같습니다.

    연결감사 보고서와 감사 결과 전달은 D6.5 보안 감사, 경영진 보고의 형태는 D6.3 보안 프로세스 데이터의 7절에서 다룹니다.

    레거시 시스템, 공급자 의존, 운영 중단 불가처럼 즉시 수정이 불가능한 경우가 현실에 많습니다. 이때는 보완 통제를 적용하고 예외로 관리합니다. 원본은 아무것도 하지 않고 “조치 중”으로 두는 것이 최악이라고 말합니다.

    연결위험 처리 선택지와 보완 통제는 D1.9 위험 관리, 미조치 잔량 지표는 D6.3 보안 프로세스 데이터의 3절, 패치 운영은 D7.8 패치·취약점 관리에서 다룹니다.

    원문 위치: D6.4.md §3 교정 · 공식 개요 6.4 “Remediation”

    4예외 처리 (Exception Handling)

    원본의 정리: 예외는 정당한 관리 수단이지만, 관리되지 않으면 통제 붕괴의 주된 경로가 된다.

    필수 요소내용
    명확한 범위어떤 시스템, 어떤 요구사항에 대한 예외인가. 포괄적 예외 금지
    사유와 업무 근거왜 준수할 수 없는가
    위험 분석이 예외로 생기는 위험
    보완 통제위험을 줄이는 대체 수단. 보완 통제 없는 예외는 단순 수락
    승인자그 위험을 수락할 권한이 있는 사람. 요청자가 승인할 수 없음
    만료일기한 없는 예외는 예외가 아니라 정책 변경
    재검토 조건만료 전 재평가, 환경 변화 시 재평가

    흔한 실패: 영구 예외(원래 사유가 사라졌는데도 남음), 만료 후 자동 연장(만료 예외 건수는 좋은 KRI), 권한 없는 승인(조직 전체 위험을 팀장이 수락), 보완 통제 미이행, 예외 목록 부재(예외 등록부 exception register 필요).

    원본은 예외의 누적이 실질적 보안 수준을 결정한다고 말합니다. 정책이 엄격해도 예외가 많으면 실제 수준은 예외가 정합니다. 그래서 예외 건수와 추세를 경영 검토 안건으로 올립니다.

    원문 사례 — 만료일 없는 예외 47건. 예외 등록부를 처음 만들자 47건이 나왔고 29건은 만료일이 없었습니다. 가장 오래된 것은 6년 전 승인된 “레거시 앱의 TLS 1.0 허용”이었는데, 그 앱은 3년 전에 폐기되어 있었습니다.

    원문 사례 — 보완 통제가 서류에만 있던 예외. MFA 미적용 레거시 시스템의 예외 조건은 “특정 IP 범위로 제한, 모든 로그인 경보 등록”이었지만 1년 뒤 점검에서 둘 다 적용되지 않았습니다. 예외 승인에 보완 통제 이행 확인 단계를 따로 두고, 미이행 시 예외를 자동 무효화했습니다.

    가상 예시병원 영상 장비에 표준 패치를 적용하면 장비 인증 상태가 바뀔 수 있어 즉시 패치가 어렵고, 장비 담당자가 구두로 “다음 정비 때까지 연기하자”고 합니다. 구두 합의는 예외가 아닙니다. 대상 장비와 버전, 연기 사유, 노출 경로와 영향 평가를 기록하고, 네트워크 분리 같은 보완 통제와 그 적용 확인 결과를 붙이고, 그 위험을 수락할 권한이 있는 사람이 만료일과 함께 승인해야 예외가 됩니다.

    연결위험 수락의 권한과 거버넌스는 D1.9 위험 관리·D1.3 보안 거버넌스, 예외 승인 기록의 수집은 D6.3 보안 프로세스 데이터의 2절, 의료기기 등 레거시 장비의 보호는 D3.5 아키텍처별 취약점에서 다룹니다.

    원본 연습문제 · D6.4-Q23

    보안 예외에 만료일이 있어야 하는 이유는?

    1. 문서 보존 요구사항을 준수하기 위해.
    2. 만료일이 없으면 예외가 사실상 영구화되어 표준을 대체해 버리고 위험을 다시 검토하는 시점이 없어지기 때문.
    3. 조직이 부여할 수 있는 예외 수를 제한하기 위해.
    4. 승인자의 권한이 정해진 기간만 유효하므로.
    정답과 해설 보기

    정답 B. 예외는 한시적 위험 수용이다. 만료일이 없으면 승인된 그 상태가 계속되고 환경이 바뀌어도 아무도 다시 보지 않는다. 만료일이 있으면 갱신 시점에 여전히 필요한지와 보완 통제가 작동하는지를 재확인하게 된다. 반복 갱신되는 예외는 표준 자체를 고쳐야 한다는 신호다.

    • A · 문서 보존과 다른 목적이다.
    • C · 수량 제한이 목적이 아니다.
    • D · 승인자 권한 기간과 무관하다.

    5윤리적 공개 (Ethical Disclosure)

    취약점을 발견했을 때 어떻게 알리는가의 문제입니다.

    모델내용
    비공개 Private개발사에만 알리고 공개하지 않음
    조정 공개 Coordinated개발사에 먼저 알리고 수정 후 함께 공개 — 현재 표준적 접근(CVD)
    완전 공개 Full즉시 전면 공개
    1. 발견
    2. 개발사·운영자에게 비공개 보고(보안 연락처, 안전한 경로)
    3. 접수 확인과 분석
    4. 수정 개발과 배포
    5. 합의된 시점에 공개(통상 90일 기준, 조정 가능)
    6. 크레딧과 CVE 할당

    목적은 이용자 보호입니다. 수정 전 공개는 공격자에게 먼저 정보를 주고, 무기한 비공개는 이용자를 위험을 모르는 채 노출시킵니다. 그래서 기한을 두고 기한 뒤에는 제한적으로 공개합니다. 활발히 악용 중인 취약점은 기한을 단축해 이용자가 즉시 완화할 수 있게 합니다. 존재와 완화책만 공개하고 악용 세부는 유보하는 방식도 쓰입니다.

    윤리적 원칙과 법적 경계

    • ISC2 윤리 강령은 사회·공공 이익 보호와 신뢰받는 행동을 요구합니다. 발견자에게는 이용자 피해를 최소화하는 방식으로 알릴 책임이 있습니다.
    • 승인 없는 테스트는 불법일 수 있습니다. “선의로” 찾았더라도 권한 없이 수행하면 법적 문제가 됩니다.
    • 버그 바운티와 세이프 하버: 프로그램 범위와 규칙 안에서 수행하면 법적 조치를 하지 않는다는 명시가 있어야 연구자가 안전합니다.
    • 데이터 접근 금지: 입증에 필요한 최소한을 넘어 실제 개인정보를 열람·보관·공개하면 윤리와 법 모두 위반입니다.
    • 대가 요구 금지: 취약점을 알린 뒤 금전을 요구하면 강요(extortion)입니다. 버그 바운티는 사전에 정의된 프로그램 안에서만 성립합니다.

    조직 측 준비

    • 보안 연락처 공개: security.txt나 보안 페이지. 경로가 없으면 보고자가 공개 채널로 알리게 됩니다.
    • 접수 확인과 진행 공유: 원본은 무응답이 완전 공개를 유발하는 가장 흔한 원인이라고 말합니다.
    • 내부 처리 절차: ISO/IEC 30111(취약점 처리 프로세스), ISO/IEC 29147(공개 절차).
    • 보복 금지 정책: 선의의 보고자에게 법적 위협을 가하면 이후 보고가 사라지고 외부 공개만 남습니다.

    원문 사례 — 보고 경로가 없어 공개된 취약점. 외부 연구자가 인가 결함을 발견했지만 보안 연락처가 없어 고객 지원 채널로 보고했고, 일반 문의로 분류되어 2개월간 방치되었습니다. 연구자는 공개 블로그에 상세 내용을 올렸습니다. 보안 연락처 공개, 접수 확인 서비스 수준, 보복 금지 정책, 내부 처리 절차로 대응했습니다.

    보충의료기기 제조사라면 이 절은 규제와도 맞닿습니다. 출시 후 취약점을 외부에서 받아 처리하는 절차(보고 창구, 접수 확인, 위험 평가, 수정 배포, 고객·규제 기관 공지)는 시판 후 사이버보안 관리의 핵심 요소로 다뤄집니다. 구체 요구는 관할 규제와 지침에 따라 다르므로 해당 문서를 직접 확인해야 하며, 이 교재는 그 내용을 확인하지 않았습니다.

    연결ISC2 윤리 강령은 D1.1 전문가 윤리, 승인 없는 접근의 법적 측면은 D1.4 법률·규제·컴플라이언스, 테스트 서면 승인은 D6.1 평가·테스트·감사 전략의 6절에서 다룹니다.

    원본 연습문제 · D6.4-Q08

    어떤 연구자가 노출된 데이터베이스를 발견하고 문제를 입증한다는 이유로 고객 기록 5만 건을 내려받은 뒤 상세 내용 제공 전에 회사에 대가를 요구했다. 올바른 설명은?

    1. 대가 요구는 수용 가능하지만 기록 내려받기는 그렇지 않다.
    2. 기록 내려받기는 증거로 수용 가능하지만 대가 요구는 그렇지 않다.
    3. 과도한 데이터 접근과 대가 요구 모두 위반이다. 입증은 필요한 최소한으로 제한해야 하고 보상은 사전에 정의된 프로그램 안에서만 성립한다.
    4. 연구자가 실제 취약점을 발견했으므로 두 행위 모두 수용 가능하다.
    정답과 해설 보기

    정답 C. 취약점 입증에 필요한 최소를 넘어 실제 개인정보를 대량 열람하고 보관하는 것은 윤리와 법 모두 위반이다. 또한 취약점을 알린 뒤 금전을 요구하면 강요에 해당하며 보상은 사전에 정의된 버그 바운티 프로그램의 범위와 규칙 안에서만 성립한다.

    • A · 사전 프로그램 없는 대가 요구는 강요가 된다.
    • B · 5만 건 대량 내려받기는 입증 최소 범위를 크게 넘는다.
    • D · 취약점의 실재성이 수단을 정당화하지 않는다.

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    취약점 관리 점검 결과다. ㉠ 스캐너 결과를 검증 없이 전달해 거짓 양성이 다수 섞였다. ㉡ 같은 설정 오류가 분기마다 새 서버에서 반복되고 매번 개별 건만 닫힌다. ㉢ 예외 47건 중 29건에 만료일이 없다. ㉣ 외부 연구자의 보고가 고객 지원 채널에서 두 달간 방치되었다. 가장 적절한 대책 묶음은?

    1. ㉠ 보고 전 검증 단계와 거짓 양성률 지표 / ㉡ 빌드 이미지·배포 과정의 근본 원인 수정 / ㉢ 예외 등록부, 모든 예외에 만료일과 재평가 / ㉣ 보안 연락처 공개, 접수 확인 기한, 보복 금지 정책
    2. ㉠ 스캐너 교체 / ㉡ 스캔 주기 단축 / ㉢ 예외를 정책으로 흡수 / ㉣ 연구자에게 법적 경고
    3. ㉠ 모두 시스템 소유자가 판별 / ㉡ 그대로 / ㉢ 만료일 일괄 10년 / ㉣ 블로그 글 삭제 요청만
    4. ㉠ 긴급 표시만 보고 / ㉡ 해당 서버 폐기 / ㉢ 예외 전면 금지 / ㉣ 완전 공개 정책 채택
    정답과 해설 보기

    정답 A. ㉠ 1절(검증 없는 보고는 신뢰를 잃는다), ㉡ 1절(반복은 근본 원인 미해결), ㉢ 4절(기한 없는 예외는 정책 변경), ㉣ 5절(무응답이 완전 공개를 부른다, 보복은 보고를 없앤다). D의 “예외 전면 금지”는 현실에서 비공식 우회를 늘리기 쉽습니다.

    7핵심 개념을 내 말로 설명하기

    복습

    보고서에 수정 완료라고 쓸 수 있는 근거는 무엇인가요?

    설명 확인하기

    변경 기록은 어떤 조치를 했는지 보여 주고, 재검증 결과는 처음 문제가 된 조건에서 통제가 이제 동작하는지 보여 줍니다. 보완 통제로 처리했다면 남은 위험과 승인 기한도 남깁니다.

    8핵심 요약

    1. 보고서의 성공 기준 = 조치가 일어났는가.
    2. 분석: 검증 → 중복 제거 → 근본 원인 → 위험 평가 → 우선순위 → 보고 → 교정·예외 → 재검증.
    3. 거짓 양성 = 신뢰 상실, 거짓 음성 = 노출 지속(더 위험), 보고서에 안 보여서 커버리지·교차 검증으로 찾는다.
    4. 200건 = 근본 원인 1건. 근본 원인을 안 고치면 다음 테스트에 다시 나온다.
    5. 위험 평가: 악용 가능성, 노출, 자산 중요도, 보완 통제, 연쇄(공격 경로). 우선순위는 위험 감소 효율 순.
    6. 보고서: 경영진(결정) / 관리자(책임·자원) / 기술(재현·수정). 발견 항목 = 영향·증거·범위·근거·구체적 권고. 보고서 = 공격 지침서. 재검증 후 종결.
    7. 교정: 완화·회피·이전·수락. 식별 가능한 책임자, 기한, POA&M. 즉시 수정 불가 → 보완 통제 + 예외.
    8. 예외: 범위, 사유, 위험, 보완 통제, 권한 있는 승인자, 만료일, 재검토. 기한 없는 예외 = 정책 변경. 예외 등록부.
    9. 공개: 조정 공개(CVD)가 표준, 통상 90일, 악용 중이면 단축. 무단 테스트·데이터 열람·대가 요구(강요) 금지.
    10. 조직: 보안 연락처(security.txt), 접수 확인, ISO/IEC 30111·29147, 보복 금지.
    원문 위치: D6.4.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다. 용어는 제작기준에 따라 “보상 통제”를 “보완 통제”로 통일했습니다.

    9주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    False Positive / False Negative · 거짓 양성 / 거짓 음성

    없는 결함을 보고하는 것과 있는 결함을 놓치는 것. 후자가 더 위험하다.

    Root Cause Analysis · 근본 원인 분석

    증상이 아니라 결함을 만든 원인을 찾는 분석.

    Attack Path · 공격 경로

    개별 심각도는 낮으나 조합하면 치명적 결과에 이르는 연쇄.

    Executive Summary · 경영 요약

    기술 용어 없이 위험과 필요한 결정을 제시하는 보고서 앞단.

    Compensating Control · 보완 통제

    요구된 통제를 적용할 수 없을 때 위험을 줄이는 대체 수단.

    POA&M (Plan of Action and Milestones) · 조치 계획과 주요 일정

    결함, 조치 계획, 책임자, 자원, 마일스톤, 완료 예정일을 담은 문서.

    Retest · 재검증

    조치 완료 주장을 실제로 확인하는 활동. 종결 전 필수다.

    Exception · 예외

    요구사항을 충족할 수 없을 때 승인 하에 일시적으로 허용하는 상태.

    Exception Register · 예외 등록부

    조직의 모든 예외와 그 범위, 승인자, 만료일을 모아 관리하는 목록.

    Risk Acceptance · 위험 수용

    위험을 인지하고 받아들이는 처리 방식. 권한 있는 승인자가 기록으로 남긴다.

    CVD (Coordinated Vulnerability Disclosure) · 조정 취약점 공개

    개발사에 먼저 비공개 보고하고 수정 후 공개하는 조정 공개 모델.

    Full Disclosure · 완전 공개

    수정 여부와 무관하게 즉시 전면 공개하는 모델.

    Safe Harbor · 세이프 하버

    정의된 규칙 안에서 수행한 연구에 법적 조치를 하지 않겠다는 명시.

    security.txt · 보안 신고 연락처를 게시하는 표준 파일

    보안 취약점 보고 연락처를 표준 위치에 공개하는 파일.

    연습문제 5개

    문항을 선택하면 본문의 지문과 해설로 이동합니다.

    1. 보안 테스트에서 거짓 음성이 일반적으로 거짓 양성보다 더 위험한 이유는?
    2. 테스트 결과에서 같은 설정 오류가 분기마다 새 서버에서 반복된다. 시정은 매번 각 건을 닫는다. 무엇이 빠져 있는가?
    3. 보안 예외에 만료일이 있어야 하는 이유는?
    4. 어떤 연구자가 노출된 데이터베이스를 발견하고 문제를 입증한다는 이유로 고객 기록 5만 건을 내려받은 뒤 상세 내용 제공 전에 회사에 대가를 요구했다. 올바른 설명은?
    5. 취약점 관리 점검 결과다. ㉠ 스캐너 결과를 검증 없이 전달해 거짓 양성이 다수 섞였다. ㉡ 같은 설정 오류가 분기마다 새 서버에서 반복되고 매번 개별 건만 닫힌다. ㉢ 예외 47건 중 29건에 만료일이 없다. ㉣ 외부 연구자의 보고가 고객 지원 채널에서 두 달간 방치되었다. 가장 적절한 대책 묶음은?
