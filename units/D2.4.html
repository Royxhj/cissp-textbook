    연습문제 6개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    데이터는 만들어지고, 저장되고, 쓰이고, 공유되고, 보관되다가 사라집니다. 이 단원은 그 일생의 각 단계에서 누가 무엇을 책임지는지, 그리고 가장 자주 소홀해지는 마지막 단계, 즉 정말로 지우는 방법을 다룹니다.

    이 단원의 위치

    단원어떻게 이어지는가
    D1.3 보안 거버넌스 · D2.3 안전한 프로비저닝소유자·관리자·시스템 소유자. 이 단원은 공식 개요가 명시한 데이터 역할 5종으로 넓힌다 (1절)
    D1.4 법률·규제·컴플라이언스Controller·Processor·정보주체, 최소 수집, 국경 간 이전의 법적 근거 (1~3절)
    D1.5 조사 유형 · D7.1 조사소송이 예상되면 삭제를 멈추는 보존 의무(Legal Hold) (5절)
    D2.2 자산 취급 요구사항매체 재사용 전 데이터 삭제를 요구했다. 그 방법이 이 단원이다 (7~9절)
    D2.5 자산 보존 (EOL·EOS)자산 보존(EOL/EOS)과 데이터 보존의 차이, 오래 보관할 데이터의 기술적 과제 (5절)
    D7.5 자원 보호운영 단계의 매체 관리와 정화 수행 (8절)
    D3.6 암호 솔루션암호 소거가 기대는 키 수명주기 관리 (7절)

    1데이터 역할 5종

    왜 필요한가

    데이터에 문제가 생기면 “누가 결정했고 누가 실행했는가”를 따지게 됩니다. 공식 개요 2.4는 데이터 역할 다섯 가지를 명시합니다.

    역할하는 일
    Owner 소유자분류 결정, 접근 승인, 보존 결정
    Controller 컨트롤러처리의 목적과 수단을 결정
    Custodian 데이터 관리자소유자 지시에 따른 일상 보호 수행
    Processor 프로세서컨트롤러의 지시에 따라 처리
    User / Subject 사용자 / 정보주체데이터를 이용하는 사람 / 그 데이터가 가리키는 본인

    헷갈리는 두 쌍

    쌍어디서 쓰는 구분인가기준
    Owner / Custodian조직 내부의 책임 구분결정 / 수행
    Controller / Processor개인정보 보호법의 구분목적·수단 결정 / 지시에 따른 처리

    원본은 클라우드 제공자는 통상 Processor이고 고객 조직이 Controller라고 정리합니다. 정보주체(Data Subject)는 그 개인정보가 가리키는 본인이며, GDPR의 접근권·삭제권 같은 권리를 행사하는 주체입니다.

    용어 주의원본 D2.4는 Controller를 ‘관리자’, Custodian을 ‘보관자’로 옮기지만, 이 교재는 다른 단원과 맞추어 Custodian = 데이터 관리자, Controller / Processor = 컨트롤러 / 프로세서로 씁니다. 한국 개인정보 보호법의 ‘개인정보처리자’, ‘수탁자’와 일대일로 같은 개념인지는 이 교재에서 확인하지 않았습니다.

    보충두 쌍은 서로 다른 질문에 답하므로 한 조직이 동시에 두 쌍의 역할을 가집니다. 병원이 환자 기록을 외부 클라우드에 보관한다면, 병원은 개인정보 관점에서 Controller이고 클라우드 사업자는 Processor입니다. 병원 안에서는 진료 기록의 업무 책임자가 Owner, 병원 IT팀이 Custodian입니다. “통상 Processor”라는 말에도 조건이 붙습니다. 처리자가 고객 데이터를 자기 목적(예: 자체 제품 개선)으로 쓰기 시작하면 그 처리에 대해서는 스스로 목적을 정하는 쪽이 되므로, 계약과 적용 법을 다시 봐야 합니다.

    연결Owner·Custodian은 D1.3 보안 거버넌스과 D2.1 자산 식별과 분류에서, System Owner는 D2.3 안전한 프로비저닝에서 나왔습니다. Controller·Processor·정보주체와 GDPR의 권리는 D1.4 법률·규제·컴플라이언스에서 다뤘습니다. 처리자를 선정하고 감독하는 일은 D1.11 공급망 위험 관리의 공급자 관리와 같은 일입니다.

    원문 위치: D2.4.md §3 데이터 역할, §4 Data Controller / Data Processor·Data Subject, §5 첫 표 · 공식 개요 2.4 “Data roles (i.e., owners, controllers, custodians, processors, users/subjects)” · 기존 문제 주제(역할 구분)

    2수집

    왜 필요한가

    원본의 출발점은 이것입니다. 보유하지 않는 데이터는 유출될 수 없다. 그래서 생애주기의 첫 단계인 수집에서 통제를 시작합니다. 원본은 이를 데이터 최소화 원칙으로 요약합니다. 필요한 것만 모으고, 필요한 기간만 갖고, 끝나면 확실히 없앤다.

    수집 단계의 네 원칙

    • 최소 수집(Data Minimization) — 목적 달성에 필요한 최소한만 모은다. “나중에 쓸지도 모르니 일단 모은다”가 가장 흔하고 위험한 관행이다.
    • 목적 제한(Purpose Limitation) — 수집할 때 밝힌 목적 외로 쓰지 않는다. 다른 목적으로 쓰려면 새로운 적법 근거가 필요하다.
    • 동의와 적법 근거 — 동의는 여러 근거 중 하나다. 동의를 받는다면 자유롭고 구체적이며 명확한 의사표시여야 한다.
    • 수집 시점의 분류 — 수집하는 순간 분류가 정해져야 이후 통제가 적용된다. 나중에 분류하려 하면 이미 부적절한 곳에 저장되어 있다.

    가상 예시장비 사용 기록을 회사로 보내는 기능을 설계한다고 합시다. 고장 분석에 필요한 것은 오류 코드, 부품 상태, 소프트웨어 버전, 발생 시각입니다. 화면에 표시되던 검사 대상자 이름과 번호를 “혹시 필요할지 몰라서” 함께 보내면, 회사는 개인정보를 수집하는 Controller(또는 병원의 Processor)가 되고 보존 기간, 접근 통제, 국외 이전 검토, 삭제 요청 대응이 모두 따라옵니다. 처음부터 보내지 않으면 이 모든 의무가 생기지 않습니다.

    연결적법 근거의 종류와 동의의 조건은 D1.4 법률·규제·컴플라이언스, 수집 시점의 분류 기준은 D2.1 자산 식별과 분류에서 다룹니다. 설계 단계부터 수집 범위를 줄이는 것은 D3.1 안전한 설계 원칙의 설계 단계 프라이버시(Privacy by Design)입니다.

    원본 연습문제 · D2.4-Q13

    어떤 서비스가 사용자가 특정 국가의 성인인지만 확인해야 하는데 양식이 생년월일과 주민등록번호, 전체 주소를 수집한다. 적용되는 원칙은?

    1. 데이터 최소화. 명시된 목적이 요구하는 것만 수집해야 하므로 성인 여부 표시와 국가만으로 충분하다. 침해 영향과 준수 부담이 모두 줄어든다.
    2. 데이터가 많으면 서비스 품질이 개선되므로 데이터 가용성.
    3. 항목이 많으면 교차 확인이 가능하므로 데이터 무결성.
    4. 항목을 나중에 삭제할 수 있으므로 데이터 보존.
    정답과 해설 보기

    정답 A. 수집하지 않은 데이터는 유출될 수 없고 보호할 비용도 들지 않는다. 목적이 성인 여부 확인이면 생년월일 전체가 아니라 성인 여부라는 판정 결과만 보관하면 된다. "나중에 쓸 수도 있으니" 수집하는 관행이 침해 시 피해 범위와 규제 노출을 키우는 가장 흔한 원인이다.

    • B · 가용성은 다른 보안 속성이다.
    • C · 무결성과 무관한 쟁점이다.
    • D · 보존은 수집 이후 단계의 문제다.

    3소재지: 데이터는 어디에 있는가

    데이터가 어디에 있는지 모르면 보호할 수 없습니다. 원본이 추적하라고 하는 위치는 다섯 종류입니다.

    위치예
    1차 저장소운영 데이터베이스, 파일 서버
    복제본백업, 재해복구 사이트, 읽기 전용 복제본
    파생본분석용 추출, 개발·테스트 환경 복사본, 보고서
    최종 사용자 사본로컬 다운로드, 이메일 첨부, 개인 저장소
    클라우드·SaaS제공자가 어느 리전에 저장하는지

    개발·테스트 환경이 흔한 공백입니다. 운영 데이터를 그대로 복사해 쓰면서 통제는 느슨한 경우가 많습니다. 원본의 해법은 마스킹 또는 합성 데이터입니다.

    원문 사례 — 개발 환경의 운영 데이터. 개발팀이 디버깅을 위해 운영 데이터베이스를 그대로 복사해 썼습니다. 개발 환경은 인터넷에 노출되어 있었고 접근 통제가 약했습니다. 원본은 이것을 데이터 소재지 관리의 실패로 봅니다.

    원문 사례 — 삭제했는데 남아 있던 데이터. 고객의 삭제 요청에 따라 운영 데이터베이스에서 레코드를 지웠는데, 6개월 뒤 백업에서 복원하자 그 고객 데이터가 되살아났습니다. 삭제는 모든 사본에 적용되어야 하고, 백업·재해복구 사이트·분석 환경·로그까지 포함한 데이터 맵이 없으면 완전한 삭제가 불가능합니다. 백업에서 즉시 지우기 어렵다면 보존 주기가 지나면 자동으로 사라지게 하고, 복원할 때 다시 지우는 절차를 정해 둡니다.

    데이터 소재지(Data Residency)는 법적 쟁점이기도 합니다. 국경 간 이전 규제와 현지화 요구가 아키텍처를 제약합니다.

    판단 순서“이 데이터를 지웠다”고 말하기 전에 ① 데이터 맵에서 그 데이터가 있는 모든 위치를 꺼내고(1차·복제·파생·사용자 사본·클라우드) ② 위치마다 지웠는지, 지울 수 없다면 언제 자동으로 사라지는지를 확인하고 ③ 백업처럼 남아 있는 곳은 복원 시 재삭제 절차가 있는지 봅니다. 셋 중 하나라도 답이 없으면 “지웠다”가 아니라 “운영본에서 지웠다”입니다.

    연결국경 간 이전과 현지화는 D1.4 법률·규제·컴플라이언스, 사본도 원본과 같은 등급의 통제를 받는다는 원칙은 D2.2 자산 취급 요구사항, 백업 설계는 D7.10 복구 전략에서 다룹니다. 마스킹·토큰화 같은 기법은 D2.6 데이터 보안 통제의 데이터 보호 통제입니다.

    원본 연습문제 · D2.4-Q07

    고객의 삭제 요청에 따라 운영 데이터베이스에서 레코드를 삭제했다. 6개월 뒤 백업 복원으로 해당 데이터가 되살아났다. 가장 누락되었을 가능성이 높은 것은?

    1. 운영 데이터베이스의 더 긴 보존 기간.
    2. 데이터베이스 관리자에 대한 다중요소 인증.
    3. 백업, 복제본, 파생 사본을 포괄하는 문서화된 데이터 맵.
    4. 운영 데이터베이스를 위한 더 강력한 암호화 알고리즘.
    정답과 해설 보기

    정답 C. 삭제는 모든 사본에 적용되어야 한다. 백업, 재해복구 사이트, 분석 환경, 로그까지 포함한 데이터 맵이 없으면 완전한 삭제가 불가능하다. 백업 즉시 삭제가 어려우면 보존 주기 경과 후 자동 소멸과 복원 시 재삭제 절차를 정의한다.

    • A · 보존 기간 연장은 삭제 요청과 상충한다.
    • B · MFA 는 접근 통제이며 삭제 범위를 넓히지 않는다.
    • D · 암호화 강도는 사본 추적 문제와 무관하다.

    4유지

    저장된 데이터는 시간이 지나면서 틀려지고, 낡고, 늘어납니다. 원본이 드는 유지 활동입니다.

    • 정확성 — 틀린 데이터는 잘못된 의사결정을 만든다. 무결성(변경되지 않았음)과 정확성(사실과 맞음)은 다르다.
    • 최신성 — 오래된 접근 권한, 퇴사자 정보
    • 접근 권한 주기 검토 — 권한 누적 방지
    • 중복 제거 — 사본이 늘수록 공격면이 늘어난다
    • 정정 요청 처리 — 정보주체의 정정권 대응

    보충정확성을 유지하는 일에는 동기화 확인도 들어갑니다. 고객 주소를 원본 시스템에서 고쳤다고 해서 그 주소를 받아 쓰는 다른 시스템, 백업, 외부 처리자의 사본까지 바뀐 것은 아닙니다. 정정 요청을 처리했다면 그 값을 쓰는 곳들이 언제 갱신되는지까지 확인해야 정정이 끝난 것입니다.

    연결무결성과 정확성의 차이는 D1.2 보안 개념 (CIA 등)에서 자세히 다뤘습니다(무결성 통제는 권한 없는 변경을 잡고, 사실과 맞는지는 입력 검증과 업무 통제의 영역). 권한 누적은 D1.8 인적 보안, 접근 권한 주기 검토는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D2.4.md §3 유지 · 공식 개요 2.4 “Data maintenance”

    5보존

    왜 필요한가

    원본의 핵심 문장은 보존 기간은 길수록 안전한 것이 아니다입니다. 많은 조직이 “혹시 모르니 다 남겨 두자”를 안전한 선택으로 여기지만, 남겨 둔 데이터는 모두 보호해야 할 대상이고, 유출되면 피해가 됩니다.

    보존 기간을 정하는 요소

    • 법정 보존 의무 — 세법, 회계, 산업 규제
    • 계약상 요구
    • 업무상 필요
    • 개인정보 보호 요구 — 목적 달성 후 지체 없이 파기
    • 소송 대비 — 단, 소송이 예상되면 보존 의무(Legal Hold)로 삭제를 멈춘다

    과잉 보존의 위험

    • 유출 시 피해 범위가 커진다
    • 개인정보 보호 규제 위반이 될 수 있다. 목적 달성 후 보유 자체가 위반
    • 소송 시 전자증거 개시(eDiscovery) 비용이 커진다
    • 저장·관리 비용

    보존 기간이 서로 다를 때는 가장 긴 법정 의무를 따르되, 그 의무가 적용되지 않는 데이터는 분리해 더 짧게 보존합니다. 그리고 원본은 자동 삭제가 핵심이라고 강조합니다. 수동 삭제에 의존하면 지켜지지 않으므로 보존 정책을 시스템 수준에서 강제합니다.

    원문 사례 — 과잉 보존이 키운 피해. 침해 사고로 유출된 데이터에 10년 전 탈퇴한 회원 정보가 들어 있었습니다. 법정 보존 의무는 5년이었습니다. 보유할 이유가 없는 데이터를 보유한 것 자체가 규제 위반이었고, 피해 규모와 과징금을 키웠습니다.

    보충“가장 긴 법정 의무를 따르되 분리한다”는 말을 풀면 이렇습니다. 같은 고객 데이터라도 거래 기록은 세법상 오래 보존해야 하고, 마케팅 수신 동의 정보는 목적이 끝나면 지워야 할 수 있습니다. 둘을 한 테이블에 섞어 두면 긴 쪽에 맞춰 전부 남기게 되고, 짧은 쪽은 과잉 보존이 됩니다. 보존 기간이 다른 데이터를 따로 저장하는 것은 D2.1 자산 식별과 분류에서 본 “민감 데이터를 분리하면 비용이 준다”와 같은 설계 원리입니다.

    연결자산 보존(EOL/EOS)과 데이터 보존의 차이, 오래 보관해야 하는 데이터의 매체 수명과 포맷 노후화는 D2.5 자산 보존 (EOL·EOS), 보존 의무(Legal Hold)는 D1.5 조사 유형와 D7.1 조사에서 다룹니다. 두 의무는 방향이 반대입니다. 보존 기간은 “기간이 지나면 지운다”, 보존 의무는 “지우지 마라”이고, 보존 의무가 걸리면 자동 삭제를 그 범위에서 멈춰야 합니다. 개인정보 파기 의무와 과징금은 D1.4 법률·규제·컴플라이언스에서 다뤘습니다.

    이해 확인 · 자작 상황 문제 (실제 시험 문제 아님)

    회사의 고객 데이터베이스 보존 정책은 “탈퇴 후 5년 보관 후 삭제”이고, 담당자가 매년 말 수작업으로 지운다. 감사에서 7년 전 탈퇴자 데이터가 대량으로 발견되었다. 담당자는 바뀐 지 2년 되었다. 가장 적절한 개선은?

    1. 보존 기간을 10년으로 늘려 규정 위반을 없앤다.
    2. 새 담당자에게 매년 삭제를 잊지 말라고 교육한다.
    3. 보존 기간이 지난 레코드가 시스템에서 자동으로 삭제되게 하고, 소송 보존 대상은 예외로 묶는 기능을 둔다.
    4. 오래된 데이터를 암호화해서 그대로 둔다.
    정답과 해설 보기

    정답 C. 담당자가 바뀌자 수작업 삭제가 끊긴 전형입니다. 원본이 말하는 대로 보존 정책은 시스템 수준에서 자동으로 강제해야 하고, 보존 의무가 걸린 데이터는 그 자동 삭제에서 빼는 장치가 함께 있어야 합니다.

    • A: 보유 근거 없이 기간만 늘리면 과잉 보존이 정책이 됩니다.
    • B: 사람의 기억에 기대는 방식이 이미 실패했습니다.
    • D: 암호화는 유출 시 피해를 줄일 수 있지만, 보유할 이유가 없는 데이터를 갖고 있는 문제는 남습니다.
    문제 목록으로 돌아가기

    6잔류: 지웠는데 왜 남는가

    쉬운 설명

    데이터 잔류(Data Remanence)는 삭제 처리 후에도 매체에 데이터가 남아 복구할 수 있는 상태입니다. 원본이 드는 원인입니다.

    원인설명
    논리적 삭제파일 삭제는 포인터만 제거하고 데이터 블록은 남는다
    포맷빠른 포맷은 파일 시스템 구조만 초기화한다
    슬랙 공간 Slack Space할당 단위 안의 미사용 영역에 이전 데이터가 남는다
    저널·스냅샷파일 시스템 저널, 섀도 복사본
    SSD 웨어 레벨링 Wear Leveling컨트롤러가 수명을 고르게 하려고 물리 블록을 재배치해, 덮어쓰기가 원래 블록에 닿지 않을 수 있다
    오버프로비저닝SSD의 예비 영역에 데이터가 남는다
    백업·복제본원본을 지워도 사본이 남는다

    보충책의 목차에서 한 장을 지워도 그 장의 종이는 책 안에 그대로 있는 것과 같습니다. 파일 삭제는 목차(파일 시스템의 포인터)를 지우는 일입니다. HDD에서는 같은 자리에 새 데이터를 덮어쓰면 이전 내용이 사라지지만, SSD는 컨트롤러가 “덮어쓰기” 요청을 다른 빈 블록에 기록하고 이전 블록은 나중에 정리합니다. 그래서 운영체제에서 덮어써도 원래 블록이 남을 수 있고, 운영체제가 접근할 수 없는 예비 영역도 있습니다. 원본이 SSD에서는 전통적인 덮어쓰기를 신뢰할 수 없다고 하는 이유입니다.

    연결잔류는 공격자에게는 복구 기회, 조사자에게는 증거입니다. 삭제된 파일과 슬랙 공간에서 증거를 복구하는 디지털 포렌식은 D7.1 조사에서 다룹니다. 백업·복제본에 남는 문제는 3절의 데이터 맵과 같은 이야기입니다.

    원본 연습문제 · D2.4-Q19

    데이터 잔존(data remanence)이란?

    1. 법적 의무를 충족하기 위해 의도적으로 보존된 데이터.
    2. 보존 기간을 초과한 데이터.
    3. 가용성을 위해 여러 시스템에 복제된 데이터.
    4. 제거를 시도한 뒤에도 매체에 남는 데이터의 잔여 표현. 그래서 삭제는 정화와 같지 않다.
    정답과 해설 보기

    정답 D. 파일을 삭제하면 운영체제가 참조만 지우고 내용은 디스크에 남는다. 복구 도구로 상당 부분 되살릴 수 있다. 이 때문에 매체를 재사용하거나 폐기할 때 삭제가 아니라 소거·정화·파괴 중 적절한 방법을 적용해야 한다. SSD 는 마모 평준화 때문에 덮어쓰기가 보장되지 않아 암호 소거나 파괴가 선호된다.

    • A · 의도적 보존은 보존 정책의 영역이다.
    • B · 기간 초과는 폐기 대상 상태다.
    • C · 복제는 가용성 설계다.

    7파기: Clear, Purge, Destroy

    쉬운 설명

    매체 정화(Sanitization)는 NIST SP 800-88의 세 방법으로 구분합니다. 원본은 이 셋을 반드시 구분해야 한다고 강조합니다.

    방법무엇을 막는가매체 재사용원본이 드는 기법
    Clear일반적인 복구 시도(표준 인터페이스로 읽기)같은 환경에서 재사용 가능논리적 덮어쓰기, 공장 초기화
    Purge실험실 수준의 복구까지재사용 가능디가우징, 암호 소거, 펌웨어 보안 삭제(Secure Erase) 명령
    Destroy물리적으로 복구 불가능재사용 불가분쇄, 소각, 분말화, 용융, 파쇄

    암호 소거

    암호 소거(Cryptographic Erase, Crypto-shredding)는 암호화된 데이터의 키를 파기해 복호화를 불가능하게 만드는 방식입니다. 원본은 클라우드에서 특히 유용하다고 합니다. 물리 매체에 접근할 수 없어도 키만 파기하면 되기 때문입니다. 전제는 처음부터 암호화되어 있어야 한다는 것입니다.

    원문 사례 — 암호 소거가 유일한 수단이었던 경우. 클라우드 제공자의 물리 매체에 접근할 수 없어 전통적 파기를 할 수 없었습니다. 저장 시점부터 고객 관리 키로 암호화해 두었기 때문에, 계약 종료 시 키를 파기하는 것으로 복구 불가능한 상태를 만들 수 있었습니다. 원본의 결론은 암호 소거는 사전 암호화가 전제이며 나중에 결정할 수 없다입니다.

    보충암호 소거가 실제로 효과가 있는지는 키가 정말 사라졌는지에 달려 있습니다. 키 백업, 키 관리 서비스의 복구 기능, 다른 곳에 남은 평문 사본이 있으면 키 하나를 지워도 데이터는 살아 있습니다. 그래서 암호 소거를 계획할 때는 그 키의 모든 사본과 평문 사본의 유무를 확인하고, 실행 후 결과를 검증해야 합니다(키와 사본의 위치를 확인하라는 일반적 원칙에 따른 보충).

    확인 필요NIST SP 800-88은 개정되었습니다. 원본은 Rev. 1(2014)을 기준으로 쓰였습니다. NIST는 2025년 9월 26일 Rev. 2를 최종 발행했고 Rev. 1을 대체했습니다(NIST CSRC 문서 이력). NIST 초안 공지는 이번 개정이 조직 차원의 매체 정화 프로그램 수립에 초점을 옮겼다고 밝힙니다. 업계 해설들은 Clear·Purge·Destroy 세 방법은 유지되었고, 매체별 구체 기법은 IEEE 2883 같은 외부 표준을 참조하도록 바뀌었으며, 디가우징의 위상이 낮아졌다고 전합니다. 이 세부 사항은 NIST 원문이 아니라 2차 자료로 확인한 것입니다. 시험 개요(2024판)와 기존 수험서가 Rev. 1의 틀로 설명할 수 있으므로, 이 교재는 원본의 세 방법 구분을 그대로 두고 개정 사실만 알립니다.

    연결키를 어디에 두고 어떻게 폐기하는지는 D3.6 암호 솔루션의 키 수명주기 관리, 고객 관리 키와 클라우드 종료 전략은 D8.4 도입 소프트웨어 평가에서 다룹니다. Rev. 2 개정 사실은 운영 단계의 매체 관리를 다루는 D7.5 자원 보호에서도 이 절로 연결합니다.

    원문 위치: D2.4.md §3 파기 — NIST SP 800-88, §4 Clear / Purge / Destroy·Cryptographic Erase, §5 둘째 표, §6 NIST SP 800-88 Rev.1, §7 사례 5 · 공식 개요 2.4 “Data destruction” · 외부 확인: NIST CSRC SP 800-88 Rev. 2 페이지(발행일·대체 관계), 업계 해설(IEEE 2883 참조, 디가우징)

    8매체별 적합 방법

    같은 “파기”라도 매체에 따라 효과가 다릅니다.

    매체적합부적합
    자기 디스크(HDD)덮어쓰기, 디가우징, 물리 파괴—
    SSD·플래시암호 소거, 물리 파괴디가우징(효과 없음)
    광 매체(CD/DVD)물리 파쇄덮어쓰기 불가
    종이교차 절단 파쇄, 소각—

    디가우징은 SSD에 효과가 없습니다. 디가우징은 강한 자기장으로 자기 기록을 지우는 방식인데, SSD는 자기 저장이 아니라 플래시 메모리에 전하로 기록하기 때문입니다. SSD에는 암호 소거나 물리 파괴를 씁니다.

    또 디가우징한 자기 디스크는 대부분 재사용할 수 없습니다. 디스크가 헤드 위치를 잡는 데 쓰는 서보 트랙까지 지워지기 때문입니다. 원본은 이 점에서 디가우징이 실질적으로 폐기에 가깝다고 설명합니다.

    원문 사례 — 디가우징한 SSD. 폐기 절차에 따라 모든 저장 매체를 디가우저에 통과시켰는데, 샘플 검증에서 SSD의 데이터가 그대로 복구되었습니다. 조직은 절차를 매체 유형별로 나누고 SSD는 암호 소거 또는 물리 파괴로 바꿨습니다.

    보충이 사례에서 문제를 찾아낸 것은 샘플 검증입니다. 절차를 수행했다는 기록만 있었다면 아무도 몰랐을 것입니다. 정화는 수행과 검증이 짝입니다. 그리고 장비 안에 저장 매체가 있다는 사실 자체를 놓치기 쉽습니다. 프린터·복합기, 네트워크 장비, 의료 장비, 산업용 컨트롤러에도 저장 장치가 들어 있으므로 폐기 목록은 “PC와 서버”가 아니라 “저장 매체를 가진 모든 장비”여야 합니다.

    CISSP 관점매체 정화 상황에서는 ① 매체 종류(자기, 플래시, 광, 종이)를 먼저 확인하고 ② 그 매체에 효과가 있는 방법인지 보고(SSD에 디가우징은 무효) ③ 매체를 재사용할지, 조직 밖으로 나가는지 ④ 데이터 등급을 따져 Clear / Purge / Destroy 중 고릅니다. 원본은 디가우징과 SSD의 조합을 가장 흔한 함정으로 꼽습니다.

    원본 연습문제 · D2.4-Q01

    조직이 폐기 대상 저장 매체를 모두 디가우저에 통과시켰다. 이후 샘플 검증에서 SSD 로부터 읽을 수 있는 데이터가 복구되었다. 이 결과의 원인은?

    1. 디가우징은 자기 매체에만 작용하며 플래시 메모리에는 효과가 없다.
    2. 드라이브가 암호화되어 있어 디가우징이 작동하지 않았다.
    3. 디가우징은 처리 중 드라이브에 전원이 공급되어야 한다.
    4. 디가우저의 자기장 세기가 부족하게 설정되었다.
    정답과 해설 보기

    정답 A. 디가우징은 자기 저장 방식의 매체에만 작용한다. SSD 는 플래시 메모리라 자기장의 영향을 받지 않아 데이터가 그대로 남는다. SSD 에는 암호 소거(cryptographic erase) 또는 물리 파괴를 사용해야 한다.

    • B · 암호화는 디가우징 효과와 무관하며 오히려 암호 소거의 전제가 된다.
    • C · 디가우징은 전원 공급과 무관하게 수행된다.
    • D · 세기 문제가 아니라 저장 원리가 다르다.

    조직 통제를 벗어나는가

    매체가 조직 통제를 벗어난다면 더 강한 방법을 씁니다. 내부 재사용이면 Purge, 외부 반출·폐기면 Destroy를 고려합니다.

    파기 증명서(Certificate of Destruction)는 무엇을, 언제, 어떤 방법으로 파기했는지 기록한 증빙이며 외부 업체에 맡길 때 특히 필요합니다. 원본은 위탁해도 책임은 조직에 남는다고 강조합니다.

    가상 예시현장에서 회수한 장비 30대를 처리해야 합니다. 그중 20대는 정비 후 다른 병원에 재설치하고, 10대는 폐기 업체로 보냅니다. 장비 안의 SSD에는 검사 기록이 남아 있을 수 있습니다. 재설치할 20대는 장비는 다시 쓰지만 매체가 조직 밖(다른 병원)으로 나가므로, 원본 기준으로는 Destroy를 고려할 상황입니다. 장비를 재사용하면서 이 기준을 맞추는 방법은 저장 장치만 새것으로 바꾸고 기존 SSD를 파괴하는 것입니다. 저장 장치를 그대로 쓰겠다면 Purge(장비가 저장 암호화를 쓰고 있었다면 암호 소거, 아니면 제조사의 보안 삭제 명령)와 샘플 복구 시험을 하되, 그 수준이 데이터 등급에 비해 충분한지 소유자가 판단하고 기록으로 남깁니다. 폐기할 10대는 업체가 물리 파괴하고, 장비 일련번호별 파기 증명서를 받습니다. 증명서를 받았다고 책임이 업체로 넘어가지 않으므로, 업체 선정과 현장 확인 기록도 남깁니다.

    연결업체를 고르고 계약에 파기 의무와 증명을 넣는 일은 D1.11 공급망 위험 관리(종료 시 데이터 반환·파기)에서 다뤘습니다. 정보시스템을 퇴역시킬 때의 절차는 D3.10 정보시스템 생애주기, 운영 중 매체 관리는 D7.5 자원 보호, 종이 문서의 세단은 D2.2 자산 취급 요구사항에 있습니다.

    원문 위치: D2.4.md §3 파기 선택 기준과 증빙, §4 Certificate of Destruction · 기존 문제 주제(파기 증명서, 위탁 책임)

    종합 · 자작 상황 문제

    한 회사가 클라우드 서비스를 해지하면서 다음 계획을 세웠다. ㉠ 서비스 업체에 물리 디스크를 디가우징해 달라고 요청한다. ㉡ 운영 데이터베이스의 개인정보는 지우지만 분석용으로 추출해 둔 사본은 “혹시 몰라서” 10년 보관한다. ㉢ 해지 후 남은 사내 노트북 SSD는 파일 삭제 후 재배포한다. 가장 적절한 평가는?

    1. 세 계획 모두 문제없다.
    2. ㉠ 고객이 물리 매체에 접근할 수 없는 클라우드에서는 사전 암호화와 키 파기가 현실적인 수단이다 / ㉡ 파생본도 삭제 대상이며 근거 없는 장기 보존은 과잉 보존이다 / ㉢ 파일 삭제는 포인터만 지우므로 SSD에는 암호 소거 등 Purge 수준이 필요하다
    3. ㉠ 디가우징이 SSD에도 가장 강한 방법이다 / ㉡ 사본은 원본과 별개라 관계없다 / ㉢ 빠른 포맷이면 충분하다
    4. ㉠ 업체가 Processor이므로 회사는 책임이 없다 / ㉡ 보존은 길수록 안전하다 / ㉢ 재배포 대신 반드시 소각해야 한다
    정답과 해설 보기

    정답 B.

    • ㉠ 원문 사례 5. 클라우드 업체의 디스크는 고객이 직접 처리할 수 없고 여러 고객이 공유할 수 있습니다. 게다가 매체가 SSD라면 디가우징은 효과가 없습니다(7·8절).
    • ㉡ 데이터 맵에 파생본이 포함되어야 하고(3절), 근거 없는 보존은 과잉 보존입니다(5절).
    • ㉢ 잔류의 원인(6절)과 SSD의 덮어쓰기 한계 때문에 파일 삭제로는 부족합니다. 재사용이 목적이므로 Destroy까지 갈 필요는 없지만 Purge 수준이 필요합니다.

    D가 틀린 이유: 처리를 맡겨도 Controller의 책임은 남고, 재사용할 매체를 반드시 소각할 이유는 없습니다.

    11핵심 개념을 내 말로 설명하기

    복습

    운영본을 삭제한 데이터가 복구 시험 뒤 되살아났다면 무엇을 놓친 것인가요?

    설명 확인하기

    운영본과 별개인 백업 사본의 보존과 복원 후 재삭제 규칙을 놓쳤을 수 있습니다. 사본의 위치·보존 사유·정화 방법과 결과를 하나의 생애주기로 관리합니다.

    12핵심 요약

    1. 데이터 역할 5종: Owner / Controller / Custodian / Processor / User·Subject.
    2. Owner = 결정, Custodian = 수행(조직 내부) / Controller = 목적·수단 결정, Processor = 지시에 따른 처리(개인정보 법). 클라우드 제공자는 통상 Processor.
    3. 보유하지 않는 데이터는 유출될 수 없다. 수집: 최소 수집 + 목적 제한 + 적법 근거 + 수집 시점 분류.
    4. 소재지: 1차 저장소 + 복제본 + 파생본 + 사용자 사본 + 클라우드. 개발·테스트 환경이 흔한 공백 → 마스킹·합성 데이터.
    5. 데이터 맵 없이는 완전한 삭제가 불가능. 백업은 자동 소멸 + 복원 시 재삭제.
    6. 유지: 정확성(무결성과 다름), 최신성, 권한 검토, 중복 제거, 정정 요청.
    7. 보존은 길수록 좋은 것이 아니다. 과잉 보존 = 규제 위반 + 피해 확대 + eDiscovery 비용. 자동 삭제로 강제, 소송 예상 시 보존 의무로 삭제 중단.
    8. 잔류: 논리 삭제는 포인터만 제거. 슬랙 공간, 저널·스냅샷, SSD 웨어 레벨링, 오버프로비저닝, 백업.
    9. Clear(일반 복구 방어) < Purge(실험실 복구 방어) < Destroy(물리 파괴, 재사용 불가).
    10. Purge 기법: 디가우징, 암호 소거, 펌웨어 보안 삭제. 암호 소거는 사전 암호화가 전제, 클라우드에서 특히 유용.
    11. 디가우징은 SSD에 무효. SSD는 암호 소거 또는 물리 파괴. 디가우징한 HDD는 대부분 재사용 불가.
    12. 방법 선택: 분류 등급 + 매체 유형 + 재사용 여부 + 조직 통제 이탈. 위탁 시 파기 증명서, 책임은 조직에 남는다.
    13. NIST SP 800-88은 2025년 9월 Rev. 2로 개정되었다(세 방법은 유지).
    원문 위치: D2.4.md §8 CISSP 시험 관점, §9 핵심 암기 요약(15항목). 원본의 “가장 자주 출제되는 함정” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다. 원본 §6의 ISO/IEC 27002:2022(정보 삭제, 매체 폐기, 데이터 마스킹), NIST SP 800-53 MP·SI 통제군, DoD 5220.22-M(과거 널리 인용된 덮어쓰기 기준, 지금은 SP 800-88이 기준)은 여기에 적어 둡니다.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Data Controller / Data Processor · 데이터 컨트롤러 / 데이터 프로세서

    Controller 는 처리의 목적과 수단을 결정하고, Processor 는 Controller 의 지시에 따라 처리한다. 클라우드 제공자는 통상 Processor 다.

    Data Subject · 정보주체

    개인정보가 가리키는 본인. 접근권·삭제권 등을 행사하는 주체다.

    Data Minimization · 데이터 최소화

    목적 달성에 필요한 최소한만 수집하는 원칙.

    Purpose Limitation · 목적 제한

    수집 시 밝힌 목적 외로 사용하지 않는 원칙.

    Data Residency · 데이터 소재지

    데이터가 물리적으로 저장되는 국가·지역. 법적 제약의 대상이 된다.

    Retention Period · 보존 기간

    데이터를 보유하는 기간. 법정 의무, 계약, 업무 필요, 개인정보 보호 요구를 함께 고려한다.

    Data Remanence · 데이터 잔류

    삭제 처리 후에도 매체에 데이터가 남아 복구 가능한 상태.

    Slack Space · 슬랙 공간

    할당 단위 내 미사용 영역. 이전 데이터가 잔존할 수 있다.

    Wear Leveling · 웨어 레벨링

    SSD 컨트롤러가 수명 균등화를 위해 물리 블록을 재배치하는 기능. 덮어쓰기가 원본 블록에 닿지 않을 수 있다.

    Clear / Purge / Destroy · 논리적 소거 / 정화 / 파괴

    NIST SP 800-88 의 정화 단계. 일반 복구 방어 / 실험실 복구 방어 / 물리 파괴.

    Degaussing · 디가우징

    강력한 자기장으로 자기 매체 데이터를 파괴하는 기법. SSD 에는 효과가 없다.

    Cryptographic Erase / Crypto-shredding · 암호 소거

    암호화된 데이터의 키를 파기해 복호화 불가능하게 만드는 방식. 사전 암호화가 전제다.

    Certificate of Destruction · 파기 증명서

    파기 대상·일시·방법을 기록한 증빙. 외부 위탁 시 필수다.
