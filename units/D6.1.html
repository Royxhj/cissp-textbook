    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    도메인 6은 “통제가 정말 작동하는가”를 확인하는 도메인입니다. 그 첫 단원은 개별 테스트 기법보다 한 단계 위, 즉 무엇을, 무엇에 비추어, 얼마나 자주, 어떤 방법으로, 누가 볼 것인가를 정하는 전략을 다룹니다. 자원은 유한하므로 모든 것을 같은 깊이로 매년 볼 수 없고, 그래서 위험 기반 전략이 필요합니다. 그리고 그 전략 자체가 맞는지도 검증해야 합니다.

    1테스트, 평가, 감사

    구분답하는 질문수행 주체
    테스트 Testing통제가 작동하는가주로 기술팀
    평가 Assessment통제가 위험을 줄이는 데 충분한가보안팀·평가자
    감사 Audit정의된 기준을 지켰는가를 독립적으로 확인독립 감사인
    • 테스트: 특정 통제가 의도대로 동작하는지 확인합니다. 취약점 스캔, 침투 테스트, 코드 검토.
    • 평가: 테스트 결과와 문서, 인터뷰를 종합해 통제가 위험을 적절히 줄이는지 판단합니다.
    • 감사: 표준·규제·계약 같은 정의된 기준에 대한 준수 여부를 독립적으로 확인하고 의견을 냅니다. 독립성이 핵심 요건입니다.

    보충자동차로 비유하면, 테스트는 “브레이크를 밟으면 서는가”, 평가는 “이 브레이크가 이 차의 무게와 속도에 충분한가”, 감사는 “이 차가 안전 기준을 충족한다는 것을 제3자가 확인해 서명하는가”입니다. ISO 27001 인증 심사가 감사이고, 그 준비 과정에서 자체로 통제를 돌려 보는 것이 테스트·평가에 가깝습니다. 세 활동은 서로의 입력이 됩니다. 테스트 결과는 평가의 근거가 되고, 평가와 테스트 기록은 감사의 증거가 됩니다.

    원본 연습문제 · D6.1-Q01

    보안 감사를 보안 평가와 구별하는 것은?

    1. 감사는 기술적 통제만, 평가는 관리적 통제만 다룬다.
    2. 감사는 사고 후에, 평가는 사고 전에 수행된다.
    3. 감사는 정의된 기준에 대한 준수 여부에 독립적인 의견을 제공한다.
    4. 감사는 항상 자동화 도구를 사용하고 평가는 면담에 의존한다.
    정답과 해설 보기

    정답 C. 감사는 표준, 규제, 계약 같은 정의된 기준에 대한 준수 여부를 독립적으로 확인하고 의견을 내는 활동이며 독립성이 핵심 요건이다. 평가는 통제가 위험을 적절히 줄이는지 판단하는 활동으로 기준 준수 의견 제시를 목적으로 하지 않는다.

    • A · 둘 다 기술적·관리적 통제를 모두 대상으로 할 수 있다.
    • B · 수행 시점은 구별 기준이 아니다.
    • D · 도구 사용 여부는 감사와 평가를 구별하는 기준이 아니다.

    2전략 설계의 구성요소

    구성요소정하는 것원본이 짚는 요점
    범위 Scope시스템, 데이터, 프로세스, 인력, 공급자, 물리 시설자산 인벤토리가 없으면 범위를 정할 수 없다. 실패 모드: 편한 대상만 보거나, 범위를 명시하지 않아 중요한 자산을 못 건드림
    기준 Criteria조직 정책, 표준(ISO 27001, NIST SP 800-53), 규제, 계약기준이 없으면 결과가 평가자의 주관이 됨
    주기 Frequency얼마나 자주위험 기반 차등(외부 노출 고위험은 자주). 규제가 최소 주기를 정하기도 함. 변경 기반 트리거: 주요 아키텍처 변경, 신규 도입, 사고 후 재검증
    방법 Method검토(Examine), 면담(Interview), 시험(Test)NIST SP 800-53A의 세 방법. 문서상 통제가 실제 동작을 보장하지 않으므로 조합. “정책이 있다”는 검토 결과, “실제로 적용된다”는 시험 결과
    독립성 Independence누가 보는가자기 업무를 자기가 검증하면 신뢰할 수 없다. 독립성은 정도의 문제
    보고 경로 Reporting line결과가 어디로 가는가조치 권한이 있는 곳까지 도달해야 함. 감사 기능은 통상 경영진이 아닌 이사회나 감사위원회에 보고

    판단 순서전략을 세우는 순서는 도구에서 시작하지 않습니다. ① 의무(규제·계약)와 위험을 식별하고 ② 범위와 목표를 정하고 ③ 기준을 고르고 ④ 통제 유형별로 맞는 방법을 고르고 ⑤ 필요한 독립성과 주기를 정하고 ⑥ 결과를 누가 받아 무엇을 결정하는지 정합니다. “스캐너부터 사고 나서 무엇을 스캔할지 정하기”는 도구가 볼 수 있는 것만 보게 만듭니다.

    보충결과의 수신자는 한 곳이 아닙니다. 위험을 수용할지 투자할지 결정하는 위험 책임자와, 실제로 고쳐야 하는 조치 팀이 각자 내릴 결정에 맞는 형태로 받아야 합니다. 경영진만 받으면 고쳐지지 않고, 기술팀만 받으면 수용·투자 판단이 빠집니다.

    연결자산 인벤토리는 D2.3 안전한 프로비저닝, 결과 분석과 보고는 D6.4 결과 분석과 보고, 감사 기능의 독립성과 보고 경로는 D6.5 보안 감사에서 다룹니다.

    원본 연습문제 · D6.1-Q16

    평가·테스트 전략을 수립하는 올바른 순서는?

    1. 테스트 도구를 선정하고 그 도구로 무엇을 테스트할지 정한다.
    2. 결과의 일관성을 위해 보고서 양식을 먼저 정의한다.
    3. 의무와 위험을 식별하고 범위와 목표를 정의한 뒤 통제 유형별로 적합한 방법을 고르고 빈도와 책임자를 정하고 경영진 승인을 받은 다음 수행하고 보고한다.
    4. 먼저 광범위 스캔을 수행하고 그 결과가 전략을 정의하게 한다.
    정답과 해설 보기

    정답 C. 도구가 전략을 정하면 도구가 볼 수 있는 것만 보게 된다. 의무와 위험에서 출발해 목표를 정하고 관리적 통제는 문서 검토와 인터뷰, 기술적 통제는 스캔과 시험처럼 통제 유형에 맞는 방법을 고른다. 경영진 승인은 자원 배분과 업무 영향에 대한 합의를 확보하는 단계다.

    • A · 도구 중심은 범위를 도구의 한계로 좁힌다.
    • B · 양식은 전략의 산출물이며 출발점이 아니다.
    • D · 결과 주도는 중요한 미탐지 영역을 놓친다.

    원본 연습문제 · D6.1-Q08

    내부 감사 기능의 독립성을 유지하기 위해 주된 보고 대상은 누구여야 하는가?

    1. 보안 통제를 소유하는 최고정보보호책임자.
    2. 감사를 받는 경영진이 아니라 이사회 또는 감사위원회.
    3. 발견 사항에 가장 빠르게 조치할 수 있는 IT 운영 책임자.
    4. 규제 기관 연락을 담당하는 법무 부서.
    정답과 해설 보기

    정답 B. 감사 기능이 피감 대상인 경영진에게 보고하면 불편한 결과를 보고하기 어려운 압력이 생겨 독립성이 훼손된다. 이사회나 감사위원회에 직접 보고하면 결과가 피감 대상의 영향을 받지 않고 조치 권한이 있는 곳까지 도달한다.

    • A · 보안 통제 소유자에게 보고하면 자기 영역을 평가받는 구조가 된다.
    • C · 조치 속도가 독립성을 대체하지 않는다.
    • D · 법무는 규제 대응 창구이며 감사 독립성 보장 구조가 아니다.

    보안 평가 결과를 받아야 하는 대상은?

    1. 직원을 불안하게 하지 않기 위해 경영진만.
    2. 시정을 수행할 기술 팀만.
    3. 그것을 요청한 외부 감사인만.
    4. 수용이나 투자를 결정하는 위험 책임자와 조치해야 하는 팀 양쪽. 각자 내릴 결정에 맞는 형태로 전달한다.
    정답과 해설 보기

    정답 D. 기술 팀만 받으면 투자와 위험 수용 결정이 이루어지지 않고 경영진만 받으면 실제 조치가 일어나지 않는다. 같은 발견 사항이라도 경영진에게는 업무 영향과 선택지가 필요하고 기술 팀에게는 재현 절차와 수정 방법이 필요하다. 보고 경로가 정의되지 않으면 결과가 어디에도 닿지 않는다.

    • A · 실제 조치가 일어나지 않는다.
    • B · 위험 수용 결정이 이루어지지 않는다.
    • C · 내부 대응이 누락된다.

    3내부, 외부, 제3자

    공식 개요는 세 구분을 통제 범위 기준으로 정의합니다.

    구분정의장점단점
    내부 Internal조직 통제 범위 안. 조직 인력이 자기 조직을 평가(내부 감사, 자체 스캔, 내부 레드팀)맥락 이해, 저비용, 자주 수행, 즉시 조치독립성 제한. 같은 가정과 사각지대 공유, 불편한 결과 보고 압력
    외부 External조직 통제 범위 밖. 조직이 고용한 외부 전문가(외부 감사인, 컨설팅 침투 테스트)독립성·전문성, 새 시각, 업계 비교비용, 맥락 이해 시간, 접근 권한 부여 자체가 위험. 조직이 비용을 내므로 완전한 독립은 아님
    제3자 Third-party기업 통제 범위 밖. 조직이 통제하지 않는 주체가 수행하거나, 조직이 의존하는 제3자를 대상으로 함공급자 직접 테스트가 불가능할 때의 증거범위·시기를 조직이 정하지 못함

    내부 평가의 독립성 보완책: 보고 경로 분리(감사위원회 직보), 평가자와 운영자 분리, 주기적 외부 검증.

    원문 사례 — 독립성이 훼손된 내부 평가. 내부 보안팀이 자신들이 설계·운영하는 방화벽 정책을 스스로 평가해 늘 “적정”이었지만, 외부 테스트에서 불필요하게 넓은 허용 규칙 다수가 발견되었습니다. 운영과 평가 담당을 분리하고, 외부 검증으로 교차 확인하고, 감사 보고 경로를 감사위원회로 분리했습니다.

    제3자의 세 형태와 SOC 2

    • 공급자 평가: 쓰는 서비스 공급자의 통제 확인. 직접 테스트가 안 되면 SOC 2 Type II 같은 제3자 감사 보고서에 의존.
    • 인증 기관 심사: ISO 27001 인증 심사처럼 인증 체계가 지정한 심사원이 수행.
    • 규제 기관 검사: 조직이 거부할 수 없고 범위도 정하지 못함.
    SOC 2다루는 것
    Type I특정 시점의 통제 설계
    Type II일정 기간(보통 6~12개월)의 운영 효과성 → 의존할 수 있는 증거

    제3자 보고서를 받을 때 확인할 것: 보고 기간, 범위(어떤 서비스가 포함되는가), 예외 사항(exception), 보완 사용자 통제(CUEC). CUEC는 공급자가 아니라 조직 자신이 해야 하는 일이라, 놓치면 통제 공백이 생깁니다.

    원문 사례 — SOC 2 보고서의 CUEC 누락. 클라우드 인사 시스템을 도입하며 SOC 2 Type II를 받고 승인했지만, 1년 뒤 감사에서 CUEC 12개 중 7개를 조직이 수행하지 않고 있었습니다. 그 안에는 “고객은 관리자 계정 접근 검토를 분기별로 수행해야 한다”가 있었습니다. 보고서 수령 때 CUEC를 추출해 책임자와 주기를 배정하는 절차를 추가했습니다.

    보충Type II 보고서는 “보고 기간에 실제로 무엇을 시험했고 결과가 어땠는가”를 읽는 문서입니다. 보고 기간이 6월에 끝났다면 8월에 출시한 기능은 보고서가 말해 주지 않으므로 별도 증거가 필요할 수 있습니다. 조직이 쓰는 기능이나 지역이 보고서 범위에 없다면 그 부분도 마찬가지입니다. ISO 27001 심사원이라면 익숙한 질문, “이 인증서의 적용 범위에 우리가 쓰는 서비스가 들어 있는가”와 같은 구조입니다.

    연결SOC 보고서 유형과 감사 수행은 D6.5 보안 감사, 공급자 관리는 D1.11 공급망 위험 관리, 외부 소프트웨어·서비스의 보안 영향은 D8.4 도입 소프트웨어 평가에서 다룹니다.

    원문 위치: D6.1.md §3 내부 / 외부 / 제3자, §7 사례 2, 사례 5 · 공식 개요 6.1 “Internal (e.g., within organization control)”, “External (e.g., outside organization control)”, “Third-party (e.g., outside of enterprise control)”

    4위치 — 온프레미스, 클라우드, 하이브리드

    공식 개요가 명시한 항목입니다. 위치가 테스트 가능한 범위와 방법을 바꿉니다.

    위치테스트 범위핵심 주의점
    온프레미스전 계층을 소유 → 제약이 가장 적음(물리, 네트워크, 호스트, 앱)운영 영향, 유지보수 창 확보
    클라우드책임 공유 모델이 결정. IaaS는 게스트 OS 위가 고객 범위, PaaS는 앱과 설정, SaaS는 자기 설정·권한·데이터 처리·연동 정도사업자 동의와 정책 준수 필수. 공유 인프라 테스트(서비스 거부, 다른 테넌트 영향)는 대개 금지. 공급자 영역은 증거로 대체
    하이브리드가장 어려움. 범위가 경계를 넘나듦연결 지점의 책임 공백(VPN·전용 연결, 디렉터리 동기화, 연합 신뢰), 로그 분산과 상관분석, 결과 종합 단계 필요

    클라우드 고유 검증 항목은 신원·권한 설정(과도한 IAM 권한, 공개 접근), 스토리지 공개 설정, 네트워크 보안 그룹, 로깅 활성화, 암호화 설정, 조직 수준 정책 가드레일입니다. 원본은 대부분 설정 오류가 주된 위험이므로 지속적 설정 평가(CSPM 류)가 주기적 테스트보다 효과적이라고 봅니다.

    원문 사례 — 동의 없이 수행한 클라우드 테스트. 외부 테스터가 사업자 정책이 금지한 서비스 거부 성격의 트래픽을 발생시켜, 사업자 자동 보호가 계정을 제한하고 운영 서비스가 영향을 받았습니다. 테스트 승인서에 사업자 정책 준수 조항, 금지 기법 목록, 긴급 중단 연락 체계를 넣었습니다.

    원문 사례 — 하이브리드 연결 지점의 사각지대. 온프레미스 팀과 클라우드 팀이 각자 범위를 테스트해 둘 다 문제가 없었지만, 디렉터리 동기화 서버와 연합 신뢰 구성은 어느 범위에도 없었고 동기화 계정이 양쪽에 과도한 권한을 갖고 있었습니다. 연결 지점을 별도 범위 항목으로 정의하고 두 결과를 종합하는 단계를 추가했습니다.

    가상 예시고객 포털이 관리형 앱(PaaS)에서 돌지만 계정 승인과 기록 분류는 회사가 직접 한다고 합시다. 감사 전략에 “공급자 보고서 수령 일정”만 적혀 있다면 절반이 빠진 것입니다. 통제마다 수행자, 시스템, 기간을 표시해 보면, 공급자만 운영하는 기반 서비스는 범위가 맞는 독립 보고서로, 회사가 하는 계정 승인과 분류는 회사 자체의 기록 검토와 시험으로 증거를 모아야 한다는 것이 드러납니다.

    연결책임 공유 모델은 D3.1 안전한 설계 원칙·D8.4 도입 소프트웨어 평가, 클라우드 설정 오류와 CSPM은 D3.5 아키텍처별 취약점, 하이브리드 동기화 계정의 위험은 D5.3 연합 식별의 3절에서 다룹니다.

    원문 위치: D6.1.md §3 위치, §7 사례 3, 사례 4 · 공식 개요 6.1 “Location (e.g., on-premises, cloud, hybrid)”

    5전략의 검증 (Validate)

    공식 개요가 “설계와 검증”이라고 쓴 부분입니다. 전략 자체가 적절한지를 확인합니다.

    검증 항목질문
    커버리지자산 인벤토리와 테스트 대상을 대조했을 때 누락된 자산은?
    방법 적절성그 방법이 그 통제 유형을 실제로 검증하는가? (자동 스캔은 논리 결함·권한 설계 오류를 못 찾음)
    결과의 유용성결과가 조치로 이어졌는가? 같은 결함이 반복되면 교정 절차의 문제
    기준의 최신성표준·규제가 바뀌었는데 기준이 그대로인가?
    독립성 유지평가자가 피평가 영역에 이해관계를 갖게 되지 않았는가?
    가정의 재확인“이 시스템은 내부 전용” 같은 가정이 여전히 참인가?

    원본의 핵심 문장: 테스트 결과가 깨끗할 때 먼저 의심할 것은 커버리지다. 결함이 없는 것과 보지 않은 것은 결과표에서 구분되지 않습니다.

    원문 사례 — 깨끗한 보고서가 숨긴 미검증 영역. 연간 취약점 평가가 “중대 결함 없음”이었지만, 인벤토리상 1,240대 중 스캔 대상은 790대였습니다. 누락된 450대 대부분이 부서가 직접 도입한 시스템과 클라우드 자원이었고, 그중 패치되지 않은 외부 노출 시스템이 있었습니다. 인벤토리와 스캔 대상의 자동 대조를 상시화하고 미검증 자산 수를 지표로 보고했습니다.

    원문 사례 — 방법이 통제 유형에 맞지 않은 경우. 앱 접근 통제를 자동 취약점 스캔만으로 검증해 깨끗했지만, 다른 사용자 식별자를 넣으면 남의 데이터가 반환되었습니다. 인가 로직에 수동 테스트와 오용 사례 테스트를 추가하고, 통제 유형별 적합한 방법을 전략에 명시했습니다.

    연결커버리지 분석과 오용 사례 테스트는 D6.2 보안 통제 테스트의 7절과 6절, IDOR는 D5.1 물리적·논리적 접근 통제의 6절에서 다룹니다.

    원문 위치: D6.1.md §3 전략의 검증, §7 사례 1, 사례 6

    6테스트가 만드는 위험

    평가 활동 자체가 위험을 만들며, 전략은 이를 관리해야 합니다.

    위험대응
    운영 영향: 스캔·테스트가 서비스를 멈출 수 있음창구 조정, 사전 통지, 중단 기준(kill switch), 롤백 계획
    접근 권한 부여: 테스트 후 회수되지 않으면 그 자체가 결함기한부 권한, 종료 시 회수 확인
    결과물의 민감도: 취약점 보고서는 공격 지침서접근 제한, 암호화 보관, 보존 기간, 파기 절차
    법적 승인: 서면 승인 없는 침투 테스트는 불법이 될 수 있음서면 승인(authorization to test)에 범위, 기간, 연락 체계, 긴급 중단 조건

    보충운영 서비스에 부하를 주는 시험을 승인할 때는 대상뿐 아니라 시간, 영향 한도, 중단 조건, 연락 책임을 문서화합니다. 목적이 실제 동작 확인이라면 대표성 있는 별도 환경을 쓸 수 있는지도 검토하고, 운영과 다른 조건에서 시험했다면 결과를 해석할 때 그 차이를 밝혀야 합니다. 의료기기처럼 운영 중 장애가 환자 안전으로 이어질 수 있는 환경에서는 이 원칙이 더 무겁습니다.

    원문 위치: D6.1.md §3 테스트가 만드는 위험

    7종합 이해 확인

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    연간 평가 결과 보고서에 “중대 결함 없음”이 적혀 있다. 함께 확인된 사실: ㉠ 스캔 대상은 인벤토리의 64%였다. ㉡ 클라우드 HR 서비스는 SOC 2 Type II를 받아 승인했지만 CUEC는 배정되지 않았다. ㉢ 방화벽 정책 평가는 운영팀이 직접 했다. ㉣ 디렉터리 동기화 서버는 온프레미스·클라우드 어느 범위에도 없었다. 이 보고서에 대한 가장 적절한 판단은?

    1. 결함이 없으므로 다음 해에도 같은 전략을 유지한다.
    2. 스캐너를 더 비싼 제품으로 교체한다.
    3. 결과가 아니라 전략에 공백이 있다. 커버리지 대조, CUEC 책임 배정, 평가·운영 분리, 연결 지점의 범위 편입으로 전략을 검증·보완한다.
    4. SOC 2 Type II가 있으므로 클라우드 HR은 조직이 할 일이 없다.
    정답과 해설 보기

    정답 C. ㉠ 5절(깨끗한 결과에서 먼저 의심할 것은 커버리지), ㉡ 3절(CUEC는 조직의 의무 — D가 틀린 이유), ㉢ 3절(자기 업무의 자기 검증), ㉣ 4절(하이브리드 연결 지점). B는 도구가 아니라 범위의 문제를 놓칩니다.

    8핵심 개념을 내 말로 설명하기

    복습

    통제 정책과 담당자 면담을 읽고 운영 효과를 판단할 수 있나요?

    설명 확인하기

    정책과 면담은 의도와 책임의 근거가 됩니다. 평가하려는 기간의 실행 기록과 예외 후속 조치, 필요하면 실제 동작 시험까지 봐야 운영 중 효과를 판단할 수 있습니다.

    9핵심 요약

    1. 테스트 = 작동하는가, 평가 = 충분한가, 감사 = 기준 준수를 독립적으로 확인.
    2. 전략 구성요소: 범위(인벤토리 전제), 기준, 주기(위험 기반 + 변경 트리거), 방법(검토·면담·시험 조합), 독립성, 보고 경로.
    3. 감사 기능은 이사회·감사위원회에 보고. 결과는 위험 책임자와 조치 팀 모두에게.
    4. 내부(통제 범위 안, 독립성 제한) / 외부(고용된 외부 전문가, 완전 독립은 아님) / 제3자(기업 통제 밖, 공급자 보고서·인증 심사·규제 검사).
    5. SOC 2 Type I = 시점의 설계, Type II = 기간의 운영 효과성. 확인: 기간, 범위, 예외, CUEC(조직 자신의 의무).
    6. 위치: 온프레미스(제약 최소) / 클라우드(책임 공유, 사업자 동의, 공급자 영역은 증거로, CSPM) / 하이브리드(연결 지점을 명시적으로 범위에).
    7. 전략 검증: 커버리지, 방법 적절성, 결과 유용성, 기준 최신성, 독립성, 가정. 깨끗한 결과 → 먼저 커버리지를 의심.
    8. 테스트의 위험: 운영 영향, 테스터 권한 회수, 보고서 = 공격 지침서, 서면 승인.
    원문 위치: D6.1.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 “시험 구분법”, “시험에 자주 나온다” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    10주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Testing / Assessment / Audit · 테스트 / 평가 / 감사

    통제 동작 확인, 통제 적절성 판단, 기준 준수에 대한 독립적 의견.

    Examine / Interview / Test · 검토 / 면담 / 시험

    NIST SP 800-53A 의 세 가지 평가 방법.

    Internal / External / Third-party · 내부 / 외부 / 제3자 평가

    조직 통제 범위 내, 조직이 고용한 외부, 조직이 통제하지 않는 주체.

    Independence · 독립성

    평가자가 피평가 대상에 이해관계를 갖지 않는 성질. 감사의 핵심 요건이다.

    SOC 2 Type I / Type II · 특정 시점 설계 평가 / 기간의 운영 효과 포함 평가

    특정 시점의 통제 설계 적정성 보고서와 일정 기간 운영 효과성 보고서.

    제3자 보고서에서 고객이 직접 수행해야 하는 보완 통제.

    Shared Responsibility Model · 공동 책임 모델

    클라우드에서 공급자와 고객의 보안 책임 경계를 정의한 모델.

    Coverage Analysis · 커버리지 분석

    자산과 테스트 대상을 대조해 미검증 영역을 찾는 활동.

    Authorization to Test · 테스트 승인서

    침투 테스트의 범위, 기간, 연락 체계, 중단 조건을 명시한 서면 승인.

    Risk-Based Frequency · 위험 기반 주기

    자산 위험 수준에 따라 평가 주기를 차등 적용하는 방식.

    CSPM (Cloud Security Posture Management) · 클라우드 보안 상태 관리

    클라우드 설정을 지속적으로 평가해 오설정을 탐지하는 체계.
