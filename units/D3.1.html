    연습문제 6개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    어떤 보안 제품을 고르든, 어떤 시스템을 만들든 같은 질문이 반복됩니다. 권한은 최소인가, 하나가 뚫려도 다음이 막는가, 아무 설정도 안 했을 때 안전한가, 고장 나면 어느 쪽으로 넘어지는가. 공식 개요 3.1은 이 질문들을 11개의 설계 원칙으로 정리합니다. 원칙은 개별 기술이 아니라 설계를 평가하는 기준입니다.

    이 단원의 위치

    도메인 3은 “안전하게 설계하고 만드는 법”입니다. 이 단원의 원칙이 뒤의 보안 모델(3.2), 통제 선택(3.3), 시스템 보안 기능(3.4), 취약점 평가(3.5)의 기준이 됩니다.

    단원어떻게 이어지는가
    D1.10 위협 모델링원칙 1 위협 모델링의 방법(STRIDE, 데이터 흐름도, 신뢰 경계) (1절)
    D1.2 보안 개념 (CIA 등) · D1.8 인적 보안알 필요성·최소권한, 권한 누적, 직무 분리와 이중 통제 (2절, 6절)
    D2.2 자산 취급 요구사항 · D2.4 데이터 생애주기“기본값이 곧 정책”, 데이터 최소화·목적 제한 (4절, 9절)
    D3.2 보안 모델 · D3.4 시스템 보안 기능원칙을 형식 규칙으로 만든 보안 모델, TCB와 참조 모니터 (7절)
    D4.1 네트워크 아키텍처 · D4.3 안전한 통신 채널제로 트러스트와 마이크로세그멘테이션, ZTNA와 VPN (8절, 11절)
    D8.4 도입 소프트웨어 평가클라우드 서비스 모델별 공동 책임 (10절)
    D7.14 물리적 보안물리 출입문의 fail-safe와 fail-secure (5절)

    원본의 공통 전제는 보안은 나중에 덧붙일 수 없다입니다. 설계에 들어가지 않은 보안은 나중에 넣으려면 비용이 크게 늘거나 아예 불가능해집니다. 핵심 구조를 바꿔야 하는 문제를 운영 단계에서 발견하면 바꿀 범위가 그만큼 커지기 때문입니다.

    1위협 모델링

    설계 단계에서 무엇이 잘못될 수 있는지를 체계적으로 찾아내는 일입니다. 방법(STRIDE, PASTA, 데이터 흐름도와 신뢰 경계)은 D1.10 위협 모델링에서 자세히 다뤘습니다.

    원본은 설계 원칙으로서 위협 모델링의 의미를 이렇게 정리합니다. 다른 모든 원칙을 어디에 적용할지 알려 준다. 위협을 모르면 심층 방어의 계층을 어디에 둘지, 무엇을 최소권한으로 묶을지 정할 수 없습니다.

    보충위협 모델이 설계 문서에서 끝나면 효과가 반만 남습니다. 새로 생긴 신뢰 경계마다 “여기에 어떤 통제가 꼭 있어야 하는가”를 정하고, 그것을 시험 항목으로 바꿔야 구현이 설계를 따랐는지 확인할 수 있습니다. 예를 들어 승인 API와 조회 API의 역할이 다르면, 설계 문서에는 역할별 동작을, 시험에는 “잘못된 역할로 호출하면 거부되는가”를 남깁니다.

    원문 위치: D3.1.md §2 11원칙 목록·공통 전제, §3 1) 위협 모델링 · 공식 개요 3.1 “Threat modeling”

    2최소권한

    주체에게 업무 수행에 필요한 최소한의 권한만, 필요한 기간만 부여합니다.

    • 알 필요성(need-to-know)과 함께 적용된다
    • 적시 권한(Just-in-Time, JIT) — 필요할 때만 일시적으로 권한을 올린다
    • 적정 관리(Just-Enough-Administration, JEA) — 전체 관리자 대신 작업별 최소 권한

    위반의 대표 증상이 권한 누적(Privilege Creep)입니다.

    보충“필요한 기간만”이라는 부분이 자주 빠집니다. 상시 관리자 권한은 그 계정이 탈취되는 순간 공격자에게 그대로 넘어갑니다. 적시 권한은 평소에는 권한이 없고, 작업할 때 승인을 받아 정해진 시간만 권한을 갖게 합니다. 탈취되더라도 권한이 없는 시간대가 대부분이 되므로 피해 가능성이 줄어듭니다. 적정 관리는 “서버 관리자” 대신 “이 서비스 재시작만 가능” 같은 좁은 권한을 줍니다.

    가상 예시현장 장비의 원격 지원 계정이 모든 장비에 대해 상시 관리자 권한을 가지고 있다고 합시다. 최소권한을 적용하면 ① 엔지니어는 지원 요청이 들어온 장비에만 ② 요청 승인 후 몇 시간만 ③ 로그 수집과 진단 명령만 가능한 권한을 받습니다. 펌웨어 교체처럼 큰 작업은 별도 승인을 거칩니다. 지원 계정 하나가 유출되어도 모든 장비가 동시에 위험해지지 않습니다.

    연결최소권한과 알 필요성의 차이(할 수 있는 것 vs 볼 수 있는 것)는 D1.2 보안 개념 (CIA 등), 권한 누적은 D1.8 인적 보안, 특권 계정 관리는 D7.4 기본 보안 운영 개념, 권한을 부여하고 회수하는 생애주기는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원본 연습문제 · D3.1-Q23

    최소 권한 원칙이 요구하는 것은?

    1. 모든 사용자가 업무 시간에만 관리자 권한을 받는 것.
    2. 시스템마다 관리자가 한 명만 존재하는 것.
    3. 권한을 넓게 부여하고 연간 검토하는 것.
    4. 각 주체가 자기 기능을 수행하는 데 요구되는 권한만, 그것이 필요한 기간 동안만 부여받는 것.
    정답과 해설 보기

    정답 D. 최소 권한은 범위와 기간 두 축을 모두 포함한다. 필요한 권한만 주는 것과 필요 없어지면 회수하는 것이 함께 적용되어야 한다. 기간을 빠뜨리면 권한이 누적되고, 이것이 역할 변경 시 이전 권한을 회수하지 않아 생기는 권한 누적의 원인이다.

    • A · 시간 제한만으로는 범위 제한이 없다.
    • B · 관리자 수를 규정하는 원칙이 아니다.
    • C · 넓은 부여는 원칙에 반한다.

    3심층 방어

    쉬운 설명

    심층 방어(Defense in Depth)는 여러 계층의 통제를 겹쳐서 하나가 뚫려도 다음이 막게 하는 설계입니다. 다층 방어(layered defense)라고도 합니다.

    물리 보안
    →
    네트워크 분할
    →
    호스트 강화
    →
    애플리케이션 통제
    →
    데이터 암호화

    단순히 많이 쌓는 것이 아니다

    원본은 같은 유형의 통제를 겹치면 같은 공격에 함께 뚫린다고 경고합니다. 성격이 다른 통제를 배치해야 합니다. 예방·탐지·대응을 섞고, 관리적·기술적·물리적 통제를 섞습니다. 단일 장애점(SPOF) 제거와 짝을 이루는 개념입니다.

    원문 사례 — 심층 방어를 잘못 이해한 경우. 조직이 서로 다른 벤더의 방화벽 3대를 직렬로 두고 심층 방어라고 불렀습니다. 같은 유형의 통제라서 애플리케이션 계층 공격은 세 대를 모두 그대로 통과했습니다. 조직은 방화벽(네트워크) + WAF(애플리케이션) + 입력 검증(코드) + 최소권한 DB 계정(데이터)으로 바꿨습니다.

    보충방화벽 세 대가 실패한 이유는 셋 다 같은 질문(“이 패킷의 주소와 포트가 허용되는가”)만 했기 때문입니다. 애플리케이션 공격은 허용된 포트로 들어오므로 셋 모두 “예”라고 답합니다. 계층을 설계할 때는 “각 계층이 서로 다른 질문을 하는가”를 확인하면 됩니다. 원본 사례의 바뀐 구성은 네트워크(누가 어디로), 애플리케이션(요청 내용이 정상인가), 코드(입력이 기대한 형식인가), 데이터(이 계정이 이 테이블을 지울 수 있는가)로 네 가지 다른 질문을 합니다.

    연결통제의 기능 분류(예방·탐지·교정 등)와 유형 분류(관리적·기술적·물리적)는 D1.9 위험 관리, 네트워크 분할은 D4.1 네트워크 아키텍처, WAF와 IPS의 운영은 D7.7 탐지·예방 수단, 입력 검증은 D8.5 안전한 코딩에서 다룹니다.

    원본 연습문제 · D3.1-Q01

    조직이 서로 다른 벤더의 방화벽 3대를 직렬로 배치하고 이를 심층 방어라 불렀다. 애플리케이션 계층 공격이 세 대를 모두 그대로 통과했다. 어떤 설계 오류인가?

    1. 심층 방어는 일관성을 위해 단일 벤더 사용을 요구한다.
    2. 방화벽을 직렬이 아니라 병렬로 배치했어야 한다.
    3. 3개 계층은 부족하며 최소 5개가 필요하다.
    4. 동일한 유형의 통제를 겹치는 것은 다른 계층의 위협을 다루지 못한다.
    정답과 해설 보기

    정답 D. 심층 방어는 같은 통제를 겹치는 것이 아니라 서로 다른 성격의 통제를 배치하는 것이다. 네트워크 방화벽, 애플리케이션 WAF, 코드 수준 입력 검증, 데이터 계층 최소권한처럼 계층과 성격을 달리해야 하나가 뚫려도 다음이 막는다.

    • A · 벤더 다양성은 부차적이며 계층 다양성이 핵심이다.
    • B · 배치 형태가 아니라 통제 유형의 다양성이 문제다.
    • C · 계층의 개수가 아니라 성격의 차이가 중요하다.

    4안전한 기본값

    설정하지 않았을 때 가장 안전한 상태가 되어야 합니다. 사용자가 보안을 켜야 안전해지는 구조가 아니라, 꺼야 덜 안전해지는 구조입니다.

    • 기본 거부(default deny) — 명시적으로 허용한 것만 통과
    • 불필요한 기능·서비스는 기본 비활성화
    • 기본 계정 비활성화, 기본 비밀번호 강제 변경
    • 공유 범위는 기본적으로 최소

    원본의 근거는 단순합니다. 대부분의 사용자는 기본값을 바꾸지 않는다. 그래서 기본값이 사실상 조직의 보안 수준을 결정합니다.

    원문 사례 — 기본값이 바꾼 결과. 사내 협업 도구에서 새 채널의 기본값이 “전사 공개”여서 민감한 인사 논의가 의도치 않게 전 직원에게 노출되었습니다. 기본값을 “비공개, 초대 기반”으로 바꾸자 비슷한 사건이 사라졌습니다. 원본의 결론은 안전한 기본값은 교육보다 효과적이다입니다.

    연결D2.2 자산 취급 요구사항의 “기본값이 곧 정책이다”(무기한 공유 링크 사례), D2.3 안전한 프로비저닝의 기본 자격증명 변경과 골든 이미지가 같은 원칙을 다른 장면에서 보여 줍니다. 방화벽 규칙의 기본 거부는 D4.1 네트워크 아키텍처에서 다룹니다.

    원문 위치: D3.1.md §3 4) 안전한 기본값, §4 Secure Defaults, §7 사례 5 · 공식 개요 3.1 “Secure defaults”

    5안전한 실패

    쉬운 설명

    시스템은 언젠가 고장 납니다. 그때 안전한 상태로 넘어져야 합니다. 문제는 “안전한 상태”가 무엇을 보호하느냐에 따라 반대가 된다는 점입니다.

    방식실패 시우선 보호예
    Fail-secure / Fail-closed차단기밀성(데이터)인증 서버 장애 시 접근 거부
    Fail-safe / Fail-open개방인명 안전화재 시 비상구 개방

    원본은 용어 혼동을 주의시킵니다. 물리 보안에서 fail-safe는 사람의 안전을 뜻해 문이 열리고, 정보 보안에서는 데이터 보호를 위해 차단되는 것이 “안전한” 쪽입니다. 판단 기준은 무엇을 보호하는가입니다.

    안전한 실패에는 오류 메시지에 내부 정보를 노출하지 않는 것도 포함됩니다. 스택 트레이스, 쿼리문, 내부 경로가 그대로 나가면 공격자에게 지도를 주는 셈입니다.

    원문 사례 — 안전하지 않은 실패. 인증 서버가 장애를 일으키면 애플리케이션이 인증을 건너뛰고 접근을 허용하도록 구현되어 있었습니다. 가용성을 위한 선택이었지만, 공격자는 인증 서버에 부하를 걸어 일부러 장애를 만든 뒤 인증 없이 들어왔습니다.

    보충이 사례의 교훈은 “실패 동작도 공격자가 이용할 수 있는 기능”이라는 것입니다. 장애 시 열리는 문이 있으면 공격자는 장애를 일으키는 법만 찾으면 됩니다. 물리 출입문은 방향을 나눠 생각하면 두 요구를 함께 맞출 수 있습니다. 정전이 되어도 밖에서 들어오는 쪽은 잠겨 있고(보안), 안에서 나가는 쪽은 열리게(인명) 할 수 있습니다. “차단이냐 개방이냐”를 문 하나의 상태로 묶지 않는 것입니다.

    판단 순서실패 동작을 정하는 상황에서는 ① 이 지점이 지키는 것이 사람인가 데이터인가 ② 사람이면 개방(fail-safe), 데이터면 차단(fail-closed) ③ 둘 다 걸려 있으면 방향이나 대상을 나눌 수 있는지 ④ 실패 시 내보내는 메시지에 내부 정보가 없는지 순서로 봅니다. 지문에 인명 안전이 나오면 다른 모든 고려보다 우선합니다.

    연결출입문과 잠금 장치의 fail-safe·fail-secure는 D7.14 물리적 보안, 오류 처리와 안전한 코딩은 D8.5 안전한 코딩, 사람의 안전이 최우선이라는 원칙은 D7.15 인원 안전의 인원 안전에서 다시 나옵니다. 인증 서버 장애 시의 동작은 D5.6 인증 시스템의 인증 시스템 설계와도 이어집니다.

    이해 확인 · 자작 상황 문제 (실제 시험 문제 아님)

    병원 장비의 관리 콘솔이 권한 정책 서버에 연결하지 못하는 장애가 생겼다. 설계 회의에서 네 가지 안이 나왔다. 가장 적절한 것은?

    1. 정책 서버에 연결되지 않으면 모든 관리 기능을 허용해 진료가 멈추지 않게 한다.
    2. 관리 기능(설정 변경, 사용자 추가)은 차단하고, 환자 검사 같은 진료 기능은 계속 동작하게 하며, 오류 화면에는 내부 주소를 표시하지 않는다.
    3. 장비 전체를 즉시 정지한다.
    4. 오류 원인을 빨리 파악하도록 화면에 정책 서버 주소와 오류 스택을 그대로 보여 준다.
    정답과 해설 보기

    정답 B. 보호 대상을 나눴습니다. 권한이 걸린 관리 기능은 fail-closed, 진료(사람)와 직결된 기능은 계속 동작하게 하고, 오류 메시지에서 내부 정보를 뺐습니다.

    • A: 원문 사례 2와 같은 구조입니다. 장애를 일으키면 관리 권한이 열립니다.
    • C: 인명과 관련된 진료 기능까지 멈춥니다. 보호 대상을 구분하지 않았습니다.
    • D: 안전한 실패에는 오류 메시지의 내부 정보 비노출이 포함됩니다.

    6직무 분리

    한 사람이 전 과정을 혼자 끝내지 못하게 나눕니다. 공모에 약하다는 한계, 이중 통제와의 차이는 D1.8 인적 보안에서 다뤘습니다.

    원본이 설계 관점에서 강조하는 것은 시스템이 직무 분리를 강제하게 만드는 것입니다. 정책 문서에만 두면 지켜지지 않으므로, 요청자와 승인자를 같은 계정으로 할 수 없게 애플리케이션이 막아야 합니다.

    보충화면을 요청·승인·실행으로 나눠도 같은 계정이 세 화면에 모두 들어갈 수 있으면 분리는 이름뿐입니다. 설계 단계에서 역할을 나누어 두면 운영 단계에서 “같은 계정에 서로 충돌하는 역할이 함께 부여되었는가”를 자동으로 검사할 수 있습니다.

    연결운영 단계의 직무 분리와 직무 순환은 D7.4 기본 보안 운영 개념, 직무 분리를 모델 안에 넣은 보안 모델 Clark-Wilson은 D3.2 보안 모델에서 다룹니다.

    7단순하고 작게

    원본의 문장은 복잡성은 보안의 적이다. 이해할 수 없는 시스템은 안전하게 만들 수 없다입니다.

    • 공격면 최소화 — 기능이 적을수록 취약점도 적다
    • 메커니즘의 경제성(Economy of Mechanism) — 보호 메커니즘은 작고 단순해야 검증할 수 있다
    • TCB(Trusted Computing Base)를 작게 — 보안을 강제하는 하드웨어·소프트웨어·펌웨어의 집합. 신뢰해야 하는 부분이 작을수록 검증이 쉽다

    원본은 이것이 Saltzer와 Schroeder(1975)의 고전적 설계 원칙과 직접 이어진다고 설명합니다. 그 원칙 목록에는 메커니즘의 경제성, 안전한 기본값, 완전한 조정, 개방 설계, 권한 분리, 최소권한, 공통 메커니즘 최소화, 심리적 수용성이 있습니다.

    보충Saltzer·Schroeder 목록과 공식 11원칙을 나란히 놓으면 겹치는 것이 많습니다(안전한 기본값, 최소권한, 권한 분리 ≈ 직무 분리, 경제성 ≈ 단순하고 작게). 목록에만 있는 완전한 조정(complete mediation)은 모든 접근을 매번 검사하라는 뜻으로, 제로 트러스트의 “매 요청마다 검증”과 같은 생각입니다. 심리적 수용성(psychological acceptability)은 사용자가 받아들일 수 있어야 통제가 작동한다는 뜻으로, 이 교재가 여러 번 본 “과잉 통제는 우회를 낳는다”의 원형입니다.

    연결TCB와 그 안의 참조 모니터·보안 커널은 D3.4 시스템 보안 기능, 공격면을 줄이는 강화 작업은 D2.3 안전한 프로비저닝에서 다룹니다.

    원본 연습문제 · D3.1-Q08

    보안 메커니즘을 단순하고 작게 유지하는 원칙이 중요한 이유는?

    1. 작은 메커니즘은 현대 하드웨어에서 항상 더 빠르게 실행된다.
    2. 신뢰 컴퓨팅 기반(TCB)이 작을수록 정확성을 분석하고 검증하기 쉽다.
    3. 단순한 설계는 접근 통제의 필요성을 완전히 제거한다.
    4. 작은 코드베이스는 보안 테스트 요건에서 면제된다.
    정답과 해설 보기

    정답 B. 이해할 수 없는 시스템은 안전하게 만들 수 없다. 보호 메커니즘이 작고 단순할수록 검증이 가능하고 공격면도 줄어든다. Saltzer 와 Schroeder 의 경제성(economy of mechanism) 원칙과 직접 연결된다.

    • A · 성능은 부수적 효과이며 보안상의 이유가 아니다.
    • C · 단순성이 접근 통제를 대체하지 않는다.
    • D · 규모와 무관하게 보안 테스트는 필요하다.

    8제로 트러스트

    왜 필요한가

    전통적 경계 모델은 내부는 신뢰한다는 전제였습니다. 한 번 들어오면 자유롭게 이동할 수 있어서, 침해되면 횡적 이동(Lateral Movement)이 쉬웠습니다. 제로 트러스트의 구호는 “절대 신뢰하지 않고 항상 검증한다(never trust, always verify)”이고, 전제는 네트워크 위치가 신뢰의 근거가 되지 않는다입니다. 내부망이든 외부망이든 매 요청마다 검증합니다.

    주체의 요청사용자·기기·서비스
    →
    PEP정책 집행 지점
    ⇄
    PDP정책 결정 지점
    신원·기기 상태·행위·위치

    자원세션 단위 허용
    • PDP(Policy Decision Point) — 접근 허용 여부를 결정
    • PEP(Policy Enforcement Point) — 결정을 집행
    • 모든 자원에 대한 명시적 검증
    • 최소권한과 세션 단위 접근
    • 지속적 평가 — 한 번 인증했다고 끝이 아니다
    • 기기 상태, 사용자 행위, 위치 등 여러 신호를 종합한 동적 판단

    네트워크 쪽 구현 수단은 마이크로세그멘테이션이고, 전제 조건은 강한 식별·인증입니다. 원본은 공식 개요가 함께 제시한 신뢰하되 검증(trust but verify)을 제로 트러스트보다 완화된 접근으로 설명합니다.

    원문 사례 — 제로 트러스트가 막은 횡적 이동. 피싱으로 직원 한 명의 단말이 침해되었습니다. 전통 모델이었다면 내부망 전체를 탐색할 수 있었겠지만, 애플리케이션 단위 ZTNA가 적용되어 있어서 그 사용자에게 허락된 애플리케이션 2개 외에는 존재 자체가 보이지 않았습니다. 원본의 결론은 제로 트러스트의 가치는 침해를 막는 것이 아니라 침해의 영향 범위를 제한하는 데 있다입니다.

    보충제로 트러스트는 사람에게만 적용되지 않습니다. 사내 배치 작업이 주문 API를 호출할 때 “사내망 주소에서 왔으니 허용”이면, 같은 망에 새로 들어온 다른 서비스도 똑같이 허용됩니다. 호출한 서비스의 신원과 요청 목적을 확인해 필요한 작업(예: 주문 조회)만 허용해야 합니다. 또 PDP가 장애일 때 어떻게 할지도 미리 정해야 합니다. 정책 서버가 멈추면 모두 허용하는 설계라면 5절의 안전하지 않은 실패가 됩니다.

    연결마이크로세그멘테이션과 네트워크 관점의 제로 트러스트는 D4.1 네트워크 아키텍처, ZTNA와 VPN의 차이는 D4.3 안전한 통신 채널, 강한 인증과 지속적 인증은 D5.2 식별·인증 전략·D5.6 인증 시스템에서 다룹니다. 횡적 이동은 D1.10 위협 모델링의 공격 흐름에서도 나왔습니다.

    CISSP 관점제로 트러스트 상황에서는 ① 지문의 설계가 네트워크 위치(내부망, VPN 접속 여부)를 신뢰의 근거로 쓰는지 찾고 ② 쓰고 있다면 그것이 문제점이며 ③ 개선안은 매 요청 검증, 최소권한, 지속적 평가 쪽입니다. 효과를 묻는다면 “침해 완전 차단”보다 “횡적 이동 제한, 영향 범위 축소”가 원본의 설명에 맞습니다. PDP는 결정, PEP는 집행입니다.

    9설계 단계 프라이버시

    Privacy by Design은 프라이버시를 나중에 추가하지 않고 설계에 내재시키는 원칙입니다. 원본은 일곱 가지 기초 원칙을 듭니다.

    1. 사후 대응이 아닌 사전 예방
    2. 기본값으로서의 프라이버시(privacy by default)
    3. 설계에 내재
    4. 기능 전체 — 제로섬이 아닌 포지티브섬(보안과 기능을 맞바꾸지 않는다)
    5. 종단 간 보안 — 전 생애주기 보호
    6. 가시성과 투명성
    7. 이용자 프라이버시 존중

    실무에서는 데이터 최소화, 목적 제한, 보존 기간 설정, 가명화로 나타나고, GDPR 제25조(Data protection by design and by default)가 이를 법적 요구로 명문화했습니다.

    연결최소 수집·목적 제한·보존은 D2.4 데이터 생애주기, 가명화와 익명화는 D2.6 데이터 보안 통제, GDPR의 원칙과 정보주체 권리는 D1.4 법률·규제·컴플라이언스에서 다뤘습니다. “기본값으로서의 프라이버시”는 4절의 안전한 기본값을 개인정보에 적용한 것입니다.

    원본은 어떤 모델이든 고객이 항상 책임지는 세 가지를 강조합니다. 데이터 자체, 접근 권한 관리(IAM), 구성 설정입니다. 원본은 클라우드 침해 대부분이 제공자의 결함이 아니라 고객의 잘못된 설정에서 나온다고 설명하며, “클라우드를 쓰니 보안은 제공자가 알아서 한다”는 가정을 가장 위험한 것으로 꼽습니다.

    원문 사례 — 공동 책임 모델의 오해. SaaS로 옮기면서 “보안은 제공자 책임”이라 판단해 접근 권한 검토를 중단했습니다. 2년 뒤 감사에서 퇴사자 계정 다수가 활성 상태로 발견되었습니다. 제공자는 애플리케이션의 보안을 책임지지만, 누가 접근할 수 있는지는 고객이 정합니다.

    보충표는 책임의 경계를 보여 주지만, 그 경계 안에서 실제로 누가 일을 하는지는 보여 주지 않습니다. IaaS로 옮긴 뒤 게스트 운영체제 패치를 아무도 하지 않는 일이 생기는 이유입니다. 고객 쪽 책임 항목마다 사내 담당자를 정해 두어야 공동 책임 모델이 실제로 작동합니다. 원본은 이것을 D1.11 공급망 위험 관리의 “책임은 위탁되지 않는다”와 연결합니다.

    연결공급자에게 맡겨도 최종 책임은 조직에 남는다는 원칙은 D1.11 공급망 위험 관리, 도입할 클라우드 서비스의 평가와 계약은 D8.4 도입 소프트웨어 평가, 클라우드 서비스 모델의 취약점은 D3.5 아키텍처별 취약점, 퇴사자 계정 회수와 접근 검토는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원본 연습문제 · D3.1-Q16

    IaaS 로 이전한 뒤 게스트 운영체제를 아무도 패치하지 않아 장애가 발생했다. 이것이 드러내는 것은?

    1. 공급자가 모든 것을 처리하도록 SaaS 로 이전해야 한다.
    2. IaaS 는 본질적으로 온프레미스 인프라보다 신뢰성이 낮다.
    3. 공급자가 서비스 수준 협약을 충족하지 못했다.
    4. 공동 책임 경계가 지정된 담당자에게 매핑되지 않았다. IaaS 에서 게스트 운영체제는 고객 책임이므로 책임을 계층별로 문서화해 배정해야 하며 플랫폼이 바뀌면 책임도 자동으로 옮겨 간다고 가정하면 안 된다.
    정답과 해설 보기

    정답 D. 클라우드 이전에서 가장 흔한 사고 유형이 "공급자가 해 줄 것으로 생각했다" 는 공백이다. IaaS 는 하이퍼바이저 아래를 공급자가, 게스트 운영체제 위를 고객이 맡는다. 모델을 아는 것으로 끝나지 않고 각 계층의 책임을 문서화해 실제 담당자 이름까지 배정해야 공백이 없어진다. 서비스 모델을 바꾸는 것은 경계를 옮기는 것이지 없애는 것이 아니다.

    • A · SaaS 도 데이터와 접근 책임이 남는다.
    • B · 신뢰성 문제가 아니라 책임 배정 문제다.
    • C · 게스트 운영체제는 협약 범위가 아니다.

    11SASE

    왜 등장했는가

    전통 모델은 모든 트래픽을 본사 데이터센터로 끌어와(백홀, backhaul) 검사한 뒤 내보냈습니다. 그런데 사용자는 어디에나 있고 애플리케이션은 클라우드에 있습니다. 집에서 클라우드 서비스를 쓰는데 본사를 거쳐 가면 지연이 생기고 비효율적입니다. SASE(Secure Access Service Edge)는 네트워크 기능과 보안 기능을 클라우드에서 통합해 사용자와 가까운 엣지에서 정책을 집행합니다.

    영역구성 요소
    네트워크SD-WAN
    보안ZTNA(제로 트러스트 네트워크 접근)
    보안CASB(클라우드 접근 보안 중개)
    보안SWG(보안 웹 게이트웨이)
    보안FWaaS(서비스형 방화벽)

    보안 기능만 묶은 것을 SSE(Security Service Edge)라 부르며, 원본은 SASE = SD-WAN + SSE로 정리합니다. SASE는 네트워크 위치가 아니라 신원과 상황으로 접근을 결정하므로 제로 트러스트를 구현하는 실천적 아키텍처이기도 합니다.

    연결CASB의 네 축과 배치 방식은 D2.6 데이터 보안 통제, SD-WAN은 D4.1 네트워크 아키텍처, ZTNA와 VPN은 D4.3 안전한 통신 채널에서 다룹니다.

    원문 위치: D3.1.md §3 11) SASE, §4 SASE·SSE·ZTNA · 공식 개요 3.1 “Secure access service edge (SASE)”

    12원칙이 서로 부딪힐 때

    원칙들은 때로 충돌합니다.

    • 심층 방어 vs 단순성 — 계층을 늘리면 복잡해진다
    • 안전한 실패 vs 가용성 — 차단하면 서비스가 멈춘다
    • 최소권한 vs 업무 효율

    원본의 판단 기준은 보호 대상의 가치와 위험 수준입니다. 인명이 걸리면 안전 우선, 민감 데이터면 기밀성 우선입니다. 그리고 지나친 통제는 우회를 낳는다는 점을 항상 함께 고려합니다.

    판단 순서두 원칙이 부딪히는 설계 상황에서는 ① 보호 대상이 사람인지, 어떤 등급의 데이터인지 확인하고 ② 그 대상에 가장 중요한 속성(안전, 기밀성, 무결성, 가용성)을 정한 뒤 ③ 그 속성을 지키는 원칙을 우선하고 ④ 나머지 원칙은 우회가 생기지 않을 만큼 맞춥니다. 예를 들어 계층을 하나 더 넣으면 운영이 너무 복잡해져 설정 오류가 늘어날 정도라면, 단순성을 위해 그 계층을 빼는 것이 오히려 안전할 수 있습니다.

    연결CIA 사이의 균형은 D1.2 보안 개념 (CIA 등), 과잉 통제가 우회를 낳는 사례는 D2.2 자산 취급 요구사항·D2.1 자산 식별과 분류에서 봤습니다.

    복습

    계층을 여러 개 쌓았는데 같은 관리 계정으로 전부 바꿀 수 있다면 어떤 설계 문제가 남나요?

    설명 확인하기

    중복 통제가 하나의 실패 지점에 의존하고 있습니다. 관리자 권한을 분리하고 독립적으로 작동하는 경계와 승인·기록을 두어 한 권한의 실패가 모든 층으로 번지는지 검증합니다.

    15핵심 요약

    1. 공식 11원칙: 위협 모델링 / 최소권한 / 심층 방어 / 안전한 기본값 / 안전한 실패 / 직무 분리 / 단순하고 작게 / 제로 트러스트·신뢰하되 검증 / 설계 단계 프라이버시 / 공동 책임 / SASE.
    2. 보안은 설계에 내재시킨다. 나중에 덧붙이면 비용이 크게 늘거나 불가능하다.
    3. 위협 모델링은 다른 원칙을 어디에 적용할지 알려 준다.
    4. 최소권한 = 필요한 만큼, 필요한 기간만. 적시 권한(JIT), 적정 관리(JEA). 위반 증상은 권한 누적.
    5. 심층 방어 = 성격이 다른 통제의 중첩. 같은 통제를 여러 번 겹치면 같은 공격에 함께 뚫린다.
    6. 안전한 기본값 = 기본 거부. 사용자는 기본값을 바꾸지 않으므로 기본값이 실제 보안 수준을 정한다.
    7. Fail-closed = 데이터(기밀성) 우선, Fail-open = 인명 안전 우선. 기준은 보호 대상. 오류 메시지에 내부 정보를 노출하지 않는다.
    8. 직무 분리는 시스템이 강제해야 한다.
    9. 단순성 = 검증 가능성. TCB는 작게, 공격면은 최소로. Saltzer·Schroeder 원칙과 연결.
    10. 제로 트러스트: 네트워크 위치는 신뢰 근거가 아니다. PDP(결정) + PEP(집행) + 지속적 평가 + 마이크로세그멘테이션. 가치는 영향 범위 제한.
    11. Privacy by Design: 사전 예방, 기본값으로서의 프라이버시, 전 생애주기 보호. GDPR 제25조.
    12. 공동 책임: 데이터·IAM·설정은 모든 모델에서 고객 책임. IaaS(운영체제 이상) / PaaS(앱·데이터) / SaaS(데이터·IAM·설정).
    13. SASE = SD-WAN + SSE, SSE = ZTNA + CASB + SWG + FWaaS. 사용자 가까운 엣지에서 정책 집행.
    14. 원칙이 충돌하면 보호 대상의 가치와 위험으로 판단하고, 과잉 통제가 우회를 낳는다는 점을 함께 본다.
    원문 위치: D3.1.md §8 CISSP 시험 관점, §9 핵심 암기 요약(16항목). 원본의 “대체로 오답”, “틀린 적용” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다. 원본 §6의 NIST SP 800-160 Vol.1(시스템 보안 엔지니어링), OWASP Security Design Principles, ISO/IEC 27001/27002는 여기에 적어 둡니다.

    16주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Least Privilege · 최소권한

    업무 수행에 필요한 최소한의 권한만 필요한 기간만 부여하는 원칙.

    Defense in Depth · 심층 방어

    서로 다른 성격의 통제를 여러 계층에 중첩해 하나가 뚫려도 다음이 막게 하는 설계.

    Secure Defaults · 안전한 기본값

    설정하지 않았을 때 가장 안전한 상태가 되도록 하는 원칙. 기본 거부가 대표적이다.

    Fail Securely · 안전한 실패

    시스템 실패 시 안전한 상태로 떨어지게 하는 원칙. 보호 대상에 따라 차단(fail-closed) 또는 개방(fail-open)을 택한다.

    Economy of Mechanism · 메커니즘의 경제성

    보호 메커니즘을 작고 단순하게 유지해 검증 가능하게 하는 원칙.

    TCB — Trusted Computing Base · 신뢰 컴퓨팅 기반

    보안을 강제하는 하드웨어·소프트웨어·펌웨어의 집합. 작을수록 검증이 쉽다.

    Zero Trust · 제로 트러스트

    네트워크 위치를 신뢰의 근거로 삼지 않고 매 요청마다 명시적으로 검증하는 모델.

    PDP / PEP — Policy Decision Point / Policy Enforcement Point · 정책 결정 지점 / 정책 집행 지점

    Policy Decision Point 는 접근 허용 여부를 결정하고, Policy Enforcement Point 는 그 결정을 집행한다.

    Lateral Movement · 횡적 이동

    침해한 지점에서 내부의 다른 시스템으로 이동하는 공격 행위.

    Privacy by Design · 설계 단계 프라이버시

    프라이버시를 사후 추가가 아니라 설계에 내재시키는 원칙. 기본값으로서의 프라이버시를 포함한다.

    Shared Responsibility Model · 공동 책임 모델

    클라우드에서 제공자와 고객이 보안 책임을 나누는 체계. 데이터 처리와 접근 설정에서 고객이 맡는 부분이 있다. 구체적인 책임은 서비스 모델과 기능·계약 범위를 대조해 확인한다.

    SASE — Secure Access Service Edge · 보안 접근 서비스 엣지

    네트워크(SD-WAN)와 보안(ZTNA, CASB, SWG, FWaaS)을 클라우드 엣지에서 통합 제공하는 아키텍처.

    SSE — Security Service Edge · 보안 서비스 엣지

    SASE 중 보안 기능만을 묶은 것. SASE = SD-WAN + SSE.

    ZTNA — Zero Trust Network Access · 제로 트러스트 네트워크 접근

    신원과 상황 기반으로 애플리케이션 단위 접근을 허용하는 기술. 전통 VPN 의 광범위한 네트워크 접근을 대체한다.

    문항을 선택하면 본문의 지문과 해설로 이동합니다.

    1. 최소 권한 원칙이 요구하는 것은?
    2. 조직이 서로 다른 벤더의 방화벽 3대를 직렬로 배치하고 이를 심층 방어라 불렀다. 애플리케이션 계층 공격이 세 대를 모두 그대로 통과했다. 어떤 설계 오류인가?
    3. 병원 장비의 관리 콘솔이 권한 정책 서버에 연결하지 못하는 장애가 생겼다. 설계 회의에서 네 가지 안이 나왔다. 가장 적절한 것은?
    4. 보안 메커니즘을 단순하고 작게 유지하는 원칙이 중요한 이유는?
    5. IaaS 로 이전한 뒤 게스트 운영체제를 아무도 패치하지 않아 장애가 발생했다. 이것이 드러내는 것은?
    6. 새 클라우드 서비스의 설계 검토에서 다음이 발견되었다. ㉠ 사내 VPN으로 접속한 사용자는 모든 내부 애플리케이션에 접근할 수 있다. ㉡ 관리자 계정이 상시 전체 권한을 가진다. ㉢ 새 저장소의 기본 공개 범위가 “조직 외부 포함”이다. ㉣ SaaS 제공자가 보안을 책임진다며 사용자 권한 검토 절차를 두지 않았다. 각 항목이 어긋난 원칙을 바르게 짝지은 것은?
