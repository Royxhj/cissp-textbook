    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    보안 사고가 났을 때 “누구 책임인가”를 묻는 순간 답이 정해져 있어야 합니다. 누가 방향을 정하고, 누가 실행하고, 누가 책임지는지를 미리 정해 두는 틀이 거버넌스입니다. 통제나 도구를 고르는 일은 그다음입니다.

    공식 개요 세부 항목
    • Alignment of the security function to business strategy, goals, mission, and objectives
    • Organizational processes (e.g., acquisitions, divestitures, governance committees)
    • Organizational roles and responsibilities
    • Security control frameworks (e.g., ISO, NIST, COBIT, SABSA, PCI, FedRAMP)
    • Due care / due diligence

    1거버넌스란 무엇이고 경영과 어떻게 다른가

    왜 필요한가

    보안팀이 열심히 일해도 조직의 목표와 다른 방향이면 헛일이 됩니다. 반대로 방향만 정하고 아무도 감독하지 않으면 실행이 어긋나도 알 수 없습니다. 방향을 정하는 일과 실행하는 일을 구분해 각각 주인을 정해 두려는 것이 거버넌스입니다.

    쉬운 설명

    보안 거버넌스(Security Governance)는 보안이 조직의 비즈니스 목표를 지원하도록 방향을 설정하고 감독하는 체계입니다.

    구분거버넌스 Governance경영 Management
    질문무엇을 · 왜어떻게
    역할방향 설정 · 감독계획 · 실행
    주체이사회, 경영진CISO, 실무 조직

    거버넌스는 평가(Evaluate) → 지시(Direct) → 감시(Monitor)의 순환으로 작동합니다. 현재 상태와 위험을 평가하고, 그에 따라 방향을 지시하고, 지시대로 되고 있는지 감시한 뒤 다시 평가합니다.

    가상 예시한 회사의 제품 보안을 예로 들면,

    • 거버넌스: 이사회와 경영진이 “출시 제품에는 알려진 고위험 취약점을 남기지 않는다”는 방침을 정하고, 분기마다 달성 여부를 보고받는다. (무엇을·왜, 감시)
    • 경영: 보안 책임자와 개발 조직이 취약점 점검 도구를 고르고, 점검 일정을 짜고, 발견된 결함을 고친다. (어떻게)

    경영진이 스캐너 제품을 직접 고르고 있다면 거버넌스가 경영 영역으로 내려온 것이고, 실무자가 “고위험 취약점을 남겨도 되는지”를 스스로 정하고 있다면 경영이 거버넌스 영역을 대신하고 있는 것입니다.

    보충ISO/IEC 27001 심사 경험과 연결하면, 5절 리더십(최고경영자의 방침 수립과 역할 부여)과 9.3 경영검토가 거버넌스의 ‘지시’와 ‘감시’에 해당하고, 8절 운영이 경영에 해당합니다. 경영검토 기록을 심사에서 확인하는 것은 거버넌스의 순환이 실제로 도는지를 보는 일입니다. 원본이 관련 표준으로 드는 ISO/IEC 27014가 정보보안 거버넌스를 직접 다루는 표준입니다.

    원문 위치: D1.3.md §2, §3 거버넌스와 경영의 구분, §4 Security Governance, §6 ISO/IEC 27014 · 암기노트 K02 · 기존 문제 Q11 주제

    2최종 책임은 경영진: Accountability와 Responsibility

    쉬운 설명

    이 단원에서 가장 중요한 원칙입니다. 정보보안의 최종 책임은 경영진(senior management)에게 있습니다. 실무는 위임할 수 있지만 책임(accountability)은 위임되지 않습니다.

    영어뜻위임질문 (보충)
    Responsibility 실무 책임일을 실제로 수행할 의무위임된다“누가 하는가”
    Accountability 최종 책임결과에 대해 답해야 하는 의무위임되지 않는다“잘못되면 누가 답하는가”

    보충한국어로는 둘 다 ‘책임’이라 헷갈립니다. 일을 맡기는 순간 Responsibility는 넘어가지만, 맡긴 사람의 Accountability는 그대로 남습니다. 백업을 운영팀에 맡겨도, 클라우드 업체에 맡겨도, 백업이 없어서 생긴 결과에 답하는 것은 맡긴 쪽입니다. D1.2 보안 개념 (CIA 등)의 IAAA에 나오는 Accountability(책임추적성)는 같은 단어지만 ‘행위를 특정인에게 귀속시킬 수 있음’이라는 기술적 의미로 쓰인 것입니다.

    연결이 원칙이 다른 단원에서 반복되는 모습입니다.

    • D1.9 위험 관리: 잔여위험은 경영진이 공식적으로 수용해야 하고 실무자가 임의로 판단할 수 없다. 위험을 전가해도 법적 책임과 평판은 남는다.
    • D1.11 공급망 위험 관리: 업무는 위탁할 수 있지만 책임은 위탁할 수 없다.
    • D3.3 통제 선택 (RMF·CC): RMF의 Authorize 단계는 책임자가 잔여위험을 수용하고 운영을 승인하는 결정이며, 기술 담당자가 하는 것이 아니다.
    • D1.6 정책·표준·절차·지침: 표준의 예외를 승인하는 것은 위험 수용이고, 그 권한은 위험을 감당할 수 있는 직위에 있어야 한다.

    네 문장은 모두 “Accountability는 위임되지 않는다”를 각자의 맥락에서 말한 것입니다.

    보안은 비즈니스를 가능하게 하는 수단

    원본의 또 다른 원칙: 보안은 그 자체가 목적이 아니라 비즈니스를 가능하게 하는 수단(business enabler)입니다. 보안 기능은 조직의 사명(mission), 목표(goals), 세부목표(objectives), 전략(strategy)을 지원해야 합니다. 정렬이 깨진 전형적 신호는 다음과 같습니다.

    • 보안 통제가 핵심 업무 프로세스를 지속적으로 지연시킨다
    • 보안 투자 우선순위가 비즈니스 위험이 아니라 기술 유행을 따른다
    • 보안 지표가 비즈니스 언어로 보고되지 않는다

    원문 사례 — 보안 예산이 반려되는 이유. 보안팀이 “미패치 취약점 1,200건”을 근거로 예산을 요청했으나 반려되었습니다. 다음 분기에 “해당 취약점으로 고객 결제 데이터가 유출되면 과징금과 복구 비용이 얼마, 서비스 중단 시 일 매출 손실이 얼마”로 바꿔 보고하자 승인되었습니다. 경영진은 취약점 개수가 아니라 손실 가능 금액과 규제 위반 위험으로 판단합니다.

    연결기술 지표를 금액으로 바꾸는 도구가 D1.9 위험 관리의 정량 분석(SLE·ALE)이고, 같은 단원이 경영진 보고는 기술 지표가 아니라 비즈니스 영향으로 번역해야 한다고 다시 말합니다. 첫 번째 신호(통제가 업무를 지연)는 D1.2 보안 개념 (CIA 등)의 “CIA는 균형의 문제”와 같은 이야기를 조직 차원에서 본 것입니다.

    CISSP 관점“누가 궁극적으로 책임지는가”를 묻는 상황에서는 일을 수행한 사람(CISO, 보안팀, 외주 업체)과 결과에 답하는 사람을 구분합니다. 원본은 답이 경영진이라고 정리합니다. 다만 질문이 “누가 수행하는가”, “누가 분류를 결정하는가”처럼 다른 역할을 묻는 것인지 먼저 확인하세요(4절). 책임의 종류에 따라 답이 달라집니다.

    이해 확인 1 · 자작 상황 문제 (실제 시험 문제 아님)

    한 회사가 고객 데이터 보관을 클라우드 업체에 맡겼고, 계약서에 보안 운영은 업체가 수행한다고 명시했다. 업체의 설정 실수로 고객 데이터가 유출되었다. 고객과 규제기관에 대한 최종 책임에 관해 가장 적절한 설명은?

    1. 보안 운영을 맡은 클라우드 업체가 최종 책임을 진다.
    2. 계약을 담당한 구매팀이 최종 책임을 진다.
    3. 데이터를 맡긴 회사의 경영진에게 최종 책임이 남는다. 업체에는 계약에 따른 책임을 물을 수 있다.
    4. CISO가 최종 책임을 진다.
    정답과 해설 보기

    정답 C. 위임된 것은 실무(Responsibility)입니다. 고객과 규제기관 앞에서 답해야 하는 Accountability는 데이터를 맡긴 조직, 그 조직의 경영진에게 남습니다.

    • A: 업체는 계약상 책임을 지지만, 그것이 위탁한 조직의 책임을 없애지 않습니다.
    • B: 구매팀은 실무를 수행했을 뿐입니다.
    • D: CISO는 보안 프로그램을 설계·운영하고 경영진에게 보고하는 역할입니다. 최종 책임의 자리는 아닙니다.

    3정책 문서 계층

    왜 필요한가

    경영진이 정한 방향이 실무자의 손끝까지 내려가려면 문서로 옮겨져야 합니다. 한 문서에 방향과 세부 절차를 다 적으면 기술이 바뀔 때마다 최고 경영진 승인을 다시 받아야 합니다. 그래서 잘 바뀌지 않는 것(방향)과 자주 바뀌는 것(세부)을 층으로 나눕니다.

    쉬운 설명

    문서성격원문 예시답하는 질문 (보충)
    정책 Policy최상위 의무, 강제정보보안 정책무엇을 왜 해야 하는가
    표준 Standard강제, 구체적암호 알고리즘 규격무엇을 써야 하는가
    기준선 Baseline강제 최소 수준서버 보안 설정 기준최소 어디까지 해야 하는가
    지침 Guideline권고, 선택적재택근무 보안 권고어떻게 하면 좋은가
    절차 Procedure강제, 단계별계정 발급 절차어떤 순서로 하는가

    지침만 선택적이고 나머지는 강제입니다. 그리고 정책은 경영진 승인이 있어야 효력을 가지며, 정기 검토와 구성원 교육이 뒤따라야 합니다.

    가상 예시“저장 데이터는 암호화한다”가 층을 내려가는 모습입니다.

    • 정책: 민감 정보는 저장 시 암호화하여 보호한다.
    • 표준: 저장 암호화에는 AES-256을 사용한다.
    • 기준선: 모든 업무용 노트북은 디스크 전체 암호화가 켜져 있어야 한다.
    • 절차: 새 노트북 지급 시 ① 암호화 활성화 ② 복구 키를 관리 시스템에 등록 ③ 자산 대장에 기록.
    • 지침: 이동식 저장매체는 가급적 쓰지 않고, 써야 하면 암호화 기능이 있는 제품을 권장한다.

    연결다섯 문서 각각의 상세와 수명주기(개발 → 승인 → 배포 → 교육·수령 확인 → 집행 → 검토 → 폐기), 표준을 지킬 수 없을 때의 예외 처리는 D1.6 정책·표준·절차·지침에서 다룹니다. 문서로 정한 기준선을 실제 시스템에 적용하고 어긋남을 찾는 일은 D2.3 안전한 프로비저닝과 D7.3 구성 관리의 구성 관리로 이어집니다. 경영진 승인·교육·제재의 세 조건은 D1.1 전문가 윤리의 조직 윤리 강령에서 본 것과 같습니다.

    CISSP 관점문서 종류를 가르는 상황에서는 ① 반드시 지켜야 하는가(아니면 지침) ② 방향인가 구체적 규격인가 최소선인가 순서인가를 봅니다. “먼저 할 일”을 묻는 상황에서 원본은 기술 구현보다 정책 승인이 앞선다고 정리합니다. 근거가 되는 정책 없이 통제부터 넣으면 집행할 근거가 없기 때문입니다. 다만 지문에서 정책이 이미 있다면 다음 단계가 답이 됩니다.

    4조직 역할과 책임

    쉬운 설명

    역할하는 일하지 않는 일
    Senior Management 경영진정보보안의 최종 책임. 정책 승인, 자원 배분, 위험 수용 결정
    CISO / 보안 책임자보안 프로그램을 설계·운영하고 경영진에게 보고최종 책임을 대신 지지 않는다
    Data Owner 데이터 소유자보통 해당 업무의 관리자. 데이터 분류를 결정하고 접근 권한을 승인일상 운영. 책임을 위임하지 않는다
    Data Custodian 데이터 관리자소유자가 정한 바에 따라 일상적 보호 조치를 수행. 백업, 패치, 복구분류 결정
    System Owner 시스템 소유자시스템의 보안 상태와 통제 구현에 책임
    Data Controller / Processor개인정보 보호 맥락의 역할. Controller는 처리 목적과 수단을 결정, Processor는 Controller의 지시에 따라 처리
    User 사용자정책을 준수하고 최소권한 범위에서 자산을 사용
    Auditor 감사인통제가 설계대로 작동하는지 독립적으로 검증통제의 설계·운영

    소유자와 관리자: 결정하는 사람과 수행하는 사람

    가장 자주 헷갈리는 쌍입니다. 구분 기준은 결정과 수행입니다.

    보충왜 IT 부서가 아니라 업무 관리자가 소유자인지 생각해 보면 구분이 쉬워집니다. 분류는 “이 데이터가 새거나 바뀌면 사업에 얼마나 큰 피해가 나는가”로 정하는데, 그것을 아는 사람은 그 데이터로 일하는 업무 책임자입니다. IT 부서는 데이터가 어디에 저장되고 어떻게 백업되는지를 알지만, 내용의 사업적 가치를 판단할 위치가 아닙니다. 그래서 IT는 대개 Custodian입니다. ‘소유자’라는 말 때문에 DB 관리자를 떠올리기 쉬운데, 서버를 가진 사람이 아니라 데이터의 가치에 답하는 사람입니다.

    가상 예시현장 장비에서 수집되는 사용 기록 데이터가 있다고 합시다.

    • 이 데이터를 사업에 쓰는 서비스 사업부장 → Data Owner. “대외비로 분류한다, 서비스 엔지니어에게만 열람을 허용한다”를 결정.
    • 데이터가 저장된 DB를 운영하는 인프라팀 → Data Custodian. 그 결정에 따라 접근 권한을 설정하고 백업하고 패치.
    • 인프라팀이 “용량이 크니 등급을 낮춰 저렴한 저장소로 옮기자”고 스스로 정했다면 → Custodian이 Owner의 결정을 대신한 것으로 역할이 어긋난 것.

    연결소유자가 분류를 어떤 기준으로 정하는지는 D2.1 자산 식별과 분류에서, 소유권과 프로비저닝은 D2.3 안전한 프로비저닝에서, Controller·Processor를 포함해 공식 개요가 명시한 데이터 역할은 D2.4 데이터 생애주기에서 다룹니다. 소유자가 승인한 접근 권한이 실제로 맞게 유지되는지 주기적으로 확인하는 일은 D5.5 프로비저닝 생애주기의 계정 접근 검토입니다.

    감사인의 독립성

    감사인은 통제를 설계하거나 운영하지 않습니다. 원본 암기노트의 설명: 감사인은 자신이 설계하거나 운영한 통제를 감사할 수 없습니다. 이해충돌로 객관성이 훼손되기 때문이며, 내부 감사인에게도 똑같이 적용되고 경영진 승인으로 면제되지 않습니다.

    연결D6.1 평가·테스트·감사 전략은 독립성을 “자기 업무를 자기가 검증하면 신뢰할 수 없다”로 설명하고, 독립성이 있다/없다가 아니라 정도의 문제라고 덧붙입니다. 또 감사 기능은 통상 경영진이 아닌 이사회나 감사위원회에 보고해 피감 대상의 영향을 받지 않게 합니다. 1절의 거버넌스 ‘감시’가 제대로 작동하려면 감시자가 감시 대상 아래에 있으면 안 된다는 뜻입니다. ISO/IEC 27001 내부심사에서 심사원이 자기 업무를 심사하지 않도록 하는 것과 같은 원칙입니다.

    이해 확인 2 · 자작 상황 문제

    인사팀장이 관리하는 급여 데이터가 IT 운영팀의 서버에 저장되어 있다. 새 급여 분석 프로젝트를 위해 외부 컨설턴트에게 이 데이터의 열람 권한을 줄지 정해야 한다. 누가 결정하고 누가 설정하는가?

    1. IT 운영팀이 결정하고 설정한다. 서버를 운영하기 때문이다.
    2. 인사팀장이 결정하고, IT 운영팀이 그 결정에 따라 권한을 설정한다.
    3. 보안팀이 결정하고 인사팀이 설정한다.
    4. 컨설턴트가 필요한 범위를 스스로 정하고 IT 운영팀이 설정한다.
    정답과 해설 보기

    정답 B. 인사팀장이 Data Owner로서 접근을 승인하고, IT 운영팀이 Data Custodian으로서 수행합니다.

    • A: 서버를 운영한다는 것은 Custodian이라는 뜻입니다. 결정권이 아닙니다.
    • C: 보안팀은 기준과 검토를 제공할 수 있지만, 데이터의 가치와 접근 필요성을 판단하는 주체는 소유자입니다.
    • D: 접근을 받는 사람이 자기 권한을 정하는 것은 승인이 아닙니다.

    이해 확인 3 · 자작 상황 문제

    작년에 접근 통제 절차를 직접 설계한 보안 담당자가 올해 내부 감사팀으로 옮겼다. 감사팀장이 인력이 부족하니 그 담당자에게 접근 통제 영역의 감사를 맡기려 하고, 경영진도 괜찮다고 했다. 가장 적절한 판단은?

    1. 그 영역을 가장 잘 아는 사람이므로 맡기는 것이 효율적이다.
    2. 경영진이 승인했으므로 문제가 없다.
    3. 자신이 설계한 통제를 감사하게 되어 독립성이 훼손되므로, 그 영역은 다른 감사인에게 맡긴다.
    4. 감사 보고서에 본인이 설계자였다는 사실만 적으면 된다.
    정답과 해설 보기

    정답 C.

    • A: 잘 아는 것과 객관적으로 평가할 수 있는 것은 다릅니다. 자기 설계의 결함을 스스로 지적하기 어렵습니다.
    • B: 독립성 요건은 경영진 승인으로 면제되지 않습니다.
    • D: 사실을 밝히는 것은 필요하지만 이해충돌 자체를 없애지 못합니다.

    5거버넌스 위원회와 조직 변화: 인수 · 매각 · 아웃소싱

    보안 운영위원회

    보안 운영위원회(Security Steering Committee)는 여러 부서 대표가 참여해 보안 우선순위와 자원 배분을 조율하는 거버넌스 기구입니다. 보안이 IT 부서만의 일이 되지 않도록 하는 장치입니다.

    조직이 바뀔 때 왜 보안이 문제가 되는가

    공식 개요 1.3은 조직 프로세스의 예로 인수, 매각, 거버넌스 위원회를 듭니다. 회사가 합쳐지거나 갈라질 때는 시스템·사람·데이터의 경계가 한꺼번에 바뀌고, 그 틈에서 통제가 빠집니다.

    상황해야 할 일이유 · 흔한 실패
    인수 Acquisition인수 전 대상 기업의 보안 수준을 실사(due diligence). 인수 후에는 통합 전에 보안 기준선을 맞춘다미해결 침해, 규제 위반 이력, 기술 부채가 인수 후 그대로 승계된다
    매각·분할 Divestiture데이터 분리, 접근 권한 회수, 라이선스와 지식재산 정리, 공유 인프라 분리분리된 조직 인원의 계정이 그대로 남는 것이 가장 흔한 실패
    아웃소싱·제3자 계약보안 요구사항을 계약서에 명시하고 감사 권한(right to audit)을 확보계약에 없으면 공급자의 통제를 확인할 방법이 없다

    원문 사례 — 인수 후 드러난 미공개 침해. A사가 B사를 인수한 뒤, B사가 협상 중에 이미 침해를 알고 있었으나 공개하지 않은 사실이 드러났습니다. 침해 대응 비용과 규제 책임은 인수한 A사가 부담했습니다. 인수 전 보안 실사에서 침해 이력, 규제 조치 이력, 로그 보존 상태를 확인해야 합니다.

    원문 사례 — 분할 이후 남은 계정. 사업부 매각 6개월 뒤 내부 감사에서, 분리된 조직 직원 40여 명의 계정이 본사 시스템에 활성 상태로 남아 있는 것이 발견되었습니다. 매각 체크리스트에 접근 권한 회수가 빠져 있었습니다.

    판단 순서조직 변화 상황을 읽는 순서입니다.

    1. 경계가 어느 방향으로 바뀌는지 본다. 들어오는가(인수), 나가는가(매각), 밖에 맡기는가(아웃소싱).
    2. 들어오는 것은 들이기 전에 확인한다. 인수에서 ‘실사’는 계약 전, ‘기준선 맞추기’는 네트워크·계정 통합 전이다. 순서가 바뀌면 상대의 문제가 내 환경으로 들어온다.
    3. 나가는 것은 연결을 끊는다. 매각에서는 계정·데이터·공유 인프라의 분리가 먼저다.
    4. 맡기는 것은 확인할 권리를 계약에 넣는다. 계약 뒤에는 넣기 어렵다.

    연결세 상황 모두 다른 단원의 원리가 조직 단위로 일어난 것입니다.

    • 인수 전 실사는 D1.1 전문가 윤리의 Due Diligence(하기 전에 알아본다)입니다. 상대 기업의 위험이 승계된다는 것은 D1.9 위험 관리의 용어로 그 위험을 떠안는 것이므로, 알고 수용하거나 가격·조건에 반영해야 합니다.
    • 매각 시 계정 회수는 D5.5 프로비저닝 생애주기의 디프로비저닝이 수십 명 단위로 한꺼번에 일어나는 경우입니다. 남은 계정은 그 단원에서 말하는 고아 계정(orphaned account)이 됩니다. D1.8 인적 보안의 퇴사 처리와도 같은 구조입니다.
    • 아웃소싱의 계약 요구사항과 감사 권한은 D1.11 공급망 위험 관리에서 공급망 전체로 확장됩니다. 직접 감사가 어려울 때 제3자 감사 보고서를 쓰는 방법은 D6.1 평가·테스트·감사 전략에 있습니다.

    인수한 서비스에서 책임과 증거가 이동하는 과정

    가상 예시조직이 외부 회사를 인수하면서 고객용 SaaS를 그대로 운영하기로 했습니다. 목표는 서비스 유지지만, 누가 접근을 승인하고 공급자 사고를 보고하는지 계약과 운영 문서에 나오지 않습니다.

    판단 순서

    1. 업무 책임자와 통합 목표를 먼저 정하고, 서비스 및 정보 소유권을 매핑합니다.
    2. 공급자에게 위임한 통제에는 어떤 증거를 언제 받고 누가 검토할지 정합니다.
    3. 정보 소유자는 접근 조건을 승인하고 운영자는 적용합니다.
    4. 조직의 위험 책임자가 미해결 사항과 수용 근거를 기록합니다.

    조건을 바꿔 보기. 회사를 매각하는 경우라면 자료의 이전·보존 범위, 공유 접근 회수와 서비스 종료 책임이 먼저 드러납니다. 인수와 매각 모두 계약 완료일이 통제 전환 완료일과 같지는 않습니다.

    이해 확인 4 · 자작 상황 문제

    회사가 소프트웨어 업체를 인수하기로 하고 계약 체결을 2주 앞두고 있다. 사업 부서는 인수 직후 두 회사의 사내 네트워크와 계정 체계를 바로 연결해 협업을 시작하고 싶어 한다. 보안 책임자가 가장 먼저 추진해야 할 것은?

    1. 인수 직후 바로 연결하고, 문제가 생기면 그때 대응한다.
    2. 계약 전에 대상 업체의 침해 이력·규제 조치 이력·통제 수준을 실사하고, 그 결과를 경영진의 인수 판단에 제공한다.
    3. 인수 후 대상 업체 직원 전원에게 보안 교육을 실시한다.
    4. 대상 업체의 모든 시스템을 자사 표준 제품으로 교체하는 계획을 세운다.
    정답과 해설 보기

    정답 B. 지금은 계약 전이므로 ‘들이기 전에 확인’ 단계입니다. 실사 결과는 인수 여부·가격·조건을 정하는 경영진의 결정 재료가 됩니다.

    • A: 상대의 미해결 문제가 자사 환경으로 그대로 들어옵니다. 통합은 기준선을 맞춘 뒤입니다.
    • C, D: 필요할 수 있지만 인수 뒤의 일이고, 무엇이 문제인지 모른 채 세운 계획입니다.

    조건을 바꿔 보기: 이미 계약이 끝났고 실사도 마쳤다면, 다음으로 적절한 것은 네트워크·계정 통합 전에 보안 기준선을 맞추는 일입니다.

    거버넌스가 “무엇을 해야 하는가”를 정할 때 백지에서 시작하지 않으려고 쓰는 틀입니다. 이름이 많지만 각자 다루는 층이 다릅니다. 그 층을 구분하는 것이 목표입니다.

    프레임워크원본의 설명다루는 층 (보충)
    ISO/IEC 27001정보보안 경영시스템(ISMS) 요구사항. 인증이 가능한 국제 표준. 27002는 통제 실행 지침관리 체계
    NIST Cybersecurity Framework 2.06개 기능: Govern, Identify, Protect, Detect, Respond, Recover. 2024년 2.0에서 Govern이 추가됨보안 활동의 전체 지도
    NIST SP 800-37 RMF연방 시스템의 위험관리 수명주기. Prepare, Categorize, Select, Implement, Assess, Authorize, Monitor시스템 단위의 절차
    COBIT (ISACA)IT 거버넌스와 관리 프레임워크. 비즈니스 목표와 IT 목표의 연결, 거버넌스와 경영의 분리를 강조IT 거버넌스
    SABSA비즈니스 주도(business-driven) 보안 아키텍처 프레임워크. 계층별로 What/Why/How/Who/Where/When을 묻는 매트릭스 구조아키텍처 설계
    PCI DSS카드 결제 산업의 보안 표준. 법률이 아니라 계약상 의무특정 데이터 보호
    FedRAMP미국 연방기관이 사용하는 클라우드 서비스의 보안 평가·승인 프로그램클라우드 조달 승인

    헷갈리는 지점 세 가지

    • 인증이 되는가. ISO/IEC 27001은 인증 취득이 가능하고, NIST CSF는 인증 체계가 아닙니다.
    • 법인가 계약인가. PCI DSS는 카드 브랜드와의 계약에 근거한 산업 표준입니다. 원본 암기노트에 따르면 미준수 제재는 법적 처벌이 아니라 과태료나 카드 처리 권한 제한입니다.
    • CSF의 여섯 번째 기능. Govern이 새로 추가되어 다섯 개에서 여섯 개가 되었습니다. 이 단원의 주제인 거버넌스가 프레임워크의 한 기능으로 올라온 것입니다.

    보충COBIT이 “거버넌스와 경영의 분리”를 강조한다는 설명은 1절의 표와 같은 구분입니다. COBIT의 거버넌스 영역 이름이 평가·지시·감시(Evaluate, Direct and Monitor)라는 점을 알면 1절의 순환과 한 번에 묶입니다. 그리고 PCI DSS가 법률이 아니라고 해서 선택 사항이라는 뜻은 아닙니다. 카드 결제를 처리하려면 계약상 지켜야 하고, 어기면 사업을 계속하기 어려울 수 있습니다. 구분하는 이유는 강제의 근거와 제재의 종류가 다르기 때문입니다.

    연결프레임워크는 세 단원에 나뉘어 나옵니다. 이 단원은 통제·거버넌스 프레임워크를, D1.9 위험 관리는 위험 평가·관리 프레임워크(NIST SP 800-30/39, ISO/IEC 27005, ISO 31000, FAIR, COSO ERM)와 상황별로 고르는 기준을, D3.3 통제 선택 (RMF·CC)은 RMF의 각 단계와 제품 평가 기준(Common Criteria)을 다룹니다. 법률과 계약의 차이는 D1.4 법률·규제·컴플라이언스가 정리합니다(법률·규제 / 계약 / 산업 표준, 위반 결과가 각각 다름).

    CISSP 관점프레임워크를 고르는 상황에서는 지문이 요구하는 것이 ① 인증·보증인지 ② 거버넌스 구조인지 ③ 아키텍처 설계인지 ④ 특정 데이터에 대한 의무인지를 먼저 가립니다. 선택지가 PCI DSS를 “법적 요구사항”이라고 서술하면 근거가 틀린 것입니다. 다만 지문이 특정 국가 법률이 PCI DSS 준수를 요구한다고 명시했다면 그 지문 안에서는 다르게 읽어야 합니다.

    원문 위치: D1.3.md §3 주요 통제 프레임워크, §4 ISMS, §5 셋째 표, §6 · 암기노트 K05, K06, K07 · 기존 문제 Q04, Q05, Q10 주제 · NIST CSF 2.0의 6개 기능과 Govern 추가는 원본 서술이며 이번에 NIST 원문을 다시 대조하지는 않았습니다.

    7Due Care · Due Diligence와 경영진의 법적 책임

    쉬운 설명

    D1.1 전문가 윤리에서 정의한 두 개념이 여기서 경영진의 책임과 묶입니다. Due Diligence는 조치 전후의 조사·검증이고, Due Care는 그 결과에 따라 실제로 합리적인 조치를 수행하는 것입니다.

    • 태만(Negligence) — 경영진이 합리적인 사람이라면 취했을 조치를 하지 않으면 태만이 되어 법적 책임으로 이어질 수 있다.
    • 신중한 사람 원칙(Prudent Person Rule) — 합리적이고 신중한 사람이라면 같은 상황에서 어떤 조치를 취했을지를 기준으로 경영진의 책임을 판단하는 원칙.
    • 하류 책임(Downstream Liability) — 자사의 취약한 시스템이 제3자 공격에 이용되어 타인에게 손해를 입히면 질 수 있는 법적 책임.

    보충신중한 사람 원칙의 요점은 기준이 “완벽했는가”가 아니라 “합리적이었는가”라는 점입니다. 사고가 났다는 사실만으로 태만이 되지는 않습니다. 같은 처지의 신중한 경영자라면 했을 조사(Due Diligence)와 조치(Due Care)를 했고 그 기록이 남아 있다면, 사고가 나도 책임을 다했다고 주장할 수 있습니다. 2절의 Accountability가 “결과에 답할 의무”라면, 이 원칙은 “어떻게 답하면 되는가”의 기준입니다. 위험 평가 기록, 경영검토 회의록, 위험 수용 승인서가 법적으로도 의미를 갖는 이유입니다.

    가상 예시하류 책임의 모습입니다. 한 회사의 원격 지원 서버가 오래 방치된 결함으로 장악되었고, 공격자가 그 서버를 발판으로 이 회사의 고객사 여러 곳에 침입했습니다. 이 회사는 직접 공격하지 않았지만, 알려진 결함을 합리적인 기간 안에 고치지 않아 남의 피해 경로가 되었다는 점에서 책임을 물을 수 있습니다. ‘하류’는 피해가 자사에서 고객·협력사 쪽으로 흘러 내려간다는 뜻입니다.

    연결D1.9 위험 관리의 “통제 가치가 음수면 경제적으로는 도입하지 않는다”에 예외가 붙는 이유가 이 절입니다. 다른 조직들이 당연히 하는 조치를 비용 때문에 뺐다면, 사고 뒤에 신중한 사람 원칙으로 판단받게 됩니다. 공식 위험 수용에서는 위험을 분석하고 판단 근거를 기록해 권한자의 승인을 받은 뒤 주기적으로 재검토합니다. 기록과 승인은 당시 판단을 보여 줍니다. 실제 조치가 상황에 비추어 합리적이었는지와 법적 의무를 충족했는지는 별도로 확인합니다. 하류 책임은 D1.11 공급망 위험 관리의 공급망 위험을 공급자 쪽에서 본 모습이기도 합니다.

    이해 확인 5 · 자작 상황 문제

    침해 사고 뒤 조사에서 두 회사의 상황이 드러났다. 갑 회사는 해당 취약점의 위험을 분석해 보완 통제를 적용하고, 남은 위험을 경영진이 문서로 승인했으며 재검토 일자를 정해 두었다. 을 회사는 같은 취약점을 알고 있었지만 아무 분석이나 기록 없이 두었다. 두 회사에 대한 평가로 가장 적절한 것은?

    1. 둘 다 사고가 났으므로 똑같이 태만이다.
    2. 갑 회사는 합리적인 조사와 조치를 했다는 근거가 있고, 을 회사는 신중한 사람이라면 했을 조치를 하지 않아 태만으로 평가될 가능성이 높다.
    3. 을 회사는 비용을 아꼈으므로 더 합리적으로 판단한 것이다.
    4. 갑 회사는 위험을 알고도 남겨 두었으므로 을 회사보다 책임이 무겁다.
    정답과 해설 보기

    정답 B. 기준은 결과가 아니라 과정의 합리성입니다.

    • A: 사고 발생만으로 태만이 되지 않습니다.
    • C: 분석 없이 조치하지 않은 것은 판단이 아니라 방치입니다.
    • D: 분석과 권한자 승인은 공식 위험 수용 절차의 일부입니다. 필요한 조치가 합리적이었는지는 판단 근거와 당시 상황을 함께 봅니다.

    종합 · 자작 상황 문제

    새로 부임한 보안 책임자가 조직을 살펴보니 다음과 같았다. ㉠ 정보보안 정책 문서가 3년 전 실무자가 작성한 초안 상태로, 경영진 승인 기록이 없다. ㉡ 데이터 분류는 DB 관리자가 저장 비용을 기준으로 정하고 있다. ㉢ 보안 현황은 “차단한 공격 건수”로만 보고된다. 가장 먼저 바로잡아야 할 것과 그 이유로 적절한 것은?

    1. ㉢ — 최신 보안 관제 도구를 도입해 더 많은 지표를 수집한다.
    2. ㉡ — DB 관리자에게 분류 교육을 시켜 더 정확히 분류하게 한다.
    3. ㉠ — 정책을 정비해 경영진 승인을 받는다. 승인된 정책이 있어야 역할(㉡)과 보고(㉢)를 바로잡을 근거가 생긴다.
    4. 세 가지 모두 실무 문제이므로 보안팀 내부에서 조용히 처리한다.
    정답과 해설 보기

    정답 C. 세 문제는 각각 정책의 효력(3절), 소유자와 관리자의 역할(4절), 비즈니스 언어 보고(2절)에 해당합니다. 그중 정책 승인이 나머지의 근거가 됩니다. 정책이 역할을 정하고, 역할이 정해져야 누가 분류하고 누가 무엇을 보고받는지가 정해집니다.

    • B: 문제는 DB 관리자의 실력이 아니라 분류를 결정할 위치가 아닌 사람이 결정하고 있다는 점입니다.
    • D: 셋 다 경영진이 관여해야 하는 거버넌스 문제입니다.

    복습

    경영진이 보안 운영을 공급자에게 맡겼을 때 남는 의무는 무엇인가요?

    설명 확인하기

    공급자가 수행을 맡아도 조직은 정책과 위험을 결정하고 통제 결과를 감독합니다. 데이터 소유자가 접근을 승인하고 관리자는 이를 적용하듯, 결정과 실행을 구분하면 책임이 어디에 남는지 알 수 있습니다.

    10핵심 요약

    1. 거버넌스는 무엇을·왜(방향 설정·감독), 경영은 어떻게(계획·실행). 거버넌스는 평가 → 지시 → 감시로 순환한다.
    2. 정보보안의 최종 책임은 경영진. 실무(responsibility)는 위임되지만 책임(accountability)은 위임되지 않는다.
    3. 보안은 비즈니스를 가능하게 하는 수단. 투자 근거와 보고는 비즈니스 영향으로 제시한다.
    4. 문서 계층에서 지침만 권고, 정책·표준·기준선·절차는 강제. 정책은 경영진 승인이 있어야 효력을 가진다.
    5. Data Owner가 분류를 결정하고 접근을 승인, Custodian은 수행(백업·패치·복구).
    6. 감사인은 독립성을 유지한다. 자신이 설계·운영한 통제를 감사하지 않는다.
    7. 인수는 사전 실사와 통합 전 기준선 맞추기, 매각은 접근 권한 회수와 데이터 분리, 아웃소싱은 계약상 요구사항과 감사 권한.
    8. ISO/IEC 27001 = 인증 가능한 ISMS, NIST CSF 2.0 = Govern·Identify·Protect·Detect·Respond·Recover, COBIT = IT 거버넌스, SABSA = 비즈니스 주도 아키텍처, PCI DSS = 계약상 의무.
    9. Due Diligence는 알아보는 것, Due Care는 하는 것. 합리적 조치를 하지 않으면 태만이며 기준은 신중한 사람 원칙. 남의 피해 경로가 되면 하류 책임.
    원문 위치: D1.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약(10항목). 원본의 “항상 / 자주 나온다 / 오답 신호”류의 표현은 판단 기준으로 바꿔 적었습니다.

    11주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Security Governance · 보안 거버넌스

    보안이 비즈니스 목표를 지원하도록 방향을 설정하고 감독하는 체계. 평가-지시-감시로 순환한다.

    Due Care / Due Diligence · 상당한 주의 / 상당한 실사

    Due Care 는 합리적 조치의 수행, Due Diligence 는 사전·지속적 조사와 검증.

    Prudent Person Rule · 신중한 사람 원칙

    합리적이고 신중한 사람이라면 같은 상황에서 어떤 조치를 취했을지를 기준으로 경영진의 책임을 판단하는 원칙.

    Downstream Liability · 하류 책임

    자사 시스템의 취약점이 타 조직 피해의 경로가 되었을 때 지는 법적 책임.

    Data Owner / Data Custodian · 데이터 소유자 / 데이터 관리자

    소유자는 분류를 결정하고 접근을 승인하는 업무 관리자, 관리자는 소유자의 결정에 따라 일상 보호 조치를 수행하는 실무자.

    Security Steering Committee · 보안 운영위원회

    여러 부서가 참여해 보안 우선순위와 자원 배분을 조율하는 거버넌스 기구.

    ISMS — Information Security Management System · 정보보안 경영시스템

    ISO/IEC 27001이 규정하는 체계. 인증 취득이 가능하다.

    Divestiture · 매각·분할

    사업부나 자회사를 분리하는 것. 데이터 분리와 접근 권한 회수가 핵심 보안 과제다.

    Right to Audit · 감사 권한

    제3자 계약에서 공급자의 보안 통제를 검증할 수 있도록 계약서에 명시하는 권리.

    연습문제 6개

    문항을 선택하면 본문의 지문과 해설로 이동합니다.

    1. 한 회사가 고객 데이터 보관을 클라우드 업체에 맡겼고, 계약서에 보안 운영은 업체가 수행한다고 명시했다. 업체의 설정 실수로 고객 데이터가 유출되었다. 고객과 규제기관에 대한 최종 책임에 관해 가장 적절한 설명은?
    2. 인사팀장이 관리하는 급여 데이터가 IT 운영팀의 서버에 저장되어 있다. 새 급여 분석 프로젝트를 위해 외부 컨설턴트에게 이 데이터의 열람 권한을 줄지 정해야 한다. 누가 결정하고 누가 설정하는가?
    3. 작년에 접근 통제 절차를 직접 설계한 보안 담당자가 올해 내부 감사팀으로 옮겼다. 감사팀장이 인력이 부족하니 그 담당자에게 접근 통제 영역의 감사를 맡기려 하고, 경영진도 괜찮다고 했다. 가장 적절한 판단은?
    4. 회사가 소프트웨어 업체를 인수하기로 하고 계약 체결을 2주 앞두고 있다. 사업 부서는 인수 직후 두 회사의 사내 네트워크와 계정 체계를 바로 연결해 협업을 시작하고 싶어 한다. 보안 책임자가 가장 먼저 추진해야 할 것은?
    5. 침해 사고 뒤 조사에서 두 회사의 상황이 드러났다. 갑 회사는 해당 취약점의 위험을 분석해 보완 통제를 적용하고, 남은 위험을 경영진이 문서로 승인했으며 재검토 일자를 정해 두었다. 을 회사는 같은 취약점을 알고 있었지만 아무 분석이나 기록 없이 두었다. 두 회사에 대한 평가로 가장 적절한 것은?
    6. 새로 부임한 보안 책임자가 조직을 살펴보니 다음과 같았다. ㉠ 정보보안 정책 문서가 3년 전 실무자가 작성한 초안 상태로, 경영진 승인 기록이 없다. ㉡ 데이터 분류는 DB 관리자가 저장 비용을 기준으로 정하고 있다. ㉢ 보안 현황은 “차단한 공격 건수”로만 보고된다. 가장 먼저 바로잡아야 할 것과 그 이유로 적절한 것은?
