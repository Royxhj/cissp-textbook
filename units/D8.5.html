    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    원본은 이 단원을 이렇게 시작합니다. “안전하게 코딩하라”는 지침이 아니다. 실효성 있는 코딩 표준은 무엇을 하지 말고 무엇을 대신 쓸지 구체적으로 지정하고, 자동으로 강제되며, 안전한 선택이 기본값이 되게 만듭니다. 공식 개요 8.5는 소스 코드 수준의 약점과 취약점, API 보안, 안전한 코딩 실천, 소프트웨어 정의 보안을 듭니다. 도메인 8의 마지막 단원이자, 앞 단원에서 반복해서 “구조적 대응”이라고 부른 것의 구체적인 내용입니다.

    2주입과 출력 인코딩

    주입의 공통 원리는 데이터가 코드나 명령으로 해석되는 것입니다.

    유형데이터가 섞여 들어가는 대상
    SQL 주입SQL 질의
    명령 주입OS 명령
    LDAP 주입디렉터리 검색 필터
    XPath/XML 주입, 템플릿 주입질의 표현식, 서버 측 템플릿
    로그 주입로그 항목
    크로스 사이트 스크립팅(XSS)HTML/JavaScript 문맥

    올바른 대응에는 순서가 있습니다.

    1. 구조적 분리: 파라미터화 질의(prepared statement), 명령 실행을 API 호출로 대체. 데이터와 코드를 애초에 섞지 않습니다.
    2. 문맥에 맞는 인코딩·이스케이프: 분리가 불가능할 때
    3. 입력 검증(허용 목록): 보조 수단
    4. 최소권한: 뚫렸을 때 피해 축소

    원본은 입력 검증만으로 주입을 막으려는 것이 전형적 오류라고 강조합니다. 블랙리스트는 우회되고, 인코딩만으로는 문맥 혼동이 생깁니다. 근본 해결은 파라미터화입니다.

    XSS는 출력 문맥(HTML 본문, 속성, JavaScript, URL, CSS)마다 인코딩 규칙이 다릅니다. 그래서 자동 문맥 인식 인코딩을 기본 제공하는 템플릿 엔진이 가장 안전하고, 원시(raw) 출력은 예외로 다뤄 검토 대상으로 만듭니다.

    원문 사례 — 입력 검증만으로 막으려 한 SQL 주입. 금지 문자 블랙리스트 필터를 공격자가 인코딩 변형과 유니코드 동등 문자로 우회했습니다. 파라미터화 질의로 바꾸자 그 결함 범주가 사라졌습니다.

    원문 사례 — 문맥을 혼동한 인코딩. HTML 본문 기준 인코딩을 전역 적용했지만 JavaScript 문맥과 HTML 속성 문맥에 삽입되는 지점에서 스크립팅이 성립했습니다. 문맥 인식 템플릿 엔진으로 바꾸고 원시 출력을 예외로 관리했습니다.

    판단 순서사용자가 준 값을 처리 없이 페이지에 넣으면 무엇이 문제일까요? 값 안에 스크립트가 들어 있으면 브라우저는 그것을 그 사이트의 문맥에서 실행합니다. 세션 쿠키 탈취나 사용자 대신 요청 보내기가 가능해지는 이유입니다. 대응은 “값을 거르는 것”보다 “표시될 문맥에 맞게 인코딩해 데이터로만 해석되게 하는 것”이 먼저입니다.

    보충입력 검증과 출력 인코딩은 서로 다른 질문에 답합니다. 검증은 “받은 값의 형식과 범위가 맞는가”, 인코딩은 “이 값이 표시될 때 코드가 아닌 데이터로 해석되는가”입니다. 값이 검증을 통과했더라도 화면에서는 문맥별 인코딩, 데이터베이스 호출에서는 매개변수 사용이 각각 필요합니다. 다른 내부 시스템에서 온 값이라도 사용 문맥이 바뀌면 필요한 보호가 달라집니다.

    원본 연습문제 · D8.5-Q01

    어떤 팀이 금지 문자 블랙리스트 필터로 SQL 주입에 대응했다. 공격자가 인코딩 변형과 유니코드 동등 문자로 우회했다. 올바른 주 통제는?

    1. 질의 구조와 데이터를 분리해 데이터가 코드로 해석되지 않게 하는 파라미터화 질의.
    2. 질의 문자열을 구성하기 전에 사용자 입력의 모든 단일 인용부호를 이스케이프한다.
    3. 알려진 모든 우회 인코딩을 포함하도록 블랙리스트를 확장한다.
    4. 모든 작업에 읽기 전용 데이터베이스 계정을 사용한다.
    정답과 해설 보기

    정답 A. 주입의 공통 원리는 데이터가 코드로 해석되는 것이므로 애초에 섞지 않는 구조적 분리가 근본 해결이다. 파라미터화 질의는 질의 구조를 먼저 확정하고 데이터를 값으로만 전달하므로 입력 내용과 무관하게 구조가 바뀌지 않는다. 입력 검증과 최소권한은 보조 수단이다.

    • B · 수동 이스케이프는 누락과 문맥 혼동이 발생한다.
    • C · 블랙리스트는 새로운 우회가 계속 나타나 유지가 불가능하다.
    • D · 읽기 전용 계정은 피해를 줄이지만 조회형 주입은 그대로 성립한다.
    원문 위치 · D8.5-Q01

    원본 연습문제 · D8.5-Q23

    어떤 애플리케이션이 사용자가 제공한 값을 처리 없이 페이지에 직접 포함시킨다. 어떤 약점이 생기는가?

    1. 처리되지 않은 값이 페이지가 만들어질 때 한 번, 브라우저가 렌더링할 때 다시 읽히므로 경쟁 조건.
    2. 길이 제한 없는 사용자 제공 값이 크기 검사 없이 페이지에 복사되므로 버퍼 오버플로.
    3. 같은 처리되지 않은 값이 페이지의 나머지 내용을 가져오는 질의를 구성하는 데도 쓰이므로 SQL 주입.
    4. 값에 스크립트가 포함될 수 있고 브라우저가 그것을 해당 사이트의 문맥에서 실행하므로 크로스사이트 스크립팅.
    정답과 해설 보기

    정답 D. 사용자 입력이 HTML 로 그대로 출력되면 브라우저가 그것을 마크업과 스크립트로 해석한다. 공격자가 스크립트를 넣으면 피해자의 브라우저에서 그 사이트 권한으로 실행되어 세션 탈취 등으로 이어진다. 대응은 출력 문맥에 맞는 인코딩이며 SQL 주입은 데이터베이스 쿼리로 가는 경우의 문제다.

    • A · 시점 경쟁과 무관하다. 경쟁 조건은 확인과 사용 사이의 상태 변화 문제이고, 여기서는 값이 코드로 해석되는 것이 문제다.
    • B · 길이 문제가 아니라 해석 문제다. 웹 템플릿은 관리되는 메모리를 쓰므로 긴 문자열이 인접 메모리를 덮어쓰지 않는다.
    • C · 지문은 값을 페이지에 넣는 것만 말한다. 질의에 쓰인다면 그것은 별개의 결함이고, 브라우저가 실행하는 문제와 다르다.

    3인가 결함

    원본은 인가 결함을 자동 도구가 가장 찾기 어려운 범주로 봅니다. 코드는 문법적으로 올바르고, 명세를 알아야 틀렸다는 것을 알 수 있기 때문입니다.

    • 객체 수준 인가 누락(IDOR): 식별자를 바꾸면 남의 자원이 반환됨. 가장 흔함
    • 기능 수준 인가 누락: 관리 기능이 권한 검사 없이 노출
    • 수평·수직 권한 상승
    • 클라이언트 측 통제 의존: UI에서 버튼을 숨기는 것은 통제가 아님
    • 다단계 흐름의 중간 단계 우회: 결제 확인을 건너뛰고 완료 단계를 직접 호출
    • 대량 할당(mass assignment): 요청 본문 필드가 객체에 그대로 매핑되어 역할 필드까지 설정 가능

    대응: 모든 요청마다 서버 측 인가 검증(완전한 중재), 중앙 인가 계층(엔드포인트마다 직접 구현하면 누락), 기본 거부, 입력 바인딩 허용 목록, 오용 사례 테스트와 수동 검토.

    보충화면에서 관리자 버튼을 숨기면 일반 사용자가 보는 인터페이스만 달라집니다. 요청은 여전히 서버로 직접 보낼 수 있으므로, 해당 작업을 처리하는 서버에서 주체·객체·동작을 근거로 허용 여부를 판단해야 접근 통제가 성립합니다.

    확인 필요원본은 완전한 중재의 참조 위치를 D3.1로 적었지만, 이 저장소에서 완전한 중재(참조 모니터의 요건)는 D3.4 시스템 보안 기능와 D5.1 물리적·논리적 접근 통제에 나옵니다. 이 교재는 그 두 단원으로 연결합니다.

    연결IDOR와 객체 수준 인가는 D5.1 물리적·논리적 접근 통제, 권한 상승은 D5.5 5절, 오용 사례는 D6.2 6절에서 다룹니다. API에서의 구체적 사례는 6절에 있습니다.

    원문 위치: D8.5.md §3 2) 인가 결함

    4인증·세션 결함과 암호 사용 오류

    인증과 세션

    • 약한 자격증명 저장: 솔트 없는 빠른 해시, (해시 대신) 암호화 저장
    • 세션 식별자: 예측 가능, URL 노출, 로그인 후 재발급 누락(세션 고정)
    • 쿠키 속성 누락: HttpOnly, Secure, SameSite
    • 로그아웃·만료 미구현: 서버 측 세션 무효화 없이 클라이언트만 삭제
    • 사용자 열거: 오류 메시지와 응답 시간 차이
    • 비밀번호 재설정 흐름: 토큰 예측 가능성, 만료, 일회성, 소유 확인

    암호 사용

    원본의 요점은 암호 자체보다 사용 방식에서 결함이 생긴다는 것입니다.

    오류실천
    알고리즘·프로토콜 직접 구현검증된 라이브러리, 알고리즘과 모드를 직접 고르지 않아도 되는 고수준 API
    폐기된 알고리즘과 모드교체 가능성(crypto agility)을 고려한 설계
    비암호학적 난수로 토큰·키 생성암호학적 난수 생성기
    하드코딩된 키와 비밀비밀은 금고에서
    초기화 벡터 재사용, 무결성 없는 암호화인증 암호화(AEAD) 사용
    인증서 검증 비활성화검증 유지, 예외 금지

    연결세션 고정과 세션 관리는 D5.2 식별·인증 전략, 자격증명 저장과 사용자 열거는 D5.6 인증 시스템, 암호 선택과 교체 가능성은 D3.6 암호 솔루션, 비밀 관리는 D7.3 구성 관리에서 다룹니다.

    5역직렬화, SSRF, 경쟁 조건, 메모리, 오류 처리, 비즈니스 논리

    범주원리대응
    안전하지 않은 역직렬화직렬화된 페이로드가 생성될 타입과 상태를 지정할 수 있어 코드 실행으로 이어짐신뢰할 수 없는 입력은 역직렬화하지 않음, 데이터 전용 형식, 타입 허용 목록
    SSRF앱이 사용자가 지정한 주소로 요청을 보냄. 클라우드에서 메타데이터 서비스로 자격증명 탈취목적지 허용 목록, 내부 주소 범위 차단, 리다이렉트 추적 제한, 메타데이터 접근 통제
    경쟁 조건·TOCTOU검사 시점과 사용 시점의 간격 — 동시 요청으로 중복 사용원자적 연산, 잠금, 트랜잭션 격리 수준, 멱등성 키
    메모리 안전 결함버퍼 오버플로, 해제 후 사용, 이중 해제, 정수 오버플로메모리 안전 언어에서 대부분 제거
    오류 처리·정보 노출상세 오류, 예외 시 인가 검사를 건너뛰는 경로, 민감 정보 노출사용자에게 일반 메시지·내부에 상세 기록, fail-secure, 예외 삼키기 금지
    비즈니스 논리 결함할인 중복, 음수 수량, 금액 정합성, 단계 우회, 재시도 악용 — 명세를 알아야 찾음오용 사례 테스트

    원문 사례 — 경쟁 조건으로 중복 사용된 쿠폰. 유효성 검사와 사용 처리 사이에 간격이 있어 동시 요청으로 같은 쿠폰이 여러 번 적용되었습니다. 원자적 연산, 트랜잭션 격리, 멱등성 키를 적용했습니다.

    원문 사례 — 메타데이터 서비스를 노린 SSRF. 이미지 URL을 받아 내려받는 기능에 공격자가 클라우드 메타데이터 서비스 주소를 넣어 인스턴스 자격증명을 얻었습니다.

    원문 사례 — 예외 시 인가를 건너뛴 코드. 인가 검사 함수가 예외를 던지면 호출 측이 잡아 기본값으로 허용했고, 외부 의존성 장애 때 모든 요청이 허용되었습니다. 예외 처리 패턴을 코딩 표준과 린트 규칙으로 강제했습니다.

    판단 순서역직렬화가 위험한 이유를 묻는 질문에서 “메모리를 많이 쓴다”, “전송 중 변조를 못 막는다”는 부수적 측면입니다. 핵심은 공격자가 어떤 객체가 어떤 상태로 만들어질지를 정할 수 있다는 점입니다. 그래서 대응도 “신뢰할 수 없는 입력은 역직렬화하지 않는다, 타입을 허용 목록으로 제한한다”가 됩니다.

    연결메모리 안전 언어와 상세 오류 노출은 D8.2 개발 생태계 보안 통제, 비즈니스 논리와 오용 사례는 D6.2 보안 통제 테스트, 도구가 비즈니스 논리 결함을 놓치는 이유는 D8.3 소프트웨어 보안 효과성의 6절, SSRF와 클라우드 메타데이터는 D3.5 아키텍처별 취약점에서 다룹니다.

    원본 연습문제 · D8.5-Q08

    쿠폰 사용 처리가 쿠폰을 검증한 뒤 사용 처리했고 두 단계 사이에 간격이 있었다. 동시 요청으로 같은 쿠폰이 여러 번 적용되었다. 이는 어떤 결함 범주이며 어떻게 해소하는가?

    1. 안전하지 않은 역직렬화. 인스턴스화 가능한 타입을 제한하고 복원 전에 페이로드를 검증해 대응한다.
    2. 주입. 쿠폰 코드가 사용 처리 질의의 구조를 바꾸지 못하도록 매개변수화 질의로 대응한다.
    3. 검사 시점과 사용 시점 사이의 경쟁 조건이며 원자적 연산과 적절한 트랜잭션 격리, 멱등성 키로 해소한다.
    4. 과도한 데이터 노출. 쿠폰의 내부 상태가 클라이언트로 반환되지 않도록 응답 모델을 분리해 대응한다.
    정답과 해설 보기

    정답 C. 검사와 사용 사이에 간격이 있으면 그 사이에 상태가 바뀔 수 있고 동시 요청이 같은 검사 결과를 공유해 중복 사용이 성립한다. 검사와 사용을 하나의 원자적 연산으로 묶거나 적절한 트랜잭션 격리 수준을 적용하고 멱등성 키로 중복 처리를 차단해야 한다.

    • A · 역직렬화와 무관하다. 쿠폰 객체를 복원하는 과정이 아니라 확인과 사용 사이의 시간 간격이 문제다.
    • B · 질의 구성 문제가 아니다. 같은 정상 코드가 동시에 여러 번 처리된 것이므로 동시성 통제가 필요하다.
    • D · 데이터 노출과 무관하다. 클라이언트가 내부 상태를 보지 못하게 해도 동시 요청은 여전히 같은 간격을 파고든다.

    원본 연습문제 · D8.5-Q16

    신뢰할 수 없는 데이터를 역직렬화하는 것이 위험한 이유는?

    1. 공격자가 통제하는 데이터를 역직렬화하면 매우 큰 객체 그래프를 할당해 메모리를 소진시키고 서비스를 중단시킬 수 있으므로.
    2. 직렬화된 페이로드가 어떤 타입을 생성하고 어떤 상태를 가질지 지정할 수 있어 조작된 입력이 객체 재구성 과정에서 애플리케이션의 어떤 검증보다 먼저 코드 실행을 유발할 수 있으므로.
    3. 직렬화 형식 자체에 무결성 보호가 없어 페이로드가 전송 중에 탐지되지 않고 변경될 수 있으므로.
    4. 역직렬화는 데이터 접근 계층을 거치지 않고 객체를 복원하므로 통상의 질의 감사가 그것을 기록하지 않으므로.
    정답과 해설 보기

    정답 B. 역직렬화는 바이트를 객체로 되살리는 과정에서 생성자나 특수 메서드를 호출한다. 페이로드가 어떤 클래스를 쓰라고 지시할 수 있으면 공격자가 그 과정에 걸리는 메서드 연쇄를 구성해 코드 실행에 이를 수 있다. 애플리케이션 검증 코드는 객체가 만들어진 뒤에 돌기 때문에 늦다. 대응은 신뢰할 수 없는 데이터 역직렬화를 피하고 데이터 전용 형식과 허용 타입 목록, 무결성 검증을 쓰는 것이다.

    • A · 실제 위험의 하나이지만 가장 심각한 것이 아니다. 핵심은 페이로드가 어떤 타입을 만들지 지정할 수 있어 복원 중에 코드가 실행된다는 점이다.
    • C · 서명이나 암호화를 덧붙여 해결할 수 있는 문제다. 신뢰할 수 없는 출처의 역직렬화가 위험한 이유는 변경 탐지가 아니라 복원 자체의 동작이다.
    • D · 감사 공백은 부수 문제다. 위험의 본질은 복원 과정이 애플리케이션 검증보다 먼저 일어나 임의 코드 실행에 이를 수 있다는 점이다.

    6API 보안

    공식 개요에 명시된 항목입니다. API는 UI라는 보호막 없이 기능을 직접 노출합니다.

    고유 위험통제
    객체 수준 인가 누락 — API에서 가장 흔함모든 요청에 기능·객체 수준 인가, 중앙 인가와 정책 집행 지점
    기능 수준 인가 누락관리 엔드포인트도 같은 인가 계층으로
    과도한 데이터 노출 — 클라이언트가 걸러낸다고 가정응답 최소화 — 서버 측에서 필요한 필드만
    대량 할당입력 바인딩 허용 목록, 요청·응답 스키마 검증
    속도 제한 부재 — 열거, 자격증명 대입, 자원 소진엔드포인트별·사용자별 속도 제한과 할당량
    문서화되지 않은 엔드포인트, 버전 간 불일치API 인벤토리와 폐기 관리
    “내부 API”라는 가정 — 인증 생략서비스 간 mTLS와 토큰 인증, 네트워크 위치를 신뢰 근거로 삼지 않음
    GraphQL류 — 질의 깊이·복잡도, 단일 엔드포인트깊이·복잡도 제한, 필드 수준 인가

    그 밖에 게이트웨이로 인증·속도 제한·로깅을 일관되게 적용하되 게이트웨이 우회 경로가 없어야 하고, 토큰은 범위 최소화·짧은 수명·대상 검증으로 설계하며, 인가 거부와 비정상 패턴을 로깅합니다.

    원문 사례 — 식별자만 바꾸면 통하던 API. 토큰으로 로그인 여부는 확인했지만 요청한 주문이 그 사용자의 것인지 검증하지 않아, 식별자를 바꾸면 다른 고객의 주문이 반환되었습니다.

    원문 사례 — 대량 할당으로 역할 변경. 프로필 수정 API가 요청 본문의 모든 필드를 바인딩해, 공격자가 역할 필드를 추가하고 자신을 관리자로 만들었습니다. 수정 가능한 필드를 명시하고 나머지는 무시하게 했습니다.

    원문 사례 — 클라이언트가 걸러낸다고 가정한 응답. 응답에 주민등록번호와 내부 메모를 포함한 전체 사용자 객체가 담겼고, 화면엔 안 보였지만 응답 본문으로는 그대로 노출되었습니다. 서버 측 응답 모델을 분리했습니다.

    원문 사례 — 속도 제한 없는 인증 엔드포인트. 로그인 API로 자격증명 대입과 사용자 열거가, 재설정 API로 대량 메일 발송이 이루어졌습니다.

    원문 사례 — 폐기되었으나 살아 있던 구버전 API. v2에서 인가를 강화했지만 v1이 비활성화되지 않아 공격자가 v1을 썼습니다. 폐기 절차에 실제 비활성화 확인을 넣었습니다.

    원문 사례 — 내부 전용이라 가정한 API. 서비스 간 API가 인증 없이 운영되었고, 서버 하나가 침해되자 그 API로 데이터를 자유롭게 조회당했습니다.

    가상 예시환자 모니터링 기기가 클라우드 API로 측정값을 올리고, 의료진 앱이 같은 API에서 환자 목록을 받는 구조를 생각해 봅시다. 점검 질문은 이렇습니다. 의료진 토큰으로 다른 병원 환자 ID를 조회하면 거부되는가(객체 수준 인가)? 응답에 앱이 쓰지 않는 필드가 들어 있지 않은가(과도한 노출)? 펌웨어 구버전이 쓰던 v1 엔드포인트가 아직 살아 있지 않은가(인벤토리)? 기기와 백엔드 사이가 “내부망”이라는 이유로 인증이 생략되지 않았는가(mTLS)? (설명을 위한 가상 구조입니다.)

    연결PDP/PEP와 우회 경로 금지는 D5.4 7절, 토큰 설계와 연합은 D5.3 연합 식별, 서비스 간 mTLS는 D7.5 자원 보호, 인가 거부 로깅은 D8.3 소프트웨어 보안 효과성의 3절에서 다룹니다.

    원문 위치: D8.5.md §3 API 보안, §7 사례 3~8 · 공식 개요 8.5 “Security of APIs” · 원본은 mTLS 참조를 D4.3으로 적었으나, 서비스 간 mTLS 설명과 내부 API 사례는 이 저장소의 D7.5에 있어 그쪽으로 연결함

    원문 위치: D8.5.md §3 안전한 코딩 실천 · 공식 개요 8.5 “Secure coding practices”

    8코딩 표준을 실제로 적용하기

    원본의 핵심 문장은 문서로 존재하는 표준은 지켜지지 않는다입니다.

    적용 수단효과
    안전한 기본값 제공가장 강함 — 실수할 여지를 줄임
    공통 라이브러리와 프레임워크매번 구현하지 않게 함
    린트 규칙과 자동 검사작성 시점에 차단
    코드 검토 체크리스트사람의 검토를 일관되게
    구체적 예시 중심 표준“하지 말 것”과 “대신 쓸 것”을 쌍으로
    반복 유형 기반 교육실제 발생 패턴에 초점

    표준 설계 원칙: 구체성(“이 함수 대신 저 함수를 이렇게”), 금지와 대안의 쌍(금지만 있으면 우회 방법을 스스로 찾음), 언어·프레임워크별, 예외 경로(승인과 기록), 갱신, 자동 측정 가능성.

    원문 사례 — 표준을 기본값으로 바꾼 성과. 코딩 표준 문서가 있었지만 출력 인코딩 결함이 계속 나왔습니다. 템플릿 엔진 기본값을 자동 인코딩으로 바꾸고 원시 출력에 린트 경고를 추가하자 그 유형의 신규 발견이 급감했습니다.

    보충ISO 27001:2022의 부속서 A에는 안전한 코딩(8.28) 통제가 있습니다. 심사에서 코딩 표준 문서만 확인하면 이 단원이 말하는 “문서로만 존재하는 표준”을 놓치기 쉽습니다. 표준의 금지 항목이 린트 규칙이나 프레임워크 기본값으로 실제 강제되는지, 예외가 승인·기록되는지까지 표본으로 확인하면 효과를 볼 수 있습니다.

    연결CWE 반복 유형과 구조적 대응은 D8.3 소프트웨어 보안 효과성의 7절, 예외 관리는 D6.4 결과 분석과 보고에서 다룹니다.

    원문 위치: D8.5.md §3 코딩 표준을 실제로 적용하기, §7 사례 12 · ISO 27001:2022 부속서 A 8.28 언급은 보충

    9소프트웨어 정의 보안

    공식 개요에 명시된 항목입니다. 보안 정책과 통제를 소프트웨어로 정의하고 자동으로 집행하는 접근입니다.

    구성설명
    정책 코드(policy as code)정책을 코드로 표현해 자동 평가, 배포 전 차단
    코드형 인프라보안 설정이 검토·버전 관리 대상
    소프트웨어 정의 네트워킹, 마이크로세그먼테이션네트워크 정책을 소프트웨어로 정의
    중앙 정책 결정·분산 집행PDP/PEP 구조
    자동 교정일탈을 자동으로 되돌림

    가치: 일관성(사람의 편차 제거), 확장성, 검토 가능성, 증거 자동 생성(적용 이력이 감사 증거), 사전 차단.

    주의:

    • 정책 코드 자체가 통제 대상입니다. 바꿀 수 있으면 모든 통제를 우회할 수 있습니다.
    • 오류가 광범위하게 전파되므로 단계적 적용과 롤백이 필요합니다.
    • 정책 집행 지점을 우회하는 경로가 없어야 합니다.
    • 정책이 과도하면 예외가 누적되어 실질 수준이 예외로 결정됩니다.

    보충정책을 코드로 관리하면 검토·배포·시험의 근거가 남지만, 승인되지 않은 정책도 자동으로 배포되면 영향이 커집니다. 정책 변경 때 허용되어야 할 흐름과 거부되어야 할 흐름을 함께 시험하고, 실제 배치가 승인된 정책 버전을 쓰는지 기록과 대조합니다.

    연결PDP/PEP는 D5.4 7절, 정책 코드·코드형 인프라·자동 교정은 D7.3 구성 관리, 변경 통제는 D7.9 변경 관리, 소프트웨어 정의 네트워킹과 마이크로세그먼테이션은 D4.1 네트워크 아키텍처, 감사 증거는 D6.5 보안 감사에서 다룹니다.

    원문 위치: D8.5.md §3 소프트웨어 정의 보안 · 공식 개요 8.5 “Software-defined security”

    10종합 이해 확인

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    주문 API 점검 결과다. ㉠ 주문 조회 시 토큰은 검증하지만 주문 소유자는 확인하지 않는다. ㉡ 인가 함수가 예외를 던지면 호출 측이 허용으로 처리한다. ㉢ v1 엔드포인트가 폐기 공지 후에도 응답한다. ㉣ 코딩 표준 문서에 “출력을 인코딩하라”는 문장만 있고 XSS가 반복된다. 가장 적절한 조치 묶음은?

    1. ㉠ 클라이언트에서 다른 사용자 주문 숨김 / ㉡ 로그만 추가 / ㉢ 문서에 폐기 표시 / ㉣ 개발자 교육 1회
    2. ㉠ 중앙 인가 계층에서 객체 수준 인가 / ㉡ fail-secure로 바꾸고 린트 규칙으로 강제 / ㉢ API 인벤토리와 실제 비활성화 확인 / ㉣ 문맥 인식 자동 인코딩 기본값과 원시 출력 린트 경고
    3. ㉠ 식별자를 난수로 변경 / ㉡ 예외를 삼켜 서비스 유지 / ㉢ 게이트웨이에서만 차단 / ㉣ 블랙리스트 필터 추가
    4. ㉠ WAF 규칙 / ㉡ 재시도 횟수 증가 / ㉢ v1 속도 제한 / ㉣ 표준 문서 분량 확대
    정답과 해설 보기

    정답 B. ㉠ 객체 수준 인가는 서버의 중앙 계층에서 모든 요청마다(3절·6절). 식별자 난수화(C)는 추측만 어렵게 할 뿐 인가가 아닙니다. ㉡ 예외 시 허용은 심각한 결함 — fail-secure(5절). ㉢ 문서화되지 않은·구버전 엔드포인트가 공격 표면 — 인벤토리와 실제 비활성화(6절). 게이트웨이만 막으면 우회 경로가 남을 수 있습니다. ㉣ 문서로 존재하는 표준은 지켜지지 않음 — 안전한 기본값과 자동 강제(8절).

    11핵심 개념을 내 말로 설명하기

    복습

    유효한 입력값을 받았다는 사실로 코드의 보안을 보장할 수 있나요?

    설명 확인하기

    형식 검증으로 받은 값이 조건에 맞는지 판단합니다. 저장이나 명령을 처리하는 API에서 데이터와 명령을 분리하고, 표시할 때는 문맥에 맞게 인코딩합니다. 해당 요청자의 권한도 별도로 확인합니다.

    12핵심 요약

    1. 세 접근 중 안전한 선택을 기본값으로 만드는 것이 가장 강함. 표준은 구체적이고, 자동 강제되고, 금지와 대안을 쌍으로.
    2. 주입 = 데이터가 코드로 해석됨. 대응 순서: 구조적 분리(파라미터화) → 문맥 인코딩 → 허용 목록 검증(보조) → 최소권한. 블랙리스트는 우회됨.
    3. XSS는 출력 문맥마다 인코딩 규칙이 다름 → 문맥 인식 템플릿 엔진, 원시 출력은 예외.
    4. 인가 결함은 도구가 가장 찾기 어려움: IDOR, 기능 수준, 클라이언트 측 통제 의존, 단계 우회, 대량 할당. 서버 측·중앙 계층·기본 거부·바인딩 허용 목록·오용 사례.
    5. 세션 고정, 쿠키 속성, 서버 측 무효화, 사용자 열거. 암호는 사용 방식에서 결함 — 검증된 라이브러리, 암호학적 난수, AEAD, 교체 가능성.
    6. 역직렬화(타입·상태를 공격자가 지정), SSRF(메타데이터 자격증명), TOCTOU(원자적 연산·멱등성 키), 메모리 안전, fail-secure, 비즈니스 논리(명세 필요).
    7. API: 객체 수준 인가가 가장 흔함, 응답 최소화, 바인딩 허용 목록, 속도 제한, 인벤토리·폐기, 내부 API도 mTLS·토큰, 게이트웨이 우회 금지.
    8. 입력 검증은 서버 측·허용 목록·정규화 후. 오류는 사용자에게 일반, 내부에 상세.
    9. 소프트웨어 정의 보안: 정책 코드, IaC, SDN·마이크로세그먼테이션, PDP/PEP, 자동 교정. 가치는 일관성·확장성·검토·증거·사전 차단, 정책 코드 자체가 통제 대상.
    원문 위치: D8.5.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    CWE (Common Weakness Enumeration) · 공통 약점 유형 목록

    소프트웨어 결함 유형 분류 체계. 근본 원인 분석과 패턴 식별에 쓰인다.

    Injection · 주입

    데이터가 코드나 명령으로 해석되는 결함 범주.

    Parameterized Query · 파라미터화 질의

    질의 구조와 데이터를 분리해 주입을 근본적으로 막는 방식.

    Context-aware Encoding · 문맥 인식 인코딩

    출력 위치에 맞는 인코딩을 자동 적용하는 방식.

    IDOR (Insecure Direct Object Reference) · 안전하지 않은 직접 객체 참조

    객체 수준 인가 검증 누락으로 식별자 변경만으로 남의 자원에 접근하는 결함.

    Mass Assignment · 대량 할당

    요청 필드가 객체에 그대로 바인딩되어 의도하지 않은 속성이 설정되는 결함.

    Session Fixation · 세션 고정

    인증 후 세션 식별자를 재발급하지 않아 가로채기가 가능한 결함(D5.2 참조).

    Insecure Deserialization · 안전하지 않은 역직렬화

    신뢰할 수 없는 직렬화 데이터 처리가 코드 실행으로 이어지는 결함.

    SSRF (Server-Side Request Forgery) · 서버 측 요청 위조

    애플리케이션이 사용자가 지정한 주소로 요청을 보내게 만드는 결함.

    TOCTOU (Time-of-Check to Time-of-Use) · 검사 시점과 사용 시점 사이의 경쟁 상태

    검사 시점과 사용 시점의 간격을 악용하는 경쟁 조건.

    Excessive Data Exposure · 과도한 데이터 노출

    응답에 필요 이상의 필드를 담아 클라이언트가 걸러낼 것으로 가정하는 API 결함.

    Rate Limiting · 속도 제한

    요청 빈도를 제한해 열거와 대입, 자원 소진을 막는 통제.

    Crypto Agility · 알고리즘 교체 가능성

    암호 알고리즘을 교체할 수 있게 설계하는 성질.

    Secure Defaults · 안전한 기본값

    설정하지 않았을 때 안전한 쪽으로 동작하는 설계.

    Policy as Code · 정책 코드

    보안 정책을 코드로 표현해 자동 평가·집행하는 방식.

    Software-defined Security · 소프트웨어 정의 보안

    보안 정책과 통제를 소프트웨어로 정의하고 자동 집행하는 접근.
