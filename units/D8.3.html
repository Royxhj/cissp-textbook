    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    원본은 이 단원을 한 가지 구분으로 시작합니다. “보안 활동을 했다”와 “소프트웨어가 안전해졌다”는 다르다. 스캔을 돌렸는지, 교육을 했는지, 도구를 도입했는지는 활동량입니다. 효과성은 결함이 줄었는지, 더 빨리 발견되는지, 운영에서 악용되지 않는지로 측정됩니다. 공식 개요 8.3은 변경에 대한 감사와 로깅, 위험 분석과 완화를 듭니다. 도메인 6이 조직 전체의 평가 전략이라면, 이 단원은 그것을 소프트웨어 보안에 적용한 것입니다.

    1활동량과 효과성

    효과성 평가의 세 질문입니다.

    1. 통제가 설계대로 작동하는가: 파이프라인 검증이 실제로 차단하는가
    2. 결과가 개선되고 있는가: 결함 밀도, 발견 단계, 수정 시간
    3. 남은 위험이 수용 가능한가: 위험 분석과 수락 결정

    보충ISO 27001 심사에서 “조치를 했다”는 기록과 “조치가 효과적이었다”는 증거를 구분해 보듯이, 소프트웨어 보안에서도 같은 구분이 필요합니다. 도구 도입 보고서가 아니라, 도입 전후에 같은 범위에서 어떤 결함이 어느 단계에서 얼마나 발견되었는지가 효과의 증거입니다.

    원문 위치: D8.3.md §2 · 공식 개요 8.3 “Assess the effectiveness of software security”

    2개발 변경의 감사

    공식 개요의 첫 항목인 “변경에 대한 감사와 로깅”에는 두 층위가 있습니다. 첫째는 개발 변경, 즉 누가 무엇을 언제 왜 바꿨는지의 추적입니다.

    • 버전 관리 이력(커밋, 작성자, 시점, 내용), 검토와 승인 기록(PR 승인자, 코멘트, 상태 검사).
    • 빌드와 배포 이력: 어떤 커밋이 어떤 아티팩트가 되어 어디에 배포되었는가.
    • 추적성 사슬: 요구사항 → 작업 항목 → 커밋 → 빌드 → 배포. 장애나 침해 때 “무엇이 들어갔는가”에 답할 수 있어야 합니다.
    • 파이프라인 설정 변경, 구성과 기능 플래그 변경, 저장소·파이프라인 접근 권한 변경.

    규제 환경에서는 변경 통제가 작동했다는 증거(작성자와 승인자 분리, 승인 없는 배포 부재, 긴급 변경의 사후 승인)를 요구합니다.

    원문 사례 — 추적성 사슬 부재. 운영 장애 뒤 최근 무엇이 배포되었는지 확인하려 했지만 아티팩트와 커밋의 연결이 없어 복구가 지연되었습니다. 아티팩트에 커밋 해시와 빌드 식별자를 넣고 배포 이력과 연결해 조회 가능하게 했습니다.

    연결개발에서의 변경 관리는 D8.1 SDLC 보안의 6절, 아티팩트 승격과 재현 빌드는 D8.2 개발 생태계 보안 통제의 7절, 감사 증거는 D6.5 보안 감사에서 다룹니다.

    원문 위치: D8.3.md §3 변경에 대한 감사와 로깅 — 개발 변경의 감사, §7 사례 4 · 공식 개요 8.3 “Auditing and logging of changes”

    3애플리케이션 런타임 로깅

    둘째 층위는 소프트웨어가 운영 중 무엇을 기록하는가이며, 이것이 탐지와 조사 가능성을 결정합니다.

    범주기록할 보안 이벤트
    인증로그인 성공·실패, MFA 등록 변경, 비밀번호 재설정
    인가접근 거부, 권한 상승, 역할 변경
    데이터민감 데이터 조회·수출, 대량 조회
    입력 검증검증 실패, 비정상 입력
    관리 작업설정 변경, 사용자 생성·삭제
    무결성·가용성서명 검증 실패, 예상치 못한 상태 전이, 속도 제한 발동, 비정상 오류율

    설계 요건: 구조화 로깅, 상관 식별자(요청 ID·세션·사용자로 여러 서비스에 걸쳐 추적, 마이크로서비스에서 필수), 동기화된 시각, 충분한 맥락(누가, 어떤 자원에, 어떤 작업을), 민감 정보 제외(비밀번호, 토큰, 개인정보 원문, 카드 번호), 중앙 전송, 로깅 실패 시 동작 정의, 로그 주입 방지(개행·제어 문자 처리). 감사 추적은 추가 전용·불변 저장, 앱이 자기 감사 로그를 수정할 수 없게, 로그 조회도 기록, 보존 기간 설정.

    원본의 핵심 문장: 애플리케이션이 기록하지 않는 것은 탐지할 수 없다. 인가 거부와 입력 검증 실패는 공격 시도의 가장 직접적인 신호인데, 많은 앱이 이를 기록하지 않습니다.

    원문 사례 — 인가 거부를 기록하지 않은 앱. 공격자가 수천 건의 인가 거부를 발생시키며 객체 식별자를 열거한 사실이 외부 WAF 로그로만 확인되었고, 앱 자체는 인가 거부를 기록하지 않아 탐지하지 못했습니다.

    원문 사례 — 맥락 없는 로그. “Access denied”만 기록되어, 사고 조사에서 누가 어떤 자원에 어떤 작업을 시도했는지 알 수 없었습니다. 주체, 자원, 작업, 결과, 요청 식별자를 담는 구조화 로깅으로 바꿨습니다.

    원문 사례 — 로그에 기록된 민감 정보. 디버깅 편의로 요청 본문 전체를 로깅해 비밀번호와 카드 번호가 평문으로 들어갔고, 로그는 여러 분석 시스템에 복제되어 있었습니다. 로깅 계층에서 민감 필드를 마스킹하고 기존 로그를 정화했습니다.

    연결로그 관리·무결성·보존은 D7.2 5절, 인증 로그 항목은 D5.6 인증 시스템의 8절, IDOR는 D5.1 물리적·논리적 접근 통제의 6절에서 다룹니다.

    원본 연습문제 · D8.3-Q01

    침해 조사에서 외부 웹 애플리케이션 방화벽 로그를 통해 공격자가 객체 식별자를 열거하며 수천 건의 인가 거부를 발생시켰음이 확인되었다. 애플리케이션 자체는 이를 전혀 기록하지 않았고 아무것도 탐지되지 않았다. 주된 공백은?

    1. 웹 애플리케이션 방화벽이 한 세션의 반복된 객체 요청에 속도 제한을 걸어 열거를 자동 차단하도록 설정되어 있어야 했다.
    2. 애플리케이션이 공격 시도의 가장 직접적인 신호 중 하나인 인가 거부를 기록하지 않아 탐지가 불가능했다.
    3. 다른 고객 레코드의 순차 열거가 불가능하도록 객체 식별자를 예측 불가능한 값으로 바꿔야 했다.
    4. 로그 보존 기간이 너무 짧아 증거가 남지 않았고, 조사가 시작되기 전에 공격자 활동 기록이 이미 순환 삭제되었다.
    정답과 해설 보기

    정답 B. 애플리케이션이 기록하지 않는 것은 탐지할 수 없다. 인가 거부와 입력 검증 실패는 공격 시도의 가장 직접적인 신호이며 대량 발생은 열거 시도를 뜻한다. 보안 이벤트 로깅 요구사항을 정의해 인증과 인가, 입력 검증, 관리 작업, 데이터 조회를 기록 대상으로 명시하고 중앙 전송과 경보를 구성해야 한다.

    • A · 방화벽은 보조 통제이고 애플리케이션 가시성 부재를 대체하지 않는다. 차단했더라도 애플리케이션 쪽 기록이 없어 무슨 일이 있었는지 알 수 없다.
    • C · 유효한 보완책이지만 탐지 공백은 그대로 남는다. 식별자를 바꿔도 인가 거부를 기록하지 않으면 다음 공격 시도 역시 보이지 않는다.
    • D · 애플리케이션이 애초에 인가 거부를 기록하지 않았으므로 보존 기간의 문제가 아니다. 보존을 늘려도 남는 기록이 없다.

    4위험 분석과 완화

    위험 식별의 출처: 위협 모델링 산출물, 테스트 결과(SAST, DAST, SCA, 침투 테스트), 운영 신호, 계속 공개되는 의존성 취약점, 아키텍처 위험(단일 실패점, 신뢰 경계, 데이터 집중), 프로세스 위험(검토 누락, 긴급 배포 남용, 기술 부채).

    분석은 기술적 심각도를 조직 위험으로 변환하는 일입니다.

    요소의미
    도달 가능성 reachability그 코드 경로가 실제로 실행되는가. 도달할 수 없는 취약점은 우선순위가 낮음
    악용 가능성인증 필요 여부, 공개 악용 코드
    노출 경로인터넷 / 내부
    데이터 민감도와 업무 영향
    기존 보완 통제WAF, 속도 제한, 분할, 탐지
    연쇄 가능성개별로는 낮아도 조합하면 치명적
    완화 선택소프트웨어 맥락
    수정(완화)코드 수정, 의존성 갱신, 설정 변경
    보완 통제WAF 가상 패치, 속도 제한, 모니터링 강화, 기능 제한 — 임시 수단
    회피기능·취약 구성요소 제거 — 가장 확실
    이전계약과 보험(제한적)
    수락권한 있는 승인, 기한, 재검토

    미뤄진 수정은 기술 부채 등록부로 가시화하지 않으면 영구화됩니다. 완화 후에는 재검증(일부 경로만 수정되는 경우가 흔함), 회귀 방지 테스트 케이스 추가(수정만 하고 테스트를 추가하지 않으면 재발), 근본 원인 반영(같은 유형이 반복되면 코딩 표준·라이브러리·설계 패턴·교육에)을 합니다.

    원문 사례 — 수정만 하고 테스트를 추가하지 않은 경우. 인가 결함을 고쳤지만 6개월 뒤 리팩터링 중 같은 결함이 다시 들어와 운영에서 발견되었습니다. 보안 결함 수정의 종결 조건에 재현 테스트 케이스 추가를 넣었습니다.

    원문 사례 — 도달 불가능한 취약점에 자원 투입. SCA가 보고한 의존성 취약점 1,100건을 심각도 순으로 처리했는데, 상당수가 앱이 호출하지 않는 코드 경로였고 도달 가능한 중간 심각도 취약점은 뒤로 밀려 있었습니다. 도달 가능성 분석을 우선순위에 넣고, 도달 불가 항목은 별도 추적 범주로 분리했습니다.

    연결위험 처리는 D1.9 위험 관리, 위협 모델링은 D1.10 위협 모델링, 우선순위와 공격 경로는 D6.4 결과 분석과 보고의 1절, 제거가 가장 확실한 조치라는 점은 D7.8 패치·취약점 관리의 5절에서 다룹니다.

    의존성 최신성지원 종료·취약 버전 사용 비율
    파이프라인 통과율과 우회 건수통제가 실제 작동하는가

    원본은 발견 단계 분포가 가장 중요한 효과성 지표라고 말합니다. 왼쪽으로 이동했다면 설계·구현 단계 발견 비율이 오르고 운영 발견 비율이 내려갑니다. 총 발견 건수는 그 자체로 좋거나 나쁘지 않습니다.

    지표 왜곡: “발견 결함 수 감소”를 성과로 쓰면 스캔 범위가 줄고, “평균 수정 시간”만 쓰면 쉬운 건부터 처리하며, “파이프라인 통과율 100%”는 차단 기준이 느슨한 것일 수 있고, “교육 이수율 100%”는 참여 지표일 뿐입니다. 짝 지표와 맥락이 왜곡을 상쇄합니다.

    원문 사례 — 발견 건수 감소라는 왜곡된 성과. 2년간 “발견 결함 수 감소”가 개선되었지만, 스캔 범위가 축소되고 일부 저장소가 제외되어 있었습니다.

    원문 사례 — 파이프라인 통과율 100%. 차단 기준이 매우 느슨해 사실상 모든 빌드가 통과하고 있었습니다. 의도적으로 결함 있는 코드를 넣어 차단되는지 검증하고, 차단 기준과 우회 건수를 함께 보고했습니다.

    가상 예시새 스캐너를 도입하자 발견 결함 수가 두 배가 되었고 개발팀은 “품질이 갑자기 떨어졌다”고 결론 내렸습니다. 비교 방법을 바로잡으면, 같은 저장소 범위에서 기존 스캐너와 새 스캐너의 결과를 나란히 놓고, 새로 잡힌 결함이 어느 유형·단계인지 보고, 운영 유출 결함이 같은 기간에 줄었는지 함께 봅니다. 그러면 “품질 저하”가 아니라 “가시성 증가”였다는 것을 보여 줄 수 있습니다. 반대로 결함이 줄었다는 결과가 나오면 검사 대상을 줄였는지부터 확인합니다.

    연결짝 지표와 지표 왜곡은 D6.3 3절, DevSecOps 측정은 D8.1 SDLC 보안의 4절에서 다룹니다.

    6평가 방법

    • 통제 작동 검증: 파이프라인에 의도적으로 결함 있는 코드를 넣어 차단되는지 확인(자동 검증의 BAS에 해당).
    • 침투 테스트와 레드팀: 실제 악용 가능성.
    • 코드 검토 샘플링: 검토가 실질적으로 수행되는지 표본 검증.
    • 성숙도 평가: SAMM 등.
    • 사후 검토: 운영에서 발견된 결함이 왜 앞 단계에서 걸리지 않았는가 — 가장 유용한 학습 출처.
    • 외부 평가: 독립적 시각.

    원본의 핵심 문장: 운영에서 발견된 결함마다 “왜 앞에서 걸리지 않았는가”를 묻는 것이 효과성 개선의 가장 직접적인 방법이다. 답이 “그 유형을 찾는 통제가 없다”면 통제를 추가하고, “통제가 있었으나 작동하지 않았다”면 통제를 고칩니다.

    원문 사례 — “왜 앞에서 걸리지 않았는가”. 운영 결함마다 원인 분석을 의무화하자, 상당수는 “그 유형을 찾는 통제가 아예 없었다”였고 일부는 “SAST가 보고했지만 거짓 양성으로 종결”이었습니다. 통제 공백에는 새 검증을, 잘못된 종결에는 분류 기준과 검토 절차 개선을 적용했습니다.

    보충자동 도구는 “알려진 패턴”을 찾고, 단위 시험은 “개발자가 의도한 동작”을 확인합니다. 그래서 환불 기능이 음수 금액을 받아 잔액을 늘리는 결함처럼 비즈니스 규칙 위반은 도구도 단위 시험도 놓칠 수 있습니다. 단위 시험이 모두 통과해도 보안 시험에 실패하는 이유가 여기 있습니다. 이런 결함은 오용 사례와 수동 검토가 찾습니다.

    연결오용 사례와 커버리지는 D6.2 보안 통제 테스트의 6·7절, 침해 공격 시뮬레이션은 D6.2 보안 통제 테스트의 9절, 성숙도 모델은 D8.1 SDLC 보안의 5절에서 다룹니다.

    원본 연습문제 · D8.3-Q15

    자동화 도구는 발견 사항을 보고하지 않았는데 검토자가 환불 기능이 음수 금액을 허용해 고객 잔액을 늘린다는 것을 발견했다. 도구가 놓친 이유는?

    1. 도구에 금융 거래 로직용 규칙 묶음이 설정되지 않아 해당 검사가 그 스캔에서 비활성화되어 있었다.
    2. 업무 로직 결함이다. 코드가 문법적으로 올바르고 안전하지 않은 함수를 쓰지 않으므로 도구가 일치시킬 패턴이 없다. 탐지하려면 그 기능이 무엇을 해야 하는지 이해해야 한다.
    3. 스캔이 이전 커밋을 대상으로 돌아서 분석 시점에는 환불 기능이 아직 작성되지 않았다.
    4. 기능이 메모리 안전 언어로 작성되었고 런타임이 산술을 처리하므로 정적 분석이 그것을 추론할 수 없다.
    정답과 해설 보기

    정답 B. 도구는 알려진 위험 패턴을 찾는다. 음수 환불은 어떤 위험 함수도 쓰지 않고 문법도 정상이며 "금액은 양수여야 한다" 는 업무 규칙을 알아야 결함임을 알 수 있다. 이런 결함이 실제 금전 손실로 이어지는 경우가 많아 자동화만으로 충분하다고 보면 안 된다. 위협 모델링과 수동 검토, 오용 사례 테스트가 이 영역을 담당한다.

    • A · 환불 금액의 부호를 검증해야 한다는 것은 이 업무에 고유한 규칙이고 어떤 규칙 묶음에도 들어 있지 않다. 도구가 알 수 있는 정답이 없다.
    • C · 시점 문제였다면 그 파일의 다른 결함도 함께 놓쳤을 것이다. 도구가 보고한 것이 없다는 사실은 범주의 한계로 설명된다.
    • D · 메모리 안전 언어도 정적 분석이 가능하다. 분석이 못 하는 것은 음수 환불이 업무상 허용되지 않는다는 의도를 알 수 없기 때문이다.

    원본 연습문제 · D8.3-Q22

    모든 단위 시험이 통과해도 시스템이 보안 시험에 실패할 수 있는 이유는?

    1. 단위 시험을 코드를 쓴 같은 개발자가 작성하므로 같은 오해를 담아 잘못된 이유로 통과하기 때문이다.
    2. 단위 시험은 구성요소를 격리된 상태에서 연결 후에는 성립하지 않을 수 있는 가정 아래 확인하므로. 인터페이스와 종단 간 동작은 자체 시험이 필요하다.
    3. 보안 시험은 단위 시험 프레임워크가 전혀 닿을 수 없는 네트워크와 사용자 인터페이스 계층을 통해 시스템을 다루기 때문이다.
    4. 단위 시험은 모의 의존성을 대상으로 돌고 모의 객체는 항상 올바르게 동작하므로 단위 계층에서는 어떤 시험도 실패할 수 없기 때문이다.
    정답과 해설 보기

    정답 B. 단위 시험은 "이 함수에 이 입력을 주면 이 결과가 나온다" 를 확인한다. 그 입력이 이미 검증되었다고 가정하면 실제로 누가 검증하는지는 확인되지 않는다. 두 구성요소가 각각 상대가 검증한다고 가정하면 연결 지점에 검증 공백이 생긴다. 그래서 통합 시험과 종단 간 인가 확인이 별도로 필요하다.

    • A · 실제로 있는 한계이지만 이 문항의 답이 아니다. 작성자가 달라도 구성요소를 떼어 놓고 보는 범위의 한계는 그대로 남는다.
    • C · 접근 계층의 차이로 설명하는 것은 부분적이다. 핵심은 구성요소를 연결했을 때 단위 시험이 전제한 가정이 깨진다는 점이다.
    • D · 모의 객체도 잘못 동작하게 만들 수 있고 단위 시험은 실패한다. 다만 모의가 실제와 다르게 동작하면 가정이 어긋나는 것은 맞다.

    7개선으로의 연결

    결함을 CWE 유형으로 분류하면 패턴이 보입니다. 같은 유형이 반복되면 개별 수정이 아니라 구조적 대응이 필요합니다.

    • 안전한 기본값 제공: 프레임워크와 공통 라이브러리에서 안전한 선택이 기본이 되게.
    • 코딩 표준과 린트 규칙: 자동 강제.
    • 교육: 반복되는 유형에 초점.
    • 설계 패턴: 공통 인증·인가 라이브러리(아키텍처 런웨이).
    • 조치 추적, 그리고 위험 수준과 필요한 결정으로 번역한 경영 보고.

    원문 사례 — 같은 CWE 유형의 반복. 결함을 CWE로 분류하자 38%가 같은 유형(출력 인코딩 누락)이었고 개별 수정이 반복되고 있었습니다. 공통 템플릿 엔진에서 자동 인코딩을 기본값으로 만들고, 수동 출력 경로에 린트 규칙을 넣고, 해당 유형 중심으로 교육했더니 그 유형의 신규 발견이 급감했습니다.

    보충같은 인가 오류가 여러 기능에서 반복되면, 개별 항목을 고치는 데서 끝내지 않고 빠진 공통 검증 흐름(PEP)을 확인합니다. 코드 검토 지침과 승인된 테스트를 함께 갱신해야 새 기능에서도 같은 실수가 걸러집니다.

    연결안전한 코딩과 안전한 기본값은 D8.5 안전한 코딩, PEP와 결정·집행 분리는 D5.4 인가 메커니즘의 7절, 근본 원인 분석은 D6.4 결과 분석과 보고의 1절에서 다룹니다.

    원본 연습문제 · D8.3-Q08

    결함을 약점 유형으로 분류하자 전체의 38% 가 출력 인코딩 누락이라는 같은 유형이었고 매 주기마다 개별 수정이 반복되고 있었다. 적절한 대응은?

    1. 그 결함 유형에 부여되는 심각도를 올려 지금보다 빨리 우선 처리되고 수정되게 한다.
    2. 출력 인코딩 결함을 전담할 엔지니어를 지정해 주기마다 보고되는 것을 코드베이스 전반에서 수정하게 한다.
    3. 기술 스택에 내재된 패턴으로 수용하고 잔여 위험으로 추적하면서 웹 애플리케이션 방화벽의 출력 필터링으로 보완한다.
    4. 공통 템플릿 엔진에서 자동 인코딩을 기본값으로 만들고 수동 출력 경로에 린트 규칙을 추가하며 그 유형에 교육을 집중한다.
    정답과 해설 보기

    정답 D. 같은 유형이 반복되면 개별 수정이 아니라 구조적 대응이 필요하다. 안전한 선택이 기본값이 되도록 공통 라이브러리와 프레임워크를 바꾸고 수동 경로에는 린트 규칙으로 자동 강제하며 반복되는 유형에 초점을 둔 교육을 진행하면 신규 발생이 급감한다.

    • A · 수정 속도는 빨라지지만 발생 자체는 줄지 않는다. 주기마다 같은 유형이 38% 나오는 구조를 그대로 두는 것이다.
    • B · 처리량은 늘지만 유입을 막지 못하고 그 한 사람에게 의존한다. 기본값을 안전하게 바꾸면 새로 들어오지 않는다.
    • C · 구조적 대응이 가능한 패턴을 수용으로 처리하는 것이다. 방화벽 필터링은 우회되고, 템플릿 엔진 기본값을 바꾸는 비용보다 비싸다.

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    소프트웨어 보안 효과 보고서다. ㉠ 앱 로그에 인가 거부가 기록되지 않는다. ㉡ 보안 KPI가 “발견 결함 수 감소”이며 2년째 개선 중이다. ㉢ 파이프라인 보안 검증 통과율이 100%다. ㉣ 출력 인코딩 누락이 결함의 38%를 차지하며 매번 개별 수정한다. 가장 적절한 판단 묶음은?

    1. ㉠ WAF 로그로 충분 / ㉡ 계속 유지 / ㉢ 우수한 품질 / ㉣ 수정 속도 향상
    2. ㉠ 인가 거부·입력 검증 실패를 맥락과 함께 구조화 로깅, 중앙 전송·경보 / ㉡ 커버리지·발견 단계 분포·유출 결함과 짝 지표로 재설계 / ㉢ 의도적 결함 코드로 차단 여부 검증, 우회 건수 함께 보고 / ㉣ 템플릿 자동 인코딩 기본값, 린트 규칙, 유형 중심 교육
    3. ㉠ 요청 본문 전체 로깅 / ㉡ 스캔 범위 축소 / ㉢ 차단 기준 완화 / ㉣ 해당 기능 삭제
    4. ㉠ 디버그 로그 활성화 / ㉡ 교육 이수율로 대체 / ㉢ 파이프라인 제거 / ㉣ 개발자 징계
    정답과 해설 보기

    정답 B. ㉠ 3절(기록하지 않는 것은 탐지할 수 없다 — C의 본문 전체 로깅은 민감 정보 유출), ㉡ 5절(발견 건수 감소는 범위 축소일 수 있음), ㉢ 5절·6절(통과율 100%는 느슨한 기준일 수 있음), ㉣ 7절(반복 유형에는 구조적 대응).

    9핵심 개념을 내 말로 설명하기

    복습

    도구를 더 자주 실행하면 어떻게 실제 보안 성과를 알 수 있나요?

    설명 확인하기

    실행 횟수는 활동량을 보여 줍니다. 비슷한 검사 범위에서 고위험 결함의 수와 노출 기간, 재발과 조치 후 재검증 결과가 어떻게 바뀌었는지 비교합니다.

    10핵심 요약

    1. 활동했다 ≠ 안전해졌다. 세 질문: 통제가 작동하는가, 결과가 개선되는가, 남은 위험이 수용 가능한가.
    2. 개발 변경 감사: 버전 이력, 검토·승인, 빌드·배포 이력, 추적성 사슬(요구 → 작업 → 커밋 → 빌드 → 배포), 파이프라인·기능 플래그·권한 변경.
    3. 런타임 로깅: 인증, 인가 거부, 데이터, 입력 검증 실패, 관리, 무결성·가용성. 구조화, 상관 식별자, 맥락, 민감 정보 제외, 중앙 전송, 로그 주입 방지. 기록하지 않는 것은 탐지할 수 없다.
    4. 위험 분석: 도달 가능성, 악용 가능성, 노출, 영향, 보완 통제, 연쇄. 완화: 수정 / 보완 통제(임시) / 회피·제거(가장 확실) / 이전 / 수락. 기술 부채 등록부.
    5. 완화 후: 재검증, 회귀 테스트 케이스 추가, 근본 원인을 표준·라이브러리·패턴·교육에 반영.
    6. 지표: 활동량 vs 결과. 발견 단계 분포가 가장 중요, 유출 결함, 최장 경과. 발견 건수 감소·통과율 100%·이수율 100%의 왜곡 → 짝 지표.
    7. 평가: 의도적 결함으로 통제 작동 검증, 침투 테스트, 검토 샘플링, 성숙도, “왜 앞에서 걸리지 않았는가”. 비즈니스 논리 결함은 도구·단위 시험이 놓침.
    8. 개선: CWE 분류로 반복 유형 파악 → 안전한 기본값, 린트, 교육, 공통 라이브러리.
    원문 위치: D8.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    11주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Effectiveness vs Activity Metrics · 효과성 지표 대 활동량 지표

    결과가 개선되었는지 측정하는 지표와 활동을 수행했는지 측정하는 지표.

    Traceability Chain · 추적성 사슬

    요구사항에서 작업 항목, 커밋, 빌드, 배포까지 연결되는 추적 경로.

    Correlation Identifier · 상관 식별자

    하나의 요청을 여러 서비스에 걸쳐 추적하기 위한 식별자.

    Log Injection · 로그 주입

    사용자 입력이 로그에 그대로 들어가 로그 위조나 파서 공격을 가능하게 하는 결함.

    Append-only Audit Trail · 추가 전용 감사 추적

    수정과 삭제가 불가능한 감사 기록 저장 방식.

    Reachability · 도달 가능성

    취약한 코드 경로가 실제 실행 경로에 포함되는지 여부.

    Escaped Defect · 유출 결함

    테스트 단계를 통과해 운영에서 발견된 결함.

    Defect Density · 결함 밀도

    코드 규모 대비 결함 수.

    Detection Stage Distribution · 발견 단계 분포

    결함이 생애주기의 어느 단계에서 발견되는지의 분포. 왼쪽으로 이동의 증거다.

    Technical Debt Register · 기술 부채 등록부

    미루어진 수정과 개선을 가시화해 관리하는 목록.

    Regression Test · 회귀 테스트

    같은 결함이 다시 들어오지 않게 추가하는 테스트.

    Compensating Control · 보완 통제

    수정이 불가능할 때 위험을 줄이는 대체 수단. 임시 성격이다.
