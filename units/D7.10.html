    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    복구 전략은 BIA가 도출한 목표를 달성할 수 있는 수단을 고르는 일입니다. 백업을 어디에 어떻게 둘지, 복구 사이트를 얼마나 준비해 둘지, 시스템을 얼마나 이중화할지는 모두 “얼마나 오래 멈춰도 되고, 얼마만큼의 데이터를 잃어도 되는가”라는 질문에서 나옵니다. 원본은 두 가지 흔한 오해를 바로잡는 데 힘을 씁니다. RTO만 보고 업무 정상화 시간을 빠뜨리는 것, 그리고 고가용성·복제를 백업으로 착각하는 것입니다.

    원본의 공식: RTO + WRT ≤ MTD. 시스템이 4시간에 복구되어도 정합성 확인과 업무 재개에 6시간이 걸리면 총 10시간이고, MTD가 8시간이면 요구를 충족하지 못합니다. RTO만 보고 WRT를 빠뜨리는 것이 전형적 오류입니다. 또 RPO는 백업 주기가 결정합니다. 일 1회 백업이면 최대 24시간 손실이 가능하므로, RPO를 줄이려면 주기를 줄이거나 복제를 씁니다.

    원문 사례 — RTO는 맞췄으나 MTD를 넘긴 복구. RTO 4시간 목표 시스템이 3시간 40분에 복구되었지만, 정합성 확인과 업무 재개에 7시간이 더 걸려 총 11시간이었고 MTD는 8시간이었습니다. WRT를 별도 측정 항목으로 넣고 전체 복구 시간 기준으로 재설계했습니다.

    가상 예시복구 시험에서 장애 시각을 09시로 잡았더니, 시스템은 12시에 이용 가능했고 업무는 14시에 정상화되었으며 복구된 데이터는 07시 30분까지였습니다. 표로 대조하면 실측 RTO 3시간, WRT 2시간, 총 중단 5시간, 실측 데이터 손실 1시간 30분입니다. 이를 각각 목표 RTO, MTD, RPO와 비교해야 “시험 통과”를 말할 수 있습니다. 시스템이 올라온 시각만 보면 절반만 본 것입니다.

    연결BIA와 복구 지표의 도출은 D1.7 업무연속성 요구사항에서 다룹니다.

    원본 연습문제 · D7.10-Q01

    복구 목표 시간 4시간으로 설계된 시스템이 3시간 40분에 복원되었으나 데이터 정합성 확인과 업무 재개에 7시간이 더 걸렸다. 최대 허용 중단 시간은 8시간이었다. 계획상의 오류는?

    1. 업무 복구 시간이 반영되지 않았다. RTO 와 WRT 의 합이 최대 허용 중단 시간 안에 들어와야 한다.
    2. 백업 일정에 비해 복구 목표 시점이 너무 공격적으로 설정되었다.
    3. 실제 결과에 맞추어 최대 허용 중단 시간을 늘려야 했다.
    4. 복구 목표 시간을 맞추기 위해 데이터 정합성 확인을 생략해야 한다.
    정답과 해설 보기

    정답 A. 시스템 복구 시간만 보고 업무 정상화에 걸리는 시간을 빠뜨리는 것이 복구 계획의 전형적 오류다. RTO 와 WRT 의 합이 MTD 를 넘으면 업무 요구를 충족하지 못한다. WRT 를 별도 측정 항목으로 두고 전체 복구 시간 기준으로 전략을 설계해야 한다.

    • B · 데이터 손실 범위가 아니라 복구 소요 시간이 문제였다.
    • C · MTD 는 업무 영향 분석이 정한 값이며 결과에 맞춰 늘릴 수 없다.
    • D · 정합성 확인 생략은 손상된 데이터로 업무를 재개하는 것이다.

    2백업 유형

    유형복사 대상복원에 필요한 것
    전체 Full전부최신 전체 1개
    증분 Incremental마지막 백업 이후 변경분전체 + 모든 증분
    차분 Differential마지막 전체 이후 변경분전체 + 최신 차분 1개

    증분은 백업이 빠르고 작지만 복원이 느리고 중간 하나가 손상되면 체인이 끊깁니다. 차분은 백업이 점점 커지지만 복원이 간단합니다. 합성 전체(synthetic full)는 증분을 서버 측에서 병합해 복원을 단순화합니다.

    • 스냅샷: 특정 시점 보존. 빠르지만 같은 저장 시스템에 있으면 그 장애·암호화에 함께 영향. 백업의 보완이지 대체가 아닙니다.
    • 연속 데이터 보호(CDP): 변경을 지속 기록해 RPO를 거의 0으로.
    • 복제: 동기식은 RPO 0에 가깝지만 거리 제약, 비동기식은 일부 손실.

    원본의 핵심 문장: 복제는 백업이 아니다. 복제는 오류와 악성 변경도 함께 복제합니다. 삭제와 암호화가 즉시 사본에 반영되므로 시점 복원이 가능한 백업이 별도로 필요합니다.

    원문 사례 — 복제가 백업이라 믿은 조직. 운영 DB를 원거리로 동기 복제하고 이를 백업으로 간주했는데, 운영자가 실수로 테이블을 삭제하자 삭제가 즉시 사본에도 반영되어 복구할 수 없었습니다.

    보충장애 전환(failover)은 “다른 곳에서 서비스를 계속 실행하는 능력”이고, 백업 복원은 “이전 상태로 되돌리는 능력”입니다. 잘못된 변경은 복제되므로, 두 능력을 서로 다른 사고(장비 고장 vs 잘못된 삭제·암호화)를 가정해 따로 시험해야 합니다.

    원문 위치: D7.10.md §3 백업 유형, §7 사례 2

    3백업 저장 전략

    위치장점단점·주의
    온사이트복구가 빠름(RTO 유리)같은 재해에 함께 소실(화재, 수해, 랜섬웨어)
    오프사이트지리적 분리멀수록 운송·복구가 느림. 운송 중 암호화·봉인·추적, 보관 환경
    클라우드지리적 분산, 용량 탄력성복원 대역폭이 RTO를 제약, 전송 비용, 공급자 장애, 계정 분리(운영 계정 침해 시 백업 삭제)

    3-2-1 원칙: 사본 3개, 서로 다른 매체 2종, 그중 1개는 오프사이트. 랜섬웨어를 고려한 확장형 3-2-1-1-0(1개는 오프라인/불변, 복원 오류 0 검증)도 쓰입니다.

    랜섬웨어 대비 백업 요건

    • 분리된 자격증명: 운영 도메인 자격증명으로 백업 시스템에 접근할 수 없게
    • 네트워크 분리: 일반 네트워크에서 도달 불가
    • 불변 저장: 일정 기간 수정·삭제 불가
    • 오프라인 사본(air-gapped)
    • 삭제 지연과 다중 승인
    • 백업 시스템 자체 모니터링: 대량 삭제와 보존 정책 변경을 경보
    • 복원 테스트: 유일한 복구 가능성 증거

    원문 사례 — 랜섬웨어가 함께 암호화한 백업. 백업 저장소가 운영 도메인 자격증명으로 접근 가능하고 일반 네트워크에서 도달 가능했으며, 오프라인 사본은 2년간 만들어지지 않았습니다. 랜섬웨어가 백업까지 암호화했습니다.

    원문 사례 — 클라우드 백업의 복원 대역폭. 재해 시 42TB를 내려받는 데 추정 11일이 걸리는 것으로 계산되었고 RTO는 24시간이었습니다. 최근 데이터는 로컬 캐시에 두고, 대용량 복원은 물리 매체 배송 옵션을 계약에 넣고, 복원 시간을 포함해 RTO를 다시 산정했습니다.

    연결백업 매체 운송과 보호는 D7.5 자원 보호의 5절, 복원 테스트와 백업 검증 지표는 D6.3 보안 프로세스 데이터의 4절에서 다룹니다.

    원본 연습문제 · D7.10-Q15

    어떤 조직이 백업 관리자와 도메인 관리자가 쓰기 가능한 네트워크 공유에 매일 밤 백업한다. 랜섬웨어가 운영 데이터와 백업 공유를 모두 암호화했다. 이를 막을 수 있었던 통제는?

    1. 백업 주기를 4시간마다로 단축한다.
    2. 운영 자격증명이 닿지 않는 불변 또는 오프라인 사본과 분리된 관리 계정, 주기적 복원 시험.
    3. 랜섬웨어가 읽지 못하도록 백업 공유를 암호화한다.
    4. 같은 공유의 다른 폴더명으로 두 번째 사본을 둔다.
    정답과 해설 보기

    정답 B. 랜섬웨어는 침해된 계정의 권한으로 도달 가능한 모든 저장소를 암호화한다. 쓰기 가능한 온라인 공유는 백업이라도 같은 피해 범위에 들어간다. 쓰기 후 변경이 불가한 불변 저장소나 오프라인 사본, 운영과 분리된 백업 관리 계정이 필요하며 복원 가능성은 주기적 시험으로만 확인된다.

    • A · 더 자주 백업해도 같은 공유면 함께 암호화된다.
    • C · 저장 암호화는 암호화 덮어쓰기를 막지 않는다.
    • D · 같은 공유 안의 사본은 같은 권한 범위에 있다.

    4복구 사이트 전략

    유형준비 상태복구 시간 / 비용
    핫 사이트장비·데이터 준비, 지속 동기화, 즉시 전환수분~수시간 / 가장 높음
    웜 사이트하드웨어·네트워크는 있으나 데이터는 백업에서 복원수시간~수일 / 중간 — 가장 흔한 실용적 선택
    콜드 사이트공간, 전원, 냉각, 통신 회선만수주 / 가장 낮음 — 짧은 RTO에는 못 씀
    모바일 사이트컨테이너·차량형 설비가변
    상호 지원다른 조직과 서로 수용 합의가변 / 낮음 — 신뢰성 낮음

    상호 지원 협약의 한계: 상대 조직의 용량 부족, 동시 재해, 기밀 유지, 구속력 약함. 구독형 복구 서비스는 용량 보장 계약(resource capacity agreement)이 없으면 대규모 재해 시 선착순으로 설비가 소진됩니다.

    원본의 경고: “핫 사이트 계약이 있다”는 것이 “전환할 수 있다”를 의미하지 않는다. 전환 절차가 시험되지 않았거나, 데이터 동기화 지연이 RPO를 초과하거나, 용량이 부족하면 작동하지 않습니다.

    원문 사례 — 상호 지원 협약의 실패. 두 조직이 상호 지원 협약을 맺었지만 지역 재해로 양쪽이 동시에 영향받았고, 구속력도 없어 어느 쪽도 상대를 수용할 수 없었습니다.

    원문 사례 — 용량 보장 없는 복구 서비스. 광역 재해 때 공급자 설비가 선착순으로 소진되어 설비를 확보하지 못했습니다. 보장 용량, 우선순위, 동시 발동 고객 수 상한을 계약에 명시했습니다.

    원문 사례 — 핫 사이트가 작동하지 않은 이유. 실제 전환 때 복제 지연이 11시간이어서 RPO 1시간을 충족하지 못했고, 전환 절차가 시험된 적이 없어 DNS 전환과 앱 설정이 수동으로 수시간 걸렸습니다. 복제 지연을 모니터링 지표로 두고, 전환을 자동화하고, 정기 전환 시험을 했습니다.

    연결DR 시험 유형은 D7.12 DRP 테스트, 공급자 계약은 D1.11 공급망 위험 관리에서 다룹니다.

    원본 연습문제 · D7.10-Q06

    어떤 조직이 복구 서비스를 구독했으나 계약에 자원 용량 조항이 없었다. 광역 재해 시 공급자 설비가 선착순으로 소진되어 조직은 용량을 확보하지 못했다. 필요했던 조항은?

    1. 정상 운영 중 미사용 용량에 대한 할인.
    2. 보장 용량과 발동 우선순위, 동시 발동 고객 수 상한을 명시한 자원 용량 보장 계약.
    3. 공급자가 광역 재해를 고객에게 통지하도록 하는 요건.
    4. 발동 실패 후 위약금 없이 계약을 해지할 수 있는 선택권.
    정답과 해설 보기

    정답 B. 구독형 복구 서비스는 다수 고객에게 같은 설비를 약정하는 구조이므로 용량 보장 조항이 없으면 광역 재해 시 선착순으로 소진된다. 보장 용량과 발동 우선순위, 동시 발동 고객 수 상한을 계약에 명시해야 계약이 실제 복구를 보장한다.

    • A · 할인은 복구 가능성과 무관하다.
    • C · 통지는 용량 확보를 보장하지 않는다.
    • D · 사후 해지권은 재해 당시의 복구를 가능하게 하지 않는다.

    구성특성
    액티브-액티브모든 사이트가 서비스. 부하 분산과 즉시 전환. 대기 설비가 실제로 작동하는지 모르는 문제가 사라짐. 대신 데이터 정합성·쓰기 충돌 처리·지연·복잡도
    액티브-패시브하나가 서비스, 다른 하나는 대기

    • 클라우드: 가용 영역 간은 저지연 동기, 리전 간은 비동기. 단일 리전 장애 대비는 리전 간 구성.
    • 공통 실패 지점: 여러 사이트가 같은 인증 체계, DNS, 공급자, 관리 평면에 의존하면 그 지점 하나로 전체가 멈춥니다.

    원문 사례 — 사이트를 늘렸으나 공통 실패 지점이 남은 경우. 세 리전에 서비스를 배치했지만 인증은 단일 리전의 신원 공급자에 의존해, 그 리전 장애 때 세 리전 모두에서 로그인이 불가능했습니다. 신원 공급자를 다중 리전으로 구성하고 장애 시 제한적 접근을 허용하는 비상 경로를 설계했습니다.

    가상 예시두 업무 사이트가 데이터를 자동 복제하고 있어 장비 고장 때는 거의 즉시 넘어갑니다. 그런데 잘못된 거래 삭제도 즉시 양쪽으로 복제되었습니다. 이중 사이트는 “어디서 계속 돌릴 것인가”를 해결했을 뿐, “언제로 되돌릴 것인가”는 해결하지 않습니다. 독립된 시점 백업과, 그 백업에 접근하는 권한·복원 절차를 별도로 시험해야 합니다.

    연결IdP 장애와 비상 계정은 D5.3 연합 식별의 9절에서 다룹니다.

    원본은 단일 실패점 식별이 복원력 설계의 출발점이라고 말하며, 흔히 놓치는 지점으로 인증 체계, DNS, 인증서 발급, 공유 스토리지, 관리 평면, 단일 담당자를 듭니다.

    QoS (Quality of Service)

    제한된 자원을 중요도에 따라 배분합니다. 대역폭 보장과 우선순위, 실시간 트래픽의 지연·지터 관리, 혼잡 시 무엇을 먼저 버리는가. 보안 관점에서 QoS는 가용성 통제이며, 서비스 거부나 재해 복구 때 제한된 회선으로 핵심 업무를 먼저 통과시킵니다. 트래픽 분류를 조작해 우선권을 얻을 수 있으면 통제가 무력화되므로 QoS 정책 자체도 보호 대상입니다.

    7복구 전략 선택

    • BIA가 요구를 정합니다. RTO·RPO가 짧으면 비싼 수단이 필요합니다.
    • 비용과 위험의 균형: 모든 업무에 핫 사이트를 두지 않습니다. 업무 중요도별 차등이 원칙입니다.
    • 의존성: 중요 업무가 의존하는 하위 시스템도 함께 복구되어야 합니다. 업무만 복구하고 의존 서비스를 빠뜨리는 것이 흔한 누락입니다.
    • 인력과 절차: 설비가 있어도 사람과 절차가 없으면 복구되지 않습니다.
    • 공급자 의존: 공급자가 같은 재해에 영향받으면 계획이 무효입니다.
    • 시험으로 검증: 시험되지 않은 계획은 가정에 불과합니다.

    원문 사례 — 의존 서비스를 빠뜨린 복구. 핵심 앱의 복구 전략을 세우고 시험했지만, 실제 재해에서 앱은 복구되었는데 그것이 의존하는 사내 인증 서비스, 메시지 큐, 파일 공유가 복구 범위에 없어 업무가 재개되지 않았습니다. 업무별 의존성 지도를 만들고 복구 범위를 의존 서비스까지 넓혔습니다.

    판단 순서전략을 고를 때 ① 업무별 MTD와 RPO(BIA) ② RTO + WRT가 MTD 안에 드는가 ③ 백업 주기·복제 방식이 RPO를 만족하는가 ④ 사이트 유형과 용량 보장 ⑤ 의존 서비스와 공통 실패 지점 ⑥ 사람·절차·공급자 ⑦ 시험 결과로 확인. 의료기관이라면 ①에서 “진료 지속”과 “환자 안전”이 MTD를 짧게 만드는 핵심 요인입니다.

    연결DR 프로세스와 인력은 D7.11 재해 복구 프로세스, 계획 시험은 D7.12 DRP 테스트, BCP는 D7.13 업무연속성 계획·훈련에서 다룹니다.

    원본 연습문제 · D7.10-Q10

    핵심 애플리케이션의 복구 전략이 정의되고 시험되었다. 실제 재해에서 애플리케이션은 가동되었으나 그것이 의존하는 사내 인증 서비스와 메시지 큐, 파일 공유가 복구 범위에 없어 업무가 재개되지 않았다. 바로잡아야 할 것은?

    1. 모든 외부 의존성을 제거하도록 애플리케이션을 재작성해야 한다.
    2. 업무별 의존성 지도를 작성하고 복구 범위를 의존 서비스까지 확장해야 한다.
    3. 애플리케이션의 복구 목표 시간을 더 단축해야 한다.
    4. 인증 없이 애플리케이션을 운영하도록 업무 사용자를 교육해야 한다.
    정답과 해설 보기

    정답 B. 업무만 복구하고 의존 서비스를 빠뜨리는 것이 흔한 누락이다. 애플리케이션이 가동되어도 인증과 메시지 큐, 파일 공유가 없으면 업무는 재개되지 않는다. 업무별 의존성 지도를 작성해 복구 범위를 의존 서비스까지 확장하고 시험도 의존성을 포함해 수행해야 한다.

    • A · 의존성 제거는 현실적이지 않고 재설계 비용이 과도하다.
    • C · RTO 단축은 범위 누락 문제를 해결하지 않는다.
    • D · 인증 우회 운영은 보안 통제를 포기하는 것이다.

    복습

    이중화와 복구 백업을 각각 어떤 사고에서 확인하나요?

    설명 확인하기

    서버 한 대의 장애에 대체 시스템이 서비스를 이어 가는지 확인합니다. 데이터 삭제나 잘못된 설정이 복제된 경우에는 이전 상태의 독립 사본을 복원할 수 있는지 따로 시험합니다.

    10핵심 요약

    1. 복구 전략 = BIA 목표를 달성하는 수단 선택. BIA → RTO·RPO → 전략 → 구현 → 시험 → 유지.
    2. RTO + WRT ≤ MTD. WRT를 빠뜨리는 것이 전형적 오류. RPO는 백업 주기가 결정.
    3. 전체 / 증분(복원 시 모든 증분, 체인 위험) / 차분(전체 + 최신 차분). 스냅샷·CDP·복제. 복제는 백업이 아니다.
    4. 온사이트(빠름, 함께 소실) / 오프사이트(지리적 분리) / 클라우드(복원 대역폭, 계정 분리). 3-2-1(-1-0).
    5. 랜섬웨어 대비: 분리된 자격증명, 네트워크 분리, 불변, 오프라인, 삭제 지연, 백업 시스템 감시, 복원 테스트.
    6. 핫(즉시, 최고 비용) / 웜(데이터 복원 필요, 흔함) / 콜드(수주) / 모바일 / 상호 지원(신뢰성 낮음). 용량 보장 계약. 계약 ≠ 전환 가능.
    7. 다중 처리: 액티브-액티브(상시 검증, 쓰기 충돌) / 액티브-패시브. 지역 내 동기 + 원거리 비동기. 공통 실패 지점(IdP, DNS, 관리 평면).
    8. 내결함성 = 무중단, 고가용성 = 짧은 중단 허용, 복원력 = 적응·회복. RAID는 백업 아님. QoS = 가용성 통제.
    9. 고가용성 ≠ 백업: HA는 구성요소 장애, 백업은 삭제·랜섬웨어·논리 손상.
    10. 선택: 업무 중요도별 차등, 의존 서비스 포함, 인력·절차, 공급자, 시험.
    원문 위치: D7.10.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    11주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    MTD / MAD — Maximum Tolerable Downtime / Maximum Acceptable Downtime · 최대 허용 중단 시간

    업무가 견딜 수 있는 최대 허용 중단 시간.

    RTO (Recovery Time Objective) · 목표 복구 시간

    시스템을 복구해야 하는 목표 시간.

    WRT (Work Recovery Time) · 업무 정상화 시간

    복구 후 업무를 정상화하는 데 필요한 시간. RTO + WRT ≤ MTD.

    RPO (Recovery Point Objective) · 목표 복구 시점

    허용 가능한 데이터 손실 범위. 백업 주기가 결정한다.

    MTBF / MTTR — Mean Time Between Failures / Mean Time to Repair · 평균 고장 간격 / 평균 수리 시간

    평균 고장 간격과 평균 수리 시간.

    Full / Incremental / Differential Backup · 전체 / 증분 / 차등 백업

    전체 / 마지막 백업 이후 변경분 / 마지막 전체 이후 변경분 백업.

    Synthetic Full · 합성 전체

    증분을 서버 측에서 병합해 전체 백업을 구성하는 방식.

    CDP (Continuous Data Protection) · 지속 데이터 보호

    변경을 지속 기록해 RPO 를 0 에 가깝게 만드는 방식.

    Replication · 복제

    데이터를 다른 위치에 동기 또는 비동기로 복사하는 것. 백업이 아니다.

    3-2-1 Rule · 3-2-1 백업 원칙

    사본 3개, 매체 2종, 그중 1개 오프사이트. 확장형은 3-2-1-1-0.

    Immutable Backup · 불변 백업

    일정 기간 수정·삭제가 불가능한 백업.

    Air-gapped Backup · 오프라인 백업

    네트워크에서 분리된 백업 사본.

    Hot / Warm / Cold Site · 핫 / 웜 / 콜드 복구 사이트

    즉시 전환 가능 / 장비는 있고 데이터 복원 필요 / 공간과 전원만 있는 복구 사이트.

    Reciprocal Agreement · 상호 지원 협약

    다른 조직과 서로 수용하기로 한 합의. 저렴하나 신뢰성이 낮다.

    Resource Capacity Agreement · 용량 보장 계약

    복구 서비스 공급자가 설비 용량을 보장하는 약정.

    Active-Active / Active-Passive · 동시 가동 / 주 시스템과 대기 시스템

    모든 사이트가 서비스하는 구성과 하나가 대기하는 구성.

    Fault Tolerance · 내결함성

    구성요소 고장에도 중단 없이 동작하는 성질.

    High Availability · 고가용성

    중단 시간을 최소화하는 설계. 짧은 전환을 허용한다.

    Resilience · 복원력

    장애와 공격, 부하 변동에 적응하고 회복하는 능력.

    Graceful Degradation · 우아한 성능 저하

    전면 중단 대신 핵심 기능만 유지하는 동작.

    QoS (Quality of Service) · 서비스 품질

    제한된 자원을 중요도에 따라 배분하는 통제.

    Single Point of Failure · 단일 실패점

    하나가 멈추면 전체가 멈추는 지점.

    2. 어떤 조직이 백업 관리자와 도메인 관리자가 쓰기 가능한 네트워크 공유에 매일 밤 백업한다. 랜섬웨어가 운영 데이터와 백업 공유를 모두 암호화했다. 이를 막을 수 있었던 통제는?

    4. 핵심 애플리케이션의 복구 전략이 정의되고 시험되었다. 실제 재해에서 애플리케이션은 가동되었으나 그것이 의존하는 사내 인증 서비스와 메시지 큐, 파일 공유가 복구 범위에 없어 업무가 재개되지 않았다. 바로잡아야 할 것은?
    5. 복구 체계 점검 결과다. ㉠ 운영 DB를 원거리로 동기 복제하며 이것을 백업으로 본다. ㉡ 백업 공유 폴더를 도메인 관리자가 쓸 수 있다. ㉢ 구독형 복구 서비스 계약에 용량 조항이 없다. ㉣ 핵심 앱만 복구 범위에 있고 인증 서비스·메시지 큐는 없다. 가장 적절한 대책 묶음은?
