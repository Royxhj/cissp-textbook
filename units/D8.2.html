    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    원본의 첫 문장은 시야를 코드 밖으로 넓힙니다. 공격 표면은 코드가 아니라 생태계 전체다. 개발자 단말, IDE 플러그인, 패키지 저장소, 빌드 서버, 코드 저장소, 배포 파이프라인, 런타임이 모두 공격 경로입니다. 코드만 안전하게 쓰고 생태계를 방치하면 공격자는 생태계를 노립니다. 공식 개요 8.2는 언어, 라이브러리, 도구, IDE, 런타임, CI/CD, 구성 관리, 코드 저장소, 애플리케이션 보안 테스트를 차례로 듭니다.

    2프로그래밍 언어

    언어 선택이 발생 가능한 결함 유형을 결정합니다(메모리 안전성, 타입 안전성, 관리 런타임, 표준 라이브러리의 안전한 기본값).

    언어 유형특성
    메모리 비안전(C/C++ 계열)메모리 안전 결함(버퍼 오버플로, 해제 후 사용, 이중 해제)이 구조적으로 가능. 완화: 안전한 함수, 경계 검사, 정적 분석, 컴파일러 보호(스택 보호, ASLR, DEP), 퍼징
    메모리 안전메모리 안전 결함 범주를 대부분 제거. 그러나 인가 결함, 입력 검증 미비, 비즈니스 논리 오류는 그대로
    인터프리터동적 평가(eval 류)와 역직렬화가 코드 실행 경로

    원본의 현실적 접근: 신규 개발은 메모리 안전 언어를 선호하고, 기존 코드베이스는 고위험 구성요소를 선별적으로 재작성하며 나머지는 완화 수단으로 관리합니다.

    원문 사례 — 메모리 안전 언어 전환 후에도 남은 결함. 핵심 서비스를 메모리 안전 언어로 재작성해 메모리 안전 결함은 사라졌지만, 인가 검증 누락, 입력 검증 미비, 비즈니스 논리 오류는 그대로 남아 침투 테스트에서 발견되었습니다. 언어 전환이 모든 문제를 해결하지 않습니다.

    연결메모리 보호와 시스템 취약점은 D3.5 아키텍처별 취약점, 안전한 코딩은 D8.5 안전한 코딩에서 다룹니다.

    원문 위치: D8.2.md §3 프로그래밍 언어, §7 사례 10 · 공식 개요 8.2 “Programming languages”

    3라이브러리와 의존성

    원본의 핵심: 보안 수준은 직접 작성한 코드가 아니라 전체 의존성 트리가 결정한다.

    위험내용
    알려진 취약점의존성의 CVE
    전이 의존성직접 선택하지 않은 간접 의존성. 대부분의 의존성이 전이적
    유지되지 않는 패키지취약점이 공개되어도 수정 안 됨
    악성 패키지, 타이포스쿼팅유사 이름으로 오타 설치 유도
    의존성 혼동내부 전용 패키지 이름을 공개 저장소에 올려 빌드가 공개 패키지를 가져오게 함
    패키지 탈취유지관리자 계정 침해로 악성 버전 게시
    빌드 시 스크립트 실행설치 과정에서 임의 코드 실행

    통제: SCA, SBOM, 버전 고정과 잠금 파일(고정하지 않으면 같은 코드가 다른 결과를 만듦), 해시·서명 무결성 검증, 내부 프록시 저장소(검증·캐싱·가용성, 의존성 혼동 대응), 허용 목록, 최소 의존성 원칙(추가하는 모든 의존성이 공격 표면), 유지 상태 평가, 갱신 자동화, 설치 스크립트 차단.

    원본의 핵심 질문 두 개: “우리가 무엇을 쓰는지 아는가”, “새 취약점이 공개되면 몇 시간 안에 영향 범위를 답할 수 있는가”.

    원문 사례 — 전이 의존성의 취약점. 직접 선언한 의존성은 12개였지만 SCA를 도입하자 전체 트리가 486개였고, 중대 취약점은 모두 전이 의존성에 있었습니다.

    원문 사례 — 의존성 혼동 공격. 내부 전용 패키지 이름이 공개 저장소에 등록되어 있지 않았고, 공격자가 그 이름으로 더 높은 버전을 게시하자 빌드가 공개 패키지를 가져왔습니다. 내부 프록시 저장소 강제, 내부 이름 공간의 공개 저장소 선점 등록, 버전 고정으로 대응했습니다.

    보충잠금 파일이 있어도 공급망 검토는 남습니다. 직접 의존성은 승인했는데, 새 빌드에서 그 구성요소가 쓰는 다른 패키지가 추가되었고 팀은 몰랐다면, 잠금 파일은 “무엇이 들어갔는지”를 고정할 뿐 “그것이 괜찮은지”는 말해 주지 않습니다. 잠금 파일 변경을 검토 대상으로 삼고 SCA가 전이 의존성의 변화를 알려 주게 합니다.

    연결SCA·SBOM과 영향 범위 산정은 D7.8 패치·취약점 관리의 10절, 외부 소프트웨어 획득은 D8.4 도입 소프트웨어 평가에서 다룹니다.

    원본 연습문제 · D8.2-Q01

    어떤 조직이 공개 저장소에 등록되지 않은 내부 전용 패키지 이름을 사용했다. 공격자가 그 이름으로 더 높은 버전 번호의 패키지를 공개 저장소에 게시했고 빌드가 공개 패키지를 가져왔다. 이를 가장 직접적으로 막는 통제는?

    1. 모든 빌드에서 소프트웨어 구성 분석을 수행하고, 패키지 게시자나 체크섬이 이전 실행과 다르면 빌드를 실패시킨다.
    2. 의존성 매니페스트의 모든 변경에 코드 검토 승인을 요구해, 설치 전에 다른 사람이 각 패키지 이름을 확인하게 한다.
    3. 의존성 갱신 빈도를 높여 빌드가 항상 최신 수정이 적용된 최신 게시 버전으로 해석되게 한다.
    4. 모든 패키지 설치를 내부 프록시 저장소를 통하게 하고 공개 저장소에 내부 이름 공간을 선점 등록하며 버전을 고정한다.
    정답과 해설 보기

    정답 D. 의존성 혼동은 패키지 해석 경로를 악용한다. 내부 프록시 저장소를 통해서만 패키지를 받으면 외부 해석이 차단되고 공개 저장소에 내부 이름을 선점하면 공격자가 그 이름을 쓸 수 없으며 버전 고정은 더 높은 버전 자동 선택을 막는다.

    • A · 탐지에는 도움이 되지만 해석 경로를 바꾸지 않는다. 악성 패키지가 이미 빌드에 들어온 뒤에 걸리고, 처음 설치되는 패키지는 비교할 이전 값이 없다.
    • B · 검토는 선언된 이름을 보지만 그 이름이 어느 레지스트리에서 해석되는지는 보지 않는다. 혼동 공격은 선언을 바꾸지 않고 해석 결과만 가로챈다.
    • C · 혼동 공격은 공격자가 더 높은 버전 번호로 게시하는 방식이다. 최신을 추구하면 오히려 공격자의 패키지를 더 빨리 가져온다.

    4도구 집합과 IDE

    대상위험통제
    개발자 단말소스 코드, 자격증명, 운영 접근 권한, 서명 키가 있는 고가치 표적엔드포인트 보호, 디스크 암호화, 패치, 최소권한(상시 관리자 대신 적시 상승). 일반 단말과 같거나 더 강하게
    IDE와 플러그인플러그인이 임의 코드를 실행. IDE 설정에 저장된 토큰·비밀번호신뢰 저장소에서만, 허용 목록, 자동 업데이트, 불필요 플러그인 제거, 금고 연동
    AI 코딩 도구코드 전송 범위, 생성된 코드에 취약 패턴 포함 가능전송 범위 통제, 생성 코드의 보안 검토
    빌드 도구·플러그인빌드 스크립트가 임의 코드 실행, 공급망 위험의존성과 동일하게 관리, 빌드 환경이 운영 자격증명에 접근하지 않게

    원문 사례 — IDE 플러그인을 통한 침해. 개발자가 비공식 저장소에서 설치한 IDE 플러그인이 저장된 자격증명과 소스 코드를 외부로 전송했습니다.

    연결적시 권한 상승은 D5.2 식별·인증 전략의 10절, 허용 목록은 D7.7 탐지·예방 수단의 4절에서 다룹니다.

    원본 연습문제 · D8.2-Q16

    개발자들이 공개 마켓플레이스에서 IDE 확장 기능을 자유롭게 설치한다. 어떤 위험이 생기는가?

    1. 확장은 개발자 권한으로 실행되어 작업 공간의 소스 코드와 자격증명, 토큰을 읽을 수 있고 빌드 시점에 코드를 주입할 수 있다. 따라서 승인 목록과 배포자 검증, 사용 전 검토가 필요하다.
    2. 여러 확장을 동시에 돌려 IDE 성능과 안정성이 떨어지고, 팀이 느려지며 편집기가 죽을 때 작업을 잃는다.
    3. 확장의 라이선스 조건과 조직 정책이 충돌해 법무가 검토하지 않은 의무가 생길 수 있다.
    4. 마켓플레이스가 게시된 확장을 검토하고 악성으로 신고된 것을 제거하며 갱신에 게시자 서명이 붙으므로 위험이 거의 없다.
    정답과 해설 보기

    정답 A. 개발자 단말은 소스 코드와 배포 자격증명이 모이는 고가치 환경이다. 확장은 그 안에서 개발자 권한으로 돌기 때문에 침해된 확장 하나가 소스 유출과 공급망 주입으로 이어진다. 이름이 유사한 위장 확장이 실제로 배포된 사례가 있어 배포자 검증과 승인 목록이 필요하다. 마켓플레이스 검토는 완전하지 않다.

    • B · 생산성 문제이고 보안 위험이 아니다. 확장이 개발자 권한으로 작업 공간의 자격증명을 읽고 빌드 시점에 코드를 주입할 수 있다는 점이 핵심이다.
    • C · 관리해야 할 쟁점이지만 일부다. 확장은 소스와 토큰을 읽을 수 있고 빌드에 개입할 수 있으므로 공급망 통제의 대상이다.
    • D · 검토는 완전하지 않고 제거는 신고 뒤에 일어난다. 서명은 게시자를 확인할 뿐이고 그 게시자 계정이 탈취되면 서명된 악성 갱신이 배포된다.

    • RASP: 앱 내부에서 공격을 탐지·차단. 맥락을 알지만 성능 영향과 오탐 관리 필요.
    • 런타임 버전 관리: 지원 종료 런타임은 패치되지 않습니다.
    • 설정 강화: 디버그 모드와 상세 오류 메시지 비활성화. 스택 트레이스 노출이 정찰 정보를 줍니다.
    • 컨테이너: 최소 기본 이미지, 비 root 실행, 이미지 서명과 검증, 특권 컨테이너 금지·호스트 마운트 제한, 이미지 취약점 지속 평가.

    원문 사례 — 상세 오류 메시지 노출. 운영에 디버그 모드가 켜진 채 배포되어 예외 시 스택 트레이스, 프레임워크 버전, 파일 경로, SQL 질의가 노출되었고 침투 테스트 팀이 이를 정찰의 주 출처로 썼습니다. 배포 설정 검증 항목에 넣고 정책 코드로 사전 차단했습니다.

    원문 위치: D8.2.md §3 런타임, §7 사례 8 · 공식 개요 8.2 “Runtime”

    파이프라인 자체의 보호

    원본의 경고: 파이프라인이 침해되면 모든 배포물이 영향을 받는다. 티어 0 자산으로 취급합니다.

    통제내용
    파이프라인 정의를 코드로, 변경 통제 대상에보안 단계 제거에 경보
    최소권한 자격증명운영 전체 권한 금지, 단기 토큰과 작업 범위 한정
    비밀 관리파이프라인 변수에 평문 비밀 금지, 런타임에 금고에서 주입, 로그 마스킹
    빌드 환경 격리와 일회성빌드마다 새 환경
    외부 의존성 통제빌드 중 임의 외부 스크립트 내려받아 실행 금지
    승인 게이트, 직무 분리운영 배포에 사람 승인, 작성자 혼자 배포 불가
    포크 PR 처리외부 기여자 PR이 비밀에 접근하는 파이프라인을 실행하지 않게

    원문 사례 — 파이프라인 자격증명의 과도한 권한. CI 파이프라인이 운영 전체에 대한 장기 자격증명을 갖고 있었고, 포크 PR도 파이프라인을 실행할 수 있어 외부 기여자의 PR이 그 자격증명을 유출했습니다. 작업 범위 단기 토큰, 포크 PR의 비밀 접근 차단, 운영 배포 별도 승인 게이트로 대응했습니다.

    원문 사례 — 파이프라인에서 제거된 보안 단계. 파이프라인 설정이 변경 통제 대상이 아니어서 한 개발자가 보안 스캔 단계를 제거한 것을 3개월간 아무도 몰랐습니다.

    연결파이프라인을 티어 0으로 다루는 이유와 비밀 주입은 D7.3 구성 관리의 4·6절, 파이프라인 변경 통제는 D7.9 변경 관리의 7절에서 다룹니다.

    원본 연습문제 · D8.2-Q23

    API 키 같은 애플리케이션 비밀정보는 어디에 저장해야 하는가?

    1. 런타임에 조회하는 비밀정보 관리 시스템에. 워크로드별로 접근을 통제하고 교체를 지원하며 버전 관리에는 절대 커밋하지 않는다.
    2. 팀 문서 저장소의 공유 스프레드시트에. 접근은 팀으로 제한하고 변경 이력을 시트 상단에 적어 둔다.
    3. 컴파일된 애플리케이션 바이너리에 하드코딩해서. 사람이 읽을 수 없고 조직이 통제하는 서버에만 배포된다.
    4. 소스 코드 저장소의 접근이 제한된 디렉터리에. 필요한 개발자가 해당 코드와 함께 받아 갈 수 있다.
    정답과 해설 보기

    정답 A. 저장소에 커밋한 비밀정보는 이력에 남아 사본과 포크, 빌드 로그로 퍼지므로 삭제해도 회수되지 않는다. 바이너리에 박아 두는 것은 역공학으로 추출되고 교체가 불가능하다. 비밀정보 관리 시스템은 접근을 통제하고 사용을 기록하며 교체를 가능하게 해 유출 시 대응 수단을 남긴다.

    • B · 워크로드 단위 접근 통제와 자동 교체가 불가능하다. 사람이 복사해 쓰는 경로가 생기고, 누가 어떤 값을 언제 읽었는지도 알 수 없다.
    • C · 역공학으로 추출되므로 읽을 수 없다는 전제가 성립하지 않는다. 교체하려면 재빌드와 재배포가 필요해 유출 대응이 느려진다.
    • D · 이력에 영구히 남아 회수가 불가능해진다. 저장소가 복제되면 함께 퍼지고, 디렉터리 권한은 과거 커밋에 소급되지 않는다.

    7코드 저장소와 소프트웨어 구성 관리

    코드 저장소 통제

    • 저장소별 최소권한, MFA 필수(피싱 저항성 선호).
    • 브랜치 보호: 주 브랜치 직접 푸시 금지, PR 필수, 승인자 수, 상태 검사 통과.
    • 서명 커밋: 작성자 위조 방지.
    • 비밀 스캐닝과 이력: 이미 커밋된 비밀은 삭제해도 이력에 남으므로 노출된 자격증명은 반드시 교체.
    • 공개 설정 관리(실수 공개가 흔한 유출 경로), 개인 포크 통제.
    • 웹훅과 통합 앱: 과도한 권한의 통합 앱이 침해 경로.
    • 퇴사자 접근 회수: 외부 호스팅 서비스는 조직 디렉터리와 별개일 수 있음.

    원문 사례 — 커밋 이력에 남은 비밀. 개발자가 API 키를 커밋한 뒤 다음 커밋에서 지웠지만 git 이력에 남아 있었고, 저장소가 실수로 공개 전환되었을 때 노출되었습니다. 원본은 삭제만으로 안전해지지 않는다고 강조합니다.

    원문 사례 — 과도한 권한의 통합 앱. 외부 분석 서비스가 모든 저장소에 읽기와 PR 쓰기 권한을 갖고 있었는데, 그 서비스가 침해되자 공격자가 조직 전체 소스 코드에 접근했습니다.

    소프트웨어 구성 관리

    버전 관리와 추적성, 아티팩트 저장소(운영에 배포된 것이 어떤 커밋인지 추적 가능), 환경 간 승격(개발 → 검증 → 운영에서 같은 아티팩트를 승격, 환경마다 다시 빌드하면 검증한 것과 배포한 것이 달라짐), 재현 가능한 빌드, 구성과 코드 분리.

    원문 사례 — 환경별 재빌드가 만든 불일치. 검증 환경에서 보안 테스트를 통과한 뒤 운영 배포 때 다시 빌드했는데, 그 사이 의존성 버전이 갱신되어 검증한 것과 다른 바이너리가 운영에 나갔습니다.

    보충브랜치 보호는 승인된 변경이 저장소에 들어오게 돕지만, 배포물이 정말 그 커밋에서 만들어졌는지는 별개의 질문입니다. 이를 확인하려면 빌드 실행 기록과 결과물의 식별 정보(해시)를 따로 보존해야 합니다. 의료기기 소프트웨어의 “릴리스 빌드와 출하 바이너리의 동일성” 확인과 같은 생각입니다.

    연결변경 관리와 코드 검토는 D8.1 SDLC 보안의 6절, 계정 생애주기는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D8.2.md §3 소프트웨어 구성 관리와 코드 저장소, §7 사례 3, 사례 4, 사례 6 · 공식 개요 8.2 “Software configuration management (CM)”, “Code repositories”

    9소프트웨어 공급망 위험

    위험내용
    의존성 침해3절의 패키지 위험
    빌드 시스템 침해소스는 정상이나 빌드 결과물에 악성 코드 삽입. 소스 코드 검토로는 탐지되지 않음
    서명 키 유출악성 코드가 정당한 서명을 받음
    배포 채널 침해업데이트 서버가 악성 업데이트 배포
    개발 도구 침해컴파일러와 빌드 도구 자체

    대응: 출처 증명, 재현 가능한 빌드(독립적으로 같은 결과 확인), 아티팩트 서명과 검증, 빌드 환경 격리와 최소권한, SBOM, 공급자 평가.

    판단 순서공급망 증거는 서로 다른 질문에 답합니다. ① SBOM: 이 산출물에 무엇이 들어 있는가 ② 출처 증명: 이 산출물이 어떤 소스와 빌드 경로로 만들어졌는가 ③ 서명 검증: 받은 파일이 신뢰한 서명 주체의 것이고 바뀌지 않았는가. 한 가지 증거가 맞다고 다른 질문의 답이 되지는 않습니다. 빌드 시스템이 침해되면 서명은 유효하게 붙지만 출처 증명과 재현 빌드가 불일치를 드러냅니다.

    연결디지털 서명은 D3.6 암호 솔루션, 공급망 위험 관리는 D1.11 공급망 위험 관리, 외부 소프트웨어 획득은 D8.4 도입 소프트웨어 평가에서 다룹니다.

    원본 연습문제 · D8.2-Q08

    침해된 빌드 시스템이 침해된 소스 저장소보다 더 위험할 수 있는 이유는?

    1. 저장소 침해는 서명 커밋으로 자동 탐지되는데 빌드 시스템에는 그에 상당하는 통제가 없다.
    2. 빌드 시스템은 저장소보다 내부 시스템에 더 넓은 네트워크 접근을 가지므로 거기서 횡적 이동이 더 쉽다.
    3. 소스는 깨끗한 상태로 유지되면서 아티팩트에 악성 코드가 삽입될 수 있어 소스 코드 검토로는 탐지되지 않는다.
    4. 빌드 시스템은 인프라로 취급되어 접근 통제와 자산 목록에서 통상 제외된다.
    정답과 해설 보기

    정답 C. 빌드 시스템 침해는 소스를 변경하지 않고 빌드 결과물에 악성 코드를 넣으므로 코드 검토와 소스 기반 분석으로 탐지되지 않는다. 대응은 아티팩트 서명과 출처 증명, 독립적으로 같은 결과를 확인하는 재현 가능한 빌드, 일회성 격리 빌드 환경과 최소권한이다.

    • A · 서명 커밋은 작성자 위조를 어렵게 하지만 침해를 자동 탐지하지 않는다. 빌드 쪽에도 산출물 서명이라는 대응 통제가 있다.
    • B · 사실인 경우가 많지만 핵심이 아니다. 더 위험한 이유는 소스가 깨끗한 채로 산출물에 코드를 심을 수 있어 코드 검토가 무력해진다는 점이다.
    • D · 실무에서 소홀히 다뤄지는 경우는 있지만 제외해야 하는 것이 아니다. 오히려 운영 환경과 같은 티어 0 으로 다뤄야 한다.

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    1. ㉠ 내부 프록시 저장소 강제·이름 선점·버전 고정 / ㉡ 작업 범위 단기 토큰, 포크 PR 비밀 접근 차단, 운영 배포 승인 게이트 / ㉢ 한 번 빌드한 서명 아티팩트를 승격 / ㉣ 키 교체와 이력 정리, 커밋 단계 비밀 스캐닝
    2. ㉠ 공개 저장소 사용 금지 / ㉡ 자격증명 암호화만 / ㉢ 재빌드 후 다시 테스트 / ㉣ 키가 있는 파일 삭제로 충분
    3. ㉠ SAST 추가 / ㉡ 포크 PR 금지만 / ㉢ 운영에서 직접 빌드 / ㉣ 저장소 비공개 전환만
    4. ㉠ 그대로 / ㉡ 그대로 / ㉢ 그대로 / ㉣ 다음 감사 때

    복습

    승인된 소스와 실제 배포물이 같은 변경에서 만들어졌다고 어떻게 판단하나요?

    설명 확인하기

    저장소의 승인 근거, 빌드 기록, 산출물 식별 정보를 비교합니다. 서명은 받은 결과 검증에 쓰이고, SBOM은 구성 요소를 확인하는 데 쓰입니다.

    12핵심 요약

    1. 공격 표면은 코드가 아니라 생태계 전체. 단말·IDE → 저장소 → 빌드 → 아티팩트 → 배포 → 런타임, 각 지점이 신뢰 사슬의 고리.
    2. 언어: 메모리 비안전은 메모리 결함이 구조적으로 가능(ASLR·DEP·퍼징으로 완화). 메모리 안전 언어도 인가·입력 검증·논리 결함은 그대로.
    3. 의존성: 전체 트리가 보안 수준을 결정, 대부분 전이적. 타이포스쿼팅, 의존성 혼동, 패키지 탈취. SCA, SBOM, 버전 고정·잠금 파일, 내부 프록시 저장소, 최소 의존성.
    4. 도구: 개발자 단말은 고가치 표적, IDE 플러그인은 임의 코드 실행, AI 생성 코드 검토, 빌드 환경은 운영 자격증명 접근 금지.
    5. 런타임: ASLR·DEP·카나리, 최소권한 실행, RASP, 디버그 모드·스택 트레이스 노출 금지, 컨테이너 비 root·서명.
    6. CI/CD: 비밀 스캐닝(커밋 단계) → SAST·SCA → 이미지·IaC → DAST → 서명·출처 증명. 파이프라인 = 티어 0: 최소권한 단기 토큰, 금고 주입, 일회성 빌드, 승인 게이트, 포크 PR.
    7. 저장소: MFA, 브랜치 보호, 서명 커밋, 이력의 비밀은 교체, 통합 앱 권한. SCM: 같은 아티팩트 승격, 재현 가능한 빌드.
    8. AST: SAST(조기·거짓 양성) / DAST(실동작·커버리지) / IAST(중간) / SCA(가장 중요). 넷 다 인가·논리 결함엔 약함. 기준선 방식.
    9. 공급망: 빌드 시스템 침해는 소스 검토로 못 찾음, 서명 키 유출, 배포 채널. SBOM(무엇) · 출처 증명(어떻게) · 서명(누가·무결성)은 다른 질문.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Memory Safety · 메모리 안전성

    버퍼 오버플로와 해제 후 사용 같은 메모리 결함이 구조적으로 방지되는 성질.

    Transitive Dependency · 전이 의존성

    직접 선택하지 않았으나 의존성의 의존성으로 포함되는 구성요소.

    Typosquatting · 타이포스쿼팅

    유명 패키지와 유사한 이름으로 오타 설치를 유도하는 공격.

    Dependency Confusion · 의존성 혼동

    내부 전용 패키지 이름을 공개 저장소에 올려 빌드가 공개 패키지를 가져오게 만드는 공격.

    Pinning / Lockfile · 버전 고정 / 잠금 파일

    의존성 버전을 고정해 빌드 재현성을 확보하는 수단.

    Internal Proxy Repository · 내부 프록시 저장소

    외부 패키지를 내부 미러로 받아 검증과 캐싱, 가용성을 제공하는 저장소.

    SBOM (Software Bill of Materials) · 소프트웨어 구성 명세서

    소프트웨어 구성요소 목록. 영향 범위 산정 속도를 결정한다.

    RASP (Runtime Application Self-Protection) · 실행 중 애플리케이션 자체 보호

    애플리케이션 내부에서 공격을 탐지·차단하는 런타임 보호.

    Provenance · 출처 증명

    아티팩트가 어떤 소스와 빌드 과정으로 만들어졌는지 입증하는 증거.

    Reproducible Build · 재현 가능한 빌드

    같은 소스에서 항상 같은 결과물이 나오는 빌드.

    Promotion · 환경 승격

    개발에서 검증, 운영으로 같은 아티팩트를 이동시키는 방식.

    Branch Protection · 브랜치 보호

    주 브랜치 직접 푸시 금지와 PR·승인 요구 설정.

    Signed Commit · 서명 커밋

    작성자 위조를 방지하는 커밋 서명.

    SAST / DAST / IAST / SCA — Static / Dynamic / Interactive Application Security Testing / Software Composition Analysis · 정적 / 동적 / 상호작용형 보안 시험 / 소프트웨어 구성 분석

    정적 분석, 동적 분석, 계측 기반 분석, 구성요소 분석.

    SLSA — Supply-chain Levels for Software Artifacts · 소프트웨어 산출물 공급망 보증 수준

    소프트웨어 아티팩트의 공급망 보증 수준을 정의한 프레임워크 개념.
