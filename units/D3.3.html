    연습문제 6개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    보안 담당자가 가장 흔히 받는 질문은 “무엇을 사야 하나요?”입니다. 원본의 답은 그 질문의 순서를 뒤집는 것입니다. 무엇을 사느냐가 아니라 무엇을 충족해야 하느냐에서 출발해야 합니다. 이 단원은 요구사항에서 통제로 내려가는 경로(NIST RMF), 제품의 보안을 평가하는 국제 기준(Common Criteria), 그리고 “평가했다”와 “운영을 승인했다”의 차이를 다룹니다.

    이 단원의 위치

    단원어떻게 이어지는가
    D1.9 위험 관리위험 평가, 통제 가치(ALE 감소분 − 비용), 잔여위험 수용 (2절, 4절, 7절)
    D1.2 보안 개념 (CIA 등)FIPS 199 범주화와 FIPS 200의 최고값 원칙. RMF의 Categorize 단계 (2절)
    D2.6 데이터 보안 통제스코핑·테일러링의 상세. 이 단원은 그것이 RMF의 Select 단계에 속한다는 것을 본다 (3절)
    D3.1 안전한 설계 원칙설계 원칙. 통제가 서로 보완하도록 예방·탐지·교정을 섞는다 (4절)
    D3.2 보안 모델TCSEC이 바탕으로 삼은 Bell-LaPadula (6절)

    1통제는 요구사항에서 출발한다

    왜 필요한가

    원본은 도구나 제품에서 출발하면 반드시 공백이나 과잉이 생긴다고 말합니다. 제품은 자기가 잘하는 것을 하지, 우리가 필요한 것을 하지 않기 때문입니다.

    비즈니스 목표·법규
    →
    보안 요구사항
    →
    위험 평가
    →
    베이스라인 → 스코핑 → 테일러링
    →
    구현 → 평가 → 인가 → 모니터링

    원본의 기준 문장입니다. 통제는 요구사항을 충족하기 위한 수단이지 목적이 아니다. “이 통제가 어떤 요구사항을 충족하는가”에 답할 수 없다면 그 통제는 다시 검토할 대상입니다.

    요구사항은 어디서 오는가

    출처예시
    법규·규제개인정보 보호, 산업별 규제
    계약SLA, PCI DSS
    비즈니스가용성 목표, 신뢰도
    위험 평가식별된 위험에 대한 대응
    내부 정책조직 표준과 기준선

    요구사항은 검증 가능하게 써야 통제로 번역됩니다. “안전해야 한다”가 아니라 “저장 데이터는 승인된 알고리즘으로 암호화한다”처럼 씁니다.

    가상 예시영업팀이 “경쟁사가 쓰는 보안 장비를 우리도 들이자”고 제안합니다. 이 단원의 방식으로 바꾸면 질문이 달라집니다. 우리에게 적용되는 요구가 무엇인가(의료기기 사이버보안 규제가 요구하는 것, 병원 고객이 계약으로 요구하는 것, 우리 위험 평가에서 나온 것), 그중 아직 충족되지 않은 것이 무엇인가, 그 장비가 그 빈 곳을 채우는가. 이 질문에 답한 뒤에야 장비 이야기가 의미를 가집니다.

    연결검증 가능한 규칙의 조건은 D2.2 자산 취급 요구사항, 법·계약상 의무의 차이는 D1.4 법률·규제·컴플라이언스, 요구사항을 개발 단계에서 정의하고 추적하는 일은 D3.10 정보시스템 생애주기과 D8.1 SDLC 보안에서 다룹니다.

    원문 위치: D3.3.md §2, §3 보안 요구사항의 출처 · 공식 개요 3.3 “Select controls based upon systems security requirements”

    2NIST RMF 7단계

    쉬운 설명

    NIST SP 800-37의 위험 관리 프레임워크(RMF, Risk Management Framework)는 시스템 하나에 통제를 고르고 운영을 승인하기까지의 단계를 정리한 것입니다.

    단계하는 일
    1. Prepare 준비역할, 위험 전략, 조직 수준의 준비
    2. Categorize 범주화정보와 시스템의 영향도 분류(FIPS 199)
    3. Select 선택베이스라인을 고르고 조정
    4. Implement 구현통제 배치와 문서화
    5. Assess 평가통제가 의도대로 작동하는지 검증
    6. Authorize 인가책임자가 잔여위험을 수용하고 운영 승인
    7. Monitor 모니터링지속적 감시와 재평가

    원본이 짚는 세 가지

    • Categorize가 Select보다 먼저다. 무엇을 보호하는지 알아야 통제를 고를 수 있다.
    • Authorize는 경영진의 위험 수용 결정이다. 기술 담당자가 하는 것이 아니다.
    • Monitor는 끝이 아니라 순환이다. 변경이 생기면 다시 평가한다.

    원문 사례 — 범주화를 건너뛴 통제 선택. 보안팀이 업계 체크리스트를 그대로 적용해 모든 시스템에 같은 통제를 배치했습니다. 영향도가 낮은 시스템에는 비용이 과했고, 높은 시스템에는 보호가 부족했습니다. Categorize가 Select보다 먼저인 이유가 여기 있습니다.

    보충단계 이름의 순서는 “알고 → 고르고 → 넣고 → 확인하고 → 책임지고 → 지켜본다”로 기억하면 자연스럽습니다. 첫 단계 Prepare는 2018년 개정(Rev. 2)에서 추가된 단계로, 시스템 하나하나보다 앞서 조직 차원의 위험 전략과 역할을 정해 두는 일입니다(개정 연도는 원본에 없는 보충). 범주화에는 D1.2 보안 개념 (CIA 등)에서 본 FIPS 199(축별 영향도)와 FIPS 200(그중 최고값으로 최소 요구 수준 결정)이 쓰입니다.

    CISSP 관점RMF 상황에서는 ① 지문의 활동이 일곱 단계 중 어디인지 붙여 보고 ② “다음에 할 일”을 물으면 순서상 바로 뒤 단계를 고릅니다. 통제를 고르기 전에 범주화가 빠졌으면 그것이 답이고, 평가가 끝났는데 운영 중이라면 인가(위험 수용 결정)가 빠진 것입니다.

    원본 연습문제 · D3.3-Q05

    보안팀이 업계 체크리스트의 동일한 통제 집합을 모든 시스템에 적용했다. 저영향 시스템에는 과도한 비용이, 고영향 시스템에는 부족한 보호가 적용되었다. 무엇을 건너뛴 것인가?

    1. ISO 27001 인증을 취득하는 것.
    2. 외부 침투 테스트 업체를 고용하는 것.
    3. 상용 거버넌스 플랫폼을 구매하는 것.
    4. 통제를 선택하기 전에 시스템을 영향도 등급으로 범주화하는 것.
    정답과 해설 보기

    정답 D. 영향도를 모르면 적정 통제 수준을 정할 수 없다. RMF 에서 Categorize 가 Select 보다 먼저인 이유이며 FIPS 199 의 high water mark 로 시스템 범주를 정한 뒤 그에 맞는 베이스라인을 고른다.

    • A · 인증은 체계 수립의 결과이지 통제 수준 결정 방법이 아니다.
    • B · 침투 테스트는 검증 활동이며 선택 기준이 아니다.
    • C · 도구는 판단의 근거를 만들어 주지 않는다.

    문제 목록으로 돌아가기

    3베이스라인 선정과 조정

    베이스라인(Baseline)은 시스템 영향도 등급에 대응하는 통제의 기본 집합입니다. NIST SP 800-53B는 Low / Moderate / High 베이스라인을 제공합니다.

    1. 영향도 범주화(Low / Moderate / High)
    2. 해당 베이스라인 선택
    3. 스코핑 — 적용 대상이 아닌 통제 제외
    4. 테일러링 — 강화·완화·보완·구체화
    5. 보완 통제 식별 — 적용할 수 없는 통제의 대체
    6. 문서화와 승인

    스코핑과 테일러링의 상세는 D2.6 데이터 보안 통제에서 다뤘습니다. 원본이 여기서 강조하는 것은 이 과정이 RMF의 Select 단계에 속한다는 점입니다.

    오버레이(Overlay)는 특정 환경이나 기술에 맞춰 미리 조정해 둔 통제 집합입니다. 클라우드, 산업제어시스템, 프라이버시 같은 영역별 오버레이가 있어 조정 작업을 줄여 줍니다.

    보충조정 단계마다 남겨야 하는 결과물이 다릅니다. 스코핑은 “이 통제가 어느 자산·연결 지점까지 적용되는가”의 경계, 테일러링은 “어떤 값과 구현으로 충족하는가”, 보완은 “기본 방식을 못 쓰는 이유와 대체 조치가 줄이는 위험”입니다. 이유가 문서에 남아 있어야 나중의 평가자가 같은 결정을 이해하고 검증할 수 있습니다.

    원문 위치: D3.3.md §3 베이스라인 선정과 조정, §6 NIST SP 800-53 Rev.5 / 800-53B

    4통제를 고르는 기준

    기준묻는 것
    효과성식별된 위험을 실제로 줄이는가
    비용 대비 효과ALE 감소분이 비용보다 큰가
    운영 영향업무를 과도하게 방해하지 않는가
    기존 통제와의 중복이미 다른 통제가 덮고 있지 않은가
    측정 가능성작동 여부를 검증할 수 있는가
    규제 충족법적 요구를 만족하는가

    원본이 기억하라고 하는 예외가 있습니다. 규제가 요구하는 통제는 경제성과 무관하게 도입한다. 그리고 통제는 서로 보완해야 하므로, 예방이 뚫리면 탐지가, 탐지 뒤에는 대응이 작동하도록 예방·탐지·교정을 함께 배치합니다.

    판단 순서통제 후보를 놓고 고를 때 ① 법규·계약이 요구하는가(그렇다면 경제성 계산 전에 도입 대상) ② 아니라면 이 통제가 어떤 요구·위험을 줄이는가 ③ 그 감소분이 비용보다 큰가 ④ 이미 같은 위험을 덮는 통제가 있는가 ⑤ 작동하는지 확인할 방법이 있는가 순서로 봅니다. ⑤에 답이 없으면 4단계(Assess)에서 평가할 수 없으므로 설계를 다시 봐야 합니다.

    연결ALE와 통제 가치 계산, 법규 통제의 예외, 통제의 기능 분류는 D1.9 위험 관리, 서로 다른 성격의 통제를 겹치는 심층 방어는 D3.1 안전한 설계 원칙에서 다뤘습니다.

    원본 연습문제 · D3.3-Q08

    적용되는 규제가 요구하는 통제의 연간 비용이 그것이 막는 기대 손실보다 크다. 가장 적절한 결정은?

    1. 더 약한 통제를 구현하고 승인 없이 동등하다고 문서화한다.
    2. 통제 가치 계산이 음수이므로 도입하지 않는다.
    3. 규제 의무를 보험으로 전가한다.
    4. 규제 요구사항은 비용 대비 효과로 거부할 수 없으므로 도입한다.
    정답과 해설 보기

    정답 D. 통제 가치가 음수이면 도입하지 않는 것이 일반 원칙이지만 법규나 규제가 요구하는 통제는 경제성과 무관하게 도입해야 한다. 미준수의 결과는 과징금뿐 아니라 영업 제한과 형사 책임까지 이어질 수 있다.

    • A · 승인 없는 임의 대체는 허위 문서화이자 컴플라이언스 위반이다.
    • B · 규제 요구에는 경제성 판단이 적용되지 않는다.
    • C · 보험은 재무 손실 일부를 보전할 뿐 규제 의무를 이전하지 못한다.

    5Common Criteria — 제품 보안 평가

    왜 필요한가

    보안 제품을 살 때 “이 제품은 안전합니다”라는 공급자의 말만 믿을 수는 없습니다. Common Criteria(공통 평가 기준, ISO/IEC 15408)는 보안 제품을 객관적 기준으로 평가하기 위한 국제 표준입니다.

    네 가지 핵심 용어

    용어의미누가 쓰나
    TOE Target of Evaluation평가 대상 제품·시스템—
    PP Protection Profile 보호 프로파일이런 종류의 제품에 필요한 보안 요구사항 집합구매자 쪽
    ST Security Target 보안 목표 명세자사 제품이 제공하는 보안 기능의 기술공급자 쪽
    EAL Evaluation Assurance Level평가 보증 수준 EAL1~EAL7—

    원본의 요약입니다. PP = “우리는 이런 제품이 필요하다”(요구), ST = “우리 제품은 이렇게 한다”(주장). 평가는 ST가 PP를 충족하는지, 그리고 제품이 ST대로 동작하는지를 검증합니다.

    EAL 등급

    등급의미
    EAL1기능 테스트
    EAL2구조 테스트
    EAL3체계적 테스트·점검
    EAL4체계적 설계·테스트·검토 (상용 제품에 널리 쓰이는 상한)
    EAL5준형식적 설계·테스트
    EAL6준형식적 검증 설계·테스트
    EAL7형식적 검증 설계·테스트

    EAL은 보안 강도가 아니다

    원본이 가장 중요한 함정으로 꼽는 부분입니다. EAL이 높다고 더 안전한 제품이 아닙니다. EAL은 “주장한 보안 기능을 얼마나 엄격하게 검증했는가”를 나타냅니다. 보안 기능이 빈약한 제품도 그 빈약한 기능을 철저히 검증하면 높은 EAL을 받을 수 있습니다. 그래서 EAL 숫자만 비교하는 것은 잘못된 평가이며, 먼저 ST에 적힌 보안 기능이 우리 요구(PP)에 맞는지 봐야 합니다.

    원문 사례 — EAL 숫자만 비교한 조달. 두 방화벽을 비교하며 EAL4 제품 대신 EAL5 제품을 골랐습니다. 도입 후, 조직에 필요했던 애플리케이션 계층 검사 기능이 그 제품의 ST에 들어 있지 않다는 것이 드러났습니다.

    보충EAL을 시험 점수가 아니라 채점의 엄격함으로 생각하면 이해가 쉽습니다. 쉬운 문제 다섯 개를 아주 엄격하게 채점받은 학생과 어려운 문제 스무 개를 보통 수준으로 채점받은 학생 중 누가 더 실력이 있는지는 채점의 엄격함만으로 알 수 없습니다. 또 평가 결과는 평가 문서가 정한 범위와 가정(설치 형태, 켜 둔 기능) 안에서만 유효합니다. 실제 배치가 평가 범위 밖 기능을 쓰거나 다른 형태라면 그 부분은 따로 검증해야 합니다.

    판단 순서인증받은 제품을 고를 때 ① 우리 환경에 꼭 필요한 기능과 운용 조건을 먼저 적고(PP의 역할) ② 각 제품의 ST가 그 기능을 평가 범위에 포함하는지 확인하고 ③ 평가된 구성과 우리 배치 형태가 같은지 보고 ④ 그다음에 EAL로 검증의 깊이를 비교합니다.

    연결암호 모듈의 인증(FIPS 140)은 D3.4 시스템 보안 기능·D3.6 암호 솔루션, 도입할 소프트웨어의 보안 평가는 D8.4 도입 소프트웨어 평가에서 다룹니다. 원본은 CC 평가 방법론으로 ISO/IEC 18045를 듭니다.

    원본 연습문제 · D3.3-Q01

    구매자가 더 안전할 것이라 가정하고 EAL4 인증 제품 대신 EAL5 인증 방화벽을 선택했다. 배포 후 필요했던 애플리케이션 계층 검사 기능이 없다는 것이 드러났다. 무엇을 오해한 것인가?

    1. EAL 은 평가의 엄격함을 나타내며 보안 기능의 풍부함이나 강도를 뜻하지 않는다.
    2. EAL 등급은 3년 후 만료되어 갱신해야 한다.
    3. EAL5 제품은 정부 배포에만 유효하다.
    4. EAL 등급은 제품이 아니라 조직에 적용된다.
    정답과 해설 보기

    정답 A. EAL 은 주장한 보안 기능을 얼마나 엄격하게 검증했는지를 나타낸다. 기능이 빈약한 제품도 그 기능을 철저히 검증하면 높은 EAL 을 받을 수 있다. 따라서 PP 로 요구를 정의하고 각 제품의 ST 가 그 요구를 충족하는지 먼저 확인한 뒤 EAL 을 비교해야 한다.

    • B · 만료 주기 문제가 본 사례의 원인이 아니다.
    • C · EAL 은 정부 전용 제도가 아니다.
    • D · EAL 은 평가 대상 제품(TOE)에 부여된다.

    공통 평가 기준에서 평가 보증 등급이 서술하는 것은?

    1. 시험 중 발견된 취약점의 수.
    2. 제품이 절대적으로 얼마나 안전한지.
    3. 공급업체가 지원을 제공할 기간.
    4. 수행된 평가의 깊이와 엄격성. 제품이 모든 용도에 안전하다는 보증이 아니며 보안 주장 자체는 별도로 기술된다.
    정답과 해설 보기

    정답 D. 보증 등급이 높다는 것은 더 엄격하게 검증했다는 뜻이고 무엇을 주장했는지는 보안 목표 문서에 따로 있다. 낮은 등급으로 평가된 제품이 특정 용도에서 충분할 수 있고 높은 등급 제품이 다른 용도에는 맞지 않을 수 있다. 그래서 등급만 보고 고르면 안 되고 평가 대상 범위와 보안 주장을 함께 확인해야 한다.

    • A · 취약점 수를 표현하지 않는다.
    • B · 절대적 안전성을 뜻하지 않는다.
    • C · 지원 기간과 무관하다.

    6역사적 평가 기준

    기준특징
    TCSEC (Orange Book)미국. 기밀성 중심, D~A1 등급. BLP 기반
    ITSEC유럽. 기능(F)과 보증(E)을 분리해 평가
    Common Criteria국제 표준. TCSEC·ITSEC을 통합·대체

    원본의 설명으로, TCSEC은 기밀성에 치우쳐 무결성·가용성을 거의 다루지 않았고 네트워크 환경을 전제하지 않았습니다. ITSEC은 기능과 보증을 분리해 유연성을 높였고, Common Criteria가 이들을 통합했습니다.

    보충세 기준의 흐름은 “하나의 등급에 기능과 검증을 묶었다(TCSEC) → 둘을 떼어 냈다(ITSEC) → 뗀 구조를 국제 표준으로 만들었다(CC)”입니다. CC에서 기능은 PP·ST가, 검증의 깊이는 EAL이 말하는 것이 바로 ITSEC의 분리를 이어받은 결과입니다. 5절의 “EAL은 기능이 아니다”가 이 역사에서 나옵니다. TCSEC이 기밀성 중심인 이유는 그 바탕이 D3.2 보안 모델의 Bell-LaPadula이기 때문입니다.

    원문 위치: D3.3.md §3 역사적 평가 기준, §5 셋째 표

    7인증과 인가

    쉬운 설명

    구분의미주체
    인증 Certification통제가 요구대로 구현·작동하는지 기술적으로 평가평가자
    인가 Accreditation평가 결과를 근거로 운영을 공식 승인경영진·책임자

    원본의 정리입니다. 인증은 “제대로 되었는가”를 확인하는 기술 활동이고, 인가는 “그 위험을 안고 운영하겠다”는 경영 결정입니다. RMF에서 Assess가 인증에, Authorize가 인가에 해당하며, 현대 RMF 용어로는 ATO(Authorization to Operate)라고 합니다. 인가는 잔여위험을 수용하는 행위이므로 적절한 권한을 가진 사람이 해야 합니다.

    원문 사례 — 인증과 인가를 혼동한 경우. 평가팀이 통제 평가를 마치고 “시스템이 인증되었으니 운영해도 된다”고 통보했습니다. 그러나 잔여위험 수용 결정은 없었습니다. 평가 보고서에 남은 위험이 적혀 있었고, 그것을 안고 운영할지는 책임자가 판단해야 했습니다.

    용어 주의‘인증’이라는 한국어는 Certification 외에 Authentication(신원 확인)에도 쓰입니다. 이 절의 인증은 시스템 평가의 Certification이고, D5.2 식별·인증 전략의 사용자 인증과는 다른 개념입니다. ISO 27001 ‘인증’(certification)은 인증기관의 심사 결과로 받는 것으로, 이 절의 시스템 인증과 단어는 같지만 맥락이 다릅니다.

    연결잔여위험과 위험 수용의 권한은 D1.9 위험 관리와 D1.3 보안 거버넌스, 통제 평가(Assess)의 방법은 D6.1 평가·테스트·감사 전략·D6.2 보안 통제 테스트에서 다룹니다.

    이해 확인 · 자작 상황 문제 (실제 시험 문제 아님)

    새 병원 연동 시스템의 통제 평가가 끝났다. 평가 보고서에는 “원격 유지보수 경로의 다중요소 인증 미적용 — 중간 위험”이 남아 있다. 운영 개시일은 내일이다. 다음 중 운영 개시 전에 반드시 있어야 하는 것은?

    1. 평가팀장의 “인증 완료” 서명
    2. 남은 위험을 알고도 운영을 승인한다는, 권한 있는 책임자의 인가(위험 수용) 결정
    3. 보안 장비의 EAL 인증서 사본
    4. 개발팀의 운영 준비 완료 보고
    정답과 해설 보기

    정답 B. 평가(인증)는 끝났고, 남은 위험을 안고 운영할지의 결정(인가)이 필요합니다.

    • A: 인증은 기술적 확인입니다. 평가자가 운영을 승인할 권한은 없습니다(원문 사례 3).
    • C: 제품 평가는 이 시스템의 운영 승인과 다릅니다.
    • D: 운영 준비는 필요하지만 위험 수용 결정을 대신하지 못합니다.

    8통제를 고른 뒤

    • 구현 문서화 — 무엇을 왜 어떻게 적용했는지
    • 평가 — 설계대로 작동하는지 시험
    • 지속 모니터링 — 환경이 바뀌면 통제의 적절성도 바뀐다
    • 재평가 트리거 — 중대 변경, 침해, 규제 변경, 정기 주기

    원문 사례 — 보완 통제로 메운 공백. 다중요소 인증이 요구되었지만 레거시 시스템이 지원하지 않았습니다. 조직은 IP 접근 제한, 전용 단말, 세션 녹화, 강화된 모니터링을 보완 통제로 적용하고 위험 수용을 기한과 함께 문서화했습니다. 테일러링의 보완 통제가 적용된 전형적인 사례입니다.

    보충통제를 고르는 순간부터 “나중에 무엇을 보고 작동한다고 판단할 것인가”를 함께 정해 두면 평가가 쉬워집니다. 어떤 요구가, 어느 자산에서, 어떤 동작으로 충족되어야 하는지 적고, 확인 방법이 설정 확인인지, 기록 확인인지, 실제 동작 시험인지 정합니다. 운영 중 큰 변경이 생기면 이 연결표가 재평가 범위의 출발점이 됩니다.

    연결보완 통제와 기한 있는 위험 수용은 D2.5 자산 보존 (EOL·EOS)·D2.6 데이터 보안 통제·D1.6 정책·표준·절차·지침, 지속 모니터링의 지표는 D6.3 보안 프로세스 데이터, 변경 관리는 D7.9 변경 관리에서 다룹니다.

    원문 위치: D3.3.md §3 통제 선택 이후, §7 사례 4

    9종합 이해 확인

    종합 · 자작 상황 문제

    한 조직의 신규 시스템 도입 과정이다. ㉠ 보안팀이 제품 카탈로그에서 장비를 먼저 고른 뒤 요구사항 문서를 그에 맞춰 작성했다. ㉡ 영향도 범주화 없이 High 베이스라인을 모든 시스템에 적용했다. ㉢ 두 제품 중 EAL이 높은 쪽을 기능 확인 없이 골랐다. ㉣ 평가 완료 후 평가팀이 운영을 승인했다. 바르게 지적한 것은?

    1. ㉠ 요구사항에서 출발해야 한다 / ㉡ Categorize가 Select보다 먼저다 / ㉢ ST가 요구를 충족하는지 먼저 본다 / ㉣ 인가는 권한 있는 책임자의 위험 수용 결정이다
    2. ㉠ 문제없음 / ㉡ 높을수록 안전하다 / ㉢ EAL이 높을수록 기능이 많다 / ㉣ 평가자가 인가할 수 있다
    3. ㉠ 오버레이를 썼어야 한다 / ㉡ 스코핑만 하면 된다 / ㉢ TCSEC으로 다시 평가한다 / ㉣ ATO는 필요 없다
    4. ㉠ 제품 선정은 Monitor 단계다 / ㉡ Prepare를 건너뛰었다 / ㉢ PP는 공급자가 쓴다 / ㉣ 인증이 곧 인가다
    정답과 해설 보기

    정답 A. ㉠ 1절, ㉡ 2절(사례 2), ㉢ 5절(사례 1), ㉣ 7절(사례 3). D의 “PP는 공급자가 쓴다”는 반대입니다. PP는 구매자 쪽 요구, ST가 공급자의 주장입니다.

    10핵심 개념을 내 말로 설명하기

    복습

    평가 등급이 높은 제품을 쓰면 시스템 통제 요구가 모두 충족되나요?

    설명 확인하기

    제품 등급은 정해진 평가 범위에서 보안 주장에 대한 보증을 알려 줍니다. 시스템의 요구를 따로 정의한 뒤 실제 기능·구성·배치와 운영 증거를 비교해야 합니다.

    11핵심 요약

    1. 통제 선택은 요구사항 → 위험 평가 → 베이스라인 → 조정 → 구현 순. 통제는 수단이지 목적이 아니다.
    2. 요구사항 출처: 법규, 계약, 비즈니스, 위험 평가, 내부 정책. 검증 가능하게 쓴다.
    3. RMF 7단계: Prepare - Categorize - Select - Implement - Assess - Authorize - Monitor.
    4. Categorize가 Select보다 먼저. Authorize = 경영진의 잔여위험 수용(ATO). Monitor는 순환.
    5. 베이스라인(800-53B의 Low/Moderate/High) → 스코핑 → 테일러링 → 보완 통제 → 문서화·승인. 이 과정은 Select 단계. 오버레이 = 특정 환경용 사전 조정 통제 집합.
    6. 선택 기준: 효과성, 비용 대비 효과, 운영 영향, 중복, 측정 가능성, 규제 충족. 규제 요구 통제는 경제성 판단의 예외. 예방·탐지·교정을 함께.
    7. Common Criteria = ISO/IEC 15408. TOE = 평가 대상, PP = 구매자의 요구, ST = 공급자의 주장, EAL = 보증 수준(EAL1~7, EAL4가 상용에 널리 쓰임).
    8. EAL은 검증의 엄격함이지 보안 강도·기능의 풍부함이 아니다. ST가 요구를 충족하는지 먼저 본다.
    9. TCSEC(기밀성 중심, D~A1, BLP 기반) → ITSEC(기능·보증 분리) → CC(통합).
    10. 인증(Certification) = 기술적 평가(평가자) / 인가(Accreditation) = 운영 승인·위험 수용(경영진).
    원문 위치: D3.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약(14항목). 원본의 “오답 방향”, “가장 자주 나오는 함정” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다. 원본 §6의 NIST SP 800-30(위험 평가), ISO/IEC 27001 부속서 A와 적용성 명세서(SoA)는 여기에 적어 둡니다.

    12주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    RMF — Risk Management Framework · 위험 관리 프레임워크

    NIST SP 800-37 의 위험관리 수명주기. Prepare-Categorize-Select-Implement-Assess-Authorize-Monitor.

    Control Baseline · 통제 베이스라인

    시스템 영향도 등급에 대응하는 통제의 기본 집합. NIST SP 800-53B 가 Low/Moderate/High 를 제공한다.

    Overlay · 오버레이

    특정 환경·기술에 맞춰 미리 조정된 통제 집합. 조정 작업을 줄여 준다.

    Common Criteria · 공통평가기준

    ISO/IEC 15408. 보안 제품을 객관적으로 평가하는 국제 표준.

    TOE — Target of Evaluation · 평가 대상

    Common Criteria 에서 평가를 받는 제품이나 시스템.

    PP — Protection Profile · 보호 프로파일

    구매자 관점에서 요구하는 보안 요구사항 집합.

    ST — Security Target · 보안 목표명세서

    공급자가 자사 제품의 보안 기능을 기술한 문서.

    EAL — Evaluation Assurance Level · 평가 보증 수준

    EAL1~EAL7. 보안 기능을 얼마나 엄격하게 검증했는지를 나타내며, 제품의 보안 강도 자체가 아니다.

    TCSEC — Trusted Computer System Evaluation Criteria (Orange Book) · 신뢰 컴퓨터 시스템 평가 기준

    미국의 초기 평가 기준. 기밀성 중심이며 D~A1 등급을 사용했다.

    ITSEC — Information Technology Security Evaluation Criteria · 정보기술 보안 평가 기준

    유럽의 평가 기준. 기능과 보증을 분리해 평가했다.

    Certification · 인증

    통제가 요구대로 구현·작동하는지 확인하는 기술적 평가.

    Accreditation · 인가

    평가 결과를 근거로 운영을 공식 승인하는 경영 결정. 잔여위험 수용을 포함한다.

    ATO — Authorization to Operate · 운영 인가

    현대 RMF 에서 인가를 가리키는 용어.

    연습문제 6개

    문항을 선택하면 본문의 지문과 해설로 이동합니다.

    1. 보안팀이 업계 체크리스트의 동일한 통제 집합을 모든 시스템에 적용했다. 저영향 시스템에는 과도한 비용이, 고영향 시스템에는 부족한 보호가 적용되었다. 무엇을 건너뛴 것인가?
    2. 적용되는 규제가 요구하는 통제의 연간 비용이 그것이 막는 기대 손실보다 크다. 가장 적절한 결정은?
    3. 구매자가 더 안전할 것이라 가정하고 EAL4 인증 제품 대신 EAL5 인증 방화벽을 선택했다. 배포 후 필요했던 애플리케이션 계층 검사 기능이 없다는 것이 드러났다. 무엇을 오해한 것인가?
    4. 공통 평가 기준에서 평가 보증 등급이 서술하는 것은?
    5. 새 병원 연동 시스템의 통제 평가가 끝났다. 평가 보고서에는 “원격 유지보수 경로의 다중요소 인증 미적용 — 중간 위험”이 남아 있다. 운영 개시일은 내일이다. 다음 중 운영 개시 전에 반드시 있어야 하는 것은?
    6. 한 조직의 신규 시스템 도입 과정이다. ㉠ 보안팀이 제품 카탈로그에서 장비를 먼저 고른 뒤 요구사항 문서를 그에 맞춰 작성했다. ㉡ 영향도 범주화 없이 High 베이스라인을 모든 시스템에 적용했다. ㉢ 두 제품 중 EAL이 높은 쪽을 기능 확인 없이 골랐다. ㉣ 평가 완료 후 평가팀이 운영을 승인했다. 바르게 지적한 것은?
