    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    정보시스템은 누군가의 요구에서 시작해 만들어지고, 운영되다가 언젠가 폐기됩니다. 이 단원은 그 일생 전체에서 보안이 각 단계에 무엇을 넣어야 하는지를 다룹니다. 원본이 가장 강조하는 원칙은 하나입니다. 보안은 앞단에 있을수록 저렴하다.

    이 단원의 위치

    단원어떻게 이어지는가

    D3.3 통제 선택 (RMF·CC)요구사항에서 통제로, RMF의 평가와 인가(ATO) (2절, 6~7절)
    D2.3 안전한 프로비저닝 · D2.5 자산 보존 (EOL·EOS)골든 이미지·기준선·인벤토리 등록, EOL 추적과 폐기 (7~9절)
    D2.4 데이터 생애주기폐기 시 데이터 처리와 매체 정화 (9절)

    원본은 결함 수정 비용을 요구사항 단계 1로 놓고 설계 수 배, 구현 수십 배, 운영 수백 배로 설명합니다. 그리고 설계 결함은 운영 단계에서 코드 수정으로 해결되지 않는 경우가 많다고 덧붙입니다. 아키텍처를 다시 그려야 하기 때문입니다.

    확인 필요위 비용 배수는 원본이 제시한 대략적인 크기입니다. 이런 배수는 오래된 연구들에서 인용되어 왔지만 근거와 수치에 대한 논쟁이 있습니다(일반 지식에 근거한 주의). 이 교재는 “늦게 고칠수록 비싸고, 설계 결함은 코드로 못 고칠 수 있다”는 방향만 받아들이고 수치는 외울 대상으로 다루지 않습니다.

    1이해관계자 요구 정의

    원본은 누구의 요구인지 식별하는 것이 먼저라고 합니다.

    이해관계자관심사
    사업 부서기능, 일정, 비용
    최종 사용자사용성, 성능
    보안기밀성·무결성·가용성 요구
    법무·컴플라이언스규제 충족
    운영유지보수성, 모니터링
    데이터 소유자분류와 접근 권한

    원본의 경고는 이것입니다. 보안이 이 단계에 참여하지 못하면 이후 모든 단계에서 뒤따라가게 된다. 요구사항으로 명시되지 않은 보안은 “추가 요청”이 되어 일정과 비용 협상의 대상이 됩니다. 상충하는 요구(사용성과 보안, 성능과 암호화)를 조정하는 것도 이 단계의 일입니다.

    원문 사례 — 요구사항에 없던 보안. 보안팀이 요구사항 정의에 참여하지 못한 채 구현이 끝났고, 보안 검토에서 암호화와 감사 로깅이 전혀 없다는 것이 확인되었습니다. 사업 부서는 “요구사항에 없던 것”이라며 추가 일정과 예산을 거부했고, 결국 위험 수용 문서를 쓰고 그대로 출시했습니다.

    가상 예시의료기기 소프트웨어라면 이 단계의 이해관계자에 규제 당국의 요구(시판 전 사이버보안 문서, SBOM, 위협 모델), 병원 IT 부서(네트워크 분리, 계정 연동), 임상 사용자(응급 시 빠른 접근)가 더해집니다. 이들의 요구가 처음부터 목록에 있으면 “응급 시 빠른 접근”과 “강한 인증”의 충돌을 설계 단계에서 조정(예: 비상 접근 + 강한 감사)할 수 있습니다. 출시 직전에 발견하면 이 단원의 원문 사례처럼 위험 수용으로 넘기게 됩니다.

    원문 위치: D3.10.md §2, §3 1) 이해관계자 요구 정의, §7 사례 1 · 공식 개요 3.10 “Stakeholders needs and requirements”

    2요구사항 분석

    도출된 요구를 검증 가능한 명세로 바꾸는 단계입니다.

    • 구체적 — “안전해야 한다”가 아니라 “저장 데이터는 승인된 알고리즘으로 암호화한다”
    • 검증 가능 — 충족 여부를 시험할 수 있어야 한다
    • 추적 가능 — 어떤 위험이나 규제에서 나왔는지 연결된다

    요구사항의 출처는 법규·규제, 계약, 조직 정책·표준, 위험 평가 결과, 위협 모델링 결과입니다.

    요구사항 추적 매트릭스(RTM, Requirements Traceability Matrix)로 요구사항-설계-구현-시험을 연결하면, 나중에 “이 통제가 왜 있는가”와 “이 요구가 구현되었는가”를 양쪽 방향으로 확인할 수 있습니다.

    보충RTM이 양방향이어야 하는 이유는 두 가지 실패가 반대 방향이기 때문입니다. 위에서 아래로(요구 → 시험) 따라가면 “구현되지 않은 요구”가 보이고, 아래에서 위로(통제 → 요구) 따라가면 “아무 요구에도 연결되지 않은 통제”가 보입니다. 앞의 것은 보안 공백, 뒤의 것은 왜 있는지 모르는 통제라서 나중에 누군가 지워도 아무도 반대하지 못합니다. D3.3 통제 선택 (RMF·CC)의 “이 통제가 어떤 요구사항을 충족하는가에 답할 수 없다면 재검토 대상”과 같은 생각입니다.

    원본 연습문제 · D3.10-Q07

    설계와 시험에 가장 유용한 보안 요구사항 기술은?

    1. 시스템은 가능한 경우 업계 모범 사례를 따라야 한다.
    2. 프로젝트 전반에 걸쳐 보안이 고려되어야 한다.
    3. 저장된 고객 기록은 조직 승인 알고리즘으로 암호화하고 키는 전사 키 관리 시스템에서 관리한다.
    4. 시스템은 알려진 모든 위협과 알려지지 않은 위협에 안전해야 한다.
    정답과 해설 보기

    정답 C. 좋은 보안 요구사항은 구체적이고 검증 가능하며 추적 가능해야 한다. 무엇을 어떤 방식으로 보호하는지 명시되어야 설계로 번역되고 시험으로 확인된다. 안전해야 한다는 표현은 요구사항이 아니라 구호이며 충족 여부를 판단할 수 없다.

    • A · 가능한 경우라는 표현이 모호해 집행할 수 없다.
    • B · 선언적 문장으로 시험 기준이 되지 못한다.
    • D · 알려지지 않은 위협까지 보장한다는 것은 검증 불가능하다.

    3아키텍처 설계

    보안이 구조로 들어가는 단계입니다.

    • 안전 설계 원칙 적용 — 최소권한, 심층 방어, 안전한 기본값, 제로 트러스트
    • 위협 모델링 — 데이터 흐름도와 신뢰 경계 식별
    • 통제 선택 — 베이스라인 선정과 조정
    • 데이터 흐름과 분류 매핑
    • 장애 모드 설계 — 안전한 실패

    원본은 이 단계의 결정이 이후를 구속한다고 말합니다. 신뢰 경계를 잘못 그으면 구현을 아무리 잘해도 구조적 취약점이 남습니다.

    연결설계 원칙은 D3.1 안전한 설계 원칙, 위협 모델링은 D1.10 위협 모델링, 통제 선택은 D3.3 통제 선택 (RMF·CC), 데이터 분류는 D2.1 자산 식별과 분류에서 다뤘습니다.

    원문 위치: D3.10.md §3 3) 아키텍처 설계 · 공식 개요 3.10 “Architectural design”

    4개발·구현

    • 안전한 코딩 표준과 교육
    • SAST — 정적 분석으로 코드 수준 결함 탐지
    • 의존성 관리와 SBOM
    • 비밀 정보 관리 — 코드에 자격증명 하드코딩 금지
    • 코드 리뷰 — 동료 검토와 보안 관점 검토
    • 개발 환경 보호 — 빌드 파이프라인 무결성

    원본은 개발 환경에 운영 데이터를 쓰지 않는다는 원칙도 다시 강조합니다. 마스킹 데이터나 합성 데이터를 씁니다.

    연결안전한 코딩은 D8.5 안전한 코딩, SAST 같은 소프트웨어 보안 시험은 D8.3 소프트웨어 보안 효과성, 파이프라인과 의존성 보안은 D8.2 개발 생태계 보안 통제, SBOM은 D1.11 공급망 위험 관리, 운영 데이터의 개발 환경 사용 금지는 D2.4 데이터 생애주기에서 다룹니다.

    원문 위치: D3.10.md §3 4) 개발·구현 · 공식 개요 3.10 “Development / implementation”

    5통합

    구성 요소를 결합하는 단계이며 새로운 신뢰 경계가 생깁니다.

    • 인터페이스 보안 — API 인증·인가
    • 구성 요소 간 상호 인증
    • 제3자 구성 요소의 보안 평가
    • 통합 환경의 접근 통제
    • 구성 관리 — 어떤 버전이 결합되었는지 추적

    원본은 통합 지점이 가장 자주 간과된다고 말합니다. 개별 구성 요소는 안전해도 그 사이의 연결이 평문이거나 인증되지 않는 경우가 많습니다.

    원문 사례 — 통합 지점의 평문 통신. 각 마이크로서비스는 자체 보안 검토를 통과했지만, 서비스 간 통신이 인증 없는 평문 HTTP였습니다. 구성 요소별 검토에서는 드러나지 않았습니다.

    보충통합 시험은 “정상일 때”만 보면 부족합니다. 예를 들어 인사 시스템과 계정 시스템이 각각 정상이어도 전보 이벤트가 전달되지 않으면 이전 부서 권한이 남습니다. 정상 이벤트, 누락·지연된 이벤트, 재시도 상황 각각에서 최종 권한 상태를 확인해야 하고, 두 시스템 사이의 연계에 책임자를 정해 두어야 “상대 팀이 처리할 줄 알았다”는 공백이 줄어듭니다.

    연결API와 마이크로서비스의 취약점은 D3.5 아키텍처별 취약점, 서비스 간에도 위치를 믿지 않는 제로 트러스트는 D3.1 안전한 설계 원칙, 계정 생애주기와 전보 처리는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D3.10.md §3 5) 통합, §7 사례 3 · 공식 개요 3.10 “Integration”

    6검증과 확인

    쉬운 설명

    원본이 이 단원에서 가장 중요한 구분으로 꼽는 부분입니다.

    구분묻는 질문기준
    검증 Verification“제대로 만들고 있는가?”
    Are we building the product right?    		명세 충족 여부
    확인 Validation“올바른 것을 만들고 있는가?”
    Are we building the right product?    		실제 요구·목적 충족 여부

    원본의 요약은 명세대로 완벽히 만들었어도(검증 통과) 명세 자체가 틀렸다면(확인 실패) 쓸모가 없다입니다.

    활동분류
    코드 리뷰, 단위 시험, 명세 대비 시험검증
    보안 테스트, 침투 테스트, 사용자 수용 시험확인
    통제 평가(RMF Assess)검증 중심
    인가(RMF Authorize)위험 수용 결정

    원문 사례 — 검증은 통과하고 확인은 실패한 시스템. 접근 통제 모듈이 명세대로 정확히 구현되어 모든 단위 시험과 코드 리뷰를 통과했습니다. 그런데 명세가 역할 기반 권한만 고려하고 데이터 소유권을 반영하지 않아, 같은 역할이면 다른 부서 데이터도 볼 수 있었습니다.

    보충두 활동의 기록을 따로 남기면 문제가 생겼을 때 어디로 돌아가야 할지 알 수 있습니다. 검증 실패는 구현(4단계)으로, 확인 실패는 요구사항(1~2단계)으로 돌아갑니다. 설계 문서가 “세션 30분 제한”을 정했고 정확히 구현했는데(검증 성공), 사용자가 30분 안에 핵심 업무를 끝낼 수 없다면(확인 실패), 고칠 것은 코드가 아니라 요구사항입니다. 의료기기 분야에서는 설계 검증(design verification)과 설계 확인(design validation)을 규제 요구로 구분하는 것도 같은 생각입니다.

    CISSP 관점지문이 “명세대로 구현되었다”, “시험을 모두 통과했다”라고 하면서 문제가 남아 있다고 하면 확인(validation)의 실패를 의심합니다. 반대로 “명세와 구현이 다르다”면 검증(verification)의 실패입니다. 기준이 명세인지 실제 요구인지를 먼저 가립니다.

    연결이 단계에서 수행하는 취약점 평가·침투 테스트는 D6.2 보안 통제 테스트, 통제 평가와 인가는 D3.3 통제 선택 (RMF·CC), 소프트웨어 개발 생애주기에서의 검증·확인은 D8.1 SDLC 보안에서 다룹니다.

    원본 연습문제 · D3.10-Q01

    접근 통제 모듈이 명세대로 정확히 구현되어 모든 단위 시험을 통과했으나, 명세 자체가 데이터 소유권을 누락해 사용자가 다른 부서 기록을 볼 수 있다. 실패한 활동은?

    1. 검증. 구현이 명세와 일치하지 않았기 때문.
    2. 확인. 명세와 일치함에도 실제 요구를 충족하지 못했기 때문.
    3. 통합. 구성요소가 잘못 결합되었기 때문.
    4. 형상 관리. 기준선이 기록되지 않았기 때문.
    정답과 해설 보기

    정답 B. 검증(Verification)은 명세대로 만들었는지를 묻고 확인(Validation)은 올바른 것을 만들었는지를 묻는다. 이 사례는 구현이 명세와 일치해 검증은 통과했지만 명세 자체가 실제 요구를 반영하지 못해 확인에 실패한 경우다. 명세가 틀리면 완벽한 구현도 틀린 결과를 낳는다.

    • A · 구현은 명세와 일치했으므로 검증은 통과했다.
    • C · 구성요소 결합의 문제가 아니다.
    • D · 기준선 기록과 무관한 요구 정의의 결함이다.

    연결골든 이미지·기준선·인벤토리 등록은 D2.3 안전한 프로비저닝, 안전한 실패와 오류 메시지는 D3.1 안전한 설계 원칙, 배포와 롤백을 포함한 변경 관리는 D7.9 변경 관리에서 다룹니다.

    시스템을 운영 환경으로 전환하는 올바른 순서는?

    1. 먼저 운영자를 교육하고 그들이 배운 것을 근거로 수락 기준을 작성한다.
    2. 문제가 즉시 눈에 띄도록 피크 시간대에 전환한다.
    3. 운영 환경에 배포한 뒤 문제가 생기는 대로 설정을 검증하고 운영자를 교육한다.
    4. 수락 기준 충족을 확인하고 운영 환경 설정을 강화·검증한 뒤 문서를 인계하고 운영자를 교육하고 모니터링과 백업이 갖춰졌는지 확인한 다음 복구 계획을 준비한 상태로 전환한다.
    정답과 해설 보기

    정답 D. 전환은 시스템이 보안 책임과 함께 운영 조직으로 넘어가는 시점이다. 모니터링과 백업이 없는 상태로 운영에 들어가면 장애를 알지 못하고 복구할 수단도 없다. 수락 기준은 설계·개발 단계에서 정의된 것이고 전환 단계에서는 그 충족을 확인한다. 복구 계획 없이 전환하면 실패 시 되돌릴 수 없다.

    • A · 수락 기준은 앞 단계 산출물이다.
    • B · 피크 시간 전환은 영향을 최대화한다.
    • C · 검증 없는 배포는 사고로 이어진다.

    • B · 접근 권한은 별개 영역이다.
    • C · 하드웨어만이 아니다.

    문서대로 만들었어도 현업이 쓸 수 없다면 어느 단계의 확인이 부족했나요?

    설명 확인하기

    명세 충족을 보는 검증에 성공했더라도 업무 요구를 충족하는지 보는 확인에는 실패할 수 있습니다. 요구사항을 실제 사용자 작업과 테스트의 기대 결과로 연결합니다.

    14핵심 요약

    1. 9단계: 이해관계자 요구 → 요구사항 분석 → 아키텍처 설계 → 개발·구현 → 통합 → 검증·확인 → 전환·배포 → 운영·유지 → 폐기·처분.
    2. 보안은 앞단일수록 저렴하다. 설계 결함은 코드 수정으로 못 고칠 수 있다.
    3. 보안은 요구사항 정의 단계에서 확보한다. 명시되지 않은 보안은 협상 대상이 된다.
    4. 좋은 요구사항: 구체적 · 검증 가능 · 추적 가능. RTM으로 양방향 추적.
    5. 설계에 위협 모델링과 설계 원칙. 설계 결정이 이후를 구속한다.
    6. 개발: 안전한 코딩, SAST, SBOM, 비밀 정보 관리, 코드 리뷰. 개발 환경에 운영 데이터 금지.
    7. 통합은 새 신뢰 경계를 만든다. 인터페이스 인증이 흔한 공백.
    8. 검증 = 명세 충족(“제대로 만드는가”), 확인 = 실제 요구 충족(“올바른 것을 만드는가”). 명세가 틀리면 완벽한 구현도 무의미.
    9. 배포 시점이 보안 기준선. 골든 이미지, 설정 점검(환경별 차이), ATO, 인벤토리 등록과 소유자 지정, 롤백 계획.
    10. 운영: 패치, 드리프트 점검, 권한 검토, 모니터링, 재평가, EOL 추적. 중대 변경은 생애주기를 되돌린다.
    11. 폐기: 의존성 확인 → 데이터 처리 → 정화 → 라이선스 해지 → 권한 회수 → 인벤토리 제거 → 증빙.
    12. 형상 관리 = 상태 기록·통제, 변경 관리 = 승인·추적. 애자일에서도 보안 요구는 백로그에.
    원문 위치: D3.10.md §8 CISSP 시험 관점, §9 핵심 암기 요약(15항목). 원본의 “시험에 자주 나온다” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    15주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    SDLC / SELC — Software Development Life Cycle / Systems Engineering Life Cycle · 소프트웨어 개발 생애주기 / 시스템 엔지니어링 생애주기

    소프트웨어 개발 생애주기와 시스템 엔지니어링 생애주기. 착안부터 폐기까지의 전 과정을 다룬다.

    Stakeholder · 이해관계자

    시스템에 이해를 갖는 모든 주체. 사업, 사용자, 보안, 법무, 운영, 데이터 소유자를 포함한다.

    RTM — Requirements Traceability Matrix · 요구사항 추적 매트릭스

    요구사항-설계-구현-시험을 연결해 양방향 추적을 가능하게 하는 도구.

    Verification · 검증

    명세대로 만들었는지 확인하는 활동. "제대로 만들고 있는가"를 묻는다.

    Validation · 확인

    실제 요구와 목적을 충족하는지 확인하는 활동. "올바른 것을 만들고 있는가"를 묻는다.

    Integration · 통합

    구성요소를 결합하는 단계. 새로운 신뢰 경계와 인터페이스 보안 요구가 생긴다.

    Transition / Deployment · 전환·배포

    운영 환경으로 이전하는 단계. 기준선 적용, 인가 획득, 인벤토리 등록이 수반된다.

    Sustainment · 유지

    운영 중 시스템의 성능과 보안 상태를 지속 유지하는 활동.

    Configuration Management · 형상 관리

    시스템 구성요소와 그 상태를 기록하고 통제하는 활동.

    Change Management · 변경 관리

    변경을 승인하고 추적하는 절차. 승인되지 않은 변경이 드리프트의 주원인이다.

    Baseline · 기준선

    형상 관리에서 승인된 기준 상태. 이후 변경은 이 기준에서 추적된다.

    Retirement / Disposal · 폐기·처분

    시스템 운영을 종료하고 데이터·매체·권한·인벤토리를 정리하는 단계.
