    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    직접 개발한 소프트웨어는 설계에 참여하고 코드를 검토하고 고칠 수 있습니다. 도입한 소프트웨어는 대개 그렇게 할 수 없습니다. 원본의 출발점은 “도입 소프트웨어의 보안은 코드를 볼 수 없는 상태에서 평가해야 한다”입니다. 그래서 통제 수단이 요구사항, 계약, 증거, 설정, 통합 지점으로 바뀝니다. 공식 개요 8.4는 대상을 COTS, 오픈소스, 제3자, 관리형 서비스, 클라우드 서비스(SaaS/IaaS/PaaS)로 나눕니다. ISO 27001 심사원에게는 공급자 관계 통제와 클라우드 서비스 이용 통제를 소프트웨어 관점에서 다시 보는 단원입니다.

    직접 개발도입 소프트웨어

    요구사항을 먼저 정합니다. 원본의 표현으로는 평가 기준이 없으면 평가가 주관이 됩니다. 조달 전에 정할 항목은 다음과 같습니다.

    • 인증과 인가: SSO 연합, MFA, 역할 기반 권한, 최소권한 설정 가능성
    • 감사와 로깅: 어떤 이벤트를 기록하고 내보낼 수 있는가. 로그 내보내기 기능이 없으면 중앙 탐지에 통합할 수 없습니다.
    • 암호화: 저장·전송, 키 관리 모델(고객 관리 키 지원 여부)
    • 데이터 처리: 저장 위치, 하위 수탁자, 처리 목적 제한
    • 취약점 관리: 패치 주기, 긴급 패치 정책, 지원 기간
    • 사고 통지: 기한과 내용 · 가용성: SLA, RTO·RPO · 통합 보안: API 인증, 웹훅, 권한 범위
    • 종료 지원: 데이터 반환 형식, 삭제 증명

    원문 사례 — 요구사항 없이 수행한 평가. SaaS 후보 셋을 평가했지만 보안 요구사항이 미리 정해져 있지 않아 공급자 자료 비교에 그쳤고, 선정 뒤에야 SSO 연합과 로그 내보내기를 지원하지 않는다는 사실이 드러났습니다. 조달 전에 요구 항목을 정의하고 후보를 그 기준으로 비교하도록 바꿨습니다.

    원문 사례 — 로그 내보내기 기능 부재. 업무 SaaS가 감사 로그를 화면으로만 보여 주고 내보내기 API가 없어 중앙 탐지에 통합할 수 없었습니다. 요구사항에 로그 내보내기와 보존 기간을 필수로 넣고, 기존 서비스에는 주기적 수동 추출과 보존 절차를 임시 보완 통제로 적용했습니다.

    원본 연습문제 · D8.4-Q15

    소프트웨어 도입 전 평가의 올바른 순서는?

    1. 업무와 보안 요구사항을 정의하고 다룰 데이터를 분류한 뒤 그 요구사항에 비추어 공급업체와 제품을 평가하고 통제된 환경에서 시험하고 계약상 보안 조건을 협의한 다음 잔여 위험을 문서화해 승인한다.
    2. 프로젝트가 지연되지 않도록 먼저 구매하고, 배포 중에 평가해 발견된 공백은 다음 릴리스 주기에 시정할 위험으로 기록한다.
    3. 표준 보안 질의서를 공급업체에 보내 응답을 기준점과 대조해 점수화하고, 통과하면 제품을 승인한다.
    4. 실제 결과가 요건 문서보다 무게가 있으므로 먼저 공급업체 운영 서비스를 대상으로 침투 시험을 수행한다.
    정답과 해설 보기

    정답 A. 요구사항과 데이터 분류가 없으면 무엇을 기준으로 평가할지 정해지지 않는다. 구매 후 평가는 협상력을 잃은 상태이며 문제가 나와도 되돌리기 어렵다. 공급업체 서비스에 대한 무단 침투 시험은 계약 위반이자 법적 문제가 될 수 있고, 질의서 응답만으로는 자기 보고를 검증하지 않은 것이다.

    • B · 구매 후에는 협상력과 선택권이 모두 사라진다. 요건을 충족하지 못하는 제품을 이미 들인 뒤이므로 남는 선택은 위험 수용뿐이다.
    • C · 질의서는 무엇을 확인할지 식별하는 출발점이고 그 자체가 검증은 아니다. 자기 보고를 독립 증거로 뒷받침하지 않으면 보증 수준이 낮다.
    • D · 요건을 정하기 전의 시험은 무엇을 합격으로 볼지 기준이 없다. 무단 시험은 계약 위반이자 법적 문제이며 다중 테넌트 환경에서는 타 고객에게 영향을 준다.

    2실사와 증거의 신뢰도

    증거신뢰도확인할 점
    제3자 감사 보고서(SOC 2 Type II 등)높음범위, 기간, 예외 사항, 고객이 수행할 보완 통제(CUEC)
    인증(ISO 27001 등)범위 확인 필요사용하는 서비스가 인증 범위에 들어가는가
    직접 테스트(허용 시)높음공급자 정책과 동의 범위
    공급자 질의서 응답낮음자기 주장 — 보조 수단
    마케팅 자료증거가 아님

    핵심 하위 수탁자, 즉 공급자의 공급자(4차 위험)도 평가 범위입니다.

    원문 사례 — 인증 범위의 함정. 공급자가 ISO 27001 인증서를 제시했지만 적용 범위가 본사 사무 환경이었고 조직이 쓰는 서비스 운영 환경은 빠져 있었습니다. 인증서의 적용 범위 명세를 확인하고 사용하는 서비스가 포함되는지 검증하는 절차를 추가했습니다.

    보충ISO 27001 심사원이라면 인증서의 적용 범위(scope statement)와 적용성 보고서(SoA)를 먼저 보는 습관이 이미 있을 것입니다. 도입 평가에서도 같은 질문을 합니다. “이 인증은 내가 쓰려는 서비스와 데이터센터를 덮는가?” SOC 2 Type II 보고서라면 여기에 “평가 기간이 언제이고, 예외가 있었으며, 고객 측에 넘겨진 통제(CUEC)는 무엇인가”가 더해집니다.

    가상 예시인사 SaaS 하나를 도입할 때도 항목마다 증거의 출처가 다릅니다. 공급자 시설의 출입 통제는 해당 시설과 평가 기간이 포함된 독립 보고서에서 통제와 예외를 확인합니다. 우리 테넌트의 관리자 권한 회수는 공급자 보고서가 아니라 우리 환경의 설정과 검토 표본, 실제 회수 기록으로 확인합니다. 계약 종료 뒤 자료 반환은 계약 조항을 찾고, 승인된 방식으로 실제 반출이 되는지 시험합니다. 판단 기준은 보고서 종류가 아니라 누가 그 통제를 수행하며 어떤 기간·환경의 증거로 확인할 수 있는가입니다.

    연결SOC 보고서의 유형과 CUEC는 D6.1 평가·테스트·감사 전략, 감사 증거와 감사권은 D6.5 보안 감사에서 다룹니다.

    원본 연습문제 · D8.4-Q01

    어떤 공급자가 ISO 27001 인증서를 제시했다. 확인해 보니 인증 범위가 공급자 본사 사무 환경이었고 조직이 사용할 서비스 운영 환경은 제외되어 있었다. 교훈은?

    1. 인증 증거는 적용 범위를 확인해 실제로 사용하는 서비스가 포함되는지 검증해야 한다.
    2. 인증서의 최신성이 결정적 확인 항목이므로, 발급 후 12개월이 지난 인증서는 만료된 것으로 보고 반려해야 한다.
    3. ISO 27001 은 기술 통제가 아니라 관리체계를 인증하므로, 평가 증거로 쓰지 않고 배경 정보로만 읽어야 한다.
    4. 인증 대신 SOC 2 Type II 보고서를 요구해야 한다. 특정 시점의 적합성이 아니라 일정 기간의 운영 효과성을 보고하기 때문이다.
    정답과 해설 보기

    정답 A. 인증은 유효한 증거이지만 범위가 핵심이다. 조직 전체가 아니라 특정 서비스나 데이터센터, 사무 환경만 포함될 수 있으므로 인증서의 적용 범위 명세를 반드시 확인하고 사용하는 서비스가 그 범위에 들어가는지 검증해야 한다.

    • B · ISO 27001 인증은 3년 주기이고 매년 사후심사를 받는다. 유효 기간 안의 인증서는 유효하며, 이 사례의 결함은 기간이 아니라 적용 범위다.
    • C · 관리체계 인증이라는 설명 자체는 맞지만 결론이 틀렸다. 범위가 적절하면 유효한 증거이고, 기술 통제는 SOC 2 나 시험 결과로 보완한다.
    • D · Type II 의 성격 설명은 맞지만 둘은 대체가 아니라 보완 관계다. SOC 2 보고서도 범위를 확인해야 하므로 범위 확인이라는 핵심은 그대로 남는다.

    판단 순서구매한 제품의 안전한 설정은 누구 책임일까요? 공급자는 기본값을 정해 출하하지만, 기본값은 대개 설치 편의를 우선합니다. 어떻게 배포하고, 무엇을 켜고, 누가 접근할지는 그 환경을 운영하는 고객이 정합니다. 그래서 설정 기준선을 적용하고 일탈을 관리하는 책임은 고객에게 있습니다. 공급자의 안전한 기본값과 가이드는 이를 돕는 입력일 뿐입니다.

    연결설정 기준선과 일탈 탐지는 D7.3 구성 관리, 지원 종료와 패치는 D7.8 패치·취약점 관리, 최소권한은 D5.1 물리적·논리적 접근 통제에서 다룹니다.

    원본 연습문제 · D8.4-Q22

    상용 애플리케이션을 구매한 뒤 그 안전한 설정에 책임이 있는 주체는?

    1. 설정 책임은 계약이 배분한 바에 따르므로 기본적으로 어느 쪽도 아니며, 다루지 않은 영역은 협상될 때까지 미지정으로 남는다.
    2. 시스템을 측정하는 설정 기준선을 정의하고 이탈을 경영진에 보고하므로 내부 감사 기능.
    3. 고객이다. 기본 설정은 설치 편의를 우선하며 어떻게 배포하고 누가 접근할 수 있고 어떤 기능을 활성화할지는 고객이 결정한다.
    4. 제품을 설계하고 기본값과 함께 출하하므로 모든 배포 환경에 안전한 설정을 가장 잘 아는 공급업체.
    정답과 해설 보기

    정답 C. 공급업체는 기본값을 설치가 쉬운 쪽으로 맞춰 둔다. 기본 계정이 활성화되어 있거나 모든 기능이 켜져 있는 경우가 많다. 그 상태로 운영에 올리면 노출이 생기고 그 결과는 고객이 부담한다. 그래서 도입 시 강화 기준선을 적용하고 공급업체의 보안 설정 안내를 확인해야 한다.

    • A · 계약에 적히지 않아도 운영 책임은 제품을 배포하고 운영하는 고객에게 있다. 미지정으로 두는 것 자체가 이 문제에서 발생한 공백이다.
    • B · 감사는 기준 대비 상태를 검증하는 독립 기능이며 설정을 수행하지 않는다. 감사가 통제를 운영하면 독립성이 깨진다.
    • D · 공급업체는 설치 편의를 우선한 기본값을 제공할 뿐이다. 누가 접근하고 어떤 기능을 켤지는 환경마다 다르므로 고객만 정할 수 있다.

    4오픈소스

    위험이점
    유지 상태 — 한 명이 유지하는 프로젝트가 핵심 의존성인 경우가 흔함코드를 볼 수 있음 — 평가와 자체 수정 가능
    약정된 대응 시간이 없음공급자 종속이 낮음
    공급망 공격(패키지 탈취, 악성 커밋, 타이포스쿼팅)투명한 취약점 이력
    라이선스(법적 위험), 포크·버전 추적자체 패치 가능 — 상용에서는 없는 선택지

    원본은 “많이 쓰이니 안전하다”는 가정은 근거가 아니다라고 경고합니다. 널리 쓰여도 코드를 실제로 검토한 사람은 적을 수 있습니다.

    통제: SCA와 SBOM, 유지 상태 평가를 선정 기준에 포함, 내부 프록시 저장소와 버전 고정, 신뢰 경계에 있는 중요 의존성만 선별해 깊이 검토, 자체 패치 역량과 상위 반영(upstream)(포크만 유지하면 이후 갱신이 어려워짐), 대체 가능성 확보, 중요 구성요소의 상업적 지원 옵션.

    원문 사례 — 한 명이 유지하는 핵심 의존성. 핵심 결제 처리 경로가 유지관리자 한 명의 라이브러리에 의존했고, 공개된 취약점의 수정이 4개월간 나오지 않았습니다. 핵심 경로 의존성의 유지관리자 수·활동·대응 이력을 평가하고, 상위 반영을 동반한 자체 패치 역량을 갖추고, 상업적 지원 옵션을 검토했습니다.

    보충라이선스가 사용 목적을 허용한다고 해서 보안 패치와 지원이 보장되는 것은 아닙니다. 사용 권한, 유지 관리 주체, 업데이트 경로를 함께 봐야 계속 운영할 수 있는지 판단할 수 있습니다.

    주의“수용하고 문서화한다”, “포크해서 내부에서만 고친다”, “오픈소스를 쓰지 않는다”는 각각 한 측면만 봅니다. 원본의 대응은 선정 기준(유지 상태), 역량(자체 패치), 지속성(상위 반영), 대안(상업 지원·대체 가능성)을 함께 묶습니다.

    연결SCA, SBOM, 프록시 저장소, 패키지 공급망 공격은 D8.2 개발 생태계 보안 통제, 공급망 위험의 일반 원칙은 D1.11 공급망 위험 관리에서 다룹니다.

    원본 연습문제 · D8.4-Q08

    핵심 결제 처리 경로가 유지관리자 한 명이 유지하는 오픈소스 라이브러리에 의존했다. 취약점이 공개되었으나 4개월간 수정이 제공되지 않았다. 어떻게 해야 하는가?

    1. 오픈소스에 내재된 노출로 수용하고 경영진 승인을 받아 잔여 위험으로 문서화한 뒤 연간 위험위원회에서 재검토한다.
    2. 라이브러리를 내부 저장소로 포크해 거기서 수정하고, 코드를 완전히 통제하기 위해 상위 릴리스 추적을 중단한다.
    3. 라이브러리를 상용 구성요소로 교체하고 결제와 인증 경로에서는 오픈소스 의존을 피한다는 기준을 채택한다.
    4. 유지 상태를 선정 기준에 포함하고 상위 반영을 수반한 자체 패치 역량을 갖추며 대체 가능성을 식별하고 핵심 구성요소에는 상업적 지원을 검토한다.
    정답과 해설 보기

    정답 D. 오픈소스는 취약점 대응 시간에 대한 약정이 없으므로 유지관리자 수와 최근 활동, 대응 이력 같은 유지 상태를 선정 기준에 넣어야 한다. 코드를 볼 수 있다는 이점을 활용해 자체 패치 역량을 갖추되 상위에 반영해야 이후 갱신이 가능하며 핵심 구성요소에는 상업적 지원 옵션을 검토한다.

    • A · 구조적 대응 수단이 여럿 남아 있는 위험을 수용으로 처리하는 것은 순서가 틀렸다. 결제 경로라는 중요도를 감안하면 더 그렇다.
    • B · 포크 자체는 유효한 수단이지만 상위 추적을 끊으면 이후의 보안 수정과 기능 개선을 잃고 유지 부담을 전부 떠안는다.
    • C · 상용 교체는 선택지의 하나이지만 전면 배제는 현실적이지 않다. 상용도 공급업체 패치에 의존하므로 같은 지연이 발생한다.

    5제3자 소프트웨어와 위탁 개발

    • 계약에 보안 요구 명시: 안전한 개발 실천, 테스트 증거 제출, 결함 수정 의무와 기한
    • 코드 소유권과 접근: 소스 코드를 받는가, 소스 코드 에스크로(제3자 예치)를 두는가
    • 테스트 권리: 인수 전 보안 테스트를 할 권리
    • 인수 조건(acceptance criteria): 보안 결함 기준을 통과해야 인수. 인수 후 발견되면 협상력이 사라집니다.
    • 개발 인력 심사, 외부 인력에게 준 저장소·환경 권한의 범위와 회수
    • 하위 위탁 고지와 동의, 계약 종료 후 보안 패치를 누가 제공하는가

    원문 사례 — 인수 후 발견된 결함. 위탁 개발물을 인수하고 대금을 지급한 뒤 보안 테스트에서 다수의 인가 결함이 나왔습니다. 계약에 보안 인수 조건이 없어 수정이 추가 유상 작업이 되었습니다. 인수 조건에 보안 기준을 넣고, 인수 전 테스트 권리와 결함 수정 의무·기한을 조항으로 넣었습니다.

    가상 예시의료기기 제조사가 모바일 연동 앱을 외주로 개발한다고 해 봅시다. 인수 조건에 “OWASP MASVS 기준의 테스트 보고서 제출, 높음 이상 결함 0건, 인가 우회 시나리오 시험 통과”를 넣고, 납품 전 자체 테스트 권리를 확보해 두면 결함이 인수 이전에 드러납니다. 계약 종료 뒤 누가 보안 패치를 제공하는지도 함께 정해야 시판 후 취약점 대응 계획이 성립합니다. (이 예시는 설명을 위한 가상 상황입니다.)

    연결외부 인력의 권한 부여와 회수는 D5.5 프로비저닝 생애주기에서 다룹니다.

    6관리형 서비스

    운영을 공급자가 수행하는 모델입니다(애플리케이션 운영 위탁, 관리형 데이터베이스, MSSP).

    항목요점
    책임 경계 문서화누가 무엇을 패치·설정·모니터링하는가. 불명확하면 양쪽 모두 상대가 할 것으로 가정
    공급자 접근 권한최소권한, 적시 상승, 세션 기록. 공급자 침해가 조직 침해로 전이
    가시성로그 접근권이 계약에 없으면 조사가 불가능
    변경 통제, 감사권공급자 변경도 조직 변경 관리를 거치는가, 직접 감사 또는 제3자 보고서
    종료 전환운영 지식, 설정, 축적된 탐지 규칙이 조직에 남는가

    원문 사례 — 관리형 서비스의 책임 공백. 데이터베이스 운영을 위탁했는데, OS 패치를 공급자는 조직이, 조직은 공급자가 할 것으로 가정해 18개월간 패치되지 않았습니다. 패치·설정·모니터링·백업·사고 대응의 책임 주체를 표로 문서화해 계약에 첨부했습니다.

    원문 사례 — 공급자 접근 권한의 과도함. 관리형 서비스 공급자가 상시 도메인 관리자 권한을 갖고 있었고, 공급자 측 침해로 공격자가 그 권한으로 조직 환경에 들어왔습니다. 최소권한 축소, 적시 상승, 세션 기록, 작업 시간대 제한과 접근 승인 절차를 두었습니다.

    보충책임 표(RACI 형태)를 만들 때는 “패치”처럼 큰 이름 대신 “게스트 OS 보안 패치 적용”, “DB 엔진 마이너 버전 업그레이드”, “백업 복구 시험”처럼 실행 단위로 나눠야 공백이 드러납니다.

    연결MSSP와 공급자 접근 통제는 D7.7 탐지·예방 수단, 변경 관리는 D7.9 변경 관리, 특권 접근과 적시 상승은 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D8.4.md §3 관리형 서비스, §7 사례 5, 사례 6

    7클라우드 서비스

    모델고객 책임평가 범위
    IaaS게스트 OS 위 전부넓음, 직접 통제 가능
    PaaS애플리케이션과 설정중간
    SaaS설정·권한·데이터·연동좁음, 공급자 증거 의존

    공급자 영역은 고객이 테스트할 수 없으므로 제3자 감사 보고서와 인증으로 대체하고, 직접 테스트는 사업자 정책과 동의 범위 안에서만 합니다. 클라우드의 주된 위험은 오설정입니다(공개 액세스, 과도한 IAM 권한, 로깅 미활성화, 암호화 미적용).

    클라우드 고유 평가 항목:

    • 신원 통합: SSO 연합과 SCIM 프로비저닝. 없으면 계정 생애주기 관리가 수동이 됩니다.
    • 로그 가용성: 관리 이벤트와 인증 로그의 내보내기, 보존 기간. 기본 보존이 짧아 조사가 불가능한 경우가 많습니다.
    • 키 관리 모델(공급자 관리 / 고객 관리 / 고객 보유), 데이터 위치와 하위 수탁자, 테넌트 격리
    • 조직 수준 가드레일(금지 구성 차단), 공유 책임 모델의 문서화

    원문 사례 — 클라우드 로그 보존이 짧아 조사 불가. SaaS 무단 접근을 조사하려 했지만 관리 이벤트 로그 보존이 30일이었고 사건은 4개월 전에 시작되어 초기 경로를 특정할 수 없었습니다. 도입 평가 항목에 보존 기간과 내보내기를 넣고, 중앙 로그 시스템으로 계속 수집해 장기 보존하도록 했습니다.

    섀도 IT

    원본은 부서가 직접 SaaS를 도입하는 것이 가장 흔한 평가 공백이라고 봅니다. 자산 인벤토리에도 없고, 평가도 계약 보호도 없는 서비스에 조직 데이터가 들어갑니다. 탐지는 네트워크·프록시 로그 분석, CASB, 결제 기록 대조로 합니다. 대응은 금지만으로는 작동하지 않으므로 간편한 승인 경로와 사전 승인 목록으로 우회 동기를 줄이는 것입니다.

    원문 사례 — 섀도 IT를 통한 데이터 유출. 마케팅팀이 승인 없이 분석 SaaS에 고객 데이터를 올렸고, 그 공급자가 침해되어 데이터가 노출되었습니다.

    연결클라우드 평가와 테스트 제약은 D6.1 평가·테스트·감사 전략, SSO·SCIM은 D5.3 연합 식별, 로그 보존은 D7.2 5절, 자산 인벤토리는 D2.3 안전한 프로비저닝, CASB는 D3.5 아키텍처별 취약점에서 다룹니다.

    원문 위치: D8.4.md §3 클라우드 서비스, 섀도 IT와 비승인 도입, §7 사례 8, 사례 9

    8도입 후 관리

    • 설정 기준선 유지와 일탈 탐지
    • 권한 검토: 공급자 측 관리자 계정, 통합 앱 권한
    • 취약점과 패치 추적: 공급자 공지 모니터링. SBOM이 있으면 영향 범위 산정이 빠릅니다.
    • 로그 통합은 도입 시점에: 나중에 하면 공백이 생깁니다.
    • 재평가: 주요 변경, 사고, 계약 갱신 시점. 최초 평가 뒤 재평가하지 않으면 평가가 낡습니다.
    • 공급자 사고 대응 연계, 집중 위험(다수 업무가 한 공급자에 의존) 추적

    보충공급자가 저장 위치를 새 지역으로 옮기거나 하위 업체를 바꾸면, 처음 받은 보고서와 증거의 범위가 더는 맞지 않을 수 있습니다. 변경 통지와 재평가 조건을 계약에 넣고 실제 구성 증거와 연결해 두어야 합니다. 위험 영향이 큰 변경은 계약 갱신까지 기다리지 않고 검토 책임자에게 넘깁니다.

    원문 위치: D8.4.md §3 도입 후 관리

    9종료 전략과 종속

    • 데이터 반환: 사용 가능한 형식으로 받을 수 있는가. 독점 형식은 전환을 어렵게 합니다.
    • 데이터 삭제 증명: 클라우드에서는 키 삭제가 사실상 유일한 확정적 수단인 경우가 있습니다.
    • 전환 기간 지원
    • 종속(lock-in): 독점 형식, 전환 비용, 통합 깊이, 데이터 중력(데이터가 쌓인 곳으로 처리와 통합이 몰리는 현상)
    • 공급자 중단 대비: 도산, 서비스 종료, 인수 후 정책 변경. 대체 수단 없는 단일 공급자 의존이 위험

    원문 사례 — 종료 전략 부재. 핵심 업무를 맡긴 SaaS가 서비스 종료를 통보했는데, 데이터는 독점 형식이었고 전환 계획이 없어 6개월간 혼란을 겪었습니다. 계약에 반환 형식과 전환 지원을 명시하고, 주기적으로 중립 형식으로 추출해 보관하며, 대체 공급자를 미리 찾아 두었습니다.

    가상 예시도입 때 공급자가 “언제든 내보낼 수 있다”고 설명했지만, 시험 내보내기를 해 보니 문서 파일은 나왔고 승인 이력과 권한 정보는 빠져 있었습니다. 판단 순서는 이렇습니다. 전환에 필요한 데이터와 메타데이터를 업무 담당자와 정하고, 내보내기의 제한·비용과 종료 시 통보·지원·삭제 증명 조건을 확인한 뒤, 승인된 환경에서 수량·내용·재사용 가능성을 실제로 시험합니다. 법적 보존 때문에 일부 자료가 남는다면 보존 대상, 접근 주체, 만료·삭제 책임을 따로 정합니다.

    연결암호학적 삭제는 D7.5 자원 보호, 매체 폐기와 삭제 수준은 D2.4 데이터 생애주기, 사업 연속성 관점은 D7.10 복구 전략에서 다룹니다.

    원문 위치: D8.4.md §3 종료 전략과 종속, §7 사례 10

    10종합 이해 확인

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    DB 운영을 관리형 서비스로 맡긴 지 2년이 되었다. ㉠ 공급자가 상시 도메인 관리자 권한을 갖고 있다. ㉡ OS 패치 주체가 계약에 없다. ㉢ 공급자 작업 로그를 조직이 볼 권리가 계약에 없다. ㉣ 최초 도입 평가 이후 재평가가 없었다. 가장 적절한 조치 묶음은?

    1. 공급자가 ISO 27001 인증을 갖고 있으므로 현 상태 유지
    2. ㉠ 최소권한·적시 상승·세션 기록 / ㉡ 실행 단위 책임 표를 계약에 첨부 / ㉢ 로그 접근권과 감사권 조항 추가 / ㉣ 주요 변경·계약 갱신 시점의 재평가 수행
    3. 공급자를 즉시 교체하고 모든 운영을 내부화
    4. 질의서를 다시 받아 점수가 기준 이상이면 유지
    정답과 해설 보기

    정답 B. ㉠ 공급자 침해가 조직 침해로 전이되므로 접근을 줄이고 기록합니다(6절). ㉡ 경계가 불명확하면 양쪽이 서로 미룹니다(6절). ㉢ 로그 접근권이 계약에 없으면 조사할 수 없습니다(6절). ㉣ 재평가하지 않으면 평가가 낡습니다(8절). A는 인증 범위도 확인하지 않은 판단이고(2절), D의 질의서는 자기 주장입니다(2절). C는 종료 전략 없이 내리는 결정입니다(9절).

    11핵심 개념을 내 말로 설명하기

    복습

    제공자에게 평가 보고서가 있을 때 도입 평가에서 먼저 읽을 것은 무엇인가요?

    설명 확인하기

    보고서가 다루는 서비스·지역·기간·예외와 고객이 해야 하는 통제를 확인합니다. 우리 환경에서 적용하는 관리자 접근과 데이터 반출은 별도 증거를 확보합니다.

    12핵심 요약

    1. 도입 소프트웨어는 코드를 볼 수 없는 상태에서 평가합니다. 통제 수단: 요구사항, 계약, 증거, 설정, 통합 지점, 보완 통제.
    2. 책임은 이전되지 않습니다. 공급자 결함도 조직의 사고이고 신고 의무는 조직에 있습니다.
    3. 요구사항을 조달 전에 정합니다: 인증·인가, 로그 내보내기, 암호화·키, 데이터 처리, 패치·지원 기간, 통지, SLA, 통합, 종료.
    4. 증거: 제3자 보고서(범위·기간·예외·CUEC) > 인증(범위가 핵심) · 직접 테스트(허용 시) > 질의서(자기 주장) > 마케팅. 4차 위험도 범위.
    5. COTS: 비안전 기본값, 공격 가치, 패치 의존 → 기준선, 최소권한 설치, 분할, 교체 계획, SBOM. 설정 책임은 배포한 고객.
    6. 오픈소스: 유지 상태가 선정 기준. 자체 패치 + 상위 반영, 중요 의존성만 선별 검토. “많이 쓰이니 안전”은 근거가 아님.
    7. 위탁 개발: 보안 인수 조건과 인수 전 테스트 권리. 인수 후 발견 = 협상력 상실.
    8. 관리형: 책임 경계 문서화, 공급자 접근 최소권한(침해 전이), 로그 접근권, 변경 통제, 감사권.
    9. 클라우드: IaaS 넓음 / PaaS 중간 / SaaS 좁음. 주 위험은 오설정. SSO·SCIM, 로그 보존·내보내기, 키 관리, 데이터 위치, 가드레일.
    10. 섀도 IT는 가장 흔한 평가 공백 → 간편한 승인 경로와 사전 승인 목록, 프록시 로그·CASB·결제 기록으로 탐지.
    11. 도입 후: 로그 통합은 도입 시점에, 재평가, 집중 위험. 종료: 반환 형식, 삭제 증명(키 삭제), 전환 지원, 종속·데이터 중력.
    원문 위치: D8.4.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 증거 신뢰도 순서(제3자 보고서 > 인증 > 직접 테스트)는 §3 표에서 직접 테스트를 “높음”으로 둔 것과 차이가 있어, 요약에서는 직접 테스트를 상위 묶음에 함께 적었습니다.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    COTS (Commercial Off-The-Shelf) · 상용 기성 소프트웨어

    상용 기성 소프트웨어. 코드를 볼 수 없고 패치가 공급자에 의존한다.

    Due Diligence · 실사

    도입 전 공급자와 제품의 보안 상태를 조사하는 활동.

    CUEC (Complementary User Entity Controls) · 고객 조직이 수행할 보완 통제

    제3자 보고서에서 고객이 수행해야 하는 보완 통제(D6.1 참조).

    SBOM (Software Bill of Materials) · 소프트웨어 구성 명세서

    구성요소 목록. 도입 제품에 대해서도 계약으로 요구할 수 있다.

    Acceptance Criteria · 인수 조건

    위탁 개발물을 인수하기 위해 충족해야 하는 기준. 보안 기준을 포함한다.

    Source Code Escrow · 소스 코드 에스크로

    공급자 중단 시 소스 코드를 받을 수 있도록 제3자에게 예치하는 방식.

    Shared Responsibility Model · 공동 책임 모델

    클라우드에서 공급자와 고객의 책임 경계를 정의한 모델.

    Shadow IT · 섀도 IT

    조직 승인 없이 도입되어 평가와 관리 범위 밖에 있는 서비스.

    CASB (Cloud Access Security Broker) · 클라우드 접근 보안 중개

    클라우드 서비스 사용을 가시화하고 통제하는 수단.

    Fourth-party Risk · 제4자 위험

    공급자의 공급자에서 비롯되는 위험.

    Vendor Lock-in · 공급자 종속

    독점 형식과 전환 비용 때문에 다른 공급자로 옮기기 어려운 상태.

    Data Gravity · 데이터 중력

    데이터가 쌓인 곳으로 처리와 통합이 몰려 이동이 어려워지는 현상.

    Concentration Risk · 집중 위험

    다수 업무가 하나의 공급자에 의존해 생기는 위험.

    Exit Strategy · 종료 전략

    공급자 중단이나 계약 종료 시의 전환 계획.
