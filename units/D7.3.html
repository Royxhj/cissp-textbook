    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    구성 관리(Configuration Management)는 시스템이 어떤 상태여야 하는지를 정의하고, 실제 상태를 그 상태로 유지하며, 모든 변화를 알고 있는 것입니다. 원본은 이것을 보안의 기초로 봅니다. 침해의 상당 부분이 제로데이가 아니라 기본 자격증명, 불필요한 서비스, 과도한 권한, 암호화·로깅 미적용 같은 잘못된 설정에서 시작되기 때문입니다. 공식 개요 7.3은 프로비저닝, 베이스라이닝, 자동화를 예로 듭니다.

    원본의 구분: 구성 관리는 “안전한 상태”를 만들고, 변경 관리는 “그 상태가 바뀌는 과정”을 통제한다. 구성 관리만 있으면 변경이 승인 없이 일어나고, 변경 관리만 있으면 기준이 되는 상태가 정의되지 않습니다.

    보충의료기기 품질 시스템을 아는 분이라면 “형상 관리”와 “설계 변경 관리”의 관계로 이해하면 쉽습니다. 형상(구성) 관리는 현재 승인된 버전이 무엇인지 알게 하고, 변경 관리는 그 버전이 누구의 승인으로 왜 바뀌었는지를 남깁니다. 둘 다 있어야 “지금 운영 중인 것이 승인된 것인가”에 답할 수 있습니다.

    원본 연습문제 · D7.3-Q01

    구성 관리는 변경 관리와 어떻게 다른가?

    1. 구성 관리는 네트워크 장비에만, 변경 관리는 서버에만 적용된다.
    2. 변경 관리는 기술적 통제이고 구성 관리는 관리적 통제다.
    3. 구성 관리는 승인된 시스템 상태를 정의하고 유지하며 변경 관리는 그 상태에 대한 변경의 승인을 통제한다.
    4. 서로 다른 프레임워크에서 같은 프로세스를 부르는 다른 이름이다.
    정답과 해설 보기

    정답 C. 구성 관리는 안전한 상태를 정의하고 그 상태를 유지하며 모든 변화를 추적한다. 변경 관리는 그 상태가 바뀌는 과정을 승인 절차로 통제한다. 구성 관리만 있으면 변경이 승인 없이 일어나고 변경 관리만 있으면 기준이 없어 무엇이 맞는지 알 수 없다.

    • A · 두 프로세스 모두 자산 유형과 무관하게 적용된다.
    • B · 둘 다 기술적 구현과 관리적 절차를 함께 갖는다.
    • D · 목적과 다루는 대상이 다른 별개 프로세스다.

    2구성 식별

    무엇을 관리할지 정합니다. 자산 인벤토리가 전제입니다.

    • 구성 항목(CI): 서버, 네트워크 장비, 애플리케이션, 컨테이너 이미지, 클라우드 자원, 정책 객체.
    • 속성: 소유자, 환경(개발/검증/운영), 분류, 의존 관계.
    • CMDB: 구성 항목과 관계를 기록합니다. 의존 관계가 변경 영향 평가의 근거가 됩니다.
    • 수동 관리 CMDB는 금방 현실과 어긋나므로 자동 발견과 조정(reconciliation)이 필요합니다.

    원본의 경고: 관리 대상에 없는 자산은 기준선도 적용되지 않고 일탈도 탐지되지 않습니다. 섀도 IT와 부서 자체 도입 시스템이 전형적 공백입니다.

    연결자산 인벤토리는 D2.3 안전한 프로비저닝, 인벤토리와 테스트 대상의 대조는 D6.1 평가·테스트·감사 전략의 5절에서 다룹니다.

    원문 위치: D7.3.md §3 구성 식별

    3베이스라이닝 (Baselining)

    승인된 안전한 설정 상태를 정의하고 문서화·고정하는 것입니다.

    1. 출발점 선택: CIS 벤치마크, 공급자 보안 기준선, 규제 요구
    2. 조정(tailoring): 조직 환경과 업무 요구에 맞게 수정
    3. 근거 문서화: 완화한 항목과 이유
    4. 승인: 권한 있는 주체
    5. 구현: 기준 이미지와 설정 코드로 반영
    6. 검증: 적용 결과 측정
    7. 주기적 재검토: 표준 개정, 신규 위협, 환경 변화

    표준 벤치마크를 그대로 적용하면 업무가 깨지거나 무의미한 예외가 대량으로 생깁니다. 그래서 조정하되, 완화는 근거와 함께 문서화하고, 범위를 최소화하고(필요한 시스템군에만), 보완 통제를 함께 정의하고, 완화 항목도 재검토합니다(레거시가 폐기되면 완화도 제거).

    기준선 유형내용
    보안 설정 기준선OS, 미들웨어, DB, 네트워크 장비별 설정 값
    기준 이미지 golden image승인된 설정이 적용된 배포용 이미지
    컨테이너 기본 이미지최소 구성, 서명, 알려진 취약점 없음
    클라우드 정책 기준선조직 수준 가드레일(암호화 강제, 공개 접근 차단, 리전 제한)

    원본의 핵심 문장: 기준 이미지를 고치지 않으면 같은 결함이 모든 신규 시스템에 다시 들어갑니다.

    원문 사례 — 기준 이미지를 고치지 않아 재발한 결함. 특정 설정 결함이 취약점 보고서에 3회 연속 같은 수량으로 나왔습니다. 매번 개별 서버만 고치고 기준 이미지에는 반영하지 않아 신규 서버가 같은 결함을 갖고 배포된 것입니다. 교정 절차에 “기준 이미지 반영 여부”를 종결 조건으로 넣었습니다.

    연결기준선의 범위 지정과 조정(scoping and tailoring)은 D2.6 데이터 보안 통제, 벤치마크 테스트는 D6.2 보안 통제 테스트의 4절, 근본 원인 분석은 D6.4 결과 분석과 보고의 1절에서 다룹니다.

    원문 위치: D7.3.md §3 베이스라이닝, §7 사례 2 · 원본의 “보상 통제”는 제작기준에 따라 “보완 통제”로 적음

    4프로비저닝 (Provisioning)

    기준선에 맞는 상태로 시스템을 생성하고 배포하는 과정입니다.

    방식특징
    수동 구성일관성 없음, 재현 안 됨, 문서와 어긋남. “서버 10대의 설정이 모두 조금씩 다르다”
    기준 이미지 기반빠르고 일관됨. 단 이미지 자체의 패치 최신성 관리 필요(오래된 이미지는 배포 즉시 취약)
    구성 관리 도구선언적 목표 상태를 기술하면 도구가 수렴
    코드형 인프라(IaC)버전 관리, 검토, 테스트, 재현이 가능

    보안 프로비저닝 요건

    • 최소 설치: 불필요한 패키지·서비스·계정을 넣지 않습니다.
    • 기본 자격증명 제거: 배포 시점에 제거·변경합니다.
    • 비밀 주입: 이미지나 코드에 넣지 않고 배포 시점에 금고에서 주입합니다.
    • 로깅·모니터링 활성화: 배포 시점부터. 나중에 켜면 공백이 생깁니다.
    • 등록: 자산 인벤토리, 취약점 관리, 백업 대상에 자동 등록. 등록 누락이 미관리 자산을 만듭니다.

    원문 사례 — 서버 10대의 설정이 모두 달랐다. 같은 역할의 웹 서버 10대를 수동으로 구성해 왔는데, TLS 설정, 로깅 수준, 불필요 서비스 활성화가 모두 조금씩 달랐고 문서와도 맞지 않았습니다. 기준 이미지와 구성 관리 코드로 선언적 목표 상태를 정의했습니다.

    원문 사례 — 오래된 기준 이미지. 기준 이미지를 8개월간 갱신하지 않아 배포 직후 시스템에 미적용 패치가 수십 개였습니다. 이미지 빌드를 주기적으로 자동화하고 이미지 빌드 시점과 미적용 패치 수를 지표로 관리했습니다.

    연결비밀 관리와 금고는 D5.2 식별·인증 전략의 8절, 패치 관리는 D7.8 패치·취약점 관리에서 다룹니다.

    원본 연습문제 · D7.3-Q05

    프로비저닝 절차 자체에 내장되어야 하는 관행 묶음은?

    1. 시스템이 기능 인수 테스트를 통과할 때까지 로깅 설정을 보류한다.
    2. 배포가 외부 시스템에 의존하지 않도록 서비스 자격증명을 이미지에 내장한다.
    3. 최소 설치, 기본 자격증명 제거, 배포 시점 비밀 주입, 처음부터 로깅 활성화, 인벤토리와 스캔 대상 자동 등록.
    4. 향후 필요를 미리 충족하도록 전체 패키지를 설치하고 나중에 강화한다.
    정답과 해설 보기

    정답 C. 필요하지 않은 패키지와 서비스는 공격 표면을 넓히므로 최소 설치가 원칙이다. 기본 자격증명은 배포 시점에 제거하고 비밀은 이미지가 아니라 금고에서 주입한다. 로깅은 배포 시점부터 켜져 있어야 공백이 생기지 않고 인벤토리와 취약점 관리, 백업 대상 자동 등록이 미관리 자산을 막는다.

    • A · 로깅을 늦추면 초기 운영 구간의 가시성 공백이 생긴다.
    • B · 이미지 내장 비밀은 이미지 유출 시 모든 배포가 함께 노출된다.
    • D · 전체 설치는 공격 표면을 넓히고 사후 강화는 누락된다.

    원본 연습문제 · D7.3-Q12

    표준 이미지를 통한 자동 프로비저닝이 주는 보안 이점은?

    1. 생성된 시스템을 패치할 필요를 없앤다.
    2. 자산 인벤토리의 필요를 없앤다.
    3. 이후 설정 오류에 면역이 되게 만든다.
    4. 모든 시스템이 승인되고 강화된 동일한 설정에서 출발하므로 설정이 들쭉날쭉한 시스템을 만드는 수동 단계의 편차가 제거된다.
    정답과 해설 보기

    정답 D. 사람이 손으로 설정하면 단계를 빠뜨리거나 다르게 적용해 같은 역할의 서버가 서로 다른 상태가 된다. 표준 이미지에서 자동 생성하면 출발점이 일정해진다. 다만 이미지 자체를 갱신하지 않으면 낡은 취약점이 복제되고, 생성 후의 설정 이탈은 별도로 감시해야 한다.

    • A · 이미지도 패치가 필요하다.
    • B · 인벤토리는 여전히 필요하다.
    • C · 생성 후 이탈은 발생한다.

    5설정 일탈 (Configuration Drift)

    시간이 지나며 실제 설정이 기준선에서 벗어나는 현상입니다. 원인은 긴급 조치를 되돌리지 않음, 문제 해결 중의 변경(“이걸 끄니 되네”가 영구 설정이 됨), 승인 없는 수동 변경, 소프트웨어 설치·업데이트, 기준선 갱신 미반영입니다.

    교정 방식장점위험
    자동 교정빠름업무상 필요한 변경을 되돌려 장애 유발
    경보 후 수동 교정안전느리고 잔량이 쌓임

    실무는 위험도에 따라 구분합니다. 명백히 안전한 항목(암호화 설정, 로깅 활성화)은 자동, 업무 영향이 있는 항목은 승인 후 교정.

    원본의 핵심 문장: 일탈 교정만 반복하면 같은 일탈이 계속 생긴다. 원인이 수동 변경이면 변경 경로를 통제하고, 기준선이 비현실적이면 기준선을 조정합니다. 모두가 같은 설정을 바꾼다면 기준선이 현실과 맞지 않을 가능성이 큽니다.

    원문 사례 — 자동 교정이 유발한 장애. 자동 교정을 전면 적용했더니, 업무상 필요해 승인받고 바꾼 DB 파라미터가 기준선과 다르다는 이유로 되돌려져 야간 배치가 실패했습니다.

    원문 사례 — 반복되는 같은 일탈. 같은 설정 항목이 매월 수십 대에서 일탈로 탐지되었는데, 운영팀이 특정 기능 때문에 그 설정을 끄는 것이 업무상 필요했고 기준선에는 반영되지 않았던 것이었습니다. 기준선을 조정하고 보완 통제를 정의했습니다.

    가상 예시운영 서버 그룹에 기준선을 자동 적용하려는데, 업무팀이 정식으로 받은 임시 예외 두 건이 코드에 반영되어 있지 않습니다. 이대로 켜면 승인된 예외가 일탈로 처리되어 되돌려집니다. 환경별 기준과 승인된 예외(만료일 포함)를 먼저 코드에 반영하고, 영향이 작은 그룹에 먼저 적용해 결과를 본 뒤 넓힙니다. 기준선을 단계적으로 전환하는 중이라면 신·구 기준선을 어느 그룹에 언제 적용하는지도 기록해야 정상 전환이 경보로 잡히지 않습니다.

    연결예외 관리와 만료일은 D6.4 결과 분석과 보고의 4절, 변경 승인 절차는 D7.9 변경 관리에서 다룹니다.

    원문 위치: D7.3.md §3 설정 일탈, §7 사례 3, 사례 4

    6자동화, IaC, 불변 인프라

    자동화가 주는 것자동화가 만드는 위험
    일관성, 속도·확장성, 재현성(복구·조사에 유용), 증거 자동 생성(감사), 일탈 자동 수렴오류가 빠르고 광범위하게 전파(10대가 아니라 10,000대), 파이프라인 자체가 고가치 표적(티어 0), IaC의 비밀은 저장소 이력에 영구히 남음, 단계적 배포·롤백 경로 필요

    IaC 보안

    • 코드 검토: 인프라 변경도 코드 검토 대상입니다.
    • 정책 코드(policy as code): 금지된 구성(공개 스토리지, 암호화 미적용)을 배포 전에 차단합니다. 사후 탐지보다 효율적입니다.
    • 상태 파일 보호: IaC 상태 파일에 민감 정보가 들어갈 수 있습니다.
    • 파이프라인 권한 최소화: 파이프라인이 침해되면 전체가 침해됩니다.

    원문 사례 — 구성 관리 도구 침해. 모든 운영 시스템에 설정과 스크립트를 밀어 넣을 수 있는 구성 관리 서버가 침해되어, 공격자가 전 환경에 악성 작업을 배포했습니다. 별도 관리 네트워크 분리, 강한 MFA와 적시 상승, 배포 작업 승인 요구, 파이프라인 권한 최소화를 적용했습니다.

    원문 사례 — IaC 저장소의 비밀. 인프라 코드 저장소에 DB 비밀번호와 API 키가 평문으로 커밋되어 있었고, 삭제했지만 git 이력에 영구히 남아 있었습니다. 커밋 단계에 비밀 스캐닝을 넣고, 노출된 자격증명을 전부 교체하고, 이력을 정리했습니다.

    불변 인프라 (Immutable Infrastructure)

    실행 중 시스템을 수정하지 않고 새 이미지로 교체합니다. 수정하지 않으므로 설정 일탈이 구조적으로 발생하지 않고, 패치는 적용이 아니라 패치된 이미지로 재배포합니다. 전제는 배포 자동화와 상태 외부화(데이터를 인스턴스에 두지 않음)입니다.

    원본이 짚는 대가: 포렌식 영향. 인스턴스가 짧게 살고 사라지므로 사후 조사용 증거를 미리 중앙 수집해야 합니다.

    원문 사례 — 불변 인프라와 증거 소멸. 침해 조사를 시도했지만 문제의 컨테이너는 이미 교체되어 사라졌고, 로그도 컨테이너 내부에만 있었습니다. 로그와 주요 아티팩트를 생성 즉시 외부로 전송하고, 사고 때는 인스턴스를 교체하지 않고 격리·스냅샷하는 절차를 추가했습니다.

    연결티어 0 자산과 특권 접근은 D7.4 기본 보안 운영 개념의 4절, 증거 보존은 D7.1 조사, 개발 파이프라인 보안은 D8.2 개발 생태계 보안 통제에서 다룹니다.

    원본 연습문제 · D7.3-Q08

    컨테이너 기반 환경에서 문제가 된 컨테이너가 이미 교체되고 로그도 내부에만 존재했기 때문에 조사가 실패했다. 무엇을 바꾸어야 하는가?

    1. 로그와 주요 아티팩트를 생성 즉시 인스턴스 외부로 전송하고 사고 시에는 인스턴스를 교체하지 않고 격리·스냅샷한다.
    2. 공격 재구성을 위해 오케스트레이터의 스케줄링 이력에 의존한다.
    3. 각 컨테이너의 수명을 최소 90일로 연장한다.
    4. 불변 인프라를 포기하고 장수명 가변 호스트로 돌아간다.
    정답과 해설 보기

    정답 A. 불변 인프라는 설정 일탈을 구조적으로 없애지만 인스턴스가 짧게 살고 사라지므로 조사 증거도 함께 사라진다. 로그와 아티팩트를 생성 즉시 중앙으로 전송하고 사고 시 교체 대신 격리와 스냅샷을 수행하는 절차가 필요하다.

    • B · 스케줄링 이력에는 공격 행위 자체가 담기지 않는다.
    • C · 수명 연장은 불변 인프라의 전제를 훼손한다.
    • D · 불변 인프라의 이점을 포기하는 과도한 대응이다.

    프로세스구성 관리와의 관계
    자산 관리무엇을 관리할지 알려 줌
    변경 관리기준선 변경을 승인
    패치 관리기준선의 패치 수준 유지

    원본은 사고 복구에서 구성 관리의 가치를 강조합니다. 침해된 시스템을 “청소”하는 것보다 기준 이미지에서 재구축하는 것이 안전합니다. 구성 관리가 없으면 재구축이 불가능해 청소에 의존하게 되고, 잔존 백도어를 놓칠 수 있습니다.

    보충세 기록은 서로 다른 질문에 답합니다. 형상(구성) 기록은 “현재 버전과 승인된 상태”, 변경 기록은 “누가 무엇을 왜 승인했는가”, 패치 기록은 “알려진 문제를 어떤 버전으로 처리했는가”. 교정 작업을 종결할 때는 세 기록을 연결해, 승인된 수정이 실제 시스템에 적용되었고 기준선도 갱신되었는지 확인합니다.

    연결변경 관리는 D7.9 변경 관리, 패치·취약점 관리는 D7.8 패치·취약점 관리, 사고 복구는 D7.6 사고 관리에서 다룹니다.

    1. ㉠ 개별 서버를 더 빨리 수정 / ㉡ 자동 교정 전면 중단 / ㉢ 배포 후 수동 패치 / ㉣ 컨테이너 수명 연장

    3. ㉠ 스캐너 교체 / ㉡ 기준선 폐기 / ㉢ 이미지 사용 중단 / ㉣ 불변 인프라 폐기
    4. ㉠ 결함을 예외로 등록 / ㉡ DB 파라미터를 기준선 그대로 유지 / ㉢ 그대로 / ㉣ 로그를 컨테이너 안에서 더 오래 보존

    정답 B. ㉠ 3절(이미지를 고쳐야 재발이 멈춘다), ㉡ 5절(위험도별 구분), ㉢ 4절(이미지 패치 최신성), ㉣ 6절(불변 인프라는 증거도 사라진다). A의 “자동 교정 전면 중단”은 안전한 항목의 자동 수렴까지 잃습니다.

    복습

    승인된 변형과 구성 일탈은 어떻게 나누나요?

    설명 확인하기

    현재 기준선 버전과 승인된 변경·예외 범위를 확인합니다. 차이가 승인 범위 안이라면 계획대로 유지하고, 밖이라면 이상 영향과 교정 방안을 검토합니다.

    10핵심 요약

    1. 구성 관리 = 상태를 정의·유지하고 모든 변화를 안다. 네 활동: 식별, 기준선, 변경 통제, 모니터링(SP 800-128).
    2. 구성 관리 = 안전한 상태, 변경 관리 = 상태가 바뀌는 과정. 둘 다 필요.
    3. 식별: 인벤토리 전제, CI·CMDB(의존 관계 = 영향 평가 근거), 자동 발견. 관리 대상 밖 = 기준선도 탐지도 없음.
    4. 기준선: 출발점 → 조정(근거 문서화·범위 최소화·보완 통제·재검토) → 승인 → 구현 → 검증 → 재검토. 이미지를 고쳐야 재발이 멈춘다.
    5. 프로비저닝: 수동은 비일관. 기준 이미지(패치 최신성), IaC. 최소 설치, 기본 자격증명 제거, 비밀 주입, 로깅 활성화, 자동 등록.
    6. 일탈: 원인 다양. 자동 교정(빠름, 장애 위험) vs 수동(안전, 느림) → 위험도별. 반복 일탈 = 변경 경로 통제 또는 기준선 조정.
    7. 자동화: 일관·재현·증거 / 오류 대량 전파, 파이프라인 = 티어 0. IaC: 코드 검토, policy as code(배포 전 차단), 상태 파일, 비밀 금지.
    8. 불변 인프라: 일탈이 구조적으로 없음, 재배포로 패치, 증거는 미리 외부로.
    9. 사고 복구: 청소보다 기준 이미지에서 재구축.
    원문 위치: D7.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    11주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Configuration Management · 구성 관리

    시스템의 승인된 상태를 정의하고 유지하며 모든 변화를 추적하는 활동.

    Configuration Item (CI) · 구성 항목

    구성 관리의 대상 단위. 서버, 장비, 애플리케이션, 클라우드 자원 등.

    CMDB (Configuration Management Database) · 구성 관리 데이터베이스

    구성 항목과 그 관계를 기록한 저장소.

    Baseline · 기준선

    승인된 안전한 설정 상태의 정의.

    Tailoring · 조정

    표준 기준선을 조직 환경과 업무 요구에 맞게 수정하는 작업.

    Golden Image · 기준 이미지

    승인된 설정이 적용된 배포용 표준 이미지.

    Provisioning · 프로비저닝

    기준선에 맞는 상태로 시스템을 생성·배포하는 과정.

    Configuration Drift · 설정 일탈

    실제 설정이 시간에 따라 기준선에서 벗어나는 현상.

    Auto-remediation · 자동 교정

    일탈을 도구가 자동으로 기준 상태로 되돌리는 방식.

    IaC — Infrastructure as Code · 코드형 인프라

    인프라 정의를 코드로 관리해 버전 관리와 검토, 재현을 가능하게 하는 방식.

    Policy as Code · 정책 코드

    금지된 구성을 배포 전에 자동 차단하는 정책 구현 방식.

    Immutable Infrastructure · 불변 인프라

    실행 중 시스템을 수정하지 않고 새 이미지로 교체하는 운영 방식.

    Minimal Installation · 최소 설치

    필요하지 않은 패키지·서비스·계정을 포함하지 않는 설치 원칙.

    Secret Injection · 비밀 주입

    자격증명을 이미지나 코드에 넣지 않고 배포 시점에 금고에서 주입하는 방식.

    Staged Rollout · 단계적 배포
