    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    조직이 쓰는 SaaS가 스무 개라면 계정도 스무 개, 퇴사 처리도 스무 번입니다. 연합 신원(Federated Identity)은 인증을 조직의 신원 공급자 한 곳에 맡기고, 외부 서비스는 “인증이 일어났다”는 서명된 증거만 믿게 하는 방식입니다. 이 단원은 공식 개요 5.3이 드는 세 가지 배치 모델(온프레미스, 클라우드, 하이브리드)과 함께, 연합이 어디서 깨지는지를 다룹니다.

    SSO와 연합의 차이

    SSO는 “한 번 인증으로 여러 시스템에 접근”하는 사용자 경험이고, 연합은 “신뢰 경계를 넘어 신원을 전달”하는 구조입니다. 조직 내부 SSO는 연합 없이도 가능하고(예: Kerberos), 연합은 보통 조직 밖까지 SSO를 실현하는 수단이 됩니다.

    보충호텔 체크인에 비유하면, 호텔(SP)은 손님의 여권 원본을 보관하지 않고 여권청(IdP)이 발급한 여권이 진짜인지(서명), 이 손님 것인지, 유효기간 안인지만 봅니다. 호텔이 여권청을 믿는 근거는 미리 알고 있는 여권의 위조 방지 요소(메타데이터와 서명 키)입니다. 그래서 여권청이 뚫리면 모든 호텔이 속습니다. 연합의 장점과 위험이 같은 지점에서 나옵니다.

    연결SSO의 장단점과 SAML·OAuth·OIDC의 첫 구분은 D5.2 식별·인증 전략의 6~7절에서 다뤘습니다.

    원본 연습문제 · D5.3-Q01

    어떤 조직이 SAML 2.0 을 사용해 제3자 SaaS 공급자와 신원을 연합한다. 사용자가 로그인할 때 SaaS 공급자가 받는 것은?

    1. 자격증명을 로컬에서 검증할 수 있도록 사용자의 비밀번호 해시.
    2. 매시간 동기화되는 조직 디렉터리의 복사본.
    3. 암호화된 채널로 전달되는 사용자의 평문 자격증명.
    4. 신원 공급자가 사용자를 인증했다는 서명된 주장.
    정답과 해설 보기

    정답 D. 연합의 본질은 자격증명을 넘기지 않는 것이다. IdP 가 사용자를 인증하고 그 사실을 서명된 주장으로 발급하면 SP 는 서명을 검증해 접근을 허용한다. SP 는 비밀번호나 그 해시를 보관하지 않으므로 SP 침해 시 자격증명이 유출되지 않는다.

    • A · 해시를 넘기면 연합의 목적인 자격증명 비전달이 깨진다.
    • B · 디렉터리 동기화는 프로비저닝이며 인증 주장 전달과 다르다.
    • C · 평문 자격증명을 SP 에 주는 것은 연합이 아니라 자격증명 공유다.

    2왜 연합이 필요한가

    제3자 SaaS를 쓰기 시작하면 선택지는 둘입니다.

    선택결과
    SaaS마다 별도 계정자격증명 분산, 퇴사자 계정 잔존, MFA 정책 제각각, 감사 추적 분산
    연합인증은 조직의 IdP가 책임지고 SaaS는 결과만 신뢰

    원본은 연합의 가장 큰 운영 가치를 퇴사 처리 한 번으로 모든 연합 서비스의 로그인이 끊긴다는 점으로 봅니다. 다만 7절에서 보듯 “로그인이 끊긴다”와 “접근이 끊긴다”는 다릅니다.

    연결외부 서비스 도입 시의 보안 평가는 D8.4 도입 소프트웨어 평가, 공급망과 제3자 관리는 D1.11 공급망 위험 관리에서 다룹니다.

    원문 위치: D5.3.md §3 왜 연합이 필요한가

    3공식 개요의 세 모델

    모델구조장점단점핵심 실패 모드
    온프레미스IdP가 조직 데이터센터 안(예: AD FS, 자체 SAML IdP)자격증명·해시가 외부로 나가지 않음. 국외 이전 제한 규제에 적합IdP가 멈추면 모든 연합 로그인이 멈춤. 인터넷 노출 구간, 패치, 인증서 갱신을 직접 운영서명 인증서 만료 → 모든 SP에서 동시에 로그인 실패
    클라우드IdP 자체가 클라우드 서비스(IDaaS)가용성·확장성을 공급자가 책임. 조건부 접근, 이상 탐지, MFA, SaaS 커넥터 내장신원 데이터가 외부에. 공급자 장애 = 조직 전체 로그인 장애. 설정 실수가 즉시 인터넷에 노출과도한 앱 동의 권한 → 악성 앱이 조직 데이터 읽기 권한을 영구 보유
    하이브리드온프레미스 디렉터리가 신원 원천, 클라우드 IdP와 동기화실무에서 가장 흔함. 기존 디렉터리 유지두 환경을 잇는 연결 지점이 생김동기화 계정 침해 → 양쪽이 함께 무너짐

    하이브리드의 인증 처리 방식

    방식동작특징
    비밀번호 해시 동기화해시를 클라우드로 보내 클라우드가 인증온프레미스 장애에도 로그인 유지
    패스스루 인증클라우드가 받은 자격증명을 온프레미스 에이전트로 검증해시가 클라우드로 가지 않음
    연합(온프레미스 IdP로 리다이렉트)인증을 온프레미스가 전담통제력 최고, 가용성 최약

    원본은 하이브리드의 고유 위험 두 가지를 짚습니다. 첫째, 동기화 계정은 양쪽에 높은 권한을 갖고 자동화되어 방치되기 쉽습니다. 둘째, 신원 원천이 어디인지 명확해야 합니다. 양쪽에서 각자 계정을 만들 수 있으면 권한 해지가 한쪽에만 반영됩니다.

    원문 사례 — 하이브리드 동기화 계정 침해. 동기화 서버가 침해되었는데, 동기화 계정은 양쪽에 높은 권한을 가졌고 3년간 비밀번호가 바뀌지 않았습니다. 공격자는 클라우드 측 계정 속성을 바꾸고 임의 사용자로 인증할 수 있었습니다. 동기화 서버를 티어 0 자산으로 격리하고, 관리형 계정으로 바꾸고, 속성 변경을 감시했습니다.

    판단 순서세 모델 중 무엇을 고를지는 ① 신원 데이터가 조직 밖에 있어도 되는가(규제) ② IdP가 멈췄을 때 감당할 수 있는 범위는 어디까지인가(가용성) ③ 누가 패치·인증서·설정을 책임지는가(운영 역량) ④ 두 환경을 잇는 연결 지점을 누가 지키는가(하이브리드)로 가립니다. 어느 모델이든 “IdP 장애 = 로그인 장애”라는 점은 같고, 장애를 누가 책임지느냐가 다를 뿐입니다.

    연결인증서 수명주기와 HSM은 D3.6 암호 솔루션, 국외 이전 규제는 D1.4 법률·규제·컴플라이언스, 티어 0과 특권 계정 관리는 D7.4 기본 보안 운영 개념, 서비스 계정 관리는 D5.1 물리적·논리적 접근 통제의 4절에서 다룹니다.

    원본 연습문제 · D5.3-Q12

    신원 공급자의 서명 인증서가 만료된 새벽 2시에 연합이 끊겨 어떤 서비스 공급자도 주장을 검증할 수 없었다. 무엇이 갖춰져 있어야 했는가?

    1. 유예 기간 동안 만료된 인증서를 자동으로 수락하는 설정.
    2. 만료 후 인증서를 시험할 서비스 공급자 한 곳 지정.
    3. 갱신 빈도를 줄이기 위한 더 긴 인증서 유효 기간.
    4. 만료일 추적과 사전 경보, 전환 전에 새 인증서를 모든 서비스 공급자에 배포하는 계획된 교체 절차, 전환 기간 중 복수의 유효 서명 키 지원.
    정답과 해설 보기

    정답 D. 연합에서 서명 인증서는 모든 서비스 공급자가 신뢰 근거로 들고 있는 값이다. 한쪽에서 바꾸면 상대 전부가 갱신해야 하므로 조율이 필요하다. 만료일을 자산으로 추적하고 사전에 경보를 받고, 전환 기간에 구·신 키를 동시에 유효하게 둬서 무중단으로 넘긴다. 유효 기간을 늘리는 것은 문제를 미루고 키 노출 위험을 키운다.

    • A · 만료 인증서 수락은 신뢰 모델을 깨뜨린다.
    • B · 만료 후 시험은 이미 장애가 난 뒤다.
    • C · 만료 관리 부재라는 근본 문제가 남는다.

    4프로토콜별 역할

    프로토콜하는 일
    SAML 2.0XML 주장으로 인증·속성 전달. 기업 웹 SSO 표준
    OIDCOAuth 2.0 위의 인증 계층. ID 토큰(JWT)으로 신원 전달
    OAuth 2.0권한 위임(인가) 프레임워크. 인증 프로토콜이 아님
    WS-Federation레거시 마이크로소프트 계열 연합
    SCIM연합 환경의 계정 프로비저닝·해지 표준

    가장 중요한 구분: SAML과 OIDC는 “이 사용자가 누구인지”를 전달하고, OAuth 2.0은 “이 앱이 무엇을 해도 되는지”를 전달합니다. OAuth 액세스 토큰을 로그인 성공의 증거로 쓰면 신원 위조로 이어집니다.

    원문 사례 — OAuth 토큰을 로그인 증거로 쓴 앱. 외부 소셜 로그인의 액세스 토큰이 유효하면 로그인 성공으로 처리했더니, 다른 앱용으로 발급된 토큰을 제출해도 통과했습니다. OIDC의 ID 토큰으로 바꾸고 발급자, 대상, nonce를 검증했습니다.

    보충‘누가 로그인했는가’를 묻는 일과 ‘어떤 API 작업을 맡기는가’를 정하는 일은 질문이 다릅니다. 앞의 것은 신원 증거(ID 토큰, SAML 주장), 뒤의 것은 위임 범위를 담은 접근 토큰이 답합니다. 발코니 열쇠를 맡긴 손님이 집주인이라는 증거는 되지 않는 것과 같습니다.

    원문 위치: D5.3.md §3 프로토콜별 역할, §7 사례 4

    5SAML 웹 브라우저 SSO 흐름

    1. 사용자가 SP에 접근
    2. SP가 IdP로 인증 요청(AuthnRequest)을 리다이렉트
    3. IdP가 사용자를 인증(비밀번호 + MFA)
    4. IdP가 서명된 SAML 주장 발급
    5. 브라우저가 SP에 주장을 전달(POST)
    6. SP가 서명·발급자·대상·유효기간을 검증한 뒤 세션 생성
    시작 방식특징
    SP-initiated위 흐름. 사용자가 SP에서 시작
    IdP-initiated포털에서 앱 아이콘을 눌러 시작. SP가 요청 상태를 모르므로 주장 재생과 피싱에 상대적으로 약함

    SP가 반드시 검증할 항목: 서명, Issuer(발급자), Audience(대상이 나인지), NotBefore / NotOnOrAfter(유효 시간), 재생 방지를 위한 Assertion ID 기록.

    보충서명 검증은 “신뢰하는 발급자가 만들었고 중간에 바뀌지 않았다”까지만 증명합니다. 같은 IdP가 여러 앱에 같은 형식으로 발급하므로, 서명이 맞아도 대상이 다른 앱이면 거부해야 합니다. 그래서 검증 항목은 하나라도 빠지면 안 되는 목록입니다. 서명(누가 만들었나) → 대상(누구를 위한 것인가) → 시간(지금 쓸 수 있나) → ID(이미 쓴 것은 아닌가) 순서로 보면 각 항목이 막는 공격이 따로 있습니다.

    원본 연습문제 · D5.3-Q18

    서비스 공급자가 SAML 주장의 서명을 검증하는 이유는?

    1. 주장이 예상한 신원 공급자에서 왔고 변경되지 않았음을 확인하기 위해. 서비스 공급자는 자기가 사용자를 인증하는 대신 그 주장을 신뢰하기 때문이다.
    2. 주장 안의 사용자 속성을 암호화하기 위해.
    3. 더 빠른 전송을 위해 주장을 압축하기 위해.
    4. 사용자가 애플리케이션에서 보유한 역할을 판단하기 위해.
    정답과 해설 보기

    정답 A. 주장은 "이 사용자는 인증되었다" 는 선언이다. 서명을 검증하지 않으면 누구나 그런 선언을 만들어 보낼 수 있다. 그래서 서명 검증은 연합 신뢰의 핵심이며 검증을 생략한 구현이 실제 침해로 이어진 사례가 있다. 압축과 암호화, 역할 판단은 별개 기능이다.

    • B · 암호화는 별개 처리다.
    • C · 서명은 압축 기능이 아니다.
    • D · 역할 판단은 인가 단계다.

    7프로비저닝과 해지 전파

    원본의 핵심 문장입니다. 연합은 인증을 통합하지만 계정 생애주기를 자동으로 통합하지는 않는다.

    방식동작해지
    JIT 프로비저닝첫 연합 로그인 때 SP가 계정 생성간편하지만 퇴사 시 계정이 SP에 남음
    SCIM 프로비저닝IdP가 SP에 생성·수정·비활성화를 밀어 넣음해지가 전파됨

    원본은 연합에서 가장 흔한 운영 사고를 “로그인은 막혔는데 접근은 살아 있는 상태”로 꼽습니다. IdP에서 계정을 비활성화해도 SP에 이미 발급된 장수명 액세스 토큰, 리프레시 토큰, 앱 비밀번호, API 키는 그대로 동작합니다. 해지는 IdP 차단 + SP 세션·토큰 무효화가 함께 이루어져야 완결됩니다.

    원문 사례 — 퇴사자가 SaaS에 남은 조직. 20개 SaaS를 SAML로 연합하고 JIT 프로비저닝을 썼습니다. 퇴사자의 IdP 계정을 비활성화했지만, 접근 검토에서 12개 SaaS에 계정이 활성 상태로 남아 있고 그중 3개는 API 키가 발급된 상태였습니다. API 키는 IdP를 거치지 않아 계속 동작했습니다. SCIM으로 전환하고 퇴사 절차에 SP 측 토큰·API 키 무효화를 넣었습니다.

    가상 예시외부 IdP로 로그인하는 SaaS에서 퇴사자를 IdP에서 지웠는데, SaaS 관리자 화면에는 계정과 열린 세션이 그대로 보입니다. 판단은 세 흐름을 따로 그리는 데서 시작합니다. 신원 확인(새 로그인을 허용할지), 계정 생성·삭제(프로비저닝), 세션 발급·회수. 연합은 첫 번째만 결정합니다. 나머지 둘은 서비스마다 별도 동작일 수 있으므로 해지 이벤트를 보낸 뒤 실제로 계정과 권한이 제거되었다는 증거를 확인합니다.

    연결계정 생애주기, 퇴사 처리, 접근 검토는 D5.5 프로비저닝 생애주기, JIT의 의미는 D5.2 식별·인증 전략의 10절에서 다룹니다.

    원문 위치: D5.3.md §3 프로비저닝과 해지 전파, §7 사례 1

    8연합 고유의 위험

    위험내용대응
    IdP 침해 = 전체 침해IdP 서명 키가 유출되면 임의 사용자로 유효한 주장을 발급할 수 있고 SP는 구분할 수 없음서명 키를 HSM에, 정기 교체, 발급 이력 감시
    주장·토큰 검증 누락서명 미검증, 알고리즘 none 허용, Audience 미확인. XML 서명 래핑(XSW): 서명된 요소를 둔 채 다른 요소를 끼워 파서와 검증기의 해석 차이를 악용검증 항목 전부 확인, 검증된 라이브러리
    도메인·메일 기반 신뢰 남용이메일 도메인이 같으면 같은 조직으로 처리 → 방치 도메인을 인수한 공격자가 테넌트 합류. 이메일을 영구 식별자로 쓰면 주소 재사용 시 접근 상속변경되지 않는 고유 식별자로 매칭
    토큰 탈취·재생세션·리프레시 토큰을 훔치면 MFA 없이 접근토큰 바인딩, 짧은 수명, 리프레시 토큰 회전, 민감 작업 재인증, 비정상 사용 탐지
    신뢰의 전이SP가 하위 서비스에 신원을 넘기면 신뢰가 연쇄토큰 교환(RFC 8693)처럼 범위를 줄이며 전달

    원문 사례 — 방치된 도메인을 통한 테넌트 침입. 캠페인용으로 쓰다 갱신하지 않은 도메인을 제3자가 인수해 메일박스를 만들었고, 이메일 도메인 일치만으로 가입을 허용하는 SaaS의 조직 테넌트에 합류했습니다. 도메인 인벤토리 관리, 테넌트 자동 가입 비활성화, IdP가 발급한 영구 식별자 기준 매칭으로 대응했습니다.

    연결서명 키 보호와 HSM은 D3.6 암호 솔루션, 자산 인벤토리는 D2.3 안전한 프로비저닝에서 다룹니다.

    원본 연습문제 · D5.3-Q07

    연합에서 신원 공급자의 서명 키가 가장 가치 높은 표적인 이유는?

    1. 모든 서비스 공급자가 저장한 데이터를 암호화한다.
    2. 이를 보유한 자는 어떤 사용자로든 유효한 주장을 발급할 수 있고 서비스 공급자는 정당한 주장과 구분할 수 없다.
    3. 모든 연합 로그인의 전송 계층을 복호화하는 데 필요하다.
    4. 사용자가 등록할 수 있는 다중 인증 요소를 통제한다.
    정답과 해설 보기

    정답 B. SP 의 신뢰는 전적으로 IdP 서명 검증에 근거한다. 서명 키를 가진 자는 임의 사용자 명의의 유효한 주장을 만들 수 있고 SP 는 서명이 맞으므로 이를 정당한 것으로 수락한다. 그래서 서명 키는 HSM 에 보관하고 정기 교체하며 발급 이력을 감시한다.

    • A · 서명 키는 SP 저장 데이터를 암호화하지 않는다.
    • C · 전송 계층 보호는 TLS 인증서의 역할이며 주장 서명 키와 다르다.
    • D · MFA 등록 정책은 IdP 설정이며 서명 키의 기능이 아니다.

    9실패 시 동작 설계

    연합은 외부 의존성입니다. IdP 장애 때의 설계 선택이 보안 수준을 결정합니다.

    선택의미위험
    Fail-secure(기본 거부)IdP가 응답하지 않으면 접근 차단가용성 손실
    Fail-open / 로컬 폴백로컬 계정으로 우회 허용공격자가 IdP를 일부러 방해해 약한 경로로 유도할 수 있음

    실무 타협은 비상 계정(break-glass account)을 소수만 두고 연합을 거치지 않게 하며, 강한 MFA, 금고 보관, 사용 즉시 알림을 적용하는 것입니다.

    원문 사례 — IdP 장애가 만든 우회 경로. IdP 장애로 전사 로그인이 멈추자 운영팀이 주요 시스템에 로컬 계정 폴백을 허용했습니다. 폴백 계정은 MFA 없이 비밀번호만 요구했고 장애 뒤에도 비활성화되지 않았습니다. 원본의 표현대로 가용성을 위해 만든 경로가 상시 취약점이 되었습니다.

    보충“연합을 쓸 수 없다”와 “인증에 실패했다”는 원인이 다르지만, 인증 증거를 얻지 못했다는 점은 같습니다. 그래서 장애를 이유로 인증을 생략하지 않고, 미리 승인된 최소 권한의 비상 접근을 사유·만료·사후 검토·정상 복귀 조건과 함께 준비해 둡니다.

    연결fail-secure와 fail-safe의 구분은 D3.1 안전한 설계 원칙, 비상 계정 관리는 D7.4 기본 보안 운영 개념에서 다룹니다.

    원문 위치: D5.3.md §3 실패 시 동작 설계, §7 사례 5

    11핵심 개념을 내 말로 설명하기

    복습

    연합으로 로그인한 사람이 퇴사하면 IdP 계정 비활성화만으로 끝날까요?

    설명 확인하기

    새로운 로그인은 막히더라도 이미 열린 세션이나 서비스에 생성된 별도 계정이 있을 수 있습니다. 해지 이벤트가 전달되는지와 서비스별 회수 증거를 확인합니다.

    12핵심 요약

    1. 연합 = IdP(인증·서명된 주장 발급) → SP/RP(검증·신뢰). 신뢰는 메타데이터와 서명 키로. 자격증명을 넘기지 않는다.
    2. SSO = 사용자 경험, 연합 = 신뢰 경계를 넘는 구조.
    3. 온프레미스: 통제↑, 인증서 만료가 핵심 실패. 클라우드: 운영 위탁, 과도한 앱 동의가 핵심 실패. 하이브리드: 가장 흔함, 동기화 계정과 신원 원천이 위험.
    4. 하이브리드 인증: 해시 동기화(장애 내성) / 패스스루(해시 비전송) / 연합 리다이렉트(통제 최고, 가용성 최약).
    5. SAML·OIDC = 누구인가, OAuth 2.0 = 무엇을 해도 되나. SCIM = 프로비저닝·해지.
    6. SP 검증: 서명, 발급자, 대상, 유효 시간, 주장 ID(재생 방지). IdP-initiated는 재생·피싱에 상대적으로 약함.
    7. OIDC: 인가 코드 흐름 + state(CSRF), nonce(재생), PKCE(코드 탈취). 암묵적 흐름 비권고.
    8. JIT는 해지가 안 됨, SCIM은 해지 전파. 해지 = IdP 차단 + SP 세션·토큰·API 키 무효화.
    9. IdP 서명 키 유출 = 임의 사용자 위조(HSM, 교체, 감시). XSW, 도메인 인수, 이메일 식별자 재사용, 토큰 재생, 신뢰 전이.
    10. IdP 장애: 기본은 fail-secure. 폴백 대신 소수 비상 계정(금고, 강한 MFA, 사용 알림).
    원문 위치: D5.3.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 “시험에서 가장 자주 나오는” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    13주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Federated Identity · 연합 식별

    서로 다른 신뢰 경계 간에 신원을 전달해 접근을 허용하는 방식.

    IdP — Identity Provider · 신원 공급자

    사용자를 인증하고 서명된 주장을 발급하는 주체.

    SP / RP (Service Provider / Relying Party) · 서비스 제공자 / 신뢰 당사자

    주장을 검증해 접근을 허용하는 주체. 자체 비밀번호를 보관하지 않는다.

    Assertion · 주장

    인증 사실과 속성을 담은 서명된 증거. SAML 에서는 XML, OIDC 에서는 JWT 형식의 ID 토큰이다.

    SAML 2.0 — Security Assertion Markup Language · 보안 주장 마크업 언어 2.0

    XML 기반 연합 표준. 기업 웹 SSO 의 사실상 표준이다.

    OIDC (OpenID Connect) · 오픈아이디 연결 인증 계층

    OAuth 2.0 위에 인증을 더한 계층. ID 토큰으로 신원을 전달한다.

    SCIM (System for Cross-domain Identity Management) · 도메인 간 신원 관리 표준

    연합 환경의 계정 프로비저닝·해지 표준. 해지 전파를 가능하게 한다.

    JIT Provisioning · 적시 프로비저닝

    첫 연합 로그인 시 SP 가 계정을 자동 생성하는 방식. 해지가 전파되지 않는 약점이 있다.

    PKCE (Proof Key for Code Exchange) · 인가 코드 교환의 요청 주체 검증

    인가 코드 탈취를 막는 OAuth 확장. 공용 클라이언트에 필수다.

    Break-glass Account · 비상 계정

    연합 장애 시 사용하는 비연합 긴급 계정. 강한 보호와 사용 알림이 필요하다.

    XSW (XML Signature Wrapping) · XML 서명 래핑

    서명 검증과 데이터 파싱의 해석 차이를 악용하는 SAML 공격.

    Token Exchange · 토큰 교환

    전달 과정에서 토큰의 권한 범위를 축소해 신뢰 전이를 제한하는 방식.
