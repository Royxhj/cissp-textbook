    주요 용어 바로가기 · Glossary

    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    접근 통제는 “누가 무엇에 무엇을 할 수 있는가”를 정하고 지키는 일입니다. 원본은 이 단원의 무게를 한 문장으로 말합니다. 접근 통제가 뚫리면 암호화도 로깅도 의미가 없다. 인가된 사용자로 들어온 공격자에게는 모든 통제가 정상 동작하는 것처럼 보이기 때문입니다. 도메인 5의 첫 단원인 이 단원은 접근 통제의 기본 구조와, 공식 개요 5.1이 드는 여섯 가지 자산(정보, 시스템, 기기, 시설, 애플리케이션, 서비스)별 통제를 다룹니다.

    이 단원의 위치

    단원어떻게 이어지는가
    D1.2 보안 개념 (CIA 등)IAAA(식별·인증·인가·책임추적성). 이 단원은 인가를 구현하는 접근 통제 (1절)
    D5.2 식별·인증 전략 · D5.6 인증 시스템인증 전략과 인증 시스템 구현 (1절)
    D5.4 인가 메커니즘인가 메커니즘(DAC·MAC·RBAC·ABAC) (5절)
    D5.5 프로비저닝 생애주기계정 생애주기와 접근 검토. 권한 누적·고아 계정 (6절)
    D3.8 사이트·설비 설계 원칙 · D3.9 사이트·설비 보안 통제시설 접근의 물리 통제 (2절, 3절)
    D3.5 아키텍처별 취약점 · D3.7 암호 분석 공격IDOR와 API 인가, 서비스 계정 공격(Kerberoasting) (3~4절)

    수동적 자원

    원본은 주체가 사람만이 아니다라고 강조합니다. 프로세스, 서비스, 기기, API 클라이언트도 주체이며, 현대 환경에서는 사람보다 기계 주체가 훨씬 많습니다. 접근 통제는 IAAA 중 인가(Authorization)를 구현합니다.

    보충IAAA의 순서를 출입 관리로 풀면 이렇습니다. 식별은 “저는 김 대리입니다”라는 주장, 인증은 사원증과 얼굴을 대조해 그 주장을 확인하는 것, 인가는 “김 대리는 3층 사무실까지 들어갈 수 있다”는 결정, 책임추적성은 “김 대리가 몇 시에 어느 문을 열었다”는 기록입니다. 앞 단계가 없으면 뒤 단계가 성립하지 않습니다. 누구인지 확인하지 않고는 권한을 줄 수 없고, 개인을 식별하지 않으면 기록이 누구의 것인지 알 수 없습니다.

    연결IAAA와 각 단계의 통제는 D1.2 보안 개념 (CIA 등), 식별과 인증 수단은 D5.2 식별·인증 전략, 인증 프로토콜은 D5.6 인증 시스템, 인가 모델은 D5.4 인가 메커니즘에서 다룹니다.

    원본 연습문제 · D5.1-Q19

    식별, 인증, 인가, 책임추적성의 올바른 순서는?

    1. 인증, 식별, 책임추적성, 인가.
    2. 식별(자신이 누구인지 주장), 인증(그것을 증명), 인가(무엇을 할 수 있는지 결정), 그다음 책임추적성(무엇을 했는지 기록).
    3. 인가, 인증, 식별, 책임추적성.
    4. 책임추적성, 식별, 인증, 인가.
    정답과 해설 보기

    정답 B. 신원을 주장하지 않으면 증명할 대상이 없고, 증명되지 않은 신원으로는 권한을 판단할 수 없다. 권한이 정해진 뒤의 행위가 기록되어야 책임을 추적할 수 있다. 책임추적성이 성립하려면 앞의 세 단계가 개인 단위로 이루어져야 하며 그래서 공유 계정은 책임추적성을 없애 버린다.

    • A · 식별이 인증보다 앞선다.
    • C · 인가가 인증보다 앞설 수 없다.
    • D · 기록은 마지막 단계다.

    2물리적·논리적·관리적 통제

    구분대상예시
    물리적공간·장비 접근출입증, 잠금, 경비
    논리적(기술적)데이터·시스템 접근인증, 권한, ACL
    관리적절차·정책승인 절차, 권한 검토

    원본은 물리적 접근이 뚫리면 논리적 통제의 상당 부분이 무력화된다고 말합니다. 장비를 만질 수 있으면 디스크를 떼어 가거나, 콘솔로 접근하거나, 하드웨어 키로거를 설치할 수 있습니다. 그래서 세 가지가 함께 작동해야 합니다. 기술적으로 완벽해도 승인 절차가 없으면 누구나 권한을 받고, 절차가 엄격해도 물리 접근이 열려 있으면 우회됩니다.

    연결통제 유형(관리적·기술적·물리적)의 분류는 D1.9 위험 관리, 물리적 접근이 논리 통제를 무력화하는 이유는 D3.8 사이트·설비 설계 원칙의 1절에서 다뤘습니다.

    원본 연습문제 · D5.1-Q07

    서버에 대한 물리적 접근이 논리적 보안 통제를 크게 약화시키는 이유는?

    1. 암호화 키는 항상 장비 라벨에 인쇄되어 있다.
    2. 누군가 데이터센터에 들어오면 논리 통제가 자동으로 비활성화된다.
    3. 물리적 존재만으로 기본적으로 관리자 자격증명이 부여된다.
    4. 공격자가 저장 매체를 떼어 가거나 콘솔로 접근하거나 하드웨어 임플란트를 설치할 수 있다.
    정답과 해설 보기

    정답 D. 장비를 직접 만질 수 있으면 디스크를 분리해 다른 곳에서 읽거나, 콘솔 포트로 접근하거나, 하드웨어 키로거나 임플란트를 설치할 수 있다. 논리 통제의 상당수가 우회되므로 물리 보안이 모든 보안의 기반이 된다. TPM 봉인 같은 대책이 일부를 보완한다.

    • A · 키를 라벨에 인쇄하지 않는다.
    • B · 자동 비활성화되는 것이 아니라 우회 경로가 생기는 것이다.
    • C · 물리적 존재가 자격증명을 주지는 않는다.

    3자산 유형별 접근 통제

    공식 개요 5.1이 명시한 여섯 가지 자산입니다.

    자산원본이 드는 핵심 통제
    정보파일·DB 권한, 열·행·셀 단위 통제, 데이터 접근과 키 접근 분리, 라벨 기반 접근(MAC)
    시스템일반·관리 계정 분리, 적시 권한 상승(JIT), 특권 접근 관리, 점프 서버, 콘솔·대역 외 관리 포트, 하이퍼바이저·클라우드 관리 평면
    기기기기 인증(인증서가 MAC보다 강함), 등록과 인벤토리 연계, 기기 상태 기반 접근, 원격 삭제, BYOD는 업무 영역만
    시설구역 등급과 인가, 출입증·생체, 출입 기록과 논리 접근 로그의 상관분석, 방문자 동행
    애플리케이션RBAC와 기능 단위 인가, 객체 수준 인가, 세션 관리, 권한 상승 경로 차단
    서비스서비스 간 인증(mTLS, 토큰), API 키·토큰의 수명과 범위, 서비스 계정 관리

    정보: 데이터 접근과 키 접근의 분리

    원본은 키 분리가 중요하다고 짚습니다. DB 관리자가 데이터에 접근할 수 있어도 복호화 키에는 접근할 수 없게 하면 평문을 볼 수 없습니다.

    원문 사례 — 키 접근 분리. DB 관리자가 운영 DB 전체에 접근할 수 있었지만, 민감 열은 애플리케이션 계층에서 암호화되어 있고 복호화 키는 별도 KMS에 있어 DBA에게 권한이 없었습니다. DBA는 데이터를 관리할 수 있지만 평문을 볼 수 없습니다. 원본은 이것을 직무 분리를 기술적으로 구현한 사례로 봅니다.

    기기와 시설

    원본은 현대 접근 통제가 “누가”뿐 아니라 “어떤 기기로”를 함께 본다고 설명합니다. 같은 사용자라도 미등록 기기에서는 제한된 접근만 허용합니다. 또 물리·논리 접근 상관분석을 강력한 탐지 수단으로 꼽습니다. 건물에 없는 사람이 사내망에 로그인하면 이상 신호입니다.

    원문 사례 — 물리·논리 로그 상관분석이 잡은 도용. 출입 기록과 VPN 로그인을 교차 분석하니, 한 직원이 출입증으로 건물 안에서 활동하던 시간에 그의 계정이 해외 IP에서 로그인한 것이 확인되었습니다. 물리적으로 한곳에 있는 사람이 동시에 다른 곳에서 로그인할 수는 없습니다.

    보충여섯 자산을 따로 나열하는 이유는 같은 사람이라도 자산마다 “문”이 다르기 때문입니다. 자료실 출입 카드와 문서 시스템 계정은 서로 다른 경계를 엽니다. 출입이 필요한 시간과 문서를 읽어야 하는 범위가 다르다면 하나의 승인으로 두 권한을 묶지 않는 편이 관리와 추적이 쉽습니다. 그리고 사고를 분석할 때도 자산 층을 나눠 봅니다. 누가 자격증명을 썼는지(인증), 인증 뒤 어떤 대상에 허락되었는지(인가), 어떤 물리 경로로 장비를 만질 수 있었는지(물리). 원인이 인가 누락이라면 인증 요소를 하나 더 붙여도 권한 범위는 그대로입니다.

    연결열·행·셀 단위 통제와 IDOR는 D3.5 아키텍처별 취약점, 점프 서버는 D4.3 안전한 통신 채널, 특권 접근 관리(PAM)는 D7.4 기본 보안 운영 개념, 기기 상태 기반 접근은 D4.2 네트워크 구성요소의 NAC와 D3.1 안전한 설계 원칙의 제로 트러스트, 키 관리는 D3.6 암호 솔루션, BYOD는 D2.2 자산 취급 요구사항에서 다룹니다.

    4서비스 계정 — 가장 자주 방치되는 영역

    사람이 쓰지 않는 계정이라 관리에서 빠지기 쉽습니다.

    문제설명
    과도한 권한“일단 관리자로” 설정하고 줄이지 않음
    비밀번호 미변경바꾸면 서비스가 멈출까 봐 수년간 유지
    소유자 불명담당자 퇴사 후 아무도 모름
    공유 사용여러 시스템이 같은 계정 사용
    대화형 로그인 가능사람이 그 계정으로 직접 로그인

    통제: 소유자 지정 필수, 최소권한, 대화형 로그인 차단, 관리형 서비스 계정(비밀번호 자동 교체), 정기 권한 검토와 사용 여부 확인, 자격증명 금고 보관.

    원문 사례 — 관리자 권한 서비스 계정. 백업 소프트웨어의 서비스 계정이 설치 당시 “권한 문제를 피하려고” 도메인 관리자 권한으로 설정된 뒤 아무도 손대지 않았습니다. 침해되자 공격자가 이 계정으로 도메인 전체를 장악했습니다. 필요 권한만 주고, 대화형 로그인을 막고, 관리형 서비스 계정으로 바꿨습니다.

    가상 예시매일 밤 데이터 정리 작업이 한 직원의 계정으로 돌아가고 있다고 합시다. 그 직원이 비밀번호를 바꾸거나 퇴사하면 작업이 실패하고, 감사 기록에서는 직원 본인의 업무와 자동 작업이 섞여 구분되지 않습니다. 자동 작업에는 독립된 서비스 신원을 만들고, 소유자와 필요한 동작만 정하고, 사람이 그 계정으로 로그인하지 못하게 합니다. 반대로 서비스 계정을 사람이 쓰는 것도 같은 문제를 반대 방향에서 만듭니다.

    연결서비스 계정 비밀번호를 노리는 Kerberoasting은 D3.7 암호 분석 공격, 소유자 지정 원칙은 D2.3 안전한 프로비저닝, 계정 생애주기와 접근 검토는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원문 위치: D5.1.md §3 서비스 계정, §7 사례 2

    기본 거부명시적으로 허용한 것만
    책임추적성개인별 식별, 공유 계정 금지

    원본은 공유 계정이 책임추적성을 파괴한다고 경고합니다. 누가 무엇을 했는지 알 수 없어 감사와 사고 조사가 불가능해집니다. 불가피하다면 금고에서 꺼내 쓰고 사용 이력을 기록합니다.

    보충권한을 표로 저장하는 방식은 두 방향이 있습니다. 접근 통제 목록(ACL)은 객체를 기준으로 “이 파일에 누가 무엇을 할 수 있는가”를 적고, 능력 테이블(capability table)은 주체를 기준으로 “이 사용자가 무엇에 무엇을 할 수 있는가”를 적습니다. 같은 접근 매트릭스를 열 방향으로 자르느냐 행 방향으로 자르느냐의 차이입니다(원본 문제 Q13의 주제, 자세한 인가 모델은 D5.4 인가 메커니즘).

    원본 연습문제 · D5.1-Q13

    접근 통제 목록과 능력 테이블을 구분하는 것은?

    1. ACL 은 객체를 기준으로 구성되어 어떤 주체가 그 객체에 행위할 수 있는지를 나열하고 능력 테이블은 주체를 기준으로 구성되어 그 주체가 어떤 객체에 행위할 수 있는지를 나열한다.
    2. 같은 구조를 다른 파일 형식으로 저장한 것이다.
    3. ACL 은 파일에, 능력 테이블은 네트워크 장비에 쓰인다.
    4. ACL 은 임의적이고 능력 테이블은 항상 강제적이다.
    정답과 해설 보기

    정답 A. 같은 접근 통제 행렬을 어느 축으로 자르는지의 차이다. ACL 은 "이 파일에 누가 접근 가능한가" 를 보기 쉽고 능력 테이블은 "이 사용자가 무엇에 접근 가능한가" 를 보기 쉽다. 접근 검토에서는 주체 기준 조회가 필요하므로 ACL 만 있는 환경에서는 사용자별 권한 전수 파악이 어렵다.

    • B · 구성 축이 다르다.
    • C · 적용 대상으로 구분되지 않는다.
    • D · 임의적·강제적 구분은 별개 축이다.

    6접근 통제가 실패하는 방식

    유형결과
    과도한 권한 부여침해 시 피해 범위 확대
    권한 누적전보 시 회수 누락
    고아 계정퇴사자 계정 잔존
    인가 검증 누락인증만 하고 권한을 보지 않음(IDOR)
    우회 경로API·백도어·대체 인터페이스

    원본은 “인증했으니 됐다”가 가장 흔한 설계 오류라고 말합니다. 인증은 “누구인가”, 인가는 “무엇을 할 수 있는가”이며 둘은 별개입니다. 모든 요청마다 인가를 검증해야 합니다.

    원문 사례 — 인증만 하고 인가를 안 본 API. API가 토큰을 검증해 로그인한 사용자인지는 확인했지만, 요청한 주문 ID가 그 사용자의 것인지는 확인하지 않았습니다. 식별자를 바꾸면 다른 고객의 주문이 그대로 반환되었습니다.

    판단 순서접근 사고의 원인을 찾을 때 ① 인증이 실패했는가(남의 자격증명) ② 인증은 맞았는데 인가가 빠졌는가(IDOR, 권한 과다) ③ 인가 경로를 우회했는가(대체 인터페이스, 물리 접근) ④ 권한이 쌓이거나 회수되지 않았는가(권한 누적, 고아 계정)를 차례로 가립니다. 원인이 ②라면 MFA를 추가해도 해결되지 않습니다.

    연결모든 접근을 매번 검사한다는 완전한 중재는 D3.4 시스템 보안 기능, 권한 누적은 D1.8 인적 보안, 고아 계정과 접근 검토는 D5.5 프로비저닝 생애주기에서 다룹니다.

    원본 연습문제 · D5.1-Q01

    어떤 API 가 호출자의 토큰을 검증해 사용자가 로그인했음은 확인하지만 요청된 주문이 그 사용자의 것인지는 검증하지 않는다. 주문 식별자를 바꾸면 다른 고객의 데이터가 반환된다. 근본 원인은?

    1. 인증은 수행되었으나 객체 수준 인가가 수행되지 않았다.
    2. 전송 계층에 TLS 암호화가 없었다.
    3. 사용자 계정의 비밀번호 복잡도 요건이 약하다.
    4. 토큰 만료 간격이 너무 길게 설정되었다.
    정답과 해설 보기

    정답 A. 인증은 누구인가를 확인하고 인가는 무엇을 할 수 있는가를 결정하는 별개 단계다. 로그인 여부만 확인하고 요청된 개별 객체에 대한 권한을 검증하지 않으면 식별자만 바꿔 남의 데이터에 접근할 수 있다. 모든 요청마다 객체 수준 인가를 검증해야 한다.

    • B · 암호화는 전송 보호이며 권한 문제를 해결하지 않는다.
    • C · 비밀번호 강도는 인가 검증 누락과 무관하다.
    • D · 토큰 수명은 세션 관리 문제다.

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    점검 결과다. ㉠ 배치 작업용 서비스 계정이 도메인 관리자 권한이고 담당자가 퇴사했다. ㉡ 고객 조회 API가 로그인만 확인하고 고객 ID 소유 여부는 보지 않는다. ㉢ DB 관리자가 환자 정보 열의 평문을 볼 수 있다. ㉣ 운영팀이 공용 관리자 계정 하나를 함께 쓴다. 가장 적절한 대책 묶음은?

    1. ㉠ 소유자 지정·최소권한·대화형 로그인 차단·관리형 계정 / ㉡ 요청마다 객체 수준 인가 / ㉢ 애플리케이션 계층 암호화와 키를 별도 KMS에 두어 DBA 권한에서 분리 / ㉣ 개인별 계정, 불가피하면 금고와 사용 이력
    2. ㉠ 비밀번호만 변경 / ㉡ MFA 추가 / ㉢ DBA 교육 / ㉣ 비밀번호를 길게
    3. ㉠ 계정 삭제 후 직원 계정으로 대체 / ㉡ TLS 적용 / ㉢ 디스크 암호화 / ㉣ 그대로
    4. ㉠ 그대로 / ㉡ 속도 제한 / ㉢ DBA 해고 / ㉣ 로그 보존 기간 연장
    정답과 해설 보기

    정답 A. ㉠ 4절, ㉡ 6절(인증이 아니라 인가 문제라 MFA로 해결되지 않음), ㉢ 3절(디스크 암호화는 DBA가 DB를 통해 읽는 것을 막지 못함), ㉣ 5절(공유 계정은 책임추적성 파괴).

    복습

    최소 권한과 알 필요성을 각각 확인하려면 무엇을 물어야 하나요?

    설명 확인하기

    어떤 기능을 얼마나 행사할 수 있어야 하는지가 최소 권한입니다. 어떤 자료를 읽어야 업무가 되는지가 알 필요성입니다. 사업장 기록을 읽을 권리와 지급을 승인할 권리는 별도로 검토합니다.

    9핵심 요약

    1. 접근 통제 = 주체 → 접근 → 객체. 주체는 사람만이 아니다(기계 주체가 더 많다). IAAA의 인가를 구현.
    2. 물리·논리·관리 통제가 함께 작동해야 한다. 물리 접근이 뚫리면 논리 통제 상당수가 무력화.
    3. 여섯 자산: 정보 / 시스템 / 기기 / 시설 / 애플리케이션 / 서비스.
    4. 정보: 열·행·셀 단위 통제, 데이터 접근과 키 접근 분리(직무 분리의 기술적 구현).
    5. 기기: “누가” + “어떤 기기로”. 시설: 물리·논리 로그 상관분석으로 도용 탐지.
    6. 애플리케이션·서비스: 객체 수준 인가, 서비스 간 인증, 토큰 수명·범위.
    7. 서비스 계정: 소유자 지정, 최소권한, 대화형 로그인 차단, 관리형 계정, 정기 검토.
    8. 원칙: 최소권한, 알 필요성, 직무 분리, 기본 거부, 책임추적성(공유 계정 금지).
    9. 실패: 과도한 권한, 권한 누적, 고아 계정, 인가 검증 누락, 우회 경로. 인증 ≠ 인가, 모든 요청마다 인가 검증.
    원문 위치: D5.1.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    10주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Subject / Object · 주체 / 객체

    접근을 요청하는 능동적 실체와 접근 대상이 되는 수동적 자원. 주체는 사람, 프로세스, 서비스, 기기를 포함한다.

    Authorization · 인가

    인증된 주체가 무엇을 할 수 있는지 결정하는 단계. 인증과 별개다.

    Physical / Logical / Administrative Control · 물리적 / 논리적 / 관리적 통제

    공간·장비 접근 통제, 데이터·시스템 접근 통제, 절차·정책 통제.

    Service Account · 서비스 계정

    사람이 아닌 애플리케이션이나 서비스가 사용하는 계정. 소유자 지정과 대화형 로그인 차단이 핵심이다.

    Managed Service Account · 관리형 서비스 계정

    비밀번호가 자동 교체되는 서비스 계정. Kerberoasting 대응에도 효과적이다.

    Object-Level Authorization · 객체 수준 인가

    요청된 개별 객체에 대해 호출자의 권한을 검증하는 것. IDOR 방어의 핵심이다.

    Orphaned Account · 고아 계정

    소유자가 없거나 퇴사자의 계정이 남아 있는 상태.

    Device Posture · 기기 상태

    패치, 암호화, 백신 상태 등 접근 허용 조건으로 쓰이는 기기의 보안 상태.

    Accountability · 책임추적성

    행위를 특정 개인에게 귀속시킬 수 있는 성질. 공유 계정은 이를 파괴한다.
