    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    공식 개요 6.2는 테스트 기법을 열 가지 넘게 나열합니다. 원본은 이것을 외울 목록이 아니라 서로 다른 질문에 답하는 도구들로 봅니다. “알려진 약점이 있는가”와 “그 약점으로 실제 침해가 되는가”와 “우리가 그 공격을 탐지하는가”는 다른 질문이고, 그래서 다른 기법이 필요합니다. 이 단원은 기법마다 무엇을 보고 무엇을 놓치는지를 정리합니다.

    침해 공격 시뮬레이션알려진 공격 기법을 탐지·차단하는가
    준수 점검요구사항을 충족하는가

    판단 순서상황을 보면 먼저 “무엇을 알고 싶은가”를 찾습니다. 탐지되는지 알고 싶다 → 침해 시뮬레이션이나 비공개 레드팀. 약점 목록이 필요하다 → 취약점 평가. 기준 대비 설정 → 벤치마크. 실제로 무엇을 달성할 수 있는지 증거가 필요하다 → 침투 테스트. 관리적 통제(승인 절차 등)가 실제로 수행되었는가 → 기록 검토와 면담. 질문이 정해지면 기법이 정해집니다.

    2취약점 평가

    알려진 취약점과 오설정을 식별하고 목록화합니다. 악용은 하지 않습니다.

    요점내용
    인증 스캔 vs 비인증 스캔인증 스캔은 로그인해 패치 수준과 설정을 정확히 봄. 비인증 스캔은 외부 공격자 시점이지만 거짓 음성(놓침)이 많음
    에이전트 기반단말에 설치해 오프라인 자산, 원격 근무 단말까지 포괄
    결과 처리거짓 양성이 많으므로 검증 단계 필수. 검증 없이 보고하면 신뢰를 잃음
    심각도CVSS 기본 점수만으로는 부족. 알려진 악용 여부, 자산 중요도, 노출 경로를 함께
    한계알려진 패턴만. 논리 결함, 인가 설계 오류, 업무 흐름 악용은 못 찾음
    운영 영향취약한 장비나 OT/ICS에서는 스캔 자체가 장애를 유발. 수동 식별이나 패시브 방식 필요

    원문 사례 — 비인증 스캔이 놓친 결함. 외부 비인증 스캔은 깨끗했지만 인증 스캔을 도입하자 같은 서버에서 누락된 OS 패치 다수와 약한 로컬 정책이 드러났습니다. 운영 자산에는 인증 스캔과 에이전트를, 비인증 스캔은 외부 노출 표면 확인용으로 한정했습니다.

    원문 사례 — CVSS 점수만으로 정한 우선순위. CVSS 9.0 이상만 우선 처리하다가, 7.5지만 공개 악용 코드가 있고 인터넷에 노출된 결제 시스템의 취약점이 3개월간 방치되었습니다. 기준을 점수 + 알려진 악용 + 노출 경로 + 자산 중요도로 바꿨습니다.

    보충경고 건수를 세기 전에 도구가 환경을 제대로 볼 수 있었는지부터 확인합니다. “목록에 없던 자산”, “접근 권한이 없어 못 본 시스템”, “검사 실패”, “정상 검사 후 문제 없음”은 결과표에서 모두 빈칸처럼 보이지만 의미가 전혀 다르므로 따로 기록합니다. 의료기기처럼 스캔에 취약한 장비가 섞인 망이라면 이 구분이 더 중요합니다.

    연결결과 분석과 거짓 양성 처리, 우선순위는 D6.4 결과 분석과 보고, 패치와 취약점 관리 운영은 D7.8 패치·취약점 관리에서 다룹니다.

    원본 연습문제 · D6.2-Q15

    스캐너가 발견 사항 400건을 보고했고 표본 점검 결과 대략 절반이 오탐이다. 적절한 대응은?

    1. 스캐너가 긴급으로 표시한 것만 보고하고 나머지는 무시한다.
    2. 스캔 결과 전체를 신뢰할 수 없다고 폐기하고 도구를 교체한다.
    3. 400건 전부를 시스템 소유자에게 보내 진짜를 판별하게 한다.
    4. 시정을 배정하기 전에 발견 사항을 검증하고 스캐너를 조정하고 확인된 오탐을 문서화해 이후 스캔에서 억제하며 오탐률을 품질 지표로 추적한다.
    정답과 해설 보기

    정답 D. 검증 없이 전부 넘기면 소유자의 신뢰를 잃고 이후 진짜 발견 사항도 무시된다. 오탐을 확인해 억제 규칙으로 남기면 같은 노이즈가 반복되지 않고, 오탐률을 추적하면 도구와 설정의 품질을 관리할 수 있다. 결과 전체 폐기는 진짜 문제를 함께 버리는 것이고 긴급만 보는 것은 등급 산정 자체가 오탐일 수 있어 위험하다.

    • A · 등급 산정도 검증 대상이다.
    • B · 진짜 발견 사항을 함께 버린다.
    • C · 소유자의 신뢰를 잃고 대응을 둔화시킨다.

    3침투 테스트와 레드·블루·퍼플팀

    실제로 악용해 침해 가능성을 입증합니다. 취약점의 존재가 아니라 영향(impact)을 보여 주는 것이 목적입니다.

    1. 사전 합의(Planning): 범위, 규칙, 승인서
    2. 정찰(Reconnaissance): 수동·능동 정보 수집
    3. 스캐닝(Scanning): 서비스·취약점 탐색
    4. 악용(Exploitation): 접근 획득
    5. 후속 활동(Post-exploit): 권한 상승, 횡적 이동, 지속성
    6. 보고(Reporting): 재현 절차, 영향, 권고
    지식 수준테스터의 사전 지식특징
    블랙박스없음(외부 공격자 모사)현실성 높지만 시간 대부분을 정찰에 씀 → 같은 예산에서 찾는 결함이 적음
    그레이박스일부(일반 사용자 수준)중간
    화이트박스전체(설계·소스 제공)효율이 가장 높음

    공개(announced) 테스트는 운영팀이 알아 협조가 쉽고, 비공개(unannounced) 테스트는 탐지·대응 역량까지 검증합니다. 원본은 비공개라도 소수의 책임자는 반드시 알아야 한다고 강조합니다. 그렇지 않으면 실제 사고로 오인해 과도한 대응이 일어나고 테스터가 법적 위험에 놓입니다.

    팀역할
    레드팀공격자 관점에서 침해 시도. 침투 테스트가 발견 범위(breadth)라면 레드팀은 특정 목표 달성(depth)과 탐지 회피. 산출물은 “조직이 이 공격을 탐지했는가”에 대한 답
    블루팀방어·탐지·대응
    퍼플팀양쪽을 연결해 학습을 순환시킴. 조직이라기보다 기능인 경우가 많음(기법 공개 → 탐지 규칙 → 재검증)

    원문 사례 — 기본 위생 없이 돌린 레드팀. 고비용 레드팀이 첫날 기본 자격증명이 설정된 관리 인터페이스로 도메인 관리자 권한을 얻었고, 보고서는 “패치와 기본 설정이 미비하다”로 끝났습니다. 원본의 교훈은 레드팀은 기본 위생이 갖춰진 뒤에 가치가 있다입니다.

    연결테스트의 서면 승인과 운영 영향 관리는 D6.1 평가·테스트·감사 전략의 6절, 권한 상승과 횡적 이동 기법은 D3.7 암호 분석 공격에서 다룹니다.

    원본 연습문제 · D6.2-Q01

    경영진이 환경에 존재하는 약점으로 공격자가 실제로 무엇을 달성할 수 있는지에 대한 증거를 요구한다. 이를 제공하는 활동은?

    1. 약점을 악용해 달성 가능한 영향을 입증하는 침투 테스트.
    2. 알려진 약점과 심각도를 열거하는 취약점 평가.
    3. 적용 규제 요구사항에 대한 준수 점검.
    4. 업계 기준선과의 설정 벤치마크 비교.
    정답과 해설 보기

    정답 A. 취약점 평가는 약점의 존재를 목록화하고 악용은 하지 않는다. 침투 테스트는 실제로 악용해 공격자가 달성할 수 있는 영향을 입증한다. 침투 테스트의 가치는 취약점의 존재가 아니라 그 영향을 보여주는 것이다.

    • B · 목록과 심각도는 영향 입증이 아니다.
    • C · 준수 점검은 요구사항 충족 여부를 다룬다.
    • D · 벤치마크는 설정 일탈을 보여주며 달성 가능한 영향을 보여주지 않는다.

    4로그 검토, 합성 트랜잭션, 벤치마크

    로그 검토

    기록이 존재하고, 보존되고, 분석 가능하고, 실제로 분석되는지 확인합니다.

    확인 항목내용
    생성 여부설정 변경, 권한 변경, 인증 성공·실패, 특권 사용이 실제로 기록되는가
    완결성전송 실패나 저장 한도 초과로 조용히 끊기지 않는가
    무결성공격자는 로그부터 지운다 → 원격 전송과 추가 전용(append-only) 저장
    시각 동기화상관분석의 전제
    실제 검토수집만 하고 보지 않으면 탐지 통제가 아님. 경보 정의와 처리 기록이 함께

    로그 검토는 다른 통제의 작동 증거를 확인하는 수단이기도 합니다. “접근 검토가 수행되었다”의 증거는 검토 수행 기록이고, “관리자 승인이 필요하다”는 정책의 시험은 승인 기록을 표본 추출해 실제로 승인이 이루어졌는지 보는 것입니다.

    원문 사례 — 로그는 있었으나 아무도 보지 않았다. 침해 조사에서 공격의 전 단계가 이미 수집된 로그에 남아 있었지만 경보가 정의되어 있지 않았습니다. 원본의 표현대로 수집은 탐지가 아닙니다.

    합성 트랜잭션

    실제 사용자 흐름을 모사한 인공 거래를 주기적으로 실행해 서비스가 정상인지 확인합니다. 로그인 → 조회 → 제출 같은 종단 간 흐름의 성공 여부와 응답 시간을 측정하며, 사용자가 신고하기 전에 장애를 잡습니다. 보안 측면에서는 인증·인가 경로가 살아 있는지, 보안 통제가 서비스를 깨뜨리지 않는지 확인합니다. 주의: 합성 트랜잭션용 계정은 실제 계정이므로 최소권한과 별도 식별이 필요하고, 테스트 데이터가 실 데이터와 섞이지 않게 합니다.

    벤치마크

    합의된 기준 설정과 현재 설정을 비교합니다(CIS 벤치마크, 공급자 기준선, 조직 표준 이미지). 자동 측정이 가능해 지속 점검에 적합하고, 핵심 가치는 기준선 일탈(drift) 탐지입니다. 기준이 조직 환경과 맞지 않으면 무의미한 예외가 대량 발생하므로 조정(tailoring)하고 근거를 문서화합니다.

    연결로그 관리와 SIEM은 D7.2 로깅·모니터링, 설정 기준선과 변경 관리는 D7.3 구성 관리, 기준선의 조정은 D2.6 데이터 보안 통제에서 다룹니다.

    원본 연습문제 · D6.2-Q22

    관리자 승인을 요구하는 정책처럼 관리적 통제를 시험하는 데 적절한 방법은?

    1. 기록 검토와 인터뷰. 승인 기록을 표본 추출해 승인이 요구대로 실제로 이루어졌는지 확인한다.
    2. 비밀번호 크래킹 시도.
    3. 영향받는 서버에 대한 포트 스캔.
    4. 네트워크 취약점 스캔.
    정답과 해설 보기

    정답 A. 시험 방법은 통제 유형에 맞춰야 한다. 관리적 통제는 사람의 행위와 기록으로 존재하므로 스캔으로는 확인할 수 없다. 승인 기록을 표본 추출해 실제로 승인되었는지, 승인자가 권한이 있는 사람인지, 일자가 선후 관계에 맞는지를 본다. 스캔과 크래킹은 기술적 통제의 시험 수단이다.

    • B · 기술적 통제의 시험 수단이다.
    • C · 기술적 통제의 시험 수단이다.
    • D · 기술적 통제의 시험 수단이다.

    5코드 검토와 테스트 (Code Review and Testing)

    방법성격강점 / 약점
    수동 코드 검토사람이 읽음논리·인가 결함, 암호 사용 오류에 강함. 자동 도구로 대체되지 않음
    SAST소스 정적 분석조기에 싸게 발견 / 실행 맥락이 없어 거짓 양성 많음
    DAST실행 중 동적 분석실제 동작 기반 / 인증 필요 영역·복잡한 상태 흐름을 놓침
    IAST실행 중 계측두 방식의 중간
    SCA오픈소스 구성요소와 알려진 취약점현대 앱 코드 대부분이 외부 의존성이라 중요도가 높음
    퍼징 fuzzing비정상 입력 대량 투입예외 처리 결함, 메모리 안전 문제

    원본은 코드 검토를 변경 단위로 상시 수행하라고 권합니다. 출시 직전 일괄 검토는 수정 비용이 가장 높은 시점에 결함을 발견합니다.

    보충SAST와 DAST는 집 점검에 비유할 수 있습니다. SAST는 설계도를 펼쳐 놓고 배선이 잘못된 곳을 찾는 것(공사 전이라 고치기 싸지만, 실제로 문제가 될지는 모름), DAST는 완공된 집의 스위치를 하나씩 눌러 보는 것(실제 동작을 보지만 잠긴 방은 못 들어감)입니다. SCA는 들여온 가전제품의 리콜 목록 확인입니다. 서로 보는 곳이 달라 하나로 다른 것을 대신할 수 없습니다.

    연결개발 수명주기 안에서의 보안 테스트 배치는 D8.2 개발 생태계 보안 통제, 오픈소스·공급망 위험은 D8.4 도입 소프트웨어 평가, 결함 수정 비용과 V&V는 D3.10 정보시스템 생애주기에서 다룹니다.

    원문 위치: D6.2.md §3 코드 검토와 테스트 · 공식 개요 6.2 “Code review and testing”

    6오용 사례 테스트 (Misuse Case Testing)

    사용 사례(use case)가 “의도된 사용”을 기술한다면 오용 사례는 “악의적 사용”을 기술합니다. 기능 테스트는 “올바른 입력에 올바른 결과”를, 오용 사례 테스트는 “공격자가 이 기능을 어떻게 악용할 수 있는가”를 확인합니다.

    기능오용 사례
    비밀번호 재설정타인 계정 탈취
    쿠폰무한 중복 적용
    파일 업로드서버 코드 실행
    검색데이터 대량 추출

    오용 사례는 위협 모델링의 산출물과 연결됩니다. 위협 모델링이 “무엇이 잘못될 수 있는가”를 식별하면 오용 사례 테스트가 그것을 검증합니다. 원본은 여기서 기능 테스트만으로는 찾지 못하는 결함이 나온다고 말합니다. 기능 명세에 “다른 사용자의 데이터를 반환하면 안 된다”가 적혀 있지 않기 때문입니다.

    원문 사례 — 오용 사례 테스트가 찾은 재설정 결함. 기능 테스트는 전부 통과했지만, 재설정 요청에서 대상 계정 식별자를 바꾸면 다른 사용자의 재설정 메일이 공격자 주소로 발송되었습니다. 오용 사례를 위협 모델링에서 도출해 테스트 케이스로 관리하게 했습니다.

    연결위협 모델링은 D1.10 위협 모델링, 비밀번호 재설정이 약한 고리라는 점은 D5.2 식별·인증 전략의 4절, 안전한 코딩 관점은 D8.5 안전한 코딩에서 다룹니다.

    원문 위치: D6.2.md §3 오용 사례 테스트, §7 사례 6 · 공식 개요 6.2 “Misuse case testing”

    7커버리지 분석 (Coverage Analysis)

    무엇이 검증되지 않았는지를 측정합니다. 두 맥락에서 쓰입니다.

    • 테스트 범위 커버리지: 자산·시스템·요구사항 중 몇 퍼센트가 검증되었는가(D6.1 평가·테스트·감사 전략의 5절).
    • 코드 커버리지: 테스트가 코드의 몇 퍼센트를 실행했는가.

    원본이 경고하는 함정: 실행했다는 것과 검증했다는 것은 다릅니다. 단정문(assertion)이 없는 테스트는 코드를 실행하고 아무것도 확인하지 않습니다. 보안 관점에서 중요한 것은 인증, 인가, 입력 검증, 오류 처리 경로의 커버리지를 따로 보는 것입니다.

    원문 사례 — 코드 커버리지 85%의 착시. 85%를 품질 근거로 제시했지만 인증·인가 경로는 30% 미만이었고 일부 테스트에는 단정문이 아예 없었습니다. 보안 경로 커버리지를 별도 지표로 분리하고 단정문 없는 테스트를 정리했습니다.

    보충API 20개를 모두 한 번씩 호출했다고 정책의 중요한 분기가 다 검증된 것은 아닙니다. “대상 커버리지(어떤 경로를 시험했나)”와 “정책 커버리지(허용돼야 할 접근과 거부돼야 할 접근을 모두 시험했나)”를 나눠 봅니다. 접근 통제라면 허용 사례만 시험하고 거부 사례를 빠뜨리는 것이 가장 흔한 빈틈입니다.

    원본 연습문제 · D6.2-Q08

    어떤 팀이 코드 커버리지 85% 를 테스트 품질의 근거로 제시했다. 검토에서 인증과 인가 경로의 커버리지는 30% 미만이고 일부 테스트에는 단정문이 전혀 없음이 드러났다. 올바른 해석은?

    1. 커버리지 도구가 잘못 보고하고 있으므로 재설정해야 한다.
    2. 80% 이상 커버리지는 일반적으로 충분하므로 조치가 필요하지 않다.
    3. 코드 커버리지를 침투 테스트로 전면 대체해야 한다.
    4. 코드를 실행하는 것은 검증하는 것과 다르다. 보안 관련 경로 커버리지를 별도로 관리하고 단정문 없는 테스트를 수정해야 한다.
    정답과 해설 보기

    정답 D. 커버리지는 테스트가 코드를 실행했는지만 측정하며 단정문이 없으면 실행만 하고 아무것도 검증하지 않는다. 보안 관점에서는 전체 수치보다 인증, 인가, 입력 검증, 오류 처리 경로의 커버리지가 중요하므로 별도 지표로 분리해 관리해야 한다.

    • A · 도구는 실행 여부를 정확히 보고했고 해석이 문제였다.
    • B · 전체 수치가 높아도 보안 경로가 비어 있으면 의미가 없다.
    • C · 두 활동은 사각지대가 달라 서로를 대체하지 않는다.

    8인터페이스 테스트

    구성요소 간 경계를 검증합니다. 공식 개요는 사용자 인터페이스, 네트워크 인터페이스, API를 명시합니다.

    원본은 경계가 취약한 이유를 이렇게 설명합니다. 각 구성요소 개발자는 “상대가 검증했을 것”이라고 가정하고, 양쪽 모두 그렇게 가정하면 검증이 아무 곳에서도 일어나지 않습니다.

    인터페이스확인할 것
    사용자 인터페이스클라이언트 측 검증은 우회됨 → 서버 측 검증 필수. UI에서 숨긴 기능은 접근 통제가 아님
    네트워크 인터페이스관리 포트 노출, 불필요한 서비스, “내부 전용” 가정의 오류
    API(가장 중요)객체·기능 수준 인가, 속도 제한, 과도한 데이터 반환, 버전 간 불일치, 문서화되지 않은 엔드포인트

    원문 사례 — UI를 통제로 착각한 API. 권한 없는 사용자에게 삭제 버튼이 보이지 않았지만 API를 직접 호출하면 삭제가 되었습니다. API 계층에 기능·객체 수준 인가를 넣고 인터페이스 테스트를 API 중심으로 재구성했습니다.

    연결PEP 우회 경로와 “표현 계층의 인가”는 D5.4 인가 메커니즘의 7절, API 보안 코딩은 D8.5 안전한 코딩에서 다룹니다.

    원문 위치: D6.2.md §3 인터페이스 테스트, §7 사례 5 · 공식 개요 6.2 “Interface testing (e.g., user interface, network interface, API)”

    9침해 공격 시뮬레이션 (BAS)

    알려진 공격 기법을 안전하게 반복 실행해 탐지와 차단이 작동하는지 검증합니다. MITRE ATT&CK 기반으로 기법 단위 커버리지를 측정하는 방식이 일반적입니다.

    비교BAS레드팀
    성격자동화, 반복 가능, 측정 가능창의적, 비싸고 1회성
    강점“이 기법을 잡는가”를 지표로 관리, 도구 도입 전후 비교조직 고유의 경로와 새로운 조합
    한계미리 정의된 기법만. 새 공격·업무 논리 악용은 못 다룸반복 측정이 어려움

    운영 환경에서 실행하므로 안전 장치와 범위 제한이 필요하고, 실제 파괴적 동작은 하지 않도록 구성합니다.

    원문 사례 — BAS로 측정한 탐지 공백. 신규 탐지 솔루션의 효과를 입증하기 위해 ATT&CK 기법 단위로 BAS를 반복 실행해 도입 전후를 비교했습니다. 자격증명 접근 기법 탐지율은 크게 좋아졌지만 횡적 이동 탐지는 변화가 없어 추가 투자 영역이 분명해졌습니다. 원본은 반복 가능한 측정이 레드팀 1회 결과보다 개선 추적에 유용했다고 정리합니다.

    연결MITRE ATT&CK과 공격 기법은 D3.7 암호 분석 공격·D1.10 위협 모델링, 탐지 운영은 D7.2 로깅·모니터링에서 다룹니다.

    원문 위치: D6.2.md §3 침해 공격 시뮬레이션, §7 사례 8 · 공식 개요 6.2 “Breach attack simulations”

    10준수 점검

    규제·표준·계약·내부 정책 요구사항을 충족하는지 확인합니다.

    • 증거 기반: “했다”가 아니라 증거로 입증합니다(정책 문서, 승인 기록, 로그, 교육 이수 기록).
    • 자동화 가능 영역: 설정 기준, 패치 수준, 암호화 적용, 로그 보존 기간.
    • 준수와 보안은 같지 않다: 준수는 최소 기준이며 통과가 안전을 뜻하지 않습니다. 반대로 준수 요구가 조직 위험과 맞지 않는 투자를 강요하기도 합니다.
    • 지속적 준수: 연 1회 점검은 그 사이의 일탈을 놓치므로 상시 측정으로 옮겨 가는 추세입니다.

    보충준수 점검이 무엇을 증명했는지 좁게 말하는 습관이 중요합니다. 백업 정책이 승인되어 있고 설정에서 주기를 확인했다면 “표준과 일치한다”는 증거를 얻은 것입니다. 파일을 실제로 복원할 수 있는지, 목표 시간 안에 업무를 올릴 수 있는지는 복원 시험이 보여 줍니다. 심사 보고서에서 결론을 증거가 닿는 범위로 한정하는 것과 같은 원리입니다.

    원문 위치: D6.2.md §3 준수 점검 · 공식 개요 6.2 “Compliance checks”

    통제 수행 증거로그·기록 검토, 준수 점검
    미검증 영역커버리지 분석

    원본의 결론은 어떤 단일 기법도 충분하지 않다입니다. 기법마다 사각지대가 다르므로 조합이 필요합니다.

    가상 예시“권한 정책이 적용되고, 사용량이 늘어도 서비스가 작동한다”는 요구를 스캔 한 번으로 검증하려 한다고 합시다. 세 질문으로 나눕니다. ① 설정·코드에 통제가 있는가(구성 검토, 코드 검토) ② 승인된 환경에서 사용자·대상 조합별로 허용과 거부가 기대대로 나오는가(오용 사례·인터페이스 테스트) ③ 기준 부하에서 서비스 경로가 유지되는가(합성 트랜잭션). 스캔은 이 중 어느 질문에도 직접 답하지 않습니다.

    원문 위치: D6.2.md §3 기법 선택과 조합

    12종합 이해 확인

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    보안 책임자가 네 가지를 알고 싶어 한다. ㉠ 새로 도입한 탐지 솔루션이 알려진 횡적 이동 기법을 잡는지, 도입 전후로 반복 측정하고 싶다. ㉡ 웹 화면에서는 숨겨진 삭제 기능이 다른 경로로는 실행되지 않는지. ㉢ 서버 설정이 CIS 기준에서 벗어났는지. ㉣ 구매 승인 절차가 실제로 지켜졌는지. 가장 적절한 기법 조합은?

    1. ㉠ 블랙박스 침투 테스트 / ㉡ 비인증 스캔 / ㉢ 침투 테스트 / ㉣ 포트 스캔
    2. ㉠ 침해 공격 시뮬레이션 / ㉡ API 인터페이스 테스트 / ㉢ 벤치마크 / ㉣ 승인 기록 표본 검토와 면담
    3. ㉠ 취약점 평가 / ㉡ SAST만 / ㉢ 합성 트랜잭션 / ㉣ 준수 점검 없이 정책 문서 확인
    4. ㉠ 코드 커버리지 / ㉡ UI 테스트 / ㉢ 레드팀 / ㉣ 비밀번호 크래킹
    정답과 해설 보기

    정답 B. ㉠ 9절(반복 가능·측정 가능한 탐지 검증), ㉡ 8절(UI 숨김은 통제가 아님, API 직접 호출 확인), ㉢ 4절(기준선 일탈), ㉣ 4절·1절(관리적 통제는 기록 표본과 면담). C의 “정책 문서 확인”은 통제가 있다는 검토 결과일 뿐 실제 수행의 증거가 아닙니다.

    13핵심 개념을 내 말로 설명하기

    복습

    기법을 고를 때 어떤 검증 질문이 먼저인가요?

    설명 확인하기

    어떤 실패가 발견돼야 하는지와 관찰할 근거를 먼저 정합니다. 승인 설정과 실제 동작은 다른 증거를 쓰며, 정상·거부 흐름과 시험하지 않은 범위를 함께 기록합니다.

    14핵심 요약

    1. 기법은 서로 다른 질문에 답한다. 먼저 “무엇을 알고 싶은가”.
    2. 취약점 평가: 알려진 약점 목록, 악용 안 함. 인증 스캔이 더 정확. 거짓 양성 검증 필수. CVSS + 악용 여부 + 노출 + 자산 중요도. 논리·인가 결함은 못 찾음.
    3. 침투 테스트: 악용으로 영향 입증. 계획→정찰→스캔→악용→후속→보고. 블랙(현실성) / 그레이 / 화이트(효율 최고). 비공개라도 소수 책임자는 인지.
    4. 레드팀 = 목표 달성·탐지 회피(depth), 산출물은 “탐지했는가”. 블루팀 = 방어. 퍼플팀 = 학습 순환 기능. 기본 위생이 먼저.
    5. 로그 검토: 생성·완결·무결성(원격, append-only)·시각 동기화·실제 검토. 수집은 탐지가 아니다. 다른 통제의 수행 증거.
    6. 합성 트랜잭션 = 종단 간 흐름 주기 실행. 벤치마크 = 기준 대비 설정, drift 탐지, tailoring 문서화.
    7. 코드: 수동 검토(논리·인가), SAST(조기·거짓 양성), DAST(실동작·커버리지 제한), IAST, SCA(의존성), 퍼징. 변경 단위로 상시.
    8. 오용 사례 = 악의적 사용. 위협 모델링에서 도출. 기능 테스트로는 못 찾는 결함.
    9. 커버리지: 실행 ≠ 검증(단정문). 보안 경로 커버리지를 따로.
    10. 인터페이스: 서로 “상대가 검증했겠지” → 아무도 안 함. UI 숨김은 통제가 아님, API가 핵심.
    11. BAS: ATT&CK 기반 반복 측정. 정의된 기법만. 준수 점검: 증거 기반, 준수 ≠ 보안, 지속적 준수.
    12. 단일 기법은 충분하지 않다. 사각지대가 다르므로 조합.
    원문 위치: D6.2.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 “시험 전략” 같은 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    15주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    Vulnerability Assessment · 취약점 평가

    알려진 취약점과 오설정을 식별해 목록화하는 활동. 악용은 하지 않는다.

    Authenticated / Unauthenticated Scan · 인증 / 비인증 스캔

    자격증명으로 로그인해 수행하는 스캔과 외부 시점에서 수행하는 스캔.

    Penetration Testing · 침투 테스트

    실제 악용을 통해 침해 가능성과 영향을 입증하는 테스트.

    Black / Gray / White Box · 정보 미제공 / 일부 제공 / 내부 정보 제공 시험

    테스터에게 주어진 사전 지식이 없음 / 일부 / 전체인 테스트 방식.

    Announced / Unannounced · 공개 / 비공개

    운영팀이 테스트를 인지하는지 여부. 비공개는 탐지·대응 역량까지 검증한다.

    Red / Blue / Purple Team · 공격 역할 / 방어 역할 / 협력 검증

    공격 역할, 방어 역할, 양쪽 학습을 순환시키는 연결 기능.

    Log Review · 로그 검토

    필요한 이벤트가 기록·보존·분석되는지 확인하는 활동.

    Synthetic Transaction · 합성 트랜잭션

    실제 사용자 흐름을 모사한 인공 거래를 주기적으로 실행해 서비스 상태를 확인하는 방법.

    Benchmark · 벤치마크

    합의된 기준 설정과 현재 설정을 비교하는 점검. CIS 벤치마크가 대표적이다.

    Configuration Drift · 설정 일탈

    기준선에서 설정이 시간에 따라 벗어나는 현상.

    SAST / DAST / IAST / SCA — Static / Dynamic / Interactive Application Security Testing / Software Composition Analysis · 정적 / 동적 / 상호작용형 보안 시험 / 소프트웨어 구성 분석

    정적 분석, 동적 분석, 계측 기반 분석, 구성요소 분석.

    Fuzzing · 퍼징

    비정상 입력을 대량 투입해 예외 처리와 메모리 안전 결함을 찾는 기법.

    Misuse Case · 오용 사례

    악의적 사용 방식을 기술한 시나리오. 사용 사례의 반대 개념이다.

    Coverage Analysis · 커버리지 분석

    검증되지 않은 자산이나 코드 경로를 측정하는 활동.

    Interface Testing · 인터페이스 테스트

    사용자 인터페이스, 네트워크 인터페이스, API 등 구성요소 경계를 검증하는 테스트.

    BAS (Breach and Attack Simulation) · 침해·공격 시뮬레이션

    알려진 공격 기법을 자동 반복 실행해 탐지·차단을 검증하는 방식.

    MITRE ATT&CK · 공격 전술·기법 지식 기반

    공격자의 전술과 기법을 체계화한 지식 기반. 탐지 커버리지 측정에 쓰인다.

    Compliance Check · 준수 점검

    규제·표준·계약·정책 요구사항 충족 여부를 증거로 확인하는 활동.
