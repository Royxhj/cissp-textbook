    Understand and integrate security in the Software Development Life Cycle (SDLC) · ISC2 CISSP Exam Outline(2024-04-15 발효) 8.1

    주요 용어 바로가기 · Glossary

    연습문제 5개 바로가기

    표시 없는 본문은 원본 정리 파일의 내용 · 보충은 원본에 없어 더한 설명 · 가상 예시는 지어낸 상황 · 연결은 다른 단원과의 관계 · 확인 필요는 그대로 확정하지 않은 부분

    도메인 8은 소프트웨어 개발 보안입니다. 그 첫 단원은 원본의 한 문장으로 요약됩니다. 보안은 단계가 아니라 전 생애주기에 걸친 활동이다. “개발이 끝나고 보안 검토”는 가장 비싼 방식입니다. 설계 결함은 코드로 고칠 수 없고, 출시 직전에 발견된 결함은 수정 비용이 가장 높습니다. 공식 개요 8.1은 개발 방법론, 성숙도 모델, 운영과 유지보수, 변경 관리, 통합 제품 팀(IPT)을 듭니다. 의료기기 소프트웨어 개발 수명주기(IEC 62304 같은)를 아는 분이라면 구조가 익숙할 것입니다.

    원문 사례 — 출시 직전 발견된 설계 결함. 출시 2주 전 보안 검토에서 인가 모델 자체가 잘못 설계되어 모든 사용자가 같은 테넌트 컨텍스트를 공유하는 구조임이 발견되었고, 수정에 3개월과 아키텍처 재설계가 필요했습니다. 설계 단계에 위협 모델링을 필수 게이트로, 아키텍처 검토를 설계 완료 조건으로 넣었습니다.

    원본 연습문제 · D8.1-Q01

    출시 2주 전 보안 검토에서 인가 모델 자체가 잘못되어 모든 사용자가 하나의 테넌트 컨텍스트를 공유하는 구조임이 발견되었다. 수정에 3개월과 아키텍처 재설계가 필요했다. 이 비용을 막을 수 있었던 실천은?

    1. 인증 세션을 포함한 완전한 스테이징 환경을 대상으로, 릴리스 전 동적 애플리케이션 보안 테스트를 더 폭넓게 수행한다.
    2. 설계 결함은 코드로 고칠 수 없으므로 설계 단계의 필수 게이트로 위협 모델링과 아키텍처 검토를 둔다.
    3. 외부 팀을 릴리스 주기에 더 일찍 투입하면서 릴리스 후보에 대한 침투 테스트 예산을 늘린다.
    4. 인가 관련 규칙 묶음을 활성화한 정적 분석을 첫 커밋부터 빌드 파이프라인에 넣는다.
    정답과 해설 보기

    정답 B. 인가 모델 자체가 잘못된 것은 구현 결함이 아니라 설계 결함이며 코드 수정으로 해결되지 않는다. 위협 모델링과 아키텍처 검토를 설계 완료 조건으로 두어야 신뢰 경계와 인가 구조를 그 시점에 바로잡을 수 있다. 수정 비용은 생애주기 뒤로 갈수록 급격히 증가한다.

    • A · 동적 테스트는 구현된 설계 안에서 결함을 찾는다. 테넌트 구분이 설계에 없으면 테스트가 찾아내도 고치는 비용은 재설계 그대로다.
    • C · 침투 테스트는 발견하는 활동이다. 더 일찍 발견해도 설계 단계를 지나친 뒤면 재설계 3개월은 그대로 든다.
    • D · 정적 분석은 코드 패턴을 본다. 모든 사용자가 한 테넌트 맥락을 공유한다는 설계 자체는 문법적으로 올바른 코드로 구현되므로 규칙에 걸리지 않는다.

    2단계별 보안 활동

    요구사항

    • 보안 요구사항을 기능 요구사항과 동등하게, 측정 가능하게 정의합니다(“안전해야 한다”가 아니라).
    • 요구사항의 출처: 데이터 분류와 적용 규제, 인증·인가 요구, 로깅·감사 요구, 가용성 요구(RTO·RPO), 프라이버시 요구(privacy by design).
    • 원본의 핵심: 요구사항이 없으면 테스트할 기준이 없다.

    원문 사례 — 요구사항에 없어 테스트되지 않은 것. 기능 테스트가 전부 통과했지만 운영에서 다른 사용자의 데이터가 반환되는 결함이 발견되었습니다. 요구사항에 “타인의 데이터를 반환하면 안 된다”가 없었고 테스트 케이스도 없었습니다. 보안 요구사항을 기능 요구사항과 동등하게 정의하고 오용 사례를 요구사항 산출물에 넣었습니다.

    설계

    위협 모델링이 이 단계의 핵심이며, 원본은 설계 결함은 코드로 고칠 수 없다고 강조합니다. 보안 설계 원칙(최소권한, 기본 거부, 완전한 중재, 심층 방어, 공격 표면 최소화), 아키텍처 검토(신뢰 경계, 데이터 흐름, 인증 흐름), 의존성 선택(프레임워크·라이브러리 결정이 이후 수준을 좌우), 보안 패턴 재사용(암호와 인증은 직접 구현하지 않음).

    구현, 테스트, 배포

    단계활동
    구현안전한 코딩 표준, 변경 단위 코드 검토, 파이프라인 내 SAST·SCA, 코드·설정에 자격증명 금지, 개발 환경 보안
    테스트단위·통합 테스트에 보안 케이스, DAST·IAST·퍼징, 오용 사례, 보안 경로 커버리지, 중요 시스템 침투 테스트
    배포보안 설정 검증(기본값, 디버그 모드 꺼짐), 배포 시점 비밀 주입, 릴리스 승인과 추적성, 정책 코드로 사전 차단

    보충의료기기 소프트웨어라면 보안 요구사항의 출처에 규제 요구(사이버보안 관련 제출 요건)와 위험 관리(ISO 14971 같은) 결과가 더해집니다. 요구사항이 위협 모델과 위험 분석에서 추적 가능하게 도출되고, 각 요구가 시험 케이스로 연결되는 “추적성”은 품질 시스템에서 이미 요구하는 것과 같은 구조입니다. 구체 요건은 관할 규제 문서를 직접 확인해야 합니다.

    연결위협 모델링은 D1.10 위협 모델링, 보안 설계 원칙은 D3.1 안전한 설계 원칙, 테스트 기법은 D6.2 보안 통제 테스트의 5~7절, 비밀 주입과 정책 코드는 D7.3 구성 관리의 4·6절, 안전한 코딩은 D8.5 안전한 코딩, 개발 환경 보안은 D8.2 개발 생태계 보안 통제에서 다룹니다.

    원본 연습문제 · D8.1-Q22

    애플리케이션 보안 요구사항은 어디에서 나와야 하는가?

    1. 이전 프로젝트에서 쌓은 개발팀의 경험. 유사한 시스템을 만든 사람들이 어떤 통제가 실제로 중요했는지 알기 때문이다.
    2. 데이터 분류와 프라이버시 의무, 적용 규제와 계약, 그 설계에 대한 위협 모델, 조직 표준.
    3. 조직이 이미 라이선스한 보안 도구의 기능. 모든 요구사항을 이미 보유한 도구로 검증할 수 있게 된다.
    4. 선택한 애플리케이션 프레임워크가 제공하는 보안 기능. 그 기술 스택에서 안정적으로 구현할 수 있는 범위를 나타낸다.
    정답과 해설 보기

    정답 B. 요구사항이 도구나 프레임워크에서 나오면 그것이 할 수 있는 것만 요구하게 된다. 출발점은 다루는 데이터와 법적 의무, 그 설계에 성립하는 위협이다. 조직 표준은 반복되는 요구를 모아 둔 것이므로 함께 참조한다. 과거 경험은 유용하지만 새 데이터 유형과 규제를 놓칠 수 있다.

    • A · 경험은 유용한 입력이지만 출처가 될 수 없다. 규제 요건과 이 설계에 고유한 위협, 신규 공격 기법은 과거 경험에 들어 있지 않다.
    • C · 도구가 요구를 정의하게 된다. 검증 수단이 없는 요건이 빠지므로, 중요하지만 자동 검증이 어려운 통제가 누락된다.
    • D · 프레임워크 기능은 구현 수단이다. 수단이 요구를 정하면 데이터 분류와 규제가 요구하는 통제 중 프레임워크에 없는 것이 사라진다.

    원문 위치: D8.1.md §3 단계별 보안 활동 — 요구사항~배포, §7 사례 2 · 기존 문제 Q22 주제

    3운영, 유지보수, 폐기

    공식 개요가 별도 항목으로 명시했습니다.

    • 모니터링과 로깅: 앱 보안 이벤트(인가 거부, 입력 검증 실패)를 중앙으로.
    • 취약점 관리: 의존성의 신규 취약점이 계속 공개됩니다. SBOM이 영향 범위 산정 속도를 결정합니다.
    • 패치와 업그레이드: 프레임워크·런타임의 지원 종료 관리.
    • 구성 관리, 사고 대응 연계.
    • 기술 부채 관리: 미뤄진 보안 조치는 가시화하지 않으면 영구화됩니다.
    • 폐기: 데이터 정화, 접근 회수, 통합 지점 정리, 도메인과 인증서 처리. 방치된 애플리케이션이 침입 경로가 됩니다.

    원본의 경고: 운영 중인 소프트웨어의 보안 수준은 시간이 지나면 저하된다. 코드가 변하지 않아도 의존성 취약점이 공개되고, 암호 알고리즘이 약해지고, 플랫폼 지원이 끝납니다. 유지보수는 선택이 아닙니다.

    원문 사례 — 코드는 그대로인데 취약해진 애플리케이션. 3년간 변경이 없던 내부 앱이 취약점 평가에서 중대 결함 다수로 보고되었습니다. 의존성 라이브러리 취약점이 공개되고, 쓰던 TLS 버전이 비권고가 되고, 런타임이 지원 종료되었기 때문입니다.

    원문 사례 — 폐기되지 않은 애플리케이션. 업무가 중단된 앱이 인터넷에 노출된 채 2년간 방치되어 패치도 모니터링도 없었고, 침해의 시작점이 되었습니다. 폐기 체크리스트(서비스 중단, 데이터 정화, 접근 회수, 통합 지점 정리, 도메인·인증서 처리)를 만들고 자산 인벤토리와 대조해 미폐기 자산을 추적했습니다.

    가상 예시출시된 의료기기의 관리 소프트웨어에 쓰인 오픈소스 라이브러리에서 심각한 취약점이 공개되었습니다. 제조사가 제품별 SBOM을 유지하고 있으면 어떤 모델·버전이 영향받는지 몇 시간 안에 답할 수 있고, 병원에 보낼 공지와 패치 계획을 빠르게 세울 수 있습니다. SBOM이 없으면 각 빌드를 다시 조사해야 합니다. 출시 후 유지보수가 개발 수명주기의 일부인 이유입니다.

    연결SBOM과 취약점 관리는 D7.8 패치·취약점 관리의 10절, 자산 폐기는 D2.5 자산 보존 (EOL·EOS), 매체 정화는 D7.5 자원 보호의 4절에서 다룹니다.

    원본 연습문제 · D8.1-Q08

    업무 사용이 중단된 애플리케이션이 모니터링 범위 밖에서 패치되지 않은 채 2년간 인터넷에 노출된 상태로 방치되어 침해의 시작점이 되었다. 수립해야 할 것은?

    1. 서비스 중단과 데이터 정화, 접근 회수, 통합 지점 정리, 도메인과 인증서 처리를 포함하고 자산 인벤토리와 대조되는 폐기 절차.
    2. 업무에 쓰이지 않는 애플리케이션의 소유권을 보안팀으로 이전해, 보안팀이 패치와 모니터링을 유지한다.
    3. 업무 판단이 내려질 때까지 해당 애플리케이션 접근을 내부 출발지 주소로 제한하는 경계 방화벽 규칙을 추가한다.
    4. 업무에 계속 쓰이는지와 무관하게 모든 애플리케이션을 매월 패치하고 모니터링에 포함하도록 하는 정책.
    정답과 해설 보기

    정답 A. 방치된 애플리케이션은 패치되지 않고 모니터링되지 않아 침입 경로가 된다. 업무 사용이 끝나면 폐기 절차를 수행해야 하며 서비스 중단과 데이터 정화, 접근 회수, 통합 지점 정리, 도메인과 인증서 처리를 체크리스트로 만들고 자산 인벤토리와 대조해 미폐기 자산을 추적해야 한다.

    • B · 폐기 결정을 미루는 것이고, 쓰이지 않는 자산을 유지하는 비용을 보안팀으로 옮길 뿐이다. 노출면은 그대로 남는다.
    • C · 완화책이며 불필요한 자산을 남긴다. 내부 침해자나 설정 변경으로 다시 열릴 수 있고, 자산 목록과의 불일치도 해소되지 않는다.
    • D · 쓰지 않는 시스템을 계속 관리하는 것은 자원 낭비다. 더 중요하게는, 없애도 되는 노출면을 정책으로 유지하기로 결정하는 셈이다.

    방법론특징보안의 이점보안의 과제

    애자일에 보안을 통합하는 방법

    보안 요구를 사용자 스토리로 백로그에 넣고, 완료 정의(Definition of Done)에 코드 검토·SAST 통과·의존성 점검을 포함하고, 보안 백로그와 기술 부채를 가시화하고, 변경 영역에 대해 스프린트 단위로 위협 모델링하고, 팀마다 보안 챔피언을 둡니다.

    DevSecOps의 구성

    파이프라인 내 자동 검증(SAST, SCA, 비밀 스캐닝, IaC 스캔, 컨테이너 이미지 스캔), 정책 코드, 빠른 피드백(몇 주 뒤 보고서는 고쳐지지 않음), 개발자 도구에 내장(IDE 경고, 커밋 훅, PR 코멘트), 공유 책임(보안팀은 문지기가 아니라 역량·도구 제공자). 측정은 빌드 차단율, 수정 시간, 우회 건수, 발견 단계 분포입니다. 원본은 DevSecOps의 핵심이 도구가 아니라 보안이 개발 흐름을 막지 않으면서 작동하게 만드는 것이라고 말합니다.

    원본의 결론: “어떤 방법론이 더 안전한가”는 잘못된 질문입니다. 워터폴은 단계 게이트에, 애자일은 백로그와 완료 정의에, DevOps/DevSecOps는 파이프라인 자동 검증과 빠른 피드백에, SAFe는 공통 기반과 팀 간 경계 책임에 보안을 넣습니다.

    원문 사례 — “다음 스프린트”로 계속 밀린 보안. 애자일 전환 후 보안 작업이 백로그 하단에서 18개월간 수행되지 않았습니다. 보안 요구를 사용자 스토리로 넣고 완료 정의에 보안 항목을 포함해 개별 작업에 내장했습니다.

    원문 사례 — 파이프라인에 도구만 넣은 DevSecOps. 6개월 뒤 발견된 결함 2,400건 중 처리된 것은 11건이었고, 빌드 차단 임계값이 높아 실질적으로 모두 통과하고 있었습니다. 신규 결함만 차단하는 기준선 방식(기존 부채는 별도 관리), 작성 시점 피드백, 수정 시간과 우회 건수 지표로 바꿨습니다.

    원문 사례 — 보안이 병목이 되어 우회된 경우. 모든 릴리스에 보안 승인이 필수였고 평균 6일이 걸리자, 개발팀이 “설정 변경은 릴리스가 아니다”라는 해석으로 상당수를 우회했습니다.

    원문 사례 — 팀 간 경계의 사각지대. 세 팀이 하나의 제품을 만들면서 각자 범위는 충실히 검증했지만, 팀 간 API 경계의 인가 검증은 양쪽 모두 상대가 할 것으로 가정해 아무 곳에서도 수행되지 않았습니다. 공통 인증·인가 라이브러리를 아키텍처 런웨이로 먼저 만들고 팀 간 인터페이스의 보안 책임을 명시했습니다.

    보충연 1회 배포에서 2주 단위 배포로 바뀌면, 예전 점검표의 “연말 1회 보안 검사”는 의미를 잃습니다. 보안 요구와 검증이 방법론의 리듬을 따라가야 합니다. 2주마다 바뀌는 부분에 대한 자동 검사와, 영향이 큰 변경에만 걸리는 수동 검토로 다시 나누는 식입니다.

    연결인터페이스 테스트는 D6.2 보안 통제 테스트의 8절, 파이프라인 보안은 D8.2 개발 생태계 보안 통제, 보안이 병목이 될 때의 우회는 D7.9 변경 관리의 6절에서 다룹니다.

    5성숙도 모델

    모델성격요점
    CMMI조직의 프로세스 성숙도 전반(보안 전용 아님)1 초기 → 2 관리 → 3 정의 → 4 정량적 관리 → 5 최적화. 프로세스가 정의되지 않은(1~2단계) 조직에서는 보안 활동도 일관되지 않음
    SAMMOWASP 소프트웨어 보증 성숙도 모델, 처방적 개선 도구거버넌스, 설계, 구현, 검증, 운영 기능별 실천 항목을 3단계로 평가. 목표 수준은 조직이 정함
    BSIMM실제 조직들의 활동을 관찰한 서술적 모델SAMM이 “무엇을 해야 하는가”라면 BSIMM은 “다른 조직들이 실제로 무엇을 하는가”. 동종 업계 비교

    원본의 주의: 점수가 목표가 되면 왜곡된다. 목표는 성숙도 4가 아니라 위험에 맞는 수준이고, 모든 영역을 같은 수준으로 올리지 않으며 위험이 높은 영역부터 올립니다. 동시에 측정 자체에 가치가 있습니다. 현재 상태를 모르면 개선 계획을 세울 수 없습니다.

    원문 사례 — 성숙도 점수가 목표가 된 경우. SAMM에서 모든 영역을 성숙도 3으로 올리는 것이 목표가 되자, 위험이 낮은 영역에 자원이 들어가는 동안 고위험 영역의 기본 통제가 미비한 채 남았습니다.

    보충공식 개요는 CMM과 SAMM을 예로 듭니다. 초기 소프트웨어 CMM은 임기응변에 의존하는 단계에서 반복 가능·정의된 단계, 측정해 관리하는 단계, 지속 개선 단계로 나아가는 개념을 설명했고, CMMI가 그 후속입니다. 성숙도 평가는 다음 개선 후보를 찾는 자료이므로, 검토 의무를 도입했다면 문서 수보다 실제 반려·수정·재발 추세로 활동이 위험을 줄였는지 판단합니다.

    연결지표가 목표가 될 때의 왜곡은 D6.3 보안 프로세스 데이터의 3절, 소프트웨어 보안 효과 측정은 D8.3 소프트웨어 보안 효과성에서 다룹니다.

    6개발에서의 변경 관리

    • 버전 관리: 모든 변경이 추적되고 코드 검토가 변경 승인이 됩니다.
    • 브랜치 보호: 주 브랜치 직접 푸시 금지, PR 필수, 승인자 수 요구.
    • 직무 분리: 작성자와 승인자 분리, 운영 배포 권한 분리.
    • 릴리스 승인, 긴급 변경(hotfix) 경로의 사전 정의와 사후 보완.
    • 파이프라인 변경 통제: 파이프라인 정의도 코드로 관리하고 변경 통제 대상에.
    • 구성 변경: 기능 플래그 변경은 코드 배포 없이 동작을 바꿉니다. 추적 대상입니다.

    보충고객 자료를 조회하는 기능을 새 채널(예: 모바일 앱)에서 재사용한다면, 처음 승인할 때 했던 권한 시험이 새 경로에도 그대로 적용되는지 확인해야 합니다. 변경 요청에 영향받는 요구사항과 신뢰 경계, 다시 시험할 허용·거부 조건을 연결해 두면 한 번 승인한 요구가 변경 뒤에도 유지됩니다.

    연결자동화 환경의 변경 관리와 파이프라인 변경 통제는 D7.9 7절, 직무 분리는 D7.4 기본 보안 운영 개념의 3절에서 다룹니다.

    원문 위치: D8.1.md §3 개발에서의 변경 관리 · 공식 개요 8.1 “Change management”

    7통합 제품 팀 (IPT)

    여러 분야 전문가가 하나의 팀으로 제품을 개발하는 구조입니다. 개발, 운영, 보안, 품질, 업무, 필요하면 법무와 조달이 함께 참여합니다.

    보안 관점의 가치실무 과제
    조기 참여(설계 시점에 함께 있으면 위협 모델링과 설계 결정에 영향), 맥락 공유(“왜”를 공유하면 합의가 쉬움), 마찰 감소, 공동 책임보안 인력 부족 → 보안 챔피언 + 중앙 보안팀 지원 조합. 독립성 긴장(팀원이 된 보안이 불편한 지적을 하기 어려움) → 중앙 보안팀의 독립 검토 유지. 역할 명확화

    원문 사례 — IPT 참여로 바뀐 설계 결정. 보안이 설계 리뷰에만 참석하던 방식을 IPT 구성원 상시 참여로 바꾸자, 한 프로젝트에서 보안이 초기 논의에 참여해 민감 데이터를 중앙에 모으는 대신 토큰화로 처리하는 설계가 채택되었고, 이후 규제 범위와 보안 요구가 크게 줄었습니다. 원본의 결론은 조기 참여는 선택지를 넓힌다입니다.

    연결평가의 독립성은 D6.1 평가·테스트·감사 전략의 3절, 토큰화는 D2.6 데이터 보안 통제에서 다룹니다.

    원문 위치: D8.1.md §3 통합 제품 팀, §7 사례 10 · 공식 개요 8.1 “Integrated Product Team”

    8종합 이해 확인

    종합 · 자작 상황 문제 (실제 시험 문제 아님)

    소프트웨어 보안 점검 결과다. ㉠ 애자일 전환 후 보안 작업이 18개월째 백로그 하단에 있다. ㉡ 파이프라인 SAST 결과 2,400건 중 11건만 처리되었다. ㉢ 세 팀 사이 API 경계의 인가 검증이 어디에도 없다. ㉣ 업무가 끝난 앱이 2년째 인터넷에 노출되어 있다. 가장 적절한 대책 묶음은?

    1. ㉠ 워터폴로 회귀 / ㉡ 임계값을 더 높임 / ㉢ 각 팀이 알아서 / ㉣ 다음 감사 때 정리
    2. ㉠ 보안 요구를 사용자 스토리로, 완료 정의에 보안 항목 / ㉡ 신규 결함 차단 기준선, 작성 시점 피드백, 수정 시간·우회 지표 / ㉢ 공통 인증·인가 라이브러리(아키텍처 런웨이), 경계 책임 명시 / ㉣ 폐기 체크리스트와 인벤토리 대조
    3. ㉠ 보안 전담 스프린트 1회 / ㉡ SAST 제거 / ㉢ API 게이트웨이 하나 추가로 충분 / ㉣ WAF 추가
    4. ㉠ 그대로 / ㉡ 모든 결함 즉시 수정 강제로 배포 중단 / ㉢ 중앙 보안팀이 모든 API를 수동 검토 / ㉣ 그대로
    정답과 해설 보기

    정답 B. ㉠ 4절(백로그에 들어가야 수행된다), ㉡ 4절(도구를 넣는 것과 작동하게 하는 것은 다르다 — D의 전면 차단은 병목을 만들어 우회를 부름), ㉢ 4절(팀 간 경계의 사각지대), ㉣ 3절(방치된 앱이 침입 경로).

    원본 연습문제 · D8.1-Q15

    4만 줄에 대한 코드 검토에서 보안 결함 24건이 발견되었다. 결함 밀도는 얼마이며 어떻게 활용해야 하는가?

    1. 검토당 24건. 밀도는 한 번의 검토 노력이 드러낸 결함 수를 나타내며 줄 수는 척도에 들어가지 않는다.
    2. 결함당 1,667줄. 팀이 결함 간 간격을 늘리는 것을 목표로 삼도록 이 값을 품질 목표로 채택해야 한다.
    3. 아직 밀도를 말할 수 없다. 검토에서 나온 원 발견 사항이 아니라 확인되고 수정된 결함으로 계산해야 하기 때문이다.
    4. 1,000줄당 0.6건. 같은 코드베이스 내에서 모듈을 비교하고 시간에 따른 추세를 추적하는 데 유용하며 절대적 품질 등급이나 프로젝트 간 비교 기준으로 쓰는 것은 적절하지 않다.
    정답과 해설 보기

    정답 D. 24 ÷ 40,000 × 1,000 = 0.6 이므로 1,000줄당 0.6건이다. 결함 밀도는 같은 조건에서 비교할 때 의미가 있다. 언어와 도메인, 검토 깊이가 다르면 수치를 직접 비교할 수 없고, 검토를 느슨하게 하면 밀도가 낮아지므로 목표로 삼으면 왜곡된다. 모듈 간 비교와 추세 관찰에 쓰는 것이 적절하다.

    • A · 밀도는 규모로 정규화한 값이다. 정규화하지 않으면 큰 모듈이 늘 더 나빠 보여 모듈 간 비교가 불가능해진다.
    • B · 역수 표현 자체는 틀리지 않지만 목표로 삼으면 왜곡된다. 결함을 덜 찾거나 검토 범위를 줄이는 쪽이 지표를 개선하기 때문이다.
    • C · 수정 건수는 밀도 계산과 무관하다. 수정률은 별개의 지표이고, 발견된 결함 수와 코드 규모만으로 밀도가 정해진다.

    9핵심 개념을 내 말로 설명하기

    복습

    보안 요구가 스프린트 항목과 릴리스 승인까지 추적되려면 무엇이 필요하나요?

    설명 확인하기

    어떤 주체가 어떤 자원과 동작을 허용받는지 검증 가능한 요구로 작성합니다. 설계에서 집행 위치를 정하고 구현과 릴리스 시험의 통과·실패 조건으로 연결합니다.

    10핵심 요약

    1. 보안은 전 생애주기 활동. 결함 수정 비용은 뒤로 갈수록 급증(개략적 경향) → shift left. 설계 결함은 코드로 고칠 수 없다.
    2. 요구사항: 기능과 동등·측정 가능. 출처는 데이터 분류, 규제, 인증·인가, 로깅, 가용성, 프라이버시. 요구사항이 없으면 테스트 기준이 없다.
    3. 설계: 위협 모델링, 설계 원칙, 아키텍처 검토, 의존성 선택, 암호·인증 직접 구현 금지. 구현·테스트·배포: 변경 단위 검토, SAST·SCA, 오용 사례, 비밀 주입.
    4. 운영: 코드가 그대로여도 보안 수준은 저하(의존성 취약점, 약해진 암호, 지원 종료). SBOM, 기술 부채 가시화, 폐기 절차.
    5. 방법론: 워터폴(게이트) / 애자일(백로그·완료 정의) / DevOps(속도 > 검토) / DevSecOps(자동화된 단계, 빠른 피드백, 막지 않으면서 작동) / SAFe(아키텍처 런웨이, 팀 간 경계). “어느 방법론이 더 안전한가”는 잘못된 질문.
    6. 성숙도: CMMI(프로세스 전반 1~5), SAMM(처방적, 3단계), BSIMM(서술적, 관찰 기반). 점수가 목표가 되면 왜곡 → 위험에 맞는 수준.
    7. 개발 변경 관리: 코드 검토 = 승인, 브랜치 보호, 작성자 ≠ 승인자, hotfix 경로, 파이프라인·기능 플래그도 통제.
    8. IPT: 조기 참여가 선택지를 넓힘. 보안 챔피언 + 중앙팀, 독립 검토 유지.
    원문 위치: D8.1.md §8 CISSP 시험 관점, §9 핵심 암기 요약. 원본의 출제 단정 표현은 판단 기준으로 바꿔 적었습니다.

    11주요 용어 (Glossary)

    영어 원어와 한국어 뜻 · English–Korean

    SDLC (Software Development Life Cycle) · 소프트웨어 개발 생애주기

    소프트웨어의 요구사항부터 폐기까지의 생애주기.

    Shift Left · 왼쪽으로 이동

    보안 활동을 생애주기 앞단으로 이동시키는 접근. 수정 비용 감소가 근거다.

    Waterfall · 워터폴

    순차적 단계 진행 방법론. 단계 게이트가 명확하다.

    Agile · 애자일

    짧은 반복으로 점진적 개발하는 방법론.

    Definition of Done · 완료 정의

    작업이 완료되었다고 판단하는 기준. 보안 항목을 포함시킨다.

    Security Champion · 보안 챔피언

    팀 내에서 보안을 대변하는 개발자 역할.

    DevOps / DevSecOps · 개발·운영 통합 / 개발·보안·운영 통합

    개발과 운영의 통합, 그리고 거기에 보안을 통합한 접근.

    SAFe (Scaled Agile Framework) · 확장형 애자일 프레임워크

    대규모 조직에서 애자일을 확장하는 프레임워크.

    Architectural Runway · 아키텍처 런웨이

    여러 팀이 재사용할 공통 기반을 선행 구축하는 개념.

    CMMI (Capability Maturity Model Integration) · 역량 성숙도 모델 통합

    프로세스 성숙도를 5단계로 평가하는 모델.

    SAMM (Software Assurance Maturity Model) · 소프트웨어 보증 성숙도 모델

    OWASP 의 소프트웨어 보증 성숙도 모델. 처방적 개선 로드맵 도구다.

    BSIMM (Building Security In Maturity Model) · 소프트웨어 보안 활동의 관측 기반 성숙도 모델

    실제 조직 활동을 관찰한 서술적 성숙도 모델. 업계 비교에 쓰인다.

    Technical Debt · 기술 부채

    미루어진 개선 작업의 누적. 가시화하지 않으면 영구화된다.

    IPT (Integrated Product Team) · 통합 제품 팀

    여러 분야 전문가가 하나의 팀으로 제품을 개발하는 구조.

    Decommissioning · 폐기

    애플리케이션 수명 종료 처리. 데이터 정화와 접근 회수, 통합 정리를 포함한다.

    Feature Flag · 기능 플래그

    코드 배포 없이 동작을 바꾸는 설정. 변경 통제 대상이다.
